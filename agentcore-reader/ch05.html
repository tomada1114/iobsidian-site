Memory: The LLM Remembers Nothing

Runtime gives each session its own private room. But what was said inside that room disappears as soon as the room is cleaned up. In this chapter, you will see how Memory saves conversations and uses them again in later conversations.

Reading time: about 13 minRoadmap stage S2-S3

In this chapter

  • The starting point: the LLM itself remembers nothing
  • Short-term memory: keeping the conversation from one session, as it is
  • Long-term memory: pulling out the key points from conversations and storing them
  • How the next conversation searches for memories and adds them in
  • The idea of managing what goes into the context window

01The LLM does not remember the last conversation

Here is an important starting point: the LLM itself has no built-in way to remember a conversation. When you say "as I mentioned before" and get a natural reply, it looks like the model remembers. In fact, the whole conversation history is sent again with every message.

This container that carries the conversation history is called the context window. It has a limit. As the history gets longer, you send more tokens (small pieces of text that the model reads), which makes the answer slower and raises the cost. When you pack in too much history, the LLM can also have trouble finding the part it really needs, so the answer can get worse. A longer conversation does not make the model smarter. If you handle it badly, it just becomes extra weight.

The tricky part is that making the window bigger does not solve the problem. Even with a larger window, if you keep sending every unrelated message, the LLM can lose track of the instructions that really matter. The real question is not how much to pack in, but what to keep and what to drop. This design question leads directly to the role of Memory, which we look at in this chapter.

02Short-term memory: keeping the session's conversation as it is

The first job of Memory is short-term memory. It saves every message in a session as an event, without changing it. Each event is tracked by an actor ID (who is talking) and a session ID (which conversation it belongs to). This lets Memory handle several sessions from the same user without mixing them up.

Short-term memory is like a raw record of the conversation. Even after a Runtime session ends and its microVM is thrown away, this record stays in Memory. When the session starts again, the conversation can continue by loading this record.

03Long-term memory: pulling out and storing just the key points

If you just keep storing the whole conversation, it will eventually not fit in the context window. So Memory pulls out the key points from the saved events, in the background and asynchronously (not while the user waits), and stores them separately as long-term memory.

You can choose a strategy for what to pull out: semantic memory, which collects facts; summary, which sums up the whole conversation; user preference, which remembers what the user likes; episodic memory, which learns from events that went well or badly; and a custom strategy, where you write your own prompt to decide what to extract. One agent can also combine several strategies.

The extracted memories are stored in separate namespaces, like separate shelves. For example, one shelf for "this user's preferences" and another for "the history of this case". Keeping shelves separate helps avoid mixing up whose memory is whose.

The extraction does not happen during the conversation. It runs in the background, asynchronously. This means the response to the user is never slowed down by the extraction step. Because it is asynchronous, you can choose a strategy that takes some time, without affecting the conversation the user is having right now.

04Retrieval: adding memory into the next conversation

Long-term memory is not useful if you just store it and never use it. When the next conversation starts, Memory searches long-term memory for entries close in meaning to the user's question, and adds them into the prompt. It searches by meaning, not by matching exact keywords, so it can find a related memory even when the wording is different.

From the agent's side, you barely need to think about this search and insertion step. If you point your calls to Memory, the conversation already starts with likely relevant memories added to the prompt.

Analogy: a work note and a patient chart

Short-term memory is like a work note where a new employee writes down everything from today's meeting, just as it happened. Long-term memory is like a customer chart, where only the key points are copied from that note. Charts are kept on separate shelves for each case and each customer. They are taken down and placed on the desk only when that customer comes up again.

05The context window: a container with a limit

Adding more memory is not always better. The context window is shared between the conversation history, the retrieved memories, the system prompt, and the tool descriptions. Deciding what to keep and what to drop is the job of the conversation manager, a part of Strands Agents.

In practice, it replaces old messages with a summary, or removes the oldest parts once the history passes a certain size. What matters most to keep depends on the agent's purpose. Deciding whether to use the default behavior, or adjust it yourself, is a real design choice.

06Do not mix up whose memory it is

When companies use long-term memory, they especially worry about mixing up whose memory it is. A poor namespace design can cause accidents, such as one customer's preferences leaking into another's data. For example, if you build namespaces around individual people rather than departments, it is easier to avoid mixed-up memories when staff change.

Where companies get stuck

Points that you barely think about in personal use become important in production. Can you delete just one user's memory when they ask for it? How long should memory be kept? Is it fine to keep personal data in long-term memory as it is? Is the stored data encrypted? These questions are not only about Memory's settings. They also affect how you choose an extraction strategy, since that strategy decides what goes into long-term memory in the first place.

Summary in three lines

  1. The LLM itself remembers nothing. The context window, which carries the conversation history, has a limit.
  2. Short-term memory keeps the whole conversation. Long-term memory uses an extraction strategy to store just the key points, by namespace.
  3. The next conversation searches for memories that are close in meaning and adds them in. Managing what to keep and what to drop is essential too.
