An Agent Is Really Just a Loop

People use the words "AI agent" in many different ways, so the meaning is often unclear. In this chapter, you will see the difference between a system that calls an LLM once and a system we call an agent.

Reading time: about 12 minRoadmap stage S1

In this chapter

  • The difference between an LLM call, a workflow, and an agent
  • Inside the agent loop: think, use a tool, check the result
  • What MCP and A2A connect
  • Why AWS moved from the old Bedrock Agents to AgentCore plus Strands

01Three levels: call it, arrange it, or let it decide

You can sort apps that use an LLM into three levels. At each level, the LLM controls more of the decisions.

The first level calls the LLM only once. You send a message like "Summarize this text," and you show the answer you get back. This is enough for tasks like translation or classification, where one input always gives one output.

The second level calls the LLM several times, following steps that a person designed. We call this a workflow. For example: classify the question, write an answer with a different prompt for each type, then check the answer for banned words. The code decides the order of the steps. The LLM only handles the work inside each step.

The third level is the agent. Here, the LLM decides the steps itself. It looks at the goal and the list of tools it can use. A tool is an action the agent can call, such as a search or a database lookup. The LLM chooses what to do next, each time: "First, search for customer information." "That is not enough, so check the order history too." "Now I can answer."

It is important to know that being further down does not mean being better. If you turn a fixed task into an agent task, it only becomes slower, more expensive, and less predictable. Deciding what to fix in code and what to leave to the LLM is the real skill in good design.

02Inside the agent loop

The heart of an agent is a very simple loop.

  1. Give the LLM the user's request and a list of the tools it can use (name, what it does, and its arguments).
  2. The LLM answers, or it asks to call a tool with certain arguments.
  3. If it asks for a tool, the program runs that tool.
  4. Add the result to the conversation, and send it back to the LLM (go back to step 2).
  5. Stop when the LLM chooses to answer.

It is important to know that the LLM never runs a tool itself. It only writes a text request that asks for a tool call. The program that receives this request is the one that actually calls the API. We sometimes call this program a harness (a harness is the straps and gear you put on a horse). It runs the loop, calls the tools, and manages the conversation history. Think of the LLM as a horse, and the harness as the reins and saddle you put on it.

The harness does more than just run the loop. It can stop a dangerous action before a tool runs. It can summarize old messages when a conversation gets too long. It can also record what happens along the way.

Analogy: the new employee

The LLM is like a new employee who thinks fast. But this new employee cannot leave the desk, and cannot make phone calls. The employee writes a note: "I want to see this customer's order history." The colleague at the next desk (the harness) uses the system and hands back the result. The new employee reads it and writes the next note. An agent is this exchange between the new employee and the colleague. This book uses the analogy of hiring a new employee from start to finish.

03Common workflow patterns

Before you build an agent, it is good practice to check if a workflow pattern can do the job. Here are some patterns that already have common names. The Skill Builder intro course also covers this kind of pattern as "agent workflow patterns."

PatternWhat it doesExample
ChainingUse the output of one step as the input for the nextDraft → translate → proofread
RoutingClassify first, then send each type to a different processSort questions into billing, technical, or cancellation
ParallelSend the same input to several processes at once, then combine the resultsReview something from several angles at the same time
Orchestrator-workersA parent LLM splits the work and gives pieces to child LLMsSplit a research topic into parts and study them in parallel
Evaluator-optimizerSplit the work into a creator role and a scorer role, and redo it until it passesWrite code → score it with tests → fix it

The "orchestrator-workers" pattern is also the first step into multi-agent systems. The parent agent calls child agents the way it would call tools.

04MCP and A2A: what do they connect?

You often hear about two standards in the world of agents. They connect different things.

MCP (Model Context Protocol) is a standard for describing tools and calling them in one common way. If you wrap an internal API as an MCP server once, you can use it the same way from an agent built with Strands, from Claude Code, or from any other framework. It is like making every plug fit the same USB port. In AgentCore, the Gateway handles this job.

A2A (Agent2Agent) is a standard that lets one agent ask another agent to do a job. You do not need to know what is inside the other agent, such as its framework or its model. You can still send "please do this job" and get back "it is done." This is similar to how employees in different departments ask each other for help.

05The old Bedrock Agents, and today's AgentCore

AWS used to offer a service called Amazon Bedrock Agents. You wrote instructions in the console and registered tools as an "Action Group." Then the agent ran on a loop that AWS built for you, like ready-made furniture. This was easy to use, but hard to change on the inside. You also could not bring in an agent built with an outside framework, such as LangGraph.

Later, AWS changed direction and released Amazon Bedrock AgentCore. This is not a service for building the agent itself. It is a set of parts that let you run an agent built with any framework in production. You write the agent itself in code, and AWS recommends Strands Agents, an open-source SDK, as the way to write it.

PointOld Bedrock AgentsAgentCore + Strands
How you build itSet it up in the consoleWrite it in code
The loopUse the one AWS gives youComes from the framework; you fully control it
FrameworkYou cannot chooseAny framework, such as Strands, LangGraph, or CrewAI
ModelBedrock models onlyYou can also use models outside Bedrock
The futureNo new use allowed after 2026-08-01AWS's main choice going forward

If a course focuses on "Action Group" or "Supervisor Agent," it is teaching the old way. This is why the roadmap is built only around AgentCore and Strands.

06The wall between a personal project and a company

You can write the agent loop itself in a few dozen lines of code. You could get it running on your own computer today. The hard part comes later: making it work for thousands of people at a company.

PointA test on your computerProduction at a company
Who uses itJust youThousands of people, each allowed to see different information
Running at the same timeOne at a timeMany people at once, without mixing up conversations
PermissionsOne API keyChecked for every action: who it is for, and what is allowed
QualityOK if it seems to workMeasured with scores, checked after every change
When it failsTry againTrace the cause from records, and explain what happened

Where companies get stuck

Many teams build a working PoC (proof of concept) but cannot move it to production. This is usually not because the LLM is not smart enough. The real problem is missing support systems, such as authentication, permissions, monitoring, evaluation, and cost control. These are the things you naturally need once you hire a new employee. AgentCore provides these support systems as ready-made parts.

Summary in three lines

  1. An agent is a loop: the LLM picks the next move, and the harness runs the tool.
  2. Write fixed-order tasks as a workflow. Good design means choosing what to leave to the LLM.
  3. The hard part is not the loop, but the support systems needed to use it at a company. AgentCore turns that into ready-made parts.
