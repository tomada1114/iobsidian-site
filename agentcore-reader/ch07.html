How does an agent get the right tools?

After this page you can explain how Gateway turns existing APIs into MCP tools behind one endpoint. You can say why it checks identity in two directions. And you can say why fewer, clearer tools make an agent more accurate.

About 8 min readThe whiteboard room

In this page

  • Why does every team rebuild the same connections?
  • What are targets, and who is checked where?
  • Why do more tools make an agent worse?
  • What are Code Interpreter and Browser for?

The whiteboard room. Leo has listed every API Quickturn has, and it fills the board.

01Too many toolboxes

L

Leo: Why not give the tutor every one of these? More tools, more it can do.

M

Maya: Let's look at a bigger company first. Billing, HR, inventory, each built by a different department.

L

Leo: Dozens of APIs.

M

Maya: And each one is a possible tool. If every team writes its own connection code, the same login check gets rewritten again and again.

L

Leo: And the checks won't match.

M

Maya: They rarely do. One team checks every caller carefully. Another lets everything through with a single API key.

L

Leo: And it gets worse with each new agent.

M

Maya: Right. Gateway solves "how do we expose these tools" once, and many agents reuse it.

L

Leo: How does it work?

M

Maya: Anything you register with Gateway is called a target. And you register resources that are already running, without rewriting them.

L

Leo: What kinds?

M

Maya: A Lambda function you already wrote, or a REST API with an OpenAPI definition.

L

Leo: Anything else?

M

Maya: An API defined with Smithy. Or an MCP server another team already runs.

L

Leo: And the agent has to learn four kinds of connection?

M

Maya: No. Gateway publishes all of them as one MCP endpoint. The agent connects to that one point and uses every tool behind it.

L

Leo: So when a new internal API appears?

M

Maya: Add it as a target. Existing agents can use it right away, without a code change.

L

Leo: So the agent never has to know where each tool lives.

M

Maya: No. Think of the agent as a new employee. Gateway is the toolbox front desk. The employee says "I want to do this," and the desk finds the right tool.

L

Leo: And checks an ID first.

M

Maya: Always. And it records who received which tool.

02Checks in two directions

L

Leo: Which ID does it check? The agent's or the user's?

M

Maya: There are two checks, in two directions. First, the agent calls Gateway. JWT or OAuth checks who is making the call.

L

Leo: And the second?

M

Maya: Gateway calls the target. That uses IAM, OAuth or an API key, depending on the target. It decides which rights to use on the target side.

L

Leo: So the agent holds all those keys?

M

Maya: Never. The agent doesn't handle credentials, the login secrets, at all. Storing them is Identity's job.

L

Leo: So if the agent's prompt leaked, no password would leak with it.

M

Maya: That's one reason for the split. What the model never sees, it can't repeat.

L

Leo: Then Gateway only picks the method.

M

Maya: Right. The method lives in Gateway, and the secrets live in Identity.

L

Leo: Is there anything between the two checks?

M

Maya: Inside Gateway, each call passes through four steps in order.

L

Leo: Which four?

M

Maya: The entry check, a tool search, a Policy check, and then the exit check.

03Fewer, clearer tools

L

Leo: Back to my list. If Gateway handles connections, why not register everything?

M

Maya: Then there could be hundreds of tools. What happens if every description goes to the LLM?

L

Leo: The context window fills with descriptions.

M

Maya: And many similar tools make wrong choices more likely.

L

Leo: So more tools can make the agent worse.

M

Maya: Yes. Gateway can search by meaning, called semantic search, to find only the tools that match a request.

L

Leo: So the agent sees a short list.

M

Maya: And the choice doesn't get harder as the total grows. Register hundreds of tools, and each request still sees only a short list.

L

Leo: So the search keeps the choice small, even when the shelf is big.

M

Maya: Say a department has 100 tools, and only a few fit this request. Gateway pulls out those few, and the LLM picks without confusion.

L

Leo: Does the tool's shape matter too?

M

Maya: A lot. If one tool matches a single API call, it can be too small, and the agent needs many calls.

L

Leo: And if one tool does everything?

M

Maya: Then it's hard to reuse in other situations. Part of designing Gateway is shaping tools to a size that's easy to use.

L

Leo: And the description?

M

Maya: It decides how often a tool gets picked. A clear note about when to use it improves both the search and the LLM's choice.

L

Leo: So what does the tutor get?

M

Maya: A small, curated set of the app's commands and queries. And no tool takes a learner id.

L

Leo: Because the model shouldn't choose whose data it reads.

M

Maya: Right. The tool design is also what Policy checks when it decides whether to allow a call.

04Isolated workspaces

L

Leo: What about the built-in tools I saw in the console?

M

Maya: Code Interpreter runs code inside an isolated sandbox, a safe, separate space. It's for data analysis and calculations.

L

Leo: And Browser?

M

Maya: The agent controls a browser running in an isolated space in the cloud. It can work with internal systems that only have a screen and no API.

L

Leo: That sounds risky.

M

Maya: A person can watch the actions live, or keep a record. A normal API call can't offer that.

L

Leo: And if it goes wrong?

M

Maya: Both run separately from production. No real data goes in; only results come out.

L

Leo: What do security reviews usually flag?

M

Maya: Every new tool gets slightly more access than it needs. Before long, every agent has admin-level rights.

L

Leo: And the other worry?

M

Maya: Indirect prompt injection: a tool follows hidden instructions inside an outside web page or file. Tools like Browser need even stronger isolation from production.

L

Leo: So every tool is a trade.

M

Maya: Each one adds capability and adds risk. That's why the list stays short.

L

Leo: And every registered tool still needs an owner.

M

Maya: And the right access. Nobody notices one extra permission, until a review finds many of them.

05Leo explains it back

M

Maya: Look at your list on the board again. What would you register?

L

Leo: Only a few focused tools, with clear notes on when to use each one. More tools means more wrong picks.

L

Leo: They go behind one gateway, as targets, and agents reach them through one MCP endpoint.

M

Maya: And who checks whom?

L

Leo: Authentication runs both ways: the caller at the entry, the right credentials at the exit. The credentials themselves are stored in Identity.

M

Maya: Circle the learner id on your list. Whatever else you register, that argument never becomes something the model writes.

Summary in three lines

  1. Gateway registers existing APIs, functions and MCP servers as targets behind one MCP endpoint.
  2. Authentication runs in two directions, and Identity stores the credentials.
  3. Semantic search, tool size and clear descriptions decide how accurately tools are chosen.
