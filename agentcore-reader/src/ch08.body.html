Whose permission is the agent using?

After this page you can separate the two questions Identity answers: who may call the agent, and whose rights it uses outside. You can also choose between the user's rights and the agent's own, and explain the confused deputy.

About 8 min readAfter the design review

In this page

  • What are the entry and exit questions?
  • How is the caller checked, and where do keys live?
  • Whose rights go out: the user's or the agent's?
  • What is a confused deputy?

After Tuesday's design review. Leo's plan for a new tutor feature has a single line under "Access": one admin API key.

01Entry and exit

L

Leo: The reviewer circled my admin key. But it's simple. The agent gets one key, and it can reach everything it needs.

M

Maya: Everything it needs, or everything?

L

Leo: Well… everything. That's what admin means.

M

Maya: Let's split the problem first. Identity handles two questions. On the entry side: who is calling this agent?

L

Leo: And the exit side?

M

Maya: Whose rights the agent uses when it touches an outside service.

L

Leo: Aren't those the same? If I check the user at the door, the rest follows.

M

Maya: No. They're handled by separate mechanisms. Finishing the entry check doesn't decide the exit rights.

L

Leo: And if a design mixes them up?

M

Maya: That's how you get a confused deputy. We'll get there.

02Who comes in, and where keys live

L

Leo: How is the caller checked?

M

Maya: Two ways. If the caller already has AWS credentials, like another AWS service, it uses an IAM SigV4 signature.

L

Leo: And for users?

M

Maya: A JWT, a signed token that proves an identity. It's issued by the company's existing ID system, such as Cognito, Microsoft Entra ID or Okta.

L

Leo: So the tutor accepts the learner's sign-in token.

M

Maya: Right. It checks that token at the entry, and acts only on behalf of that learner.

L

Leo: Does the agent have an identity of its own?

M

Maya: It gets a workload ID. Registering the agent as its own identity lets you trace which agent did what.

L

Leo: Why would that matter?

M

Maya: Say a finance agent approves a large batch of expenses overnight. With its own workload ID, the logs show which agent it was, quickly.

L

Leo: Now the exit side. Where do the keys for outside services go?

M

Maya: For Google, Slack, Salesforce or GitHub, the agent needs credentials for each. You register them with Identity as a credential provider, using OAuth2 or an API key.

L

Leo: And they're stored where?

M

Maya: In a token vault, a secure store for tokens. So you never write API keys into code or environment variables.

L

Leo: Then how does the code get a key?

M

Maya: It asks Identity, "I want to use this credential provider." The actual tokens stay outside the code.

L

Leo: So rotating a key doesn't mean a new deploy.

M

Maya: No. And a key can't leak through a log line or a copied config file, because the code never held it.

L

Leo: So in the new-employee picture…

M

Maya: The entry is a building pass, checked by the guard. The exit is a key safe. The employee never gets the master key, only the one spare key they need, each time.

03The user's rights or the agent's

L

Leo: Whose key comes out of the safe, though?

M

Maya: There are two patterns. The first acts on behalf of the user. The agent uses that user's rights, limited to what they allowed on a consent screen.

L

Leo: That's the OAuth flow with a consent screen.

M

Maya: It's called 3LO, three-legged OAuth. The second pattern uses the agent's own rights.

L

Leo: With no user involved?

M

Maya: Right. Systems exchange client credentials, a fixed system-to-system login, directly. That's 2LO, two-legged OAuth.

L

Leo: How do I choose?

M

Maya: Ask one question: in whose name should this action happen?

L

Leo: If the agent sends a Slack message for a user…

M

Maya: Use the user's rights, so the message truly comes from that user. Sending or approving something for someone fits that pattern.

L

Leo: And a nightly inventory report from an outside service?

M

Maya: It isn't tied to any one user, so the agent's own rights are enough. Batch jobs and totals across users fit there.

04The confused deputy

L

Leo: So what's wrong with my admin key, exactly?

M

Maya: Give an agent strong rights, like admin access. Now a user with weaker rights asks it for something.

L

Leo: The agent can reach it, so it does.

M

Maya: So even a low-rights user can reach any information through the agent. That's the confused deputy.

L

Leo: The agent mixes up its own rights with the rights of the person it's acting for.

M

Maya: Picture a learner asking the tutor, "Show me the top learner's mistakes." With admin rights, nothing in the agent stops it.

L

Leo: And the model might even think it's being helpful.

M

Maya: It usually does. The model isn't the check; the rights are.

M

Maya: Right. It's an old, well-known problem, and agents make it easy to repeat.

L

Leo: What's the fix?

M

Maya: Design the agent so it can only touch what the current user is allowed to see. Always narrow it to that user's rights.

L

Leo: So it carries over the user's rights, and never adds its own on top.

M

Maya: Right. And there's a bonus. When you review access later, checking the user's rights is enough. There's no separate agent to audit.

L

Leo: What do security reviews ask?

M

Maya: Almost always the same three questions. Whose rights does this agent run with? Where are the tokens stored?

L

Leo: And the third?

M

Maya: How do you stop the rights of an employee who has left?

L

Leo: With the user's rights, you'd switch off their account in the ID system.

M

Maya: And the agent loses those rights at the same moment, because it never had any of its own.

L

Leo: With my admin key, I couldn't answer any of them.

M

Maya: With the user's rights and the vault, you answer all three on the spot. That often decides whether a proof of concept reaches production.

L

Leo: So the tutor uses the learner's token for everything about that learner.

M

Maya: And nothing else. If it ever needs a batch job, that gets its own narrow rights, not the learner's and not admin.

05Leo explains it back

M

Maya: Rewrite the "Access" line in your plan. What does it say now?

L

Leo: Check who comes in at the entry, with the learner's sign-in token.

L

Leo: On the exit, choose whose rights go out. The user's rights for their own data, and the agent's only for work not tied to one user.

L

Leo: Keys stay in the token vault, never in the code.

M

Maya: And the admin key?

L

Leo: Gone. An agent with admin rights is a confused deputy waiting to happen.

M

Maya: Put the three review questions at the top of the plan, with your answers. The reviewer will ask them anyway.

Summary in three lines

  1. Identity answers two separate questions: who calls the agent, and whose rights it uses outside.
  2. Use the user's rights (3LO) for their data and the agent's own (2LO) for batch work; keep tokens in the vault.
  3. Never give an agent strong rights; let it touch only what the current user may see.
