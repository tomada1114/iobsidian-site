Whose permission is the agent using?

A signed-in learner asks the tutor for another learner’s records. The caller’s identity, outbound credentials and final data permission must agree before access.

01Entry and exit

A tutor agent needs access to a learner's records, but an administrator key gives it access to far more. That shortcut creates a difficult question: when the agent performs an action, whose permission makes the action possible? A user who can see only their own records must not gain access to everyone else's records by asking the agent.

Separate the design into two directions. Inbound authentication checks who is calling the agent. Outbound authentication supplies the credentials the agent needs when it calls another service. A successful sign-in answers the first question; it does not automatically answer the second.

Amazon Bedrock AgentCore Identity manages workload identities and credentials for agents. Quickturn’s tutor must identify the learner who started the session. It then needs appropriately limited access to that learner’s data. Entry authentication and outbound permission make separate parts of that requirement explicit.

02Who comes in, and where keys live

An AWS caller can use IAM credentials and a SigV4 signature for inbound access. The service verifies the caller using that signed request. A user-facing application may instead present a JWT from an identity system such as Cognito, Microsoft Entra ID or Okta. A JWT is a signed token. The configured authorizer validates it before the request reaches the agent.

The agent also has a workload identity of its own. That identity makes agent activity traceable: an operations team can distinguish the tutor from a finance agent or an overnight reporting job. Identifying an agent is different from giving it permission to read every user's data.

Register an outbound credential provider for the target service, using a supported OAuth flow or an API key. Identity’s token vault manages relevant credentials. This reduces the need to embed long-lived secrets in source files or copy them into application configuration.

The application requests the credential it needs for a particular provider. Depending on the integration, a token may still be returned to application code and used in a request. The vault reduces secret handling; it does not make careless logging harmless. Protect returned credentials, request only necessary scopes, and plan rotation and revocation.

Think of the two directions as a building pass and a key safe. The pass identifies the visitor entering the building. The key safe supplies access for a specific job. Checking the pass does not justify handing over a master key.

03The user's rights or the agent's

There are two common ways to obtain outbound permission. In a user-delegated flow, the user authorizes access to their account. Three-legged OAuth, often shortened to 3LO, connects the user, the application and the authorization service. The granted scopes limit what the application can request, while the target service must still enforce its resource permissions.

A system-to-system flow uses the application's own credentials. This is commonly called two-legged OAuth, or 2LO, and often uses the client credentials grant. It fits work that does not belong to one signed-in user, such as a nightly inventory report.

Choose by asking in whose name the action should happen. A Slack integration that acts for one user should use a suitable delegated flow and the scopes needed for that action. An organization-wide batch report needs a separate service identity with narrow reporting rights. Neither case justifies using an unrestricted administrator credential.

For the tutor, enforce access to the current learner’s permitted records. A later batch feature across learners needs a separate workload. Give it its own purpose, permissions and audit record.

04The confused deputy

A confused deputy is a service that uses its stronger permissions to perform an action for a caller who lacks those permissions. The service may be trying to help, yet it becomes a route around the original access rules.

Suppose a learner asks the tutor to show another learner's mistakes. With an administrator key, the agent may be able to fetch those records. A prompt telling it to respect privacy does not remove that ability. The data service must reject a request that is outside the current learner's permitted scope.

Carry the authenticated user's identity through the request and enforce it where the data is accessed. Check both the action and the target record. A valid token proves identity; the authorization check decides whether this person may read this particular record.

An access review should name whose permissions are used, where credentials are stored and how access is revoked. Disabling an account may prevent new sign-ins. Existing sessions and tokens also need a defined revocation or expiry process. Record that process rather than assuming account removal immediately ends every active connection.

A useful access plan names the inbound authorizer, the outbound provider, the allowed scopes and resources, and the revocation path. Those details let a reviewer follow the permissions from the learner's request to the final data access.

Summary in three lines

  1. Design entry authentication and outbound permission separately; Identity supplies workload identities and credential services.
  2. Use delegated rights where appropriate; a service identity still needs narrow permissions and resource checks.
  3. Give each workload only the permissions it needs, and enforce user access on user-specific requests.
