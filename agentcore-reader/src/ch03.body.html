A model-driven way to write agents

In Chapter 1, you saw the agent loop. How do you write this loop in real code? AWS recommends an open-source SDK called Strands Agents. It has a Python version and a TypeScript version, and AWS maintains both.

The main idea of Strands Agents is called model-driven design. You do not write each step in detail, like "call A, check a condition, then call B", as a graph or in code. Instead, you give the model a system prompt and a list of tools it can use. The model decides what to do next. In the three stages from Chapter 1, this is the style furthest to the right.

A minimal example is very simple. You just pass a model, some tools, and a system prompt to a class called Agent, and the loop is ready to run.

from strands import Agent, tool

@tool
def get_weather(city: str) -> str:
    """Return the weather for the given city."""
    return lookup_weather(city)

agent = Agent(model="...", tools=[get_weather], system_prompt="You are a weather guide.")
agent("What is the weather in Tokyo?")

A tool is just a normal function with @tool added above it. The function name, the argument types, and the docstring (the description written inside the function) become the instructions for the model. You do not need to write a separate spec file for each tool.

By default, Strands Agents uses Bedrock as the model provider, but you can also choose others, such as Anthropic, OpenAI, Ollama, or LiteLLM. It can also act as an MCP client (MCP is a shared way for tools to connect to models). Because of this, you can pass tools from an outside MCP server to your agent, just like your own functions.

The six layers of the harness

In Chapter 1, we called the program that runs the loop around the LLM a "harness". The official Strands Workshop lists six layers inside this harness. Let's look at each one.

Loop
This is the repeated cycle from Chapter 1: think, use a tool, look at the result.
Tools
These are normal functions, or outside tools reached through MCP. The model picks which tool to call, and the harness runs it.
Hooks
Hooks step into events inside the loop, such as before and after a tool call. You can use them to block a dangerous action, write a call to a log, or change the arguments.
Skills
Skills are instructions that the agent loads only when needed. Most of the time, the model sees only the skill's name and a short description. It loads the full text only when it actually needs to use it.
Steering
Steering adds new instructions to a running agent, based on the current situation, to adjust its direction.
Session
A session saves the state of a conversation so you can start it again later. When a conversation gets long, a part called the conversation manager decides what to drop or summarize.

The layers closer to the center relate to one tool call. The layers further out relate to the whole conversation or the whole run. Think about which layer should control the agent's behavior. This helps you decide whether to stop an action with a hook, or a simple request in the system prompt is enough.

Multi-agent: how to combine agents

In Chapter 1, we talked about a "conductor and workers" pattern. Strands Agents lets you build this in three ways. Calling an agent as a tool is the simplest way. From the parent agent's view, the child agent looks like a single function call.

A Swarm is a group of equal agents that hand work to each other. When one agent decides a task is too hard for it, it passes the conversation to the next agent. A Graph moves work between agents along a path that you set in advance. This fits cases where you want to fix the order of steps yourself.

When agents need to talk across different systems or teams, Strands Agents also supports A2A, the protocol for agent-to-agent calls from Chapter 1. For example, an agent built inside your company can be called by another team's agent through A2A.

How this differs from LangGraph

LangGraph is another well-known tool for building agents. Its design writes state changes as an explicit graph. You decide in code which node comes after which node. This makes the behavior easier to predict, even with complex branches.

Strands Agents is different because it lets the model make that decision. But agents built with either tool run the same way on AgentCore Runtime. AgentCore does not require a specific framework, so this difference is just a choice between two design styles. It does not limit whether you can use AgentCore.

Where companies get stuck

Writing "do not handle personal data" in the system prompt is only a request. If the model misreads the instruction, or a clever input pushes it past the rule, the rule breaks easily. For rules you truly need to enforce, use something on the harness side, such as a hook, or the Policy tool from Chapter 8. These stop the action in code, not just by asking.

Summary in three lines

  1. Strands Agents is a "model-driven" SDK. It lets the model decide the steps, instead of writing them as a graph.
  2. The harness has six layers: loop, tools, hooks, skills, steering, and session.
  3. Multi-agent setups come in three forms: calling an agent as a tool, Swarm, and Graph. AgentCore Runtime treats agents built with either design the same way.
