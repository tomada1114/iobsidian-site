What does AgentCore actually give you?

After this page you can name AgentCore's parts and say what each one does for an agent. You can also explain the order in which a project usually adds them, and how they're priced.

In this page

  • In what order are they added?
  • What does each part cost?

The whiteboard room. Leo has the AgentCore console open on his laptop.

01Parts, not the agent

L

Leo: I thought AgentCore would be where I write the agent. Like a framework, with classes for the loop. But I can't find any.

M

Maya: Where does the agent's loop live, in our tutor?

L

Leo: In our code. We use Strands.

M

Maya: Right. You write the agent itself in code: the harness that runs the loop, and the model it uses. AgentCore doesn't build that.

L

Leo: Then what does it do?

M

Maya: It gives you the support you need to run the agent in production. Authentication, memory, monitoring and so on.

L

Leo: So it's a service around the agent, not the agent.

M

Maya: Yes. And each part is a separate AWS feature. You can call it from an agent built with Strands, LangGraph or CrewAI, with any model.

L

Leo: Do I have to use all of them together?

M

Maya: No. Only the parts you need. Some teams use Memory without Runtime, or add Gateway first, before anything else.

02The parts

L

Leo: How many parts are there?

M

Maya: About eight. Think of the agent as a new employee. A company doesn't rely on their skill alone.

L

Leo: It gives them a desk, a notebook, a badge.

M

Maya: That's the set. Runtime runs the agent with no servers to manage, and keeps each user's session in its own space. A private room.

L

Leo: And Memory is the notebook.

M

Maya: A work notebook for the short-term conversation, and a customer file for long-term memory.

L

Leo: What about tools?

M

Maya: Gateway turns your existing APIs and Lambda functions into MCP tools. Think of a toolbox front desk.

L

Leo: And Code Interpreter and Browser?

M

Maya: They run code in an isolated space and control an isolated cloud browser. An isolated workroom.

L

Leo: Then the badge.

M

Maya: Identity holds the agent's ID and the login details for outside services. An ID badge and a spare key.

L

Leo: And rules?

M

Maya: Policy decides to allow or block a tool call, before it runs. Company rules.

L

Leo: That leaves monitoring.

M

Maya: Observability records what the agent does as a trace: a record of every step in one request. A daily work report.

L

Leo: And Evaluations is the performance review.

M

Maya: It scores the quality of the agent's answers and behavior.

L

Leo: So none of them is the brain. The brain is still the model, and the plan is still our code.

M

Maya: Yes. The parts are what the company hands the new hire, not the hire.

L

Leo: How does a request move through them?

M

Maya: The user's request goes through Identity first, which checks who the user is. Then it reaches the agent inside Runtime.

L

Leo: And the agent thinks with Memory.

M

Maya: Going back and forth with it. When it wants to act outside, it first needs approval from Policy. Then it calls internal APIs or SaaS through Gateway.

L

Leo: And Code Interpreter and Browser?

M

Maya: Tools the agent uses directly, inside an isolated space. Observability and Evaluations cover the whole process.

L

Leo: What does our tutor use?

M

Maya: Runtime, Memory, Gateway, Identity and Policy run it, and Observability and Evaluations watch it. The learner's record stays in Quickturn's own database.

L

Leo: Is there anything else I'll see in the courses?

M

Maya: The AgentCore CLI, where development starts. It creates an agent, runs it locally and deploys it, all with commands. It replaces the old Starter Toolkit.

L

Leo: And "Harness"? Some course modules have that name.

M

Maya: Same idea as ours: the program outside the LLM that runs the loop. Courses describe it differently, so don't assume exactly what AgentCore itself provides for it.

L

Leo: And payments?

M

Maya: An official Deep Dive module, "Agents that transact," covers agents that make payments. We won't go deep here.

03The order of adding parts

L

Leo: Where do I start, then? Eight parts is a lot at once.

M

Maya: The official Phase 1 workshop, "Getting Started with Amazon Bedrock AgentCore," shows an order. It builds one customer support agent and adds features one at a time.

L

Leo: What comes first?

M

Maya: A local agent that runs. Then memory, then Gateway to gather tools, then deploy to Runtime.

L

Leo: And after it's deployed?

M

Maya: Add a way to evaluate it, then a frontend. Control it with policy, adjust the harness, and finally optimize it.

L

Leo: How long does it take?

M

Maya: Nine labs, about three and a half hours. It's also available in Japanese.

L

Leo: So the workshop order is also the path from a proof of concept to production.

M

Maya: Right. Start with something that runs, then strengthen it with memory, tools, authentication, evaluation and control.

L

Leo: Is there a second phase?

M

Maya: Phase 2, "Diving Deep," has eight modules you can study in any order, working together with Claude Code.

L

Leo: So I can go deep into whatever part I need first.

M

Maya: And your roadmap points you to both phases, depending on the situation.

04Paying per part

L

Leo: How is all this priced?

M

Maya: Pay per use. Runtime, Memory and Gateway are each billed separately, and a part you don't use costs nothing.

L

Leo: What are the prices?

M

Maya: They change often, so I won't give numbers. Just remember the idea.

L

Leo: Then how do we estimate a bill?

M

Maya: From usage. Count how many sessions and tool calls you expect, then check the current price page for each part you use.

L

Leo: So early on, we'd skip the parts we don't need yet.

M

Maya: Right. Add a part when the project needs it, in the order the workshop shows.

L

Leo: Couldn't a company build these parts itself?

M

Maya: Separating each session's environment, storing login details safely, and collecting traces of every call would each take weeks.

L

Leo: So teams stop at the proof of concept.

M

Maya: Many do. Not because the agent isn't smart enough, but because they can't build all of this support. AgentCore has the parts ready.

05Leo explains it back

M

Maya: You couldn't find the framework classes this morning. Explain why.

L

Leo: AgentCore isn't a framework. Our Strands code is the agent, and AgentCore is separate parts around it.

L

Leo: Each part does one job, like a private room, a notebook, a toolbox desk, a badge, rules and a daily report.

M

Maya: And the order?

L

Leo: Something that runs first, then memory, tools, deploy, evaluation and policy. We pay only for the parts we use.

M

Maya: You left out our own case: the tutor uses those parts, but the learner's record isn't in any of them. It stays in our database.

Summary in three lines

  1. AgentCore is a set of parts that handle production needs, not the agent itself.
  2. Each part can be used alone or together, and is billed separately.
  3. The official workshop's order is also the path from proof of concept to production.
