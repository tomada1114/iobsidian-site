Why isn't 'please don't' enough?

A refund request exceeds the permitted amount even though its wording looks harmless. The tool boundary must reject the operation independently of the model.

01A prompt only asks

Adding “Never delete data” to a system prompt can guide an agent, but it does not remove the delete operation. The model may overlook a condition or misunderstand a request. It may also follow hidden instructions in user text or a tool result. A prompt describes desired behavior; an authorization control decides whether an operation can run.

Consider a refund limit of 10,000 yen. If the model produces a tool call for 15,000 yen, the tool boundary must reject it. The rule needs to hold even when the model's reasoning is mistaken. The same principle applies to restricted documents and destructive actions.

Prompt injection is an attempt to make the model treat untrusted content as an instruction. Keeping business rules outside the model limits what such an attempt can achieve. The prompt remains useful, but the permitted actions must also be defined and checked by the surrounding system.

02Check before running

When an agent calls a tool through AgentCore Gateway, an attached policy engine evaluates the request before tool access is allowed. A denied request stops at that boundary, and the agent receives a denial instead of the tool's result. The authorization decision does not depend on the LLM agreeing with it.

This protects the calls covered by the policy. It also creates a design obligation: all sensitive paths must pass through the control. A direct API call or an alternative tool with broader rights can leave another route open. Give the agent a small allowed tool set and review the permissions of every available route.

Cedar is an open-source language for authorization policies. A policy identifies the caller, the attempted action, the resource and any conditions that must hold. These four parts turn a business rule into a decision the system can evaluate.

principal · who
The identity of the caller, such as support staff.
action · what
What it's trying to do, such as call the refund tool.
resource · on what
The target tool or data, such as the refund process.
context · under what conditions
Extra details, such as an amount of 10,000 yen or less.

Consider “Only the HR role may use the HR search tool.” The role identifies the principal, the attempted invocation identifies the action, and the HR tool identifies the resource. A refund rule adds an amount condition. These terms help the team check whether the intended authorization rule is complete.

AgentCore can generate candidate policies from a plain-language description. Review and test the generated policy against the tool schema, including both allowed and denied cases. A convenient authoring method still needs a clear statement of the intended permission.

Policies live in a policy engine attached to a Gateway. A shared engine can apply consistent rules across agents using that boundary. For Quickturn's tutor, the engine should allow only the tools and parameter ranges required for tutoring.

03Policy and Guardrails

Bedrock Guardrails and AgentCore Policy inspect different parts of a request. Guardrails examines content, such as harmful language, sensitive information, disallowed topics or possible prompt attacks. Depending on the configured feature, it can block content or mask sensitive text.

Policy evaluates whether an action is authorized. It can reject a refund above the permitted amount even if the accompanying text looks harmless. A content filter alone does not authorize that call. An authorization rule alone does not judge whether a reply is appropriate.

Use the layers together when the application needs both controls. Their integrations may evolve, but the distinction remains useful: inspect the content being exchanged and authorize the operation being attempted. Avoid treating either layer as a guarantee against every kind of attack.

04A person's approval

Some authorized actions still deserve human approval. A large payment, account deletion or other difficult-to-reverse action can pause until an authorized person reviews the proposed operation. This pattern is called human-in-the-loop.

An application can use an agent framework's hooks or an explicit workflow to pause before execution. The approval screen should show the exact action, target and important parameters. When execution resumes, it must use the approved operation; a changed amount or target needs another decision.

Approval adds delay because it depends on a person's availability. Reserve it for actions whose consequences justify that delay, and decide what happens when an approval times out. Routine, reversible actions can often rely on narrow automated rules.

Before production, check whether records explain why a call was allowed. Confirm that administrators can update rules separately from agent code. Test whether the relevant agents receive those rules and whether alternate routes bypass them. Keep prompt guidance while enforcing action boundaries and approval independently.

Summary in three lines

  1. Prompts guide the model; attached Policy authorizes covered tool calls independently at Gateway.
  2. Policy evaluates covered Gateway tool calls using Cedar rules about principal, action, resource and context.
  3. Guardrails inspects configured content; Policy authorizes covered actions, while selected operations pause for exact human approval.
