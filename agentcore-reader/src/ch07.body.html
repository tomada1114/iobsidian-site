Identity: who an agent acts for, and what it may do

In enterprise projects, Identity is often the topic that people discuss the longest. It splits into two questions. The first is the entry side (inbound): who is calling the agent? The second is the exit side (outbound): whose rights does the agent use to touch outside services? This chapter looks at how AgentCore handles each question.

Two questions: entry and exit

Identity handles two main questions. The first is on the entry side: it checks "who is calling this agent." The second is on the exit side: it decides "whose rights the agent uses when it touches an outside service."

These two questions are handled by separate mechanisms. Finishing the entry-side check does not automatically decide the exit-side rights. If you design a system without this clear separation, you can run into the "confused deputy" problem, explained later in this chapter.

Entry side: who is calling the agent

There are two ways to check who is calling an agent. The first uses an IAM SigV4 signature (a way AWS confirms an identity), for when the caller already has AWS credentials. The second accepts a JWT (a signed token that proves an identity) issued by your company's existing ID system, such as Cognito, Microsoft Entra ID, or Okta.

MethodWhen to use itExample
IAM (SigV4)The caller already has AWS credentialsA call from another AWS service
JWTA user or system already signed in through your company's ID systemCognito, Microsoft Entra ID, Okta

In addition, the agent itself gets its own ID, called a workload ID. Registering the agent as its own identity lets you trace "which agent did what" later. For example, if a finance agent that handles expense approvals has its own workload ID, you can quickly find which agent approved a large batch of requests overnight, just by checking the logs.

Exit side: where to keep the keys for outside services

To use outside services like Google, Slack, Salesforce, or GitHub, an agent needs credentials for each one. You register these credentials with Identity as a "credential provider," using OAuth2 or an API key. Identity then stores them safely in a token vault (a secure storage place for tokens).

This means you can avoid writing API keys directly into code or environment variables. The agent's code only asks Identity, "I want to use this credential provider." The actual tokens are handled outside the code.

Analogy: the building pass and the key safe

The entry side is like a building pass. The guard (the ID system) checks who has arrived before letting them in. The exit side is like a safe (the token vault) that keeps spare keys collected from employees. The new employee (the agent) never gets the company's master key. Instead, they take only the one spare key they need from the safe, each time they need it.

Whose rights to use on exit: two patterns

There are two patterns for exit-side rights. The first is acting on behalf of the user. The agent uses that user's rights, limited to what the user allowed on a consent screen. This is the three-way OAuth exchange, known as 3LO (3-legged OAuth).

The second pattern uses the agent's own rights. Systems exchange client credentials (a fixed system-to-system login) directly, with no user involved. This is 2LO (2-legged OAuth).

PointOn behalf of user (3LO)Agent's own rights (2LO)
Whose rightsThe user who gave consentThe agent itself
ConsentNeeds an OAuth consent screenNot needed (client credentials)
Good forSending or approving something for the userBatch jobs and other work not tied to one user

A good rule is to ask: "in whose name should this action happen?" Sending or approving something for a user fits the on-behalf-of-user pattern. Summing up data across users, or running a routine batch job, fits the agent's own rights. For example, if the agent sends a Slack message for a user, use access on behalf of the user, so the message truly looks like it came from that user. On the other hand, pulling together a nightly inventory report from an outside SaaS is not tied to any one user, so the agent's own rights are enough.

Avoiding a "confused deputy"

If you give an agent strong rights, such as admin-level access, then even a user with weaker rights can reach any information through that agent. This is a long-known problem called the "confused deputy." It happens when the deputy, in this case the agent, mixes up its own rights with the rights of the person it is acting for.

The fix is to design the agent so it can only touch what the current user is allowed to see. Instead of giving the agent stronger rights than it needs, always narrow it down to the rights of the user it is acting for at that moment. In practice, the agent should carry over the user's existing rights, and never issue extra rights of its own. When you review access rights later, checking the rights of the represented user is enough; you do not need a separate check for the agent's own rights.

Where companies get stuck

IT security reviews almost always ask the same three questions: "Whose rights does this agent run with?" "Where are the tokens stored?" and "How do you stop the rights of an employee who has left?" Whether your design can answer these on the spot often decides if a proof of concept can move to production. Building Identity into the design from the start lets you answer all three questions with confidence.

Summary in three lines

  1. Identity handles entry (who is calling) and exit (whose rights reach the outside) as two separate questions.
  2. On the exit side, choose between acting for the user (3LO) and the agent's own rights (2LO), and keep tokens in the vault.
  3. Avoid the "confused deputy" problem by never giving the agent strong rights, and letting it touch only what the current user may see.
