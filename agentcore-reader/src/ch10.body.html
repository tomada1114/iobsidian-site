How do you know an agent is doing a good job?

After this page you can explain why an agent's behavior must be recorded as traces and spans. You can say how evaluations turn quality into a score. And you can describe the loop of observe, evaluate and fix.

01The path changes every time

An agent can answer the same question differently on two runs. It may choose another tool, supply different arguments or stop at a different point. One successful demo therefore shows that one execution path worked once. Repeating the request until it succeeds can hide the path that failed.

To investigate a strange answer, preserve the record of the original exchange. Useful evidence includes the input, model and prompt versions, tool calls, arguments, tool results, timings and final response. It shows the observable execution; it should not be mistaken for access to the model's private reasoning.

Observability records what happened. Evaluation judges the quality of the result and the steps taken. These jobs work together because an answer can be fast and free of system errors while still being incorrect.

02Traces and spans

OpenTelemetry provides a common way to describe execution data. A trace groups the work associated with a request. A span records an individual operation within it, such as a model call or tool call, with timing and other attributes.

AgentCore Observability integrates with CloudWatch and agent instrumentation. Configure the supported telemetry path for the framework and runtime you use. The trace view then helps you locate a slow operation or an unexpected tool choice.

In the timeline, a long tool span points to the part of this request that consumed time. Read its arguments and result before changing the prompt. If the agent skipped a tool entirely, the missing span may be more informative than any slow bar.

OpenTelemetry also makes integration with other monitoring systems possible where the exporter and destination support it. An existing platform may use Langfuse or Datadog alongside its infrastructure monitoring.

Watch response time, token consumption, failures and concurrent sessions, but distinguish those operational measures from answer quality. A tutor can produce a fluent, incorrect grammar explanation while every service reports success. Detecting that problem requires checking the content against a quality standard.

03Quality as a score

AgentCore Evaluations offers built-in and custom evaluators. They can assess properties such as helpfulness, correctness, safety and tool use. Many evaluations use LLM-as-a-judge: a model receives a scoring rubric and returns an assessment with a reason.

A judge model can also make mistakes. Define the rubric clearly, compare a sample of scores with human judgments, and investigate disagreements. Use deterministic checks where possible, such as verifying the shape of a result or whether a required tool was called.

Production evaluation samples real interactions to identify changes in behavior. Development evaluation runs a known dataset before release, and can form part of CI, the automated checks applied to code changes. These two settings answer different questions: how the agent behaves now, and whether a proposed change harms known cases.

The dataset should contain common questions, difficult inputs and previously observed failures. Define what passes, which failures block release, and which need manual review. Re-run it when prompts, models, tool descriptions or permissions change. Enabling an evaluator is only the first step; the dataset and decision rule determine what the team can learn from its scores.

04Observe, evaluate, fix

Start an improvement cycle with a low-scoring case and its trace. Suppose the tutor gave an incorrect answer and never called the grammar tool. The tool description may not make its purpose clear, or the prompt may fail to direct the agent toward it. The trace helps choose a specific hypothesis.

Change one relevant part, then run the same evaluation again. Compare the failing case and the wider dataset so that an apparent improvement does not hide a regression elsewhere. The cycle is observe, evaluate, change and measure again.

Evaluation consumes time and judge-model calls. Traces may contain learner text or other personal information. Decide what to record, how to redact sensitive fields, who may read the records and how long to retain them. Debugging value and privacy requirements both belong in that decision.

The official evaluation lab and the “Observe, evaluate, optimize” study module provide practice for this cycle. The practical goal is evidence for a release decision: whether a new model, prompt or tool behaves better on the tasks the application serves.

When a production question exposes a new failure, add a suitable version to the regression dataset. That converts one incident into a repeatable check. Observability supplies the work record; evaluation turns it into evidence the team can use.

Summary in three lines

  1. An agent's path changes every run, so traces and spans record what happened.
  2. Evaluations turn responses into scores, online in production and in CI before release.
  3. The design of the test set and standard matters most; keep looping observe, evaluate, fix.
