How do you know an agent is doing a good job?

After this page you can explain why an agent's behavior must be recorded as traces and spans. You can say how evaluations turn quality into a score. And you can describe the loop of observe, evaluate and fix.

The morning after a demo. Yesterday the tutor gave a great answer; today, the same question got a strange one.

01The path changes every time

L

Leo: It worked yesterday. Same question, same code. Today it went somewhere odd. I'll just run it a few more times until I see the bug.

M

Maya: What will you see if it works the next three times?

L

Leo: That it's fine, I guess.

M

Maya: Ask an agent the same question twice, and it may call its tools in a different order. The LLM chooses the next step every time.

L

Leo: So the results are hard to reproduce.

M

Maya: Right. Reading the code line by line won't find the cause either, like normal bug-hunting would.

L

Leo: Then what will?

M

Maya: A record of that exchange. What the agent thought, which tools it called with what arguments, and what came back.

L

Leo: And who keeps that record?

M

Maya: Observability keeps it. Evaluations turns it into a score for good or bad.

L

Leo: So one working run proves very little.

M

Maya: It proves that one path worked, once.

L

Leo: And the demo audience saw a different path.

M

Maya: Which is why you want every run recorded, not only the ones you watch.

02Traces and spans

L

Leo: What does the record look like?

M

Maya: AgentCore Observability follows OpenTelemetry, a common industry format. One user request becomes one trace: a record of everything that happens for it.

L

Leo: And inside the trace?

M

Maya: Each LLM call and each tool call becomes one span, a record of a single step.

L

Leo: Is it hard to set up?

M

Maya: If the agent runs on Runtime, it's easy. You check the traces in a CloudWatch dashboard built for generative AI.

L

Leo: So I'd see where it was slow, or where it took an unexpected path.

M

Maya: At a glance. That's the point of the bars.

L

Leo: Do we have to use CloudWatch?

M

Maya: No. Because it follows OpenTelemetry, you can send the same data to tools like Langfuse or Datadog. If a company already has a monitoring system, it can go there.

L

Leo: What do people watch on it?

M

Maya: Mostly the usual web-service numbers. Response time, the number of tokens used, how often errors happen, and how many sessions run at once.

L

Leo: But none of that says the answer was good.

M

Maya: Right. A fast, error-free answer can still be wrong.

L

Leo: Like today's. No errors, normal speed, and a strange explanation of the past tense.

M

Maya: The dashboard would show a healthy system. Only reading the answer, or scoring it, shows the problem.

03Quality as a score

L

Leo: So how do you score "good"?

M

Maya: That's Evaluations. AgentCore comes with built-in evaluators, tools that check a response and give it a score.

L

Leo: What do they check?

M

Maya: Whether an answer is correct, whether it's useful, whether the agent chose the right tools, and whether it's safe.

L

Leo: And our own standards?

M

Maya: You can build a custom evaluator that matches them.

L

Leo: Who does the grading? Nobody can read every conversation.

M

Maya: Mostly another LLM. It's called LLM-as-a-judge. You give the judging LLM a set of standards, and it returns a score and a reason.

L

Leo: Can I trust a judge that's also an LLM?

M

Maya: Only as far as its standards are clear. The reason it returns lets you check a sample of its scores by hand.

L

Leo: When does it run?

M

Maya: Two ways. Online evaluation takes samples of real conversations in production and scores them all the time.

L

Leo: And the other?

M

Maya: A batch of checks during development or in CI, the automatic checks that run on every code change.

L

Leo: So online catches a drop in production, and CI catches it before release.

M

Maya: That's the split. Quickturn does both: online evaluation scores tutor sessions in production, and a pre-merge evaluation lives in the repository.

L

Leo: So turning on an evaluator is enough?

M

Maya: Having the feature isn't what matters. The design of the evaluation is.

L

Leo: Meaning what?

M

Maya: A test set with common questions, edge cases and tricky questions. A clear standard for a passing score.

L

Leo: And something that runs on every change?

M

Maya: A regression test, which catches new problems caused by a change. It runs every time you change a prompt or a tool.

L

Leo: And the team that builds that carefully…

M

Maya: Catches far more problems than a team that just turns on an evaluator.

04Observe, evaluate, fix

L

Leo: And once we have scores?

M

Maya: They're material for fixing. Look at the parts that scored low, and check where the problem is.

L

Leo: The prompt, the model, or a tool's description.

M

Maya: Those three cover most causes. Today's trace might show the tutor never called the grammar tool, for example. Then the tool's description is the first suspect.

L

Leo: So I'd fix the description.

M

Maya: Fix it, then run the same evaluation again to see if the score went up.

L

Leo: Where can I practice this?

M

Maya: The last lab in the official Phase 1, and a Deep Dive module called "Observe, evaluate, optimize."

L

Leo: What does all this cost?

M

Maya: Every evaluation run costs judge calls and time. And a trace keeps the full conversation with a customer.

L

Leo: So personal data sits in the logs.

M

Maya: Before you go live, decide how long you're allowed to keep them. Longer helps debugging, and shorter protects learners.

L

Leo: Then why pay for it?

M

Maya: Think about the next model upgrade.

L

Leo: Someone will ask whether it's better.

M

Maya: Without numbers, it's hard to get approval to release a new model version. You can't show it's better or worse.

L

Leo: In the new-employee picture, observability is the daily work report.

M

Maya: And evaluations are the performance review, based on that report. Without the report, you can't explain why you gave a score.

05Leo explains it back

M

Maya: Tell me how you'll find today's bug, without rerunning it.

L

Leo: An agent's path changes every run, so I read the trace for today's request, span by span.

L

Leo: Then I score quality with evaluations: online in production, and in CI before release.

M

Maya: And after the fix?

L

Leo: Run the same evaluation again, and see if the score went up. Observe, evaluate, fix, and loop.

M

Maya: Before anything else, add today's question to the test set. Then this bug can't come back unnoticed.

Summary in three lines

  1. An agent's path changes every run, so traces and spans record what happened.
  2. Evaluations turn responses into scores, online in production and in CI before release.
  3. The design of the test set and standard matters most; keep looping observe, evaluate, fix.
