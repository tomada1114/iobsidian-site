How can an agent remember anything?

A learner returns after yesterday’s conversation and changes their study goal. Stored context can help, provided retrieval respects access and the latest request.

A video call. Leo has been chatting with the tutor on the test site all morning.

01The model remembers nothing

L

Leo: The tutor remembered something I told it last week. So the model keeps a memory of each learner, right?

M

Maya: What do you think happens when you write "as I mentioned before"?

L

Leo: It looks back at what I said.

M

Maya: The application supplies context for each call. It may select recent turns and retrieved records; the model does not independently reload last week’s conversation.

L

Leo: So the supplied history still uses tokens?

M

Maya: Yes. The context window carries input for a call and has a size limit.

L

Leo: What happens as it fills up?

M

Maya: A larger input uses more tokens. Latency and usage charges depend on the model and provider, while irrelevant context can reduce usefulness.

L

Leo: But more history means more useful context?

M

Maya: Too much hurts too. The LLM can have trouble finding the part it really needs, so the answer can get worse.

L

Leo: Then use a model with a bigger window.

M

Maya: That doesn't solve it. Keep sending every unrelated message, and it can still lose track of the instructions that matter.

L

Leo: So the question isn't how much to pack in.

M

Maya: It's what to keep and what to drop. That's where Memory comes in.

02Short-term and long-term

L

Leo: What does Memory keep first?

M

Maya: The application writes conversation turns as short-term events. Memory stores those supplied events; recording every turn requires that integration.

L

Leo: How does it tell sessions apart?

M

Maya: Actor and session IDs organize the events. The application must derive trusted IDs and enforce which records each caller may access.

L

Leo: And when the Runtime session ends and its microVM is thrown away?

M

Maya: The record stays in Memory. When the session starts again, the conversation continues by loading it.

L

Leo: But keeping every message forever won't fit in the window.

M

Maya: Right. So Memory pulls out the key points from the saved events and stores them separately, as long-term memory.

L

Leo: While the learner waits?

M

Maya: Extraction runs asynchronously after events are stored. The reply need not wait for it, while event writes and retrieval still affect the application path.

L

Leo: So a slow strategy is fine?

M

Maya: A slower strategy delays availability of extracted records. Choose whether the next reply can proceed without them and measure writes and retrieval separately.

L

Leo: Pulls out what, exactly?

M

Maya: You choose a strategy. Semantic memory collects facts. A summary sums up the whole conversation.

L

Leo: And others?

M

Maya: User preference remembers what the user likes. Episodic memory learns from events that went well or badly. And a custom strategy uses your own prompt.

L

Leo: Can one agent use several?

M

Maya: Yes, it can combine them. And the extracted memories go into separate namespaces, like separate shelves.

L

Leo: One shelf for this user's preferences, another for a case history.

M

Maya: Right. Separate shelves help avoid mixing up whose memory is whose.

L

Leo: So the shelf names organize records; what prevents access to someone else’s shelf?

M

Maya: Derive the namespace from trusted identity and enforce access permissions. A caller-selected shelf name alone is not an authorization boundary.

03Bringing memory back

L

Leo: So how did the tutor know what I said last week?

M

Maya: The application queries permitted long-term records and adds selected results to the model’s context. A framework integration can perform these steps when configured.

L

Leo: Close in meaning, not the same words?

M

Maya: Right. It searches by meaning, so it finds a related memory even when the wording differs.

L

Leo: So if I said "I keep mixing up past tenses" last week, and today I ask about "yesterday's grammar"…

M

Maya: The search can still find it. The words differ, but the meaning is close.

L

Leo: Do I write that search myself?

M

Maya: A configured integration can help. The team still chooses the query, authorized namespace and retrieved records to include, then tests their relevance.

L

Leo: Is there a simple way to picture this?

M

Maya: Think of a new employee. Short-term memory is the employee's note from today's meeting, written down as it happened. Long-term memory is a customer chart, with only the key points copied over.

L

Leo: And the charts sit on shelves until that customer comes up again.

M

Maya: Then they're taken down and placed on the desk.

L

Leo: But the desk has a size.

M

Maya: The context window, yes. It's shared by the system prompt, the tool descriptions, the chat history and the retrieved memories.

L

Leo: So who decides what to drop when it's full?

M

Maya: In Strands, the conversation manager. It replaces old messages with a summary, or removes the oldest parts past a certain size.

L

Leo: Is the default good enough?

M

Maya: It depends on what matters most for the agent. Deciding whether to keep the default or adjust it is a real design choice.

L

Leo: Last week the learner wanted exam practice; today they want conversation for work. Which goal should the summary keep?

M

Maya: Keep the new goal explicit and treat the older one as history. Test whether retrieval preserves that change rather than overriding it.

04Whose memory it is

L

Leo: What worries companies most about long-term memory?

M

Maya: Mixing up whose memory it is. A poor namespace design can leak one customer's preferences into another's data.

L

Leo: How do you design it well?

M

Maya: For this tutor, scope records to the authenticated learner. Shared organizational context may use another permitted audience, with explicit access rules.

L

Leo: What else comes up in production?

M

Maya: Questions you barely think about alone. Can you delete one user's memory when they ask? How long is memory kept?

L

Leo: Is it fine to keep personal data in it as it is?

M

Maya: And is the stored data encrypted? Those aren't only settings. The extraction strategy decides what goes into long-term memory in the first place.

L

Leo: So choosing a strategy is a privacy decision too.

M

Maya: That's why our tutor's Memory holds conversation only. The learner's weak points stay in Quickturn's own database.

L

Leo: Because the database is where deletion and export already work.

M

Maya: And where the rest of the app reads them. Memory helps the tutor talk; it isn't the learner's record.

05Leo explains it back

M

Maya: Now explain how the tutor "remembered" last week.

L

Leo: The model receives selected context. Short-term Memory keeps the conversation events the application recorded.

L

Leo: Long-term memory keeps facts extracted in the background, on separate shelves.

L

Leo: Retrieval brings them back into the next prompt, by meaning, inside a window with a limit.

M

Maya: Whose shelf is it?

L

Leo: For the tutor, the authenticated learner’s permitted records. Shared memory would need its own audience and authorization rule.

M

Maya: Add where the line is for us: the tutor's Memory keeps conversation, and the learner's record stays in our database.

Summary in three lines

  1. The model receives selected context; the window is limited and stored history must be supplied by the application.
  2. Short-term memory keeps recorded events; long-term strategies extract selected context organized by namespace.
  3. Retrieval selects related records within an authorized namespace; names alone do not enforce access.
