Gateway: one entry point for internal tools

To do real work, an agent needs "tools" that connect to internal APIs and databases. But a company often has dozens of APIs. If each team writes its own connection code for every agent, the same logic gets copied many times, and access rules end up different in every team. Gateway, the topic of this chapter, brings these internal resources together into one entry point, so agents can use them all the same way.

Too many separate toolboxes

A company has billing systems, HR systems, inventory systems, and more, each built up over time by a different department. There can be dozens of these APIs, and each one is a possible tool for an agent. If every team writes its own connection code, the same kind of login check (authentication) gets rewritten again and again.

Access rules often differ between teams too. One team checks every caller carefully, while another team lets everything through with a single API key. As the number of agents grows, this duplicate work and uneven access control keep piling up.

Gateway solves the problem of "how to expose these tools" only once. Many agents can then reuse that same setup. The next sections look at how it works.

Register existing resources as "targets"

Anything you register with Gateway is called a target. The advantage is that you can register a resource that is already running, without rewriting it.

Target typeWhat you registerGood for
Lambda functionCode you already wroteTurning your own logic into a tool without changes
REST APIAn existing API with an OpenAPI definitionWhen your system already has a public API
Smithy modelAn API defined with SmithyWhen AWS manages your API with Smithy
Existing MCP serverAn MCP server that is already runningWhen another team has already set up MCP

Once you register targets, Gateway publishes all of them as one single MCP endpoint (a single connection point). The agent does not need to know how each target is different. As we saw in Chapter 1, it just connects as an MCP client to this one endpoint, and it can then use every tool behind it.

When a new internal API appears, you do not need to change the agent's code. Just add it as a new target in Gateway, and existing agents can use it right away.

Analogy: the toolbox front desk

The new employee (the agent) does not need to remember where every tool is kept. They just tell the front desk (Gateway), "I want to do this," and the desk finds the right tool. The desk always checks an ID before handing out a tool, and it records who received which tool. Searching through hundreds of tools on the shelf is the desk's job, not the new employee's.

Authentication goes in two directions

The key point about Gateway is that authentication (checking who someone is) happens in two separate directions. The first is when the agent calls Gateway. This uses JWT or OAuth to check "who is making this call." The second is when Gateway calls the target. Here it uses IAM, OAuth, or an API key, depending on the type of target.

DirectionWhat is checkedMethod used
Agent to GatewayWho is making this callJWT, OAuth
Gateway to targetWhich rights to use on the target sideIAM, OAuth, API key

The agent itself never handles these credentials (login secrets) directly. Deciding where to store each credential is the job of Identity, covered in the next chapter, Chapter 7. Gateway only decides which authentication method to use; the credentials themselves are stored on the Identity side.

When tools grow in number, narrow them down first

As you register more targets, the number of tools available through Gateway can reach hundreds. A problem appears if you send every tool's description to the LLM. Too much description text fills up the context window (the space the LLM uses to hold information for one request), and having many similar tools also makes wrong choices more likely.

Gateway can search by meaning (semantic search) to find only the tools that match a request. The agent then only sees a short list of tools that fit the request, so the choice does not get harder as the total number of tools grows. For example, if one department has 100 tools but only a few match the current request, Gateway can pull out just those few, and the LLM can then pick the right one with no confusion.

Tool size and description text decide accuracy

Publishing a target as-is is not enough. Part of designing Gateway is shaping tools to a size that is easy to use. If one tool matches a single API call, it can be too small, and the agent ends up needing many calls. If one tool tries to do too many things at once, it becomes hard to reuse in other situations.

How you write a tool's description also decides how often it gets picked. Adding a clear note about when to use the tool, not just its name and arguments, improves the accuracy of semantic search and the LLM's choice. This tool design is also what Policy, covered in Chapter 8, checks when it decides whether to allow a call.

An isolated workspace: Code Interpreter and Browser

Besides connecting internal APIs, Gateway also offers built-in tools that AWS provides. One is Code Interpreter. It runs code inside an isolated sandbox (a safe, separate space) to do data analysis and calculations.

The other is Browser. An agent can control a browser that runs in an isolated space in the cloud. This lets it work with internal systems that only have a screen and no API. A person can also watch the actions live or keep a record of them. Normal API calls cannot do that.

Where companies get stuck

IT security reviews always flag the same problem: every time a new tool is added, teams give it slightly more access than needed. Before long, every agent has admin-level rights. Another concern is indirect prompt injection, where a tool follows hidden instructions placed inside an outside web page or file. Tools that touch outside content directly, like Browser, need even stronger isolation from production.
