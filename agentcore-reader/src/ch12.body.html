How do you design an agent you can defend?

A useful answer may quote a restricted document or trigger a payment. A defensible design connects those consequences to permissions, approval, retries and evidence.

01Permissions in search

A search index can lose the access rules of its documents. Suppose an HR folder is available only to managers. Without reliable permission metadata, the index may return a restricted passage to another employee.

The generated answer can look perfectly normal, so a well-written prompt will not reveal the mistake. Authorization must happen before restricted passages become part of the model's input.

Attach trusted metadata describing the permitted audience, then apply a retrieval filter derived from the authenticated caller's access. Maintain those permissions as documents move or users change roles. A filter is useful only when the underlying metadata and the caller's identity are reliable.

In Quickturn's tutor, the same rule limits retrieval to the signed-in learner's records. Test a request for another learner's data and confirm that the restricted record never reaches the model. The data layer should enforce the boundary even if the agent requests a broader search.

02When an agent pays

An agent that buys a course upgrade needs controls beyond a payment tool. Define a spending budget and an approval threshold. Record what was purchased, for whom and at what price.

An approval should identify the precise operation. Preserve the decision and the resulting transaction record so that a reviewer can connect the two. Also consider failures and retries: a timeout must not cause a second charge without a reliable way to identify the original operation.

If those controls are missing, keep the payment outside the agent's autonomous scope. The design can still propose an upgrade and send the user through a normal purchase flow. Add payment authority only when the team can explain its limits and recover from a partial failure.

03A checklist and real code

The AWS Well-Architected Generative AI Lens provides questions under six pillars: operational excellence, security, reliability, performance efficiency, cost optimization and sustainability. Use the questions to locate gaps in a design, then record the evidence or work needed for each gap.

Operational excellence concerns how changes are checked and how behavior is monitored. Security covers permissions and exposure to untrusted instructions. Reliability asks what happens when a model or tool fails and whether long work can resume safely.

Performance efficiency includes latency, streaming, caching and appropriate model choice. Cost optimization asks whether usage is understood and whether cheaper options meet the quality requirement. Sustainability includes avoiding unnecessary calls and resources that do not improve the result.

For a tutor, a fallback might offer a retry message, a limited non-agent feature or a tested alternative model. Choose a fallback that preserves the permissions and quality requirements of the original path. A cheaper model is not automatically an acceptable replacement.

AWS Japan's open-source GenU application provides implementation examples. Relevant areas include sign-in, security configuration, agent runtime integration and chat tool connections. Read them to understand the choices, and compare them with the risks of the application you are building.

04Choosing no agent

Agent autonomy adds operational work. A model that chooses its next action needs tools, permissions, monitoring and a way to judge the outcome. When the steps are fixed, an explicit workflow or ordinary code can be easier to test and operate.

In the language-learning example, grading a typed answer can follow a known sequence. A tutor responding to open-ended questions may need flexible tool selection. Evaluate each task separately instead of turning the entire application into one agent.

For a fixed, high-impact operation, code can enforce the required sequence directly. For an open-ended task with low impact, a limited agent may be reasonable. An open-ended, high-impact task requires especially narrow tools, permissions and approval points.

Using ordinary code removes model-driven instruction following from that operation, but ordinary software still needs secure access checks and reliable error handling. The choice should follow the actual task and its failure cost.

A defensible design names what the agent can read and change. It records evaluation, failure handling and ownership of remaining risks. Identify the weakest area and a concrete plan to address it. Reviewers can then inspect the proposed boundaries and supporting evidence before production.

Summary in three lines

  1. Search must filter by the asker's permissions, or documents leak into answers.
  2. Payment authority needs bounded spending, appropriate approval, transaction identity and a record that supports recovery.
  3. Use the Generative AI Lens as a checklist, and choose no agent when steps are fixed.
