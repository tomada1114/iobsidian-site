Runtime: A Private Room for Each Agent

In earlier chapters, you saw that the agent loop itself can be written in a few dozen lines of code. But letting many users use it is a different problem. You need to set up servers, keep each user's conversation separate, and keep long tasks running. In this chapter, you will see how Runtime, the core part of AgentCore, takes over this job of "keeping things running".

What Runtime takes over

You can write the agent loop yourself, as you saw in earlier chapters. The hard part is keeping it running so it can always accept requests. It must answer quickly when someone sends a request. It must keep each user's conversation separate, even when many people use it at once. It must also add or remove servers as needed. Whether you want to build all of this yourself is the real reason to use Runtime.

The first option many people think of is AWS Lambda. But Lambda is built for short tasks that finish quickly, and each call has a time limit. An agent calls a tool, waits for the result, then calls the next tool, again and again. If the conversation runs long, it can go past this time limit.

Another option is a container platform, such as Amazon ECS. This removes the time limit, but now you must design and build your own systems for isolation and scaling, such as keeping each user's conversation separate, and reducing the number of servers when they are not needed.

Runtime is a service that takes over these three jobs: keeping things running, keeping sessions isolated, and scaling up or down. As a developer, you only need to write the agent's own code. Runtime handles the rest. The table below compares Runtime with the simpler options.

A private room for each session

When Runtime receives a request, it sets up a microVM (a small virtual machine) just for that session, and runs the agent inside it. As Figure 1 shows, each user's session gets its own microVM, so conversations never mix.

When the session ends, its microVM is thrown away, like cleaning up a room. If the same user wants to continue the conversation later, they send a request with the same session ID, and Runtime shows them to the same room. Remembering the conversation over time is the job of Memory, covered in the next chapter. It helps to think of Runtime's job as only this: setting up an isolated place to run the agent.

Analogy: a private room and cleanup

Think of it like hiring a new employee. Each new employee gets their own private room, so another employee's papers never mix in with theirs. When a piece of work is finished, the room is cleaned up and made ready for the next task. To continue the same discussion, you just give the same reception number, the session ID, and you are shown back to the same room.

Long runs and streaming

Some agent tasks take a long time, calling many tools again and again. Runtime supports runs of up to 8 hours. This means you can hand off long tasks, such as research or data analysis, and let them keep running.

Still, it is not a good experience to make a user wait in silence for a long task. Runtime supports both asynchronous processing and streaming (sending small pieces of the answer as soon as they are ready). You can run long tasks in the background and check the result later. For short answers, you can stream the text to the screen piece by piece as it is written.

Rules that do not depend on the framework

Runtime does not care which framework you used to write the agent, or which LLM it calls. The only rule is this: your agent must offer two HTTP endpoints, /invocations (for calls) and /ping (to check that it is alive). If you follow this one simple rule, you can host an agent built with Strands Agents, LangGraph, or CrewAI in the same way.

The endpoint does not have to be HTTP only. On the same Runtime, you can also host your agent as an MCP server that offers tools, or as an A2A server that talks to other agents. Support for two-way streaming, such as for voice conversations, is also growing. This area changes fast, so check the course materials and the developer guide for the latest details.

Deployment, versions, and operation

There are two main ways to put your agent on Runtime: building a container image and placing it in ECR, or passing your code directly. There are many small settings, but the AgentCore CLI handles everything from building to deploying, so you do not need to redo the steps each time.

Every time you update your code and deploy, Runtime adds a new version. The actual requests are received by an endpoint, and the endpoint decides which version gets the traffic. As Figure 2 shows, you can fix the production endpoint to a version you have already tested, while trying the newest version on a staging endpoint. If something goes wrong, you can roll back by pointing the endpoint to an older version, using the same system.

You pay only for what you use. The design idea is that the cost goes down when the agent is not really doing work, such as while it waits for the LLM to respond. The exact prices change often, so here we focus only on the idea behind the pricing.

To authenticate calls to Runtime, you can use AWS IAM (with SigV4 signing) or JWT (with OAuth). Which one to choose depends on who is calling, and Chapter 7 covers this in detail. Runtime can also connect to a database or an internal system inside a VPC (a private network), so it can reach resources deep inside your company's network.

Where companies get stuck

In a personal prototype, people often overlook three problems: mixed-up conversations, long tasks stopping partway through, and closed networks. If a shared server handles sessions carelessly, one user's conversation can leak into another's. A long task can also get stuck when it hits a timeout. In production, teams often need the agent to reach a system that is only available inside the company network. Runtime's session isolation, long runs, and VPC connections answer exactly these needs.
