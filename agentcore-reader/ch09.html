Observability and Evaluations: how do you know it is not getting worse?

An agent may not follow the same path every time, even for the same question. Sometimes you get a strange answer today, though yesterday it was fine. To find the cause, you need a record of what the agent thought, and which tools it called, in what order. This chapter looks at Observability, which keeps this record, and Evaluations, which uses the record to score quality.

01The path changes every time

If you ask an agent the same question twice, it may not call its tools in the same order each time. This is because the LLM (the AI model behind the agent) chooses the next step every time.

In other words, the results are hard to reproduce. Say the agent gave the right answer yesterday, but a strange answer today. You cannot find the cause just by reading the code line by line, like normal bug-hunting.

What you need is a record: what the agent thought during that exchange, which tools it called and with what arguments, and what came back. Observability is the system that keeps this record. Evaluations is the system that turns the record into a score for good or bad.

02Observability: traces and spans

AgentCore Observability follows OpenTelemetry, a common industry format for recording data. One user request becomes one trace (a record of everything that happens for that request). Inside that trace, each LLM call and each tool call by the agent becomes one span (a record of a single step).

If your agent runs on Runtime, this kind of recording is easy to set up. You can check the traces you collect in a CloudWatch dashboard built for generative AI.

Because it follows OpenTelemetry, you are not limited to CloudWatch. You can send the same data, in the same format, to outside observability tools such as Langfuse or Datadog. If your company already has a monitoring system, you can choose to send the data there instead.

The metrics you watch are mostly familiar from monitoring web services: response time (latency), the number of tokens used, how often errors happen, and how many sessions run at the same time.

03Evaluations: turning quality into a score

Even with a good record, you still cannot tell if an answer was good. This is what Evaluations does: it turns the quality of a response into a score.

AgentCore comes with built-in evaluators (tools that check a response and give it a score). They can check if an answer is correct, if it is useful, if the agent chose the right tools, and if it is safe. You can also build a custom evaluator that matches your own company's standards.

Most scoring uses LLM-as-a-judge, a method where another LLM does the grading. Reading every conversation by hand is not realistic, so you give the judging LLM a set of standards, and it gives back a score and a reason.

There are two ways to run evaluations. Online evaluation takes samples of real conversations from production and scores them all the time. The other way runs a batch of checks during development or in CI (continuous integration, an automatic check that runs each time you change the code). Online evaluation helps you notice a drop in quality in production. The other kind helps you check a change before you release it.

04The design of the evaluation makes the difference

The Evaluations feature is ready to use, but having the feature is not what matters. What matters is how well you design the evaluation.

This means: how you build a test data set with common questions, edge-case questions, and tricky questions; how you decide the standard for a passing score; and how you set up a regression test (a check that catches new problems caused by a change) that runs every time you change a prompt or a tool.

A team that builds this carefully will catch far more problems in production than a team that just turns on an evaluator.

05The loop: observe, evaluate, fix

Evaluation is not just about measuring. It gives you material for fixing problems. Look at the parts that scored low. Check whether the problem is in how you wrote the prompt, which model you used, or how you described a tool. Fix it, then run the same evaluation again to see if the score went up.

The final lab in the official Phase 1, and the Deep Dive module called "Observe, evaluate, optimize", let you practice this whole loop yourself: observe, evaluate, fix, and evaluate again.

Analogy: daily work reports and performance reviews

Without a daily work report that says what a new employee did, and in what order, you cannot judge how well they worked that day. Observability is like this report. Evaluations is like the performance review that scores the work, based on that report and a set of standards. Without the report, you cannot even explain why you gave a score.

Where companies get stuck

If you cannot show numbers proving that a new model version is better or worse, it is hard to get approval to release it. Also, a trace keeps the full conversation with a customer. This can leave personal data in the logs. Before you go live, you need to decide how long you are allowed to keep these logs.
