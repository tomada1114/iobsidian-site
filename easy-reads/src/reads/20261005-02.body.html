Why write about decisions?

Q: I have many small projects online. Is the code not enough?

A: The code shows what you built, but it does not always show why you built it that way. When someone looks at your work, for a job or for a team, they want to see how you think. A short README, the text file at the top of a project, is a good place to show this.

Most small projects have no README, or only a line about how to install them. That is normal, and it also means a few clear sentences can make your project stand out.

What should I write?

Q: I do not want to write a long document. What is the minimum?

A: Three parts are enough. First, say what problem the project solves. Second, explain one choice you made. Third, say what you would change today. A good README can walk someone through your project in less than a minute, the way you would explain it to a friend at the next desk.

For example, imagine a small tool that was built to rename photo files by date. Your README could say: "This tool was built because my photo folders were hard to search. A simple script is used instead of a full app, because only one person needs it."

Explain one trade-off

Q: Why is the choice the most important part?

A: Every design has a trade-off, which means you get one good thing but give up another. A simple script is quick to write and easy to read, but it has no screen and it is harder for other people to use. When you name both sides, readers can see that you thought about the choice, not that you only took the first idea.

Many engineers worry that a simple design looks weak. In fact, choosing simple on purpose, and saying why, often shows more judgment than adding many features that nobody needed.

Be honest about changes

Q: Does saying what I would change make me look bad?

A: No. It shows that you keep learning. You could write: "If I did it again, I would add tests first, because I broke the date logic twice." If I read a sentence like that, I would trust the writer more, not less.

Here is a small step for this week. Choose one old project and add three sentences: what problem it solves, one choice you made, and one thing you would do differently. A project you already finished can become a clear example of your skill with a few honest words.

Words and phrases to notice

walk someone through
explain something to someone step by step
trade-off
getting one good thing by giving up another
README
a text file that explains a project
stand out
be easy to notice among many others
on purpose
because you decided to, not by accident

English to notice

Passive voice: “This tool was built because my photo folders were hard to search.” We use the passive when the action or the thing matters more than the person who did it.

Second conditional: “If I did it again, I would add tests first.” This pattern talks about an imagined situation: if + past tense, then would + verb.

Think about it

Think of one project you finished. What would you change if you did it again? Try using “If I did it again, I would...” in your answer.
