One person asks

On many software teams, no one adds code alone. First, a developer makes a change on their own branch. Then they ask a teammate to read it. This is called a code review.

On GitHub, this request is a pull request. On GitLab, it is a merge request. The names are different, but the idea is the same. The developer writes a short note. The note says what the change does and why.

Another person reads

The reviewer, the person who reads the change, looks at each line. The tool shows old lines and new lines side by side. The reviewer can leave a comment on any line.

The two people talk in these comments. The developer answers questions and fixes some things. Then they push the new version. This can go back and forth a few times.

When the reviewer is happy, they approve the change. Then the change is merged into the main branch. Many teams do not allow a merge without at least one approval.

More than finding bugs

Most people think reviews are for catching bugs. They do catch some bugs. But they also do a quiet second job. They spread knowledge across the team.

The reviewer learns a part of the code they did not write. The writer learns a new way to solve a problem. Later, if the writer is sick or on vacation, someone else already knows the code. A new team member can also learn fast by reading reviews.

Kind and clear comments

A good comment is kind and specific. It talks about the code, not the person. "This loop runs twice" is better than "You made a mistake."

Many reviewers put a small label at the start of a comment. The label shows how important the comment is. A nit is a very small point, like a name or a space. The writer can skip it. A question asks for help to understand. A suggestion gives an idea, but the writer can say no.

These labels save time. The writer knows what must change and what is only an idea.

Words to notice

code review
when a teammate reads your code change before it goes in
reviewer
the person who reads and checks the change
approve
to say yes, this is ready
merged
added into the main code
nit
a very small point that is not important
specific
clear and about one exact thing

Think about it

Think of a comment you once got on your work. Was it kind and specific? How did it help you?
