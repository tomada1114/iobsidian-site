Two names, one mix-up

Many teams say they use Clean Architecture and DDD. Often they talk about the two as one thing. But they are not the same. They answer two different questions.

Clean Architecture asks: which way does the code point? DDD asks a different thing. It asks: what words do we use for the business? You can use one without the other.

Clean Architecture is about direction

Think of your code as rings. The center ring holds the core rules of the app. The outer rings hold the database, the web server and the screens.

The main rule is about dependency, which means one part needs another part to work. In Clean Architecture, outer rings can know about the center. The center must not know about the outer rings.

So the core code never says "save this row to PostgreSQL." It only says "save this order." Some outer code does the real work with the database. If you change the database later, the core does not change. You can also test the core without a database.

DDD is about words

DDD means Domain-Driven Design. The domain is the business the software is for, like shipping, banking or a hotel. DDD says the code should use the same words as the people in that business.

Say the hotel staff talk about a "booking" and a "guest." Then the code should have a Booking and a Guest. It should not have DataRecord or UserRow. Developers and business people then share one language. DDD calls this the ubiquitous language, a language used everywhere in the project.

DDD also asks you to draw lines around parts of the business. A "guest" at the front desk may not mean the same as a "guest" in billing. Each part can keep its own model.

How they fit together

The two ideas work well side by side. DDD tells you what goes in the center ring. Clean Architecture tells you how to keep that center safe from the database and the web.

But a small app can follow Clean Architecture with no DDD at all. And a team can use DDD words in a simple app with no rings. When someone says "we do DDD," you can ask one question. Do they mean the words, or the direction of the code?

Words to notice

dependency
when one part of code needs another part to work
domain
the business or field the software is made for
ubiquitous language
one set of words everyone on the project uses
core
the center part that holds the main rules
mix-up
when people think two different things are the same

Think about it

Think of an app you know. Does its core code know about the database? Do its names match the words the business uses?
