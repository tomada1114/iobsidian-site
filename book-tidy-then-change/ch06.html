整えてから変えるか、変えてから整えるか第6章 / 全7章

変更の手間を大きくしているのは、部品どうしのつながりです

一か所を直したつもりが、別の場所で表示が食い違う。このとき手間を大きくしているのは、コードの量より、部品どうしのつながり方です。この章では、変更が広がる原因になる「結合」と、それを抑える「凝集」を短いコードで確かめ、変更が広がる場所を見つけて寄せる整頓を練習します。

読了 約8分学習テキスト

この章で分かること

  • 一つの条件を変えたのに、なぜ三か所で食い違いが起きるのか
  • 結合とは何で、なぜ変更の手間の大半を決めるのか
  • 一緒に変わるものを近くに寄せると、何が変わるのか
  • 練習問題：コードから結合を見つける

01同じ条件の変更を、二通りに比べます

加藤さんは、フィットネスクラブの会員管理システムを担当しています。このクラブには、月に8回以上通った会員を「ゴールド会員」とする制度があります。ゴールド会員には特典のお知らせメールが届き、ポイントの付き方が5倍になり、受付の管理画面では名前の横に「ゴールド」と表示されます。今回の依頼は、ゴールド会員の条件を「月に10回以上」に変えることでした。

コードを調べると、ゴールド会員かどうかの判定は、三つのファイルにそれぞれ書かれていました。

# mail.py
if member.visits >= 8:
    send_gold_mail(member)

# points.py
rate = 0.01
if member.visits >= 8:
    rate = 0.05

# admin.py
if member.visits > 8:
    label = "ゴールド"

ここから先は、同じ依頼を二通りに書きます。

一つ目の加藤さんは、メールを送る処理の 8 を 10 に書き換えて作業を終えました。翌月、9回通った会員から「特典のメールは来なかったのに、ポイントは5倍で付いている」という問い合わせが受付に届きました。調べると、ポイントの計算は8回のままでした。さらに、管理画面の判定は > で書かれていたので、もともと9回以上の会員にしか「ゴールド」と表示されていませんでした。三か所の判定が、変更の前から少しずつ食い違っていたことになります。

二つ目の加藤さんは、条件を書き換える前に、ゴールド会員の判定を一つの関数にまとめる整頓をしました。

# rank.py
GOLD_VISITS = 8

def is_gold(member):
    return member.visits >= GOLD_VISITS

三つのファイルは、それぞれ is_gold(member) を呼ぶ形に書き換えました。管理画面だけは > から >= に変わり、8回ちょうどの会員の表示が変わるので、受付の責任者に確認してからこの変更を別のコミットにしました。その後、GOLD_VISITS の値を 10 に書き換えました。条件の変更は1行で済み、三か所の判定がそろって変わりました。

02結合は、片方を変えるともう片方も変えなければならない関係です

二つの部品のあいだで、片方を変えるともう片方も変えなければならない関係を結合と呼びます。加藤さんのコードでは、メール、ポイント、管理画面の三つの処理が、「ゴールド会員は月に何回以上か」という同じ決まりを通して結合していました。決まりが変わると、三つすべてを変える必要があります。三つの処理は互いを呼び出していないので、呼び出し関係をたどっても、このつながりは見えません。同じ決まりを別々の場所に書いていると、関数どうしの呼び出しがなくても結合が生まれ、しかも気づきにくくなります。

結合は、変更が起きたときに初めて手間として表に出ます。ゴールドの条件が10年間変わらなければ、三か所に同じ判定が書かれていても、誰も困りません。逆に、何度も変わる決まりほど、結合している場所の数だけ手間がかかります。結合の強さは、コードを眺めただけでは決まらず、「この先どんな変更が起きるか」とあわせて考えます。

さらに、結合は連鎖します。ポイントの倍率を変えると、ポイントの残高を表示する画面や、月末にポイントを集計する処理も変える必要が出てくることがあります。一つの変更が次の変更を呼び、それがまた次を呼ぶと、手間は急に大きくなります。多くの変更は数分で終わりますが、ときどき起きるこうした連鎖の大きな変更が、ソフトウェアにかかる手間の大半を占めます。ですから、変更の手間を減らすには、連鎖を起こす結合を減らすことが近道になります。

結合と、次の節で扱う凝集という考え方は、ラリー・コンスタンティンが1960年代後半に、プログラムを組み立てる方法の研究の中で考えたものです。1974年の論文と、その後の書籍『Structured Design』で広まり、いまも設計の基本の言葉として使われています。

03一緒に変わるものを近くに寄せます

一緒に変わるものが近くにまとまっている度合いを凝集と呼びます。二つ目の加藤さんの整頓の後も、三つの処理はゴールドの判定につながっています。整頓で変わったのは、決まりが変わったときに直す場所が rank.py の1か所に集まったことです。結合を消せなくても、一緒に変わるものを近くに寄せれば、変更の範囲は狭くなります。

確かめる範囲も狭くなります。判定が1か所にあれば、is_gold に9回と10回の会員を渡して結果を見るだけで、条件の変更が正しいかを確かめられます。三か所に書かれていると、メール、ポイント、管理画面のそれぞれで、9回と10回の会員を試す必要があります。

寄せる整頓は、ファイルをまたがない小さな形でもできます。一つのファイルの中で、一緒に変わる関数どうしが離れた場所に書かれているなら、隣り合うように並べ替えます。並べ替えるだけなら動きは変わらず、次に変更する人は、画面を上下に行き来せずに関係する関数をまとめて読めます。

変更が広がりそうな場所は、次の手順で見つけて寄せます。

触る場所を数える問いは、変更の見積もりにも使えます。「この依頼で、何ファイルの何か所を変えるか」を書き出すと、思っていたより多いときに気づけます。数が多いのは、同じ決まりが複数の場所に書かれているからです。

つまずきやすいところ

結合はゼロにはできません。部品が互いに使い合わなければ、システムは一つの機能も果たせないからです。また、寄せるつもりで小さな関数やファイルに細かく分けすぎると、一つの処理を追うために何ファイルも開くことになり、読む手間がかえって増えます。寄せる対象は、実際に一緒に変わったもの、これから一緒に変わる見込みがあるものに限ります。

04練習問題

ネットスーパーの注文処理に、次のコードがあります。送料が無料になる金額は、店の方針で年に何度か変わります。

# cart.py
if total >= 3000:
    show("送料無料")

# checkout.py
fee = 0 if total >= 3000 else 400

# banner.py
msg = f"あと{3000 - total}円で送料無料"
  1. この三つの処理は、どんな決まりを通して結合していますか。
  2. 送料無料の金額を4,000円に変えるとき、触る場所は何か所ですか。
  3. 一緒に変わるものを近くに寄せる整頓を、名前の例を添えて書いてください。
  4. この決まりが10年間変わらないと分かっている場合、整頓の必要性はどう変わりますか。

05解答と解説

  1. 「合計が何円以上なら送料無料か」という決まりです。三つの処理はどれも 3000 という同じ金額に頼っています。
  2. 3か所です。banner.py の式は形が違うので、検索で 3000 を探しても、合計との差を計算していることに気づかず、直し漏れが起きやすい場所です。漏れると、合計が3,500円の客に「あと-500円で送料無料」のような表示が出ます。
  3. たとえば FREE_SHIPPING_MIN = 3000 という定数と、is_free_shipping(total) という関数を一つのファイルにまとめ、三つの処理から呼びます。この整頓を先にして、金額を変える変更は別のコミットにします。
  4. 変更が起きないなら、結合は手間として表に出ません。整頓の価値は小さくなり、他の作業を先にしてかまいません。年に何度も変わる決まりだからこそ、寄せる価値があります。

3行まとめ

  1. 片方を変えるともう片方も変えなければならない関係を結合と呼び、変更の手間の大半は結合が連鎖する大きな変更から生まれます。
  2. 結合は変更が起きたときに初めて手間になるので、何度も変わる決まりにつながる結合から先に手当てします。
  3. 結合を消せなくても、一緒に変わるものを一か所に寄せる整頓をすれば、変える場所と確かめる範囲が狭くなります。
