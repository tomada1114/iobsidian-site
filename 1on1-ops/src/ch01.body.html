Isn't observability just a fancy word for monitoring?

After this page you can explain how observability differs from monitoring. You can also say which question metrics, logs and traces each answer, and where a detail like a learner id belongs.

About 8 min readCoffee in the kitchen

In this page

  • Why can't a dashboard find one slow request?
  • Which question does each signal answer?
  • Where does a detail like a learner id belong?
  • Where do traces earn their cost?

The kitchen, standing with coffee. Leo spent an hour guessing yesterday.

01The problem with a dashboard

L

Leo: A learner reported that one round took ages to load yesterday. I opened the dashboard, and p90 latency looked normal.

M

Maya: p90 meaning?

L

Leo: Ninety percent of requests were faster than that number. So most learners were fine.

M

Maya: And the one who wasn't?

L

Leo: That's the thing. I had no idea how to find that one request. I spent an hour guessing.

M

Maya: What did you expect the dashboard to show?

L

Leo: Something red, I suppose. We have alarms and graphs, so I thought we had observability.

M

Maya: That's the common view: observability means a dashboard and some alarms. If the graphs are green, the system is fine.

L

Leo: Isn't it?

M

Maya: A dashboard shows averages and percentiles over everyone. It can't tell you about one learner's request.

L

Leo: But one slow request should show up somewhere, shouldn't it?

M

Maya: One slow request in a thousand doesn't move p90 at all. And even when a percentile moves, it can't tell you which request was slow.

L

Leo: So it answers "are things broadly okay?"

M

Maya: Right. That's monitoring: watching failure modes you knew about in advance. Is the error rate up? Is latency climbing?

L

Leo: And observability is something else?

M

Maya: Being able to ask a question you didn't plan for, without shipping new code. Like "what was different about this one request?"

L

Leo: Without new code. So the answer has to be in the data already.

M

Maya: Yes. Here's the difference in one picture.

L

Leo: So we still need monitoring.

M

Maya: Always. It tells you something known broke. Observability helps you find out why.

L

Leo: So an alarm fires, and then I go digging.

M

Maya: Or a learner writes in, like yesterday, and no alarm fires at all. Then observability is all you have.

02Three signals, three questions

L

Leo: People always say "metrics, logs and traces". Are those just three tools?

M

Maya: Think of them as three questions. Metrics are cheap numbers, collected over time.

L

Leo: Like requests per minute.

M

Maya: Right. They answer "how much, how often, and is it getting worse?"

L

Leo: And logs?

M

Maya: One record per event, with details. They answer "what happened to this request?"

L

Leo: And traces?

M

Maya: A tree of timed steps, called spans, across services for one request. They answer "where did the time go?"

L

Leo: So for my slow round, the log.

M

Maya: Yes. Every API request writes one structured JSON log line: request id, operation, outcome, status and duration in milliseconds.

L

Leo: So I search for that learner's rounds yesterday, and sort by duration.

M

Maya: And you've found the request in a minute, not an hour. Then you read what else the line says.

L

Leo: Why didn't I find it that way?

M

Maya: You started from the dashboard, which can only show everyone. Start from the question.

L

Leo: And if the line shows the request took five seconds, what then?

M

Maya: Then the metrics help again. Were DynamoDB reads throttled in that same minute? The log finds the one; the metrics say whether it was part of something wider.

L

Leo: So the signals work together, not one instead of another.

M

Maya: Right. Each one is cheap for a different kind of question.

03Cardinality and cost

L

Leo: Couldn't we add a metric per learner? Then the dashboard would show each learner's latency.

M

Maya: That's the trap. It needs one word: cardinality.

L

Leo: Which means?

M

Maya: How many distinct values a field can take. Status code has a handful. Learner id has one per learner.

L

Leo: And a metric with a learner id label?

M

Maya: Each unique label combination is its own time series, and you pay for each one. With every learner, that explodes.

L

Leo: But in a log line?

M

Maya: The same learner id is just a field. It costs a few bytes, however many learners there are.

L

Leo: Then logs are cheap. Why not log everything?

M

Maya: Volume costs too, both writing and storing. One line per request, with the fields you'd search by, goes a long way.

L

Leo: And nothing like the learner's answer text?

M

Maya: No. Ids and outcomes, not personal content.

L

Leo: So counts go in metrics, and details go in logs.

M

Maya: That's the rule. Our metrics come from API Gateway, Lambda and DynamoDB: traffic, errors, latency, throttles.

L

Leo: And the alarms watch those.

M

Maya: Five alarms and one dashboard. They catch the known failures. The logs answer the rest.

04Where traces earn their cost

L

Leo: If the log line answered my question, why do we have traces at all?

M

Maya: Tracing is extra instrumentation and extra cost. With one Lambda and one table, a request log with a duration answers most questions.

L

Leo: So when does it pay?

M

Maya: When one request crosses several steps or processes. An answer handed to the grading queue, for example.

L

Leo: The API writes the answer, the queue delivers it, a worker grades it.

M

Maya: Three steps, three log lines, maybe minutes apart. A shared trace id ties them together.

L

Leo: And the tutor agent?

M

Maya: Even more. One learner message fans out: plan, call the model, call three tools, call the model again.

L

Leo: And a log line per step doesn't show which tool call was slow?

M

Maya: Not without a shared trace id. That's where traces earn their cost.

L

Leo: What does a trace look like on screen?

M

Maya: A timeline of bars, one per step, nested under the request. The longest bar is usually your answer.

L

Leo: Can we add tracing later, when we need it?

M

Maya: That's the usual pitfall. Teams add traces after the first incident, and discover their steps never passed the id along.

L

Leo: So the id has to travel from the start.

M

Maya: Yes. That's why our API, the grading worker and the tutor agent are traced now, not after an incident.

L

Leo: And model calls?

M

Maya: Each one records its own telemetry: tokens, latency, estimated cost. The prompt version is recorded with them.

05Leo explains it back

M

Maya: A learner reports a slow round tomorrow. Walk me through how you'd think about it.

L

Leo: Monitoring tells me a known thing broke. Observability lets me ask about one request I didn't predict.

L

Leo: Metrics are cheap counts, logs are per-event detail, and traces show time across steps.

L

Leo: I'd put a high-cardinality thing like a learner id in logs, not in metric labels.

M

Maya: And traces?

L

Leo: They earn their cost where one request spans several steps or services, like our grading job or the tutor agent.

M

Maya: One practical point for tomorrow: start from the learner's log lines, sorted by duration. The dashboard is for "is it widespread?", after you've found the one.

Summary in three lines

  1. Monitoring watches known failures; observability lets you answer new questions without new code.
  2. Metrics count, logs describe one event, and traces show where the time went across steps.
  3. Keep high-cardinality detail in logs, and add traces where requests cross steps or services.
