Isn't observability just a fancy word for monitoring?

After this page you can explain how observability differs from monitoring. You can also say which question metrics, logs and traces each answer, and where a detail like a learner id belongs.

About 4 min readQuickturn case study

In this page

  • Why can't a dashboard find one slow request?
  • Which question does each signal answer?
  • Where does a detail like a learner id belong?
  • Where do traces earn their cost?

01The problem with a dashboard

A normal p90 latency graph does not explain one learner's slow round. It means 90 percent of measured requests were at or below that value; a rare slow request may leave it unchanged. Monitoring exposes known failure signals, while observability supports investigating behavior that was not anticipated in a particular dashboard.

Both are useful. An alarm can reveal widespread errors, and a request-level record can explain an isolated complaint even when no alarm fired. Begin with the question that needs answering rather than with whichever graph is easiest to open.

02Three signals, three questions

Metrics summarize frequency, volume and trends. Logs describe events with searchable fields. Traces connect timed steps across a request or job. Each signal serves a different investigative need.

Quickturn logs request ID, operation, outcome, status and duration. Find the reported learner's request and time, then compare service metrics for that interval. A trace can locate the slow step if the request crosses several components.

03Cardinality and cost

Cardinality is the number of distinct field values. A metric labeled with each learner can create a growing number of time series; combinations multiply that count. An internal learner ID in a log is instead a searchable field, though the bytes still add storage cost and privacy obligations.

Quickturn keeps metric dimensions bounded and logs IDs and outcomes rather than answers or card text. A small, intentional alarm set covers known failures. Neither small logs nor an internal ID make data automatically anonymous.

04Where traces earn their cost

Tracing earns its cost when work crosses steps: an API accepts an answer, a queue delivers it and a worker calls a model. A propagated trace or job ID ties events together even when they occur minutes apart.

The tutor can add several model and tool calls to one user turn. Instrument those paths before incidents, while deciding which content must stay out of telemetry. A long span suggests where time was spent, but investigation still needs to distinguish waiting, processing and external delay.

Summary in three lines

  1. Monitoring watches known failures; observability lets you answer new questions without new code.
  2. Metrics count, logs describe one event, and traces show where the time went across steps.
  3. Keep high-cardinality detail in logs, and add traces where requests cross steps or services.
