オブザーバビリティは監視の言い換えなのか

ある学習者の1ラウンドが遅かったのに、レイテンシのダッシュボードは平常どおりでした。集計グラフには残らない細部も、リクエスト単位の証拠なら見えることがあります。

01ダッシュボードの限界

p90 レイテンシのグラフが平常でも、ある学習者のラウンドが遅かった理由はわかりません。p90 は計測したリクエストの90%がその値以下だったという意味なので、まれに遅いリクエストがあっても、グラフは動かないことがあります。監視は既知の障害のシグナルを見せます。一方のオブザーバビリティは、特定のダッシュボードが想定していなかった振る舞いを調べられるようにします。

どちらも役に立ちます。広い範囲のエラーにはアラームで気づけますし、アラームが鳴っていなくても、一件だけの苦情をリクエスト単位の記録から説明できることがあります。開きやすいグラフから始めるのではなく、答えるべき問いから始めます。

02三つのシグナルと三つの問い

メトリクスは、頻度・量・傾向を集計します。ログは、出来事を検索できる項目つきで記録します。トレースは、一つのリクエストやジョブの中で、時間を計ったステップどうしをつなぎます。調査のどんな場面で役立つかが、シグナルごとに違います。

Quickturn のログには、リクエスト ID、操作、結果、ステータス、所要時間が入っています。報告した学習者のリクエストと時刻を見つけ、その時間帯のサービスのメトリクスと見比べます。リクエストが複数のコンポーネントをまたぐなら、トレースで遅いステップを突き止められます。

03カーディナリティとコスト

カーディナリティとは、ある項目が取りうる値の種類の数です。学習者ごとのラベルをつけたメトリクスは時系列の数をどんどん増やし、ラベルを組み合わせればその数は掛け算で増えます。一方、ログに入れた内部の学習者 ID は、検索できる項目の一つにすぎません。ただし、そのバイト数はストレージのコストになり、プライバシー上の責任も生じます。

Quickturn はメトリクスの次元を絞り、ログには回答やカードの文面ではなく、ID と結果を記録します。既知の障害は、意図して選んだ少数のアラームで押さえます。ログを小さくしても、内部 ID を使っても、それだけでデータが匿名になるわけではありません。

04トレースが代償に見合う場面

処理が複数のステップにまたがるとき、トレースが役に立ちます。たとえば、API が回答を受け付け、キューがそれを届け、ワーカーがモデルを呼び出す流れです。トレース ID やジョブ ID を引き継いでおけば、数分離れて起きた出来事どうしもひとつながりにできます。

チューター機能は、利用者の1ターンの中でモデルやツールを何度も呼び出すことがあります。こうした経路は障害が起きる前に計装し、あわせて、どの内容をテレメトリに入れないかも決めておきます。長いスパンを見れば時間がどこで使われたかの見当はつきますが、それが待ち時間なのか、処理なのか、外部の遅れなのかは、調べて切り分ける必要があります。

3行まとめ

  1. 監視は既知のシグナルを見張り、オブザーバビリティは、必要な証拠が集まっていれば新しい問いにも答えられるようにします。
  2. メトリクスは数え、ログは一つの出来事を記録し、トレースはステップをまたいで時間がどこでかかったかを示します。
  3. カーディナリティの高い詳細はログに入れ、リクエストがステップやサービスをまたぐところにはトレースを加えます。
