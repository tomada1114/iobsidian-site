Should every merge go straight to production?

After this page you can explain the difference between continuous delivery and continuous deployment. You can also describe a safe deploy pipeline, and say why data changes are the hard part of going back.

About 8 min readAfter the design review

In this page

  • Delivery or deployment?
  • What happens after a merge?
  • Why does prod wait, and how do you go back?
  • How do you ship a prompt change?

After Tuesday's design review. Someone asked why prod deploys wait for an approval.

01Delivery and deployment

L

Leo: Dev deploys on every merge, and it's been fine for weeks. Prod should do the same. A manual approval feels like the old way.

M

Maya: What do you think "CD" stands for?

L

Leo: Continuous deployment. Every merge goes live.

M

Maya: It can mean two things. Let's start one step earlier, with continuous integration.

L

Leo: Merge small changes often, and check each one.

M

Maya: Right. Continuous delivery adds one promise: every commit on main is deployable. Releasing is a button.

L

Leo: And continuous deployment?

M

Maya: No button. Every commit that passes goes out by itself.

L

Leo: So both are CD.

M

Maya: Both are. A manual approval doesn't mean you've stopped doing it. The book "Continuous Delivery", by Humble and Farley, draws the line this way.

L

Leo: But isn't deploying less often safer?

M

Maya: The research in "Accelerate" found the opposite. Small batches and frequent deploys go with more stability, not less.

L

Leo: Then why the button?

M

Maya: The button isn't about size or speed. It's about who says yes, and when.

L

Leo: So a team could deploy to prod ten times a day and still press a button each time.

M

Maya: Many do. The button takes seconds. What matters is that main is always ready, so pressing it is never scary.

L

Leo: And if main isn't ready?

M

Maya: Then you don't have continuous delivery, with or without a button. You have a release that someone has to prepare.

02The pipeline

L

Leo: Walk me through what happens after I merge.

M

Maya: The merge itself is the gate. The ruleset only lets a change reach main through a PR with green required checks.

L

Leo: So the deploy workflow doesn't wait for CI again?

M

Maya: It starts on the push to main. The checks already ran on the PR.

L

Leo: What does it do first?

M

Maya: It builds the web client. Then it assumes a deploy role using GitHub's OIDC token.

L

Leo: What's OIDC giving us here?

M

Maya: Short-lived credentials. There are no stored AWS keys anywhere to leak.

L

Leo: Where did the role itself come from? Something had to create it.

M

Maya: A small deploy-access stack, deployed by hand once per account. After that, the pipeline never needs a long-lived key.

L

Leo: And the role can do anything?

M

Maya: It trusts only this repository's main branch. And all it can do is assume CDK's bootstrap roles.

L

Leo: Then the deploy.

M

Maya: The stateful foundation stack goes first, with the table. Then the app stack. Each is deployed on its own.

L

Leo: Why foundation first?

M

Maya: The app stack reads the foundation's values as it deploys. It needs them to exist.

L

Leo: What if two merges land a minute apart?

M

Maya: A running deploy is never cancelled. The next one waits for it, and if several merges land, only the newest waits, with all their changes.

L

Leo: Why not cancel the older one? The newer code wins anyway.

M

Maya: Cancelling the job doesn't stop CloudFormation. The stack keeps changing, and the next deploy has to wait for it anyway.

L

Leo: So waiting costs nothing extra.

M

Maya: And far easier to reason about.

L

Leo: Does it ever ask for approval on dev? CDK asks when a change widens permissions.

M

Maya: Not on dev. The workflow says never to wait for approval there, because nobody is watching the run. The review on the PR is where a wider permission gets questioned.

03Why prod waits

L

Leo: So why does prod wait, if dev doesn't?

M

Maya: What does dev hold?

L

Leo: Our own test data. If it breaks, we lose an afternoon.

M

Maya: And prod holds learners' data. An approval adds a human check and an audit trail. It costs some speed.

L

Leo: Couldn't the prod role just trust the main branch, like dev's?

M

Maya: A trust keyed on the main branch can't express "approved." Any push to main would pass it.

L

Leo: So what does the prod role trust?

M

Maya: The workflow's protected prod environment. That job runs only after a reviewer approves.

L

Leo: And if a prod deploy goes wrong?

M

Maya: If the stack update fails, CloudFormation rolls it back automatically.

L

Leo: And if it succeeds, but the code is bad?

M

Maya: Then you roll forward: revert the change, merge, and let the pipeline deploy the previous code.

L

Leo: Are there gentler options?

M

Maya: Blue/green and canary releases, like Lambda aliases shifting traffic gradually. And feature flags. Each makes the blast radius, the number of users hit, smaller.

L

Leo: So what's the hard part?

M

Maya: Data. You can redeploy old code. You can't roll back a table's data.

L

Leo: So the kind of change decides how careful to be.

M

Maya: Two questions decide it. How reversible is it? And how many learners does it touch?

L

Leo: And our table changes land in the bottom-left corner.

M

Maya: Usually, yes. A migration to a new key shape rewrites every learner's items, and there's no clean way back.

L

Leo: Which is why the table has its own stack.

M

Maya: Separate, retained and changed rarely. The rollback runbook says it plainly: roll forward by revert and merge, and never roll back the stateful stack by hand.

04Shipping a prompt change

L

Leo: What about a prompt change? It's just text.

M

Maya: It's code that changes behavior without changing any types. The compiler won't notice.

L

Leo: So how is it shipped safely?

M

Maya: Version it, like any code. Any change to a prompt, a schema or a model runs the evaluation subset in CI.

L

Leo: What makes it fail?

M

Maya: A metric falling below the recorded baseline. The run has a spend cap, so a test can't cost a fortune.

L

Leo: And after it passes?

M

Maya: Roll it out gradually. And keep the prompt version in every call record.

L

Leo: So a regression next week points straight at the version.

M

Maya: Right. Same pipeline idea: small steps, a check before each one, and a way to see what changed.

L

Leo: What does "gradually" mean for a prompt?

M

Maya: Send the new version to a small share of grading calls first. Compare its records with the old version's, then widen it.

05Leo explains it back

M

Maya: Answer the question from the review, in your own words.

L

Leo: Continuous delivery means every commit on main could ship. Continuous deployment means it ships by itself.

L

Leo: Dev auto-deploys through a short-lived OIDC role, foundation first, then app.

L

Leo: Prod waits for an approval because it holds learners' data.

M

Maya: What about a bad deploy?

L

Leo: Code is easy to roll forward. Data is not, which is why the stateful stack is separate.

M

Maya: Put the rule for a bad deploy in your notes: revert and merge. Never roll back the stateful stack by hand.

Summary in three lines

  1. Delivery keeps every commit releasable; deployment releases it automatically. Both are CD.
  2. Dev deploys on merge with short-lived credentials; prod waits for an approval with an audit trail.
  3. Roll code forward by revert and merge; data can't be rolled back, so the stateful stack stays separate.
