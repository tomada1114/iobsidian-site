01Delivery and deployment

Continuous integration keeps changes validated together. Continuous delivery keeps the main branch deployable, with an explicit release decision. Continuous deployment sends accepted changes out automatically. A manual production approval can coexist with frequent, small releases.

The important question is whether release is a routine, validated action or a special preparation exercise. Deployment frequency alone does not answer who accepts production risk.

02The pipeline

Quickturn's pipeline starts from an accepted main-branch commit, builds artifacts and uses OIDC for temporary deployment access. Foundation deployment precedes the app because it supplies durable resource identifiers.

Deployments are serialized so a new run does not race a CloudFormation update already in progress. Cancelling the runner does not necessarily cancel that update. Trust conditions and workflow permissions are reviewed together, including the protected production environment's OIDC subject.

03Why prod waits

Production approval adds a check and audit trail before touching learner data. The IAM trust and protected environment must express the intended approval boundary rather than merely accept any main-branch job.

CloudFormation can roll back failed updates, but rollback is not guaranteed and does not reverse arbitrary data changes. A revert-and-redeploy can restore code; state migrations require their own recovery plan. Canary releases and feature flags reduce the number of users exposed before the team widens a change.

04Shipping a prompt change

Prompts change behavior without necessarily changing types. Version them, evaluate schema, prompt and model changes against a recorded baseline, and retain the version in each call record.

A limited rollout can compare old and new behavior before expansion. Observe both quality and operational effects, under a spending cap. Release decisions need the same traceability for model behavior as for ordinary application code.

Summary in three lines

  1. Delivery keeps every commit releasable; deployment releases it automatically. Both are CD.
  2. Dev deploys on merge with short-lived credentials; prod waits for an approval with an audit trail.
  3. Roll code forward by revert and merge; data can't be rolled back, so the stateful stack stays separate.
