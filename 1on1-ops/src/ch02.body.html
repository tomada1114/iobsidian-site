役に立つログの1行には何が要るか

保存に失敗したリクエストは、学習者の回答をログに写さなくても見つけられなければなりません。構造化した項目と、ペイロードを入れない方針は、この問題の別々の部分を解決します。

このページの内容

  • 自由記述のログが困る理由
  • 記録する項目
  • ログに入れないもの

01自由記述のログが困る理由

「saving answers for…」のような自由記述のメッセージは、毎回同じ条件で絞り込むのが難しくなります。構造化ログなら操作・結果・所要時間が項目として明示されるので、「回答の保存に失敗し、500ミリ秒を超えたリクエスト」をクエリで取り出せます。

Quickturn は、リクエストごとに完了レコードを1件、決まった項目のセットで書きます。値がない項目も null として残すので、情報が欠けていることがわかり、スキーマが予測できない形で変わることもありません。ただし、正常に完了する前にクラッシュする場合に備えるには、ライフサイクルを記録する別のレコードが必要になることもあります。

02記録する項目

サーバーは、クライアントから渡された識別子を正とせず、自分でリクエスト ID を作ります。操作名は API の契約から取り、結果は成功、安定したエラーコード、一致しないルート、想定外の失敗を区別します。認証済みの内部学習者 ID があれば、メールアドレスをログに残さずに調査できます。

{
  "requestId": "3f9c…",
  "operation": "submitAnswers",
  "outcome": "ok",
  "status": 200,
  "durationMs": 184,
  "learnerId": "l_7a2…",
  "fault": null
}

所要時間は、リクエストのうち計測した経路にかかった時間です。想定外の障害では、何が入っているかわからないメッセージではなく、安全な分類やカテゴリを記録します。項目の多いこの完了レコードが1件あれば、普段の調べものでは何行も突き合わせる必要がありません。処理の順序を細かく追う必要があるときは、トレースを使います。

03ログに入れないもの

リクエスト本文、回答、トークン、Cookie、認証コード、シークレットの値は、通常のログに入れません。加工していないパスや例外メッセージにも、入力が混ざっていることがあります。名前をつけた操作や安全な障害カテゴリなら、ペイロードを写さずに役立つ情報を残せます。

テストではログの出力を取り込み、代表的な機密値が含まれていないかを検索します。調査に別の情報が必要になったら、回答数のように範囲を絞った安全な項目を足します。内部の識別子にも、保持期間とアクセス制御は適用されます。Quickturn はリクエストの履歴を無期限には残さず、保持期間に上限を設けています。

04プロンプトもペイロード

プロンプトやモデルの出力にも、学習者の書いた内容が入りえます。通常の呼び出し記録には、プロンプト全文ではなく、プロンプトのバージョンとトークン数を残します。品質の調査で内容そのものが必要なら、アクセスを制限した別のストアに、保持期間を決めて置きます。

デバッグのためにすべてをログに残すと、守ったり消したりしなければならない二次的なデータが増え続けます。先に問いを決めると、それに答えられるもっと小さな項目が見つかることがよくあります。

3行まとめ

  1. 決まった項目を持つ構造化された完了レコードを書き、完了しなかったリクエストには別のライフサイクルのシグナルを使います。
  2. サーバーが作るリクエスト ID、操作、安定した結果コード、所要時間があれば、ログの行を見つけることも数えることもできます。
  3. 本文、回答、トークン、エラーメッセージ、プロンプトの文面はログに入れず、代わりに特定の安全な項目を足します。
