What makes a log line actually useful?

After this page you can explain why logs should be structured, one line per request, with fixed fields. You can also say which fields to write, and what must never go into a log.

About 8 min readPairing at Leo's desk

In this page

  • Why do free-text logs fail?
  • Which fields does a line need, and why?
  • What stays out of the log?
  • What goes wrong with prompts in logs?

Leo's desk. His terminal is full of debug output from a feature branch.

01Why free text fails

L

Leo: While debugging, I added console.log('saving answers', body). Should I leave it in? More logs is safer, right?

M

Maya: Safer for what?

L

Leo: For the next time something breaks. More detail to look at.

M

Maya: Let's test that. Next week, you want every failed save of answers that took over half a second. How do you find them?

L

Leo: Search for "saving answers"… and then read each one.

M

Maya: And count how many failed, per day?

L

Leo: I can't. The line doesn't say whether it failed, or how long it took.

M

Maya: That's the problem with free text. You can't filter or count strings like "saving answers for…" reliably.

L

Leo: So what's the alternative?

M

Maya: Structured logs. Each line is a JSON object with named fields. "All failed requests for this operation over 500 milliseconds" becomes one filter.

L

Leo: Like a row in a table.

M

Maya: Right. And we write exactly one line per request, at the end, when we know how it went.

L

Leo: Only one? My debugging had ten.

M

Maya: One wide line. Every field is always there, set to null when it doesn't apply. So a query never has to ask whether a key exists.

02The fields

L

Leo: So what's in our one line?

M

Maya: Here's a trimmed example:

{
  "requestId": "3f9c…",
  "operation": "submitAnswers",
  "outcome": "ok",
  "status": 200,
  "durationMs": 184,
  "learnerId": "l_7a2…",
  "fault": null
}
L

Leo: Where does the request id come from? The client could send one.

M

Maya: The server makes it, a fresh UUID. We never take it from a header, so a caller can't spoof one or collide with someone else's.

L

Leo: And when a learner reports a problem, how do we get their request id?

M

Maya: We search by their internal learner id and the time. That narrows it to a few lines, and the request id then names exactly one.

L

Leo: And it finds one request.

M

Maya: Right. The operation is the endpoint, named by the contract's operation name. The outcome says how it ended.

L

Leo: Why not just the status code?

M

Maya: Many different failures share one status. The outcome is "ok", a stable error code, "unmatched" or "failed". A stable code is what makes counting possible.

L

Leo: What's the difference between the last two?

M

Maya: "Unmatched" means no route matched the request. "Failed" means an unexpected error was thrown, and that's when fault is set.

L

Leo: So a chart of outcomes per operation per day is just a query.

M

Maya: Right. No new code, just a new question.

L

Leo: And duration covers what?

M

Maya: The whole request, from arrival to the last byte.

L

Leo: learnerId is the email?

M

Maya: The internal id, set once the request is authenticated. Never the email.

L

Leo: And fault?

M

Maya: Only the thrown error's class name, never its message. There's also a reason field for some outcomes.

L

Leo: No log level? I thought every log had debug, info, warn and error.

M

Maya: Levels help when you write many lines per request, or want to sample the noisy ones. We write one line, and the outcome code does that job.

L

Leo: One line per request, or many small lines. Is one always better?

M

Maya: One is cheaper to query, and nothing needs joining. Many lines show the order of events inside a request.

L

Leo: So we trade order for simplicity.

M

Maya: And for the rare case where order matters, a trace shows it better anyway.

03What stays out

L

Leo: What about my ten lines while debugging locally?

M

Maya: Fine on your machine. They come out before the merge.

L

Leo: So what exactly can't go in?

M

Maya: The request body. A card's text. A learner's answers. The path, tokens, cookies and auth codes.

L

Leo: Why the error message? That seems useful.

M

Maya: A message can carry user input. "Invalid answer: …" followed by what the learner typed. So only the class name is logged.

L

Leo: And the path? It's just a URL.

M

Maya: Paths can hold ids or search text. The operation name tells you the endpoint without them.

L

Leo: Let me draw what's left.

M

Maya: Go ahead. It should look small.

L

Leo: How do we make sure nobody slips a body in?

M

Maya: Tests. The log sink records lines in tests, and cases check that no body, card text, answer, token, cookie, code or secret appears.

L

Leo: But sometimes I'll wish I had the body.

M

Maya: That's the real cost. The answer is a specific, safe field for the question you have. Not the whole payload.

L

Leo: Like a count of answers in the batch, instead of the answers.

M

Maya: Exactly the kind of field. And logs cost money too: CloudWatch bills them by volume beyond its free tier.

L

Leo: How long do we keep them?

M

Maya: One month. Long enough to investigate, short enough that old data doesn't pile up.

L

Leo: And if a learner asks us to delete their data, the logs hold only an internal id?

M

Maya: Right. No names, no answers, no email. That makes deletion far simpler.

04Prompts are payloads too

L

Leo: Does this change for LLM features?

M

Maya: That's where teams leak data most. Prompts and model outputs often contain what the user typed.

L

Leo: So logging "the prompt" is logging personal data.

M

Maya: Right. Log the prompt version and the token counts, not the prompt text.

L

Leo: And our model calls?

M

Maya: Their records add the model id, the prompt version, tokens and cost. Not the learner's answer, and not the model's reply.

L

Leo: What if someone really needs the full text to debug a bad grade?

M

Maya: Then it lives in a separate store, with its own access rules and its own retention. Not in the general logs everyone can search.

L

Leo: Have you seen that go wrong?

M

Maya: At my last company, a support bot logged every prompt for debugging. A year later, the logs held thousands of customers' messages.

L

Leo: Readable by anyone with log access.

M

Maya: And kept far longer than anyone intended. Deleting it took weeks.

L

Leo: Because nobody knew which lines held what.

M

Maya: That was the problem. Free text made even the cleanup a guess.

L

Leo: So my debug line comes out before I merge.

M

Maya: Yes. If the question behind it is real, turn it into a field.

05Leo explains it back

M

Maya: Say the rule the way you'd explain it in a code review.

L

Leo: Log one structured line per request, with a server-made request id, the operation, a stable outcome code and the duration.

L

Leo: Every field is always there, so queries stay simple.

L

Leo: Keep out bodies, answers, tokens and error messages. Log the error's class instead.

M

Maya: And when you need more?

L

Leo: I add a specific, safe field, not the payload.

M

Maya: For model calls, the prompt itself is a payload. Log its version and token counts, and never its text.

Summary in three lines

  1. Write one structured JSON line per request, with fixed fields that are always present.
  2. A server-made request id, the operation, a stable outcome code and the duration make lines findable and countable.
  3. Never log bodies, answers, tokens, error messages or prompt text; add a specific safe field instead.
