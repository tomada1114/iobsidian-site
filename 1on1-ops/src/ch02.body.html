What makes a log line actually useful?

After this page you can explain why logs should be structured, one line per request, with fixed fields. You can also say which fields to write, and what must never go into a log.

About 4 min readQuickturn case study

In this page

  • Why do free-text logs fail?
  • Which fields does a line need, and why?
  • What stays out of the log?
  • What goes wrong with prompts in logs?

01Why free text fails

Free-text messages such as “saving answers for…” are difficult to filter consistently. Structured logs make operation, outcome and duration explicit, allowing a query for failed answer saves over 500 milliseconds.

Quickturn writes one completion record per request with a stable field set. A nullable field distinguishes missing information from a schema that changes unpredictably. Additional lifecycle records may still be needed for crashes that prevent normal completion.

02The fields

The server creates its own request ID rather than treating a client-provided identifier as authoritative. Operation names come from the contract; outcomes distinguish success, stable error codes, unmatched routes and unexpected failures. An authenticated internal learner ID aids investigation without logging the email.

{
  "requestId": "3f9c…",
  "operation": "submitAnswers",
  "outcome": "ok",
  "status": 200,
  "durationMs": 184,
  "learnerId": "l_7a2…",
  "fault": null
}

Duration covers the request's measured path. An unexpected fault records its safe class or category instead of its arbitrary message. This wide completion record avoids joining many lines for ordinary questions. Traces provide deeper ordering when it matters.

03What stays out

Request bodies, answers, tokens, cookies, authentication codes and secret values stay out of general logs. Raw paths and exception messages may also contain input. A named operation or safe fault category gives useful information without copying the payload.

Tests capture the log sink and search for representative sensitive values. When investigation needs another detail, add a narrowly defined safe field, such as answer count. Retention and access controls still apply to internal identifiers. Quickturn uses a bounded retention period rather than keeping request history indefinitely.

04Prompts are payloads too

Prompts and model outputs can contain learner content too. General call records use prompt versions and token counts, not full prompt text. A quality investigation that needs content belongs in a separate, restricted store with a stated retention period.

Logging everything for debugging creates a growing secondary dataset that must be secured and deleted. Defining the question first often reveals a smaller field that answers it.

Summary in three lines

  1. Write one structured JSON line per request, with fixed fields that are always present.
  2. A server-made request id, the operation, a stable outcome code and the duration make lines findable and countable.
  3. Never log bodies, answers, tokens, error messages or prompt text; add a specific safe field instead.
