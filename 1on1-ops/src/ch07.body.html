How do we know the fake database behaves like the real one?

After this page you can explain what a contract suite is, and why it makes a fake worth trusting. You can also say how the same idea proves one learner can't see another's data.

01When a fake lies

An in-memory store can accept a commit that DynamoDB rejects, making fast tests falsely reassuring about that case. The fake remains valuable, but its behavior needs a stated contract rather than a separate interpretation of database documentation.

Quickturn exposes storage through a port. Shared tests describe what each implementation must accept, reject and return.

02The contract suite

A contract-suite function receives a store factory and runs the same cases for each adapter. It checks version creation, stale updates, transaction atomicity and duplicate answer behavior.

The fake also enforces the application's commit limits. DynamoDB's action and size limits and restrictions on repeated item targets are separate conditions that must be represented where relevant.

Accepts a 101-item commit?
Without a contract: maybe. With one: refused, like DynamoDB.
Accepts a stale update?
Without a contract: maybe. With one: refused.
Lets B read A's data?
Without a contract: nobody checked. With one: proven empty.

The in-memory suite runs quickly; the DynamoDB suite runs against a pinned local service in CI. A future adapter invokes the same test function rather than copy-pasting a weaker suite. New failure cases improve both implementations.

03Isolation as a contract

Isolation cases write as learner A, try each read as B, then let B use the same record IDs without changing A's data. Compile-time coverage of the method list helps ensure that a new method cannot silently escape the suite.

This makes ownership a tested store property as well as a review concern. It remains evidence for the covered methods and cases, not a mathematical proof that no production configuration or future code can leak data.

04What it still doesn't prove

DynamoDB Local does not reproduce every cloud behavior, such as IAM or point-in-time recovery. Those need other tests or deployment checks. If the required container is unavailable, the integration suite fails with a useful prerequisite message instead of skipping and appearing green.

A shared contract is particularly valuable when several implementations claim the same semantics. Consumer-driven API contracts use a related idea: consumers state expectations and providers verify them. The precise test boundary and remaining gaps must be explicit.

Summary in three lines

  1. A contract suite writes a port's promises once and runs them against every implementation.
  2. A fake that passes the same cases as the real adapter makes every fast test meaningful.
  3. Isolation is a contract case, and DynamoDB local is still not the real service.
