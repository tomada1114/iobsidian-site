How do we know the fake database behaves like the real one?

After this page you can explain what a contract suite is, and why it makes a fake worth trusting. You can also say how the same idea proves one learner can't see another's data.

About 8 min readThe whiteboard room

In this page

  • When does a fake lie?
  • What is a contract suite?
  • How does it prove isolation?
  • What does it still not prove?

The whiteboard room. Leo's feature passed every test on the in-memory store, then failed on DynamoDB local.

01When a fake lies

L

Leo: My change passed every test. Then I ran it against DynamoDB local, and the real store refused a commit the fake had accepted.

M

Maya: What was in the commit?

L

Leo: A big batch of review updates. Over a hundred items in one transaction.

M

Maya: And DynamoDB has a per-transaction item limit.

L

Leo: So why keep a fake at all, if it lies? Shouldn't we just test against the real database?

M

Maya: How many tests use the in-memory store today?

L

Leo: Hundreds. The whole API suite runs on it.

M

Maya: And how long do they take?

L

Leo: Seconds. Against a container, it would be minutes, and every run would need Docker.

M

Maya: So the fake is worth keeping. The question is how to stop it lying.

L

Leo: Write more careful fakes?

M

Maya: Careful isn't a guarantee. Two people write two stores, and each reads the same docs differently.

L

Leo: So what's the shape we're working with?

M

Maya: Our application code talks to the learner store through a port. That's an interface: a list of what the store promises to do.

L

Leo: And two implementations sit behind it.

M

Maya: DynamoDB and in-memory. If the in-memory one accepts something DynamoDB refuses, every test built on it proves nothing.

L

Leo: Which is what just happened to me.

02The contract suite

L

Leo: So how do we keep them the same?

M

Maya: We write down, once, as tests, everything the port promises. Then we run the same tests against every implementation.

L

Leo: The same file, twice?

M

Maya: The suite is a function. It takes a name and a way to make stores, and it holds every case.

L

Leo: What kind of cases?

M

Maya: An entry is created at version 1, and each update moves it on. An update at a stale version is refused.

L

Leo: So two tabs can't overwrite each other.

M

Maya: Right. A commit is all or nothing when one condition fails. And a resent answer is rejected by its id, and changes nothing.

L

Leo: And my case?

M

Maya: A commit over the item limit is refused. By the fake too.

L

Leo: Wait, the fake already refuses it?

M

Maya: It does now. Our code holds the limit as a constant, 100, and the in-memory store checks it.

L

Leo: Then why did mine pass?

M

Maya: Your branch was cut before that case was written down. Rebase, and your test fails on the fake, in seconds.

L

Leo: Which is where I wanted to find it.

M

Maya: The function is called once for the in-memory store, in the everyday test run. And once for the DynamoDB store, against DynamoDB local, in its own suite.

L

Leo: Where does that suite run?

M

Maya: In CI, with DynamoDB local as a service container. The learner directory has its own contract, built the same way.

L

Leo: And if someone adds a third store? Say, a cache.

M

Maya: They add one call to the contract function. Never a copy of the tests.

L

Leo: Because a copy would drift, like my fake did.

M

Maya: Right. One list of promises, checked everywhere. Here's the difference it makes.

Accepts a 101-item commit?
Without a contract: maybe. With one: refused, like DynamoDB.
Accepts a stale update?
Without a contract: maybe. With one: refused.
Lets B read A's data?
Without a contract: nobody checked. With one: proven empty.
L

Leo: "Maybe" is the worrying word in that list.

M

Maya: It's what you had this morning. The fake wasn't wrong on purpose. On your branch, nobody had written the case down yet.

03Isolation as a contract

L

Leo: Is the contract only about versions and commits?

M

Maya: The first block is about isolation. It writes learner A's data, then tries every read the port offers.

L

Leo: As A, it finds the data.

M

Maya: And as B, it finds nothing. Then B writes the same keys, and A's data stays unchanged.

L

Leo: And B can't update A's entry?

M

Maya: That's the last check. Let me draw what it proves.

L

Leo: "Every read" sounds hard to keep true. What if someone adds a new read method next month?

M

Maya: The list of reads in the test is keyed by the port's own method names.

L

Leo: So a new method without an isolation case…

M

Maya: Fails to compile. The type checker makes you cover it.

L

Leo: So "one learner can never see another's data" isn't a review comment.

M

Maya: It's a tested property of every store. A reviewer can miss a line. The compiler doesn't get tired.

04What it still doesn't prove

L

Leo: So DynamoDB is fully covered now?

M

Maya: Not fully. The contract runs against DynamoDB local, not the real service.

L

Leo: Does local behave differently?

M

Maya: The suite doesn't prove local matches the service in every condition case. The team wrote that limit down.

L

Leo: What else is missing from local?

M

Maya: Point-in-time recovery, for one. Restores are tested elsewhere.

L

Leo: And the DynamoDB suite isn't in my everyday run?

M

Maya: No. It needs a container, so it stays out of the everyday gate. CI runs it.

L

Leo: What if I run it and Docker isn't up?

M

Maya: It fails, with an instruction to start the container. It never skips.

L

Leo: And in CI, the container is always there?

M

Maya: It's declared in the job, with a pinned image version. If it doesn't start, the job fails before any test runs.

L

Leo: Why not skip? That seems friendlier.

M

Maya: A skipped suite looks green. You'd think it passed.

L

Leo: What does writing all this cost?

M

Maya: Time up front. And it only pays when there are two or more implementations.

L

Leo: So for a store with only a real version, you'd skip the contract.

M

Maya: Right. You'd just test the real one.

L

Leo: Does the pattern work outside databases?

M

Maya: It keeps a payment-provider fake or a model-client fake honest in the same way.

L

Leo: And between two teams' services?

M

Maya: That's consumer-driven contract testing, with tools like Pact. The consumer writes what it expects, and the provider runs it.

L

Leo: Same idea, across a team boundary.

M

Maya: Yes. One list of promises, run against whoever claims to keep them.

05Leo explains it back

M

Maya: You asked why we keep a fake that lies. Answer it now.

L

Leo: We write what the store promises once, as a contract suite. We run it against the in-memory fake and DynamoDB local.

L

Leo: If the fake passes the same tests as the real adapter, every fast test that uses the fake means something.

L

Leo: Isolation is part of the contract, so no store can leak one learner's data to another.

M

Maya: What's left?

L

Leo: DynamoDB local isn't the real service.

M

Maya: When you find a new difference, add it as a case. The contract grows, and the fake keeps up.

Summary in three lines

  1. A contract suite writes a port's promises once and runs them against every implementation.
  2. A fake that passes the same cases as the real adapter makes every fast test meaningful.
  3. Isolation is a contract case, and DynamoDB local is still not the real service.
