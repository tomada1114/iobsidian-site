01フェイクが本物と食い違うとき

インメモリのストアは、DynamoDB なら拒否するコミットを受け入れることがあります。そうなると、速いテストがそのケースについて誤った安心を与えます。フェイクの価値がなくなるわけではありませんが、データベースのドキュメントを実装ごとに解釈するのではなく、振る舞いを契約として明文化しておく必要があります。

Quickturn は、ストレージをポートの向こう側に置いています。各実装が何を受け入れ、何を拒否し、何を返すべきかは、共通のテストが記述します。

02契約スイート

契約スイートの関数はストアのファクトリーを受け取り、アダプターごとに同じケースを実行します。確かめるのは、バージョンの作成、古い更新、トランザクションの原子性、重複した回答の扱いです。

フェイクは、アプリケーションが決めたコミットの上限も守らせます。DynamoDB のアクション数やサイズの上限、同じ項目を一度に複数回対象にできない制限は別の条件で、関係する箇所ではそれも表現しておく必要があります。

101件のコミットを受け入れるか
契約なし：受け入れるかもしれない。契約あり：DynamoDB と同じく拒否する。
古い更新を受け入れるか
契約なし：受け入れるかもしれない。契約あり：拒否する。
B が A のデータを読めるか
契約なし：誰も確かめていない。契約あり：対象の読み取りで何も返らないことをテストしている。

インメモリのスイートはすぐに終わり、DynamoDB のスイートは CI で、バージョンを固定したローカルのサービスに対して走ります。将来のアダプターは、弱いスイートをコピーして作るのではなく、同じテスト関数を呼び出します。新しい失敗ケースを足せば、両方の実装がよくなります。

03分離も契約の一部

分離のケースでは、学習者 A としてデータを書き込み、B として各読み取りを試します。続いて B が同じレコード ID を使っても、A のデータが変わらないことを確かめます。メソッドの一覧をコンパイル時に網羅しておけば、新しいメソッドが気づかれないままスイートから漏れることを防げます。

これで、誰のデータかという区別は、レビューで気をつける点であるだけでなく、テストで確かめたストアの性質にもなります。ただし結果が証拠になるのは、対象のメソッドとケースについてだけです。本番の設定や今後のコードについては、データ漏えいの可能性を別に確かめる必要があります。

04それでも証明できないこと

DynamoDB Local は、IAM やポイントインタイムリカバリーのような、クラウドの振る舞いをすべて再現するわけではありません。そうした部分には、別のテストやデプロイ時のチェックが必要です。必要なコンテナが使えないとき、結合テストのスイートはスキップして緑に見せるのではなく、前提条件をわかりやすく伝えるメッセージとともに失敗します。

共通の契約が特に役立つのは、複数の実装が同じ意味を持つと主張するときです。コンシューマー駆動の API 契約も近い考え方で、利用する側が期待を述べ、提供する側がそれを検証します。どちらの場合も、テストの境界がどこにあり、何がまだ確かめられていないのかを明示しておく必要があります。

3行まとめ

  1. 契約スイートは、ポートの約束を一度だけ書き、すべての実装に対して実行します。
  2. 共通の契約ケースがあれば、対象となる振る舞いについてフェイクを信頼できます。それでも、アプリケーションの各テストには意味のあるアサーションが必要です。
  3. 分離も契約のケースの一つです。DynamoDB local は、本物のサービスではありません。
