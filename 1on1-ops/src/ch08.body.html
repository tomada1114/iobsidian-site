コードではないものをどうテストするか

ハンドラーのテストは通るのに、コミットされた API ドキュメントは古いままです。生成ファイル、テンプレート、依存関係のルールには、それぞれを狙ったチェックが必要です。

01生成ファイルのずれ

スキーマを変えても、コミット済みの OpenAPI ドキュメントやクライアントの型が古いまま残ることがあります。ハンドラーのテストはこうした生成物を一度も見ないので、それでも通ってしまいます。ずれのチェックでは生成物を作り直して比較し、CI ではファイルを書き換えません。

変更する人はローカルで生成し直し、コミットする前に外部向けの契約の差分を確認します。同じ比較の方法は、意図して同期させている別のファイルにも使えます。このチェックの失敗が示すのは、ハンドラーの故障ではなく、生成の手順を忘れたことです。

02テストできるコードとしてのインフラ

インフラのコードからはテンプレートを合成できるので、そこに絞ったアサーションを書けます。対象は、キースキーマ、課金モード、保持の設定、本番の保護、ロールの信頼関係、許可するリソースの種類などです。オフラインでチェックするには、そのテストの経路で実環境への問い合わせを避ける必要があります。

許可リストを置くと、想定外のリソースの種類が、レビューで判断すべき選択として表に出ます。守りたい振る舞いは、巨大なテンプレートのスナップショットより、性質を絞ったアサーションのほうがはっきり見えます。アサートしていない性質は、引き続きレビューで確かめます。

03型と境界

型のテストでは、アプリケーションがコンパイルできるかだけでなく、意図どおりに推論され、代入できるかを確かめます。@ts-expect-error を使った否定のケースは、不正な呼び出しが知らないうちに許されるようになったときに失敗します。リテラルの一覧と、そこから導いたユニオン型は、食い違わないように保つ必要があります。

import のグラフを調べる別のテストが、lint とは独立に依存の向きを確かめます。チェックが独立していれば、ルールの一つがうっかり消されても、重要な境界は守られます。ただし、期待するグラフは理解できる形に保ち、レビューし続ける必要があります。

04スモークテスト

スモークテストは、ビルドしたアプリと API をローカルのデータベースとともに動かし、HTTP 越しに振る舞いをアサートします。配信された HTML とスタイルが空でないこと、代表的な保存と読み取りの経路、拒否のケースを確かめます。ブラウザーでの操作までカバーしているとは、あえて主張しません。

ビルドが最新であることと、コンテナの前提条件は明示しています。それでも、実環境の設定と、コンテンツに到達できることは、デプロイ後のチェックで確かめます。ポリシーをコードとして書いたアサーションを使えば、同じ方法を組織全体のインフラの要件にも広げられます。

3行まとめ

  1. 生成ファイルにはずれのテストを用意します。生成し直して比べ、CI で失敗させ、コマンド一つで書き換えます。
  2. インフラ、型、import のルールには、それぞれ大事な性質だけを確かめる狭いチェックを置きます。
  3. ビルドしたものへのスモークテストは HTTP 越しにプロセスを動かします。実環境の設定とコンテンツへの到達は、デプロイ後のチェックで確かめます。
