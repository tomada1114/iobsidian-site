How do you test things that aren't plain code?

After this page you can explain how generated files, infrastructure templates, types and import rules each get their own cheap check. You can also say what only a smoke test sees, and what no automated check sees.

01Drift in generated files

A schema can change while its committed OpenAPI document and client types remain stale. Handler tests can still pass because they never examine those generated artifacts. A drift check regenerates them and compares the result without rewriting files in CI.

The author regenerates locally and reviews the external contract diff before committing. The same comparison approach can protect other intentionally synchronized files. The failing check identifies a forgotten generation step rather than a broken handler.

02Infrastructure as testable code

Infrastructure code can synthesize a template for focused assertions: key schema, billing mode, retention, production protection, role trust and permitted resource types. Offline checks require avoiding live lookups in that test path.

An allowlist makes an unexpected resource type a reviewable choice. Property assertions expose the specific protected behavior more clearly than an enormous template snapshot, while still requiring review of properties that have not been asserted.

03Types and boundaries

Type tests check the intended inference and assignability, not just whether the application compiles. Negative cases using @ts-expect-error fail if an invalid call unexpectedly becomes legal. Literal lists and derived unions need to stay consistent.

A separate import-graph test checks dependency direction alongside lint. Independent checks protect an important boundary even if one rule is accidentally removed. Their expected graph must remain understandable and reviewed.

04The smoke test

The smoke test runs the built app and API with a local database and asserts behavior over HTTP. It verifies served HTML and nonempty styling, plus a representative save/read path and refusal. It intentionally does not claim browser interaction coverage.

Its build freshness and container prerequisites are explicit. Post-deploy checks still confirm live configuration and reachable content. Policy-as-code assertions can extend the same method to organization-wide infrastructure requirements.

Summary in three lines

  1. Generated files get drift tests: regenerate, compare, fail in CI, rewrite by one command.
  2. Infrastructure, types and import rules each get a narrow check of the properties that matter.
  3. Only the smoke test crosses process seams; the deployed URL is still read back by hand.
