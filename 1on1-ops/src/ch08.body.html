How do you test things that aren't plain code?

After this page you can explain how generated files, infrastructure templates, types and import rules each get their own cheap check. You can also say what only a smoke test sees, and what no automated check sees.

Leo's desk. He edited an API schema, and CI failed on a test he had never heard of.

01Drift in generated files

L

Leo: I added a field to a zod schema, and every handler test passed. Then CI failed on a test about openapi.json.

M

Maya: And you want to know why it's there.

L

Leo: Yes. Why does a JSON file have a test?

M

Maya: Where does that file come from?

L

Leo: It's generated from the zod schemas, I think. Then it's committed.

M

Maya: And who reads it?

L

Leo: The web client. Its types are generated from that document.

M

Maya: So what happens if the schema changes and the document doesn't?

L

Leo: The server accepts the new field, and the client doesn't know it exists.

M

Maya: Right. Every unit test passes, and the two sides quietly disagree.

L

Leo: So the test catches that.

M

Maya: It regenerates the document in memory and compares it with the committed file. In CI, a difference fails instead of rewriting.

L

Leo: Why not just rewrite it in CI? It knows the right answer.

M

Maya: Then the change you review isn't the change that ships. One command rewrites it on your machine, and you commit the result.

L

Leo: So I run that command, and commit the schema and the document together.

M

Maya: That's the fix. Here's the whole loop.

L

Leo: Are there other files like this?

M

Maya: The web client's generated types have the same kind of test. So does a folder we keep as an exact copy in two places.

L

Leo: Same idea each time: regenerate, compare, fail.

M

Maya: Right. It's cheap, and it turns "someone forgot to regenerate" into a red build.

02Infrastructure as testable code

L

Leo: What about the CDK stacks? You can't unit test AWS.

M

Maya: You don't need AWS. A CDK app synthesizes a CloudFormation template locally, with no credentials.

L

Leo: So the test reads the template.

M

Maya: And asserts the properties that matter, per stage. The table is on demand, keyed by a partition key and a sort key, and kept on delete and on replacement.

L

Leo: Kept even in dev?

M

Maya: Kept in both. Point-in-time recovery and deletion protection are off in dev, and on in prod.

L

Leo: What else is asserted?

M

Maya: The deploy role trusts only the main branch, and can only assume the CDK bootstrap roles. The app stack holds only an allowed list of resource types. And there are five alarms.

L

Leo: Why an allowed list of resource types?

M

Maya: So a new kind of resource can't slip in unreviewed. Adding one means changing the list, and that shows in the diff.

L

Leo: Why not a snapshot test? Save the whole template, and fail on any change.

M

Maya: A snapshot diff of a whole template is hundreds of lines. People approve it without reading.

L

Leo: So it fails on everything, and checks nothing.

M

Maya: That's the risk. A property assertion fails only when a property you care about changes, and the reviewer reads one line.

L

Leo: Like "deletion protection is on in prod."

M

Maya: Right. The test name says what's protected.

L

Leo: And if someone changes a stack for a good reason, say to add a queue?

M

Maya: The resource-type test fails first. They add the type to the list, and the reviewer sees that one line and asks why.

03Types and boundaries

L

Leo: And types? The compiler already checks them.

M

Maya: It checks your code uses them correctly. It doesn't check that a type says what you meant.

L

Leo: What would that look like?

M

Maya: Say a generic Result type. Inference might widen it to something loose, and every caller still compiles.

L

Leo: So the type got weaker, but nothing failed.

M

Maya: Type tests prove inference keeps what it should. With expectTypeOf, you check that a Result doesn't widen.

L

Leo: And the literal lists?

M

Maya: The same tool checks that a literal list stays in step with its union. Add a member to one, and the test fails until the other has it.

L

Leo: And a call that should fail?

M

Maya: A @ts-expect-error line proves a bad call fails to compile. If it ever compiles, the test breaks.

L

Leo: What about import rules? We have an ESLint rule for layers.

M

Maya: We also have a boundary test. It walks the module graph and asserts the allowed edges.

L

Leo: Such as?

M

Maya: The domain imports nothing. The infrastructure code imports nothing of the application.

L

Leo: Isn't that a duplicate of the lint rule?

M

Maya: On purpose. If someone deletes the lint rule, the boundary still holds.

L

Leo: Two independent checks for one rule.

M

Maya: For a rule that matters this much, yes. The layers are what keep the domain pure.

04The smoke test

L

Leo: So all of these are narrow checks.

M

Maya: Narrow and cheap. But none of them sees the seams between processes.

L

Leo: Like the web bundle actually talking to the API.

M

Maya: That's what the one smoke test is for. It serves the built web bundle in front of the API, on DynamoDB local.

L

Leo: With a browser?

M

Maya: No browser. It asserts over HTTP. The document is served, and a stylesheet with a real utility class is linked.

L

Leo: Why check a utility class?

M

Maya: Because a build can produce an empty stylesheet and still succeed. The page would load with no styling at all.

L

Leo: What else?

M

Maya: A round trip saves, starts, records and reads back. One contract refusal, and a bare 404.

L

Leo: What if I forgot to build first?

M

Maya: It refuses to run on a missing or stale build. It never builds for itself.

L

Leo: Why not? It would be easier.

M

Maya: Then it would test a build nobody ships. It should test the one you made.

L

Leo: And the cost?

M

Maya: It needs a build and a container, so it lives in the full gate, not the everyday one.

L

Leo: So after a deploy, is the live URL tested?

M

Maya: No automated check hits it. After each deploy, the live resources and the URL are read back by hand.

L

Leo: That's a gap.

M

Maya: A known one, written down. You should know it's there.

L

Leo: Does this scale to a big company?

M

Maya: Policy-as-code checks do. A rule like "no public bucket" runs against every template before deploy. Same idea, at company scale.

05Leo explains it back

M

Maya: So, why does a JSON file have a test?

L

Leo: Anything we generate, configure or type can drift, so each gets a cheap check against the truth.

L

Leo: Regenerate and diff for generated files. Synthesize and assert for infrastructure. expectTypeOf for types, and a graph walk for import rules.

L

Leo: Only the smoke test sees processes talking over HTTP.

M

Maya: You've stopped at the merge.

L

Leo: After a deploy, the deployed URL is read back by hand.

M

Maya: One habit for your next schema change: run the rewrite command before you push. CI will only tell you what you forgot.

Summary in three lines

  1. Generated files get drift tests: regenerate, compare, fail in CI, rewrite by one command.
  2. Infrastructure, types and import rules each get a narrow check of the properties that matter.
  3. Only the smoke test crosses process seams; the deployed URL is still read back by hand.
