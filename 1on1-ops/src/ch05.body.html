モデル呼び出しのコストをどう見るか

プロンプトを変えたあと、モデルの請求額が上がりました。呼び出しの記録からはバージョンと使用量の関係がわかり、月ごとの請求書は支出を別の角度から確かめる材料になります。

01請求書からはわからないこと

月ごとのモデルの請求書を見ても、どのプロンプト変更で採点が高くついたのかはわかりません。一つの API リクエストにモデル呼び出しが一度もないこともあれば、何度も含まれることもあります。出発点として役に立つのは、呼び出し単位の記録です。

モデル、機能、プロンプトのバージョン、入力と出力の使用量、キャッシュの使用量、レイテンシ、推定コストを記録します。下の値は説明のための例です。バージョンの項目があれば、調べる人は新旧の振る舞いを一つの合計に混ぜずに、分けて見られます。

{
  "modelId": "…haiku…",
  "promptVersion": "grade-v3",
  "feature": "grading",
  "inputTokens": 812,
  "outputTokens": 96,
  "cacheReadTokens": 640,
  "cacheWriteTokens": 0,
  "latencyMs": 1240,
  "estimatedCostUsd": 0.0013
}

02各項目の出どころ

トークンの使用量はプロバイダーが報告する値をアダプターが集め、呼び出しの所要時間もアダプターが計ります。任意で有効にできる生の呼び出しログは別のシグナルで、機密性のある内容を残すことがあります。タグをつけた推論プロファイルを使うと、請求レポートでも別の切り口で見られます。

標準的なテレメトリの規約に合わせると、ツールどうしを組み合わせやすくなります。ただし、生成 AI 向けの名前はまだ変わり続けているので、バージョンを固定して採用します。エージェントのセッショントレースは、呼び出しとツールをつなぎます。それでも、機能やプロンプトのバージョンをアプリケーションしか知らない以上、アプリケーション側の記録は欠かせません。

03記録からコストを出す

トークン数は観測された量で、コストは日付つきの価格表から計算した値です。推定を検証できるように、トークン数と価格表のバージョンを残しておきます。キャッシュの読み込みと書き込みには、同じ入力を二重に数えないための専用のルールが必要です。

どの機能か
請求書：タグがあればわかる。呼び出し記録：常にわかる。
どのプロンプトのバージョンか
請求書：わからない。呼び出し記録：常にわかる。
変更の前後を比べられるか
請求書：比べられない。呼び出し記録：バージョンと時刻で比べ、そのうえで原因を調べられる。
学習者ごとに見られるか
請求書：見られない。使用量の台帳：見られる。

生のプロンプトについては、アクセス権と保持期間を別に決める必要があります。タスクごとのポートと共通のアダプターを通せば、呼び出す側が項目を覚えていなくてもテレメトリが残ります。使用量の予約やアカウントの予算管理は支出そのものを抑え、テレメトリは実際に何が起きたかを見せます。

04多くの呼び出しと一つのタスク

エージェントの1タスクに、一つずつは安く見える呼び出しが10回含まれ、合計すると無視できないコストになることがあります。タスク、セッション、トレースのいずれかの識別子を共有し、完了したタスクと失敗したタスクごとに使用量を集計します。

タスクの実時間のレイテンシは、呼び出しの所要時間の合計になるとは限りません。呼び出しが並行して走ったり、待ち時間が入ったりするからです。タスク全体を直接計り、その内訳はスパンで説明します。呼び出し単位の詳細は診断に、タスク単位の合計はプロダクトと支出の判断に使います。

3行まとめ

  1. モデルの呼び出しはすべて、モデル、プロンプトのバージョン、機能、トークン数、レイテンシ、コストとともに記録します。
  2. アプリケーションの記録にはプロンプトのバージョンを明示的に入れます。請求レポートとプロバイダーのログは、それを補う別の問いに答えます。
  3. プロンプトには個人データが含まれることがあります。共通のタスク ID があれば、エージェントの呼び出しをつないで調べられます。
