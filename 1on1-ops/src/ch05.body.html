How do we see what a model call costs?

A model bill rises after a prompt change. Call records can connect versions and usage, while the monthly bill confirms a different view of spending.

01What the bill can't say

A monthly model bill cannot explain which prompt change made grading expensive. One API request may contain no model call or many calls, so call-level records are the useful starting unit.

Record model, feature, prompt version, input and output usage, cache usage, latency and estimated cost. The sample values are illustrative. Version fields let an investigator separate the old and new behavior instead of mixing them into one total.

{
  "modelId": "…haiku…",
  "promptVersion": "grade-v3",
  "feature": "grading",
  "inputTokens": 812,
  "outputTokens": 96,
  "cacheReadTokens": 640,
  "cacheWriteTokens": 0,
  "latencyMs": 1240,
  "estimatedCostUsd": 0.0013
}

02Where each piece comes from

The adapter collects provider-reported token usage and measures the call duration. Optional raw invocation logging is a different signal that may retain sensitive content. Tagged inference profiles provide another view in billing reports.

Standard telemetry conventions can make tooling interoperable, but evolving GenAI names should be adopted under a pinned version. Agent session traces connect calls and tools. Application records remain necessary where only the application knows the feature and prompt version.

03What the records cost

Token counts are observed quantities; cost is computed from a dated price table. Retain the counts and pricing version so estimates can be checked. Cache reads and writes need their own rules to avoid counting the same input twice.

Which feature?
The bill: only with tags. The call record: always.
Which prompt version?
The bill: never. The call record: always.
Compare changes?
The bill: no. The call record: compare versions and times, then investigate the cause.
Per learner?
The bill: no. The usage ledger: yes.

Raw prompts require separate access and retention decisions. Task ports and a shared adapter make the telemetry less dependent on callers remembering fields. Usage reservations and account budget controls act on spending; telemetry exposes what actually happened.

04Many calls, one task

An agent task can contain ten inexpensive-looking calls whose combined cost is significant. Share a task, session or trace identifier and aggregate usage per completed and failed task.

Wall-clock task latency is not always the sum of call durations because calls can run in parallel or include waiting. Measure the whole task directly and use spans to explain its parts. Per-call detail supports diagnosis; task totals support product and spending decisions.

Summary in three lines

  1. Record every model call with its model, prompt version, feature, tokens, latency and cost.
  2. Include prompt versions explicitly in application records; billing reports and provider logs answer complementary questions.
  3. Prompts may contain personal data; shared task IDs connect agent calls for investigation.
