What should wake someone up at night?

An alarm resource exists, but nobody knows whether its message reaches the responder. A controlled exercise must check that complete path before an incident.

01Symptoms, not causes

Page people for actionable user impact. High CPU or one throttle is a possible cause; failed saves or sustained latency are symptoms learners feel. Cause metrics aid diagnosis, but paging on every spike creates noise.

Latency, traffic, errors and saturation describe service health. RED emphasizes rate, errors and duration for request services; USE emphasizes utilization, saturation and errors for resources. Use those questions to choose signals, not to create alarms mechanically.

02An alarm you never saw fire

An alarm path needs a controlled exercise. Quickturn throttles development requests, confirms the expected API failures, observes alarm state and checks that the notification reaches its destination. It then restores capacity.

A missing notification subscription can leave an active alarm unheard. Deployment checks expose that missing destination, and a repeated exercise after relevant changes confirms the complete path. An observed test is stronger evidence than the presence of an alarm resource.

03Sensitivity and fatigue

Development's sparse test traffic can make a single error worth inspecting. Production needs windows, minimum traffic and rates that distinguish noise from meaningful impact. Sustained error-budget burn is more useful than a page for every isolated failure.

Every paging rule has an owner, first action and runbook. Signals without an actionable response belong on a dashboard until that gap is fixed. Thresholds and missing-data treatment must match the actual workload.

04One dashboard

Quickturn's dashboard combines request rate, 4xx and 5xx outcomes, latency percentiles, function duration and errors, and database throttling. A percentile reveals the tail better than an average, but does not identify the specific affected request.

Keep the monitored set intentional and review additions. AI tasks need completion and end-to-end timeout signals, because fast successful HTTP responses can still hide a task that never finished. Start from the user's complaint and work backward to a metric.

Summary in three lines

  1. Alarm on symptoms users feel, using RED for services and USE for resources.
  2. Exercise each alarm in a controlled environment, confirm notification delivery and restore the changed settings.
  3. Single-event alarms suit dev; at scale use rates, and page only when there's a clear first action.
