夜中に人を起こすべきアラームはどれか

アラームのリソースはあるのに、その通知が対応する人に届くのかは誰も知りません。障害が起きる前に、管理された演習でその経路全体を確かめておく必要があります。

01原因ではなく症状で呼び出す

人を呼び出すのは、対処できる利用者への影響があるときです。CPU 使用率の高さや一度のスロットリングは、原因の候補にすぎません。保存の失敗や続く遅延は、学習者が実際に感じる症状です。原因側のメトリクスは診断に役立ちますが、急上昇のたびに呼び出していてはノイズになります。

レイテンシ、トラフィック、エラー、飽和度は、サービスの健全性を表します。RED は、リクエストを処理するサービスについて、レート（Rate）・エラー（Errors）・所要時間（Duration）を重視します。USE は、リソースについて、使用率（Utilization）・飽和度（Saturation）・エラー（Errors）を重視します。これらはシグナルを選ぶための問いとして使うもので、機械的にアラームを作るためのものではありません。

02鳴ったところを見たことがないアラーム

アラームの経路は、管理された演習で確かめる必要があります。Quickturn は開発環境のリクエストをスロットリングし、想定どおり API が失敗することを確かめ、アラームの状態を観察し、通知が宛先まで届くことを確認します。最後に、キャパシティを元に戻します。

通知のサブスクリプションが欠けていると、アラームが発火しても誰にも届きません。デプロイ時のチェックで宛先の欠落を見つけ、関係する変更のあとに演習を繰り返して経路全体を確かめます。アラームのリソースがあることより、テストで実際に観察したことのほうが強い証拠になります。

03感度とアラート疲れ

開発環境はテストのトラフィックがまばらなので、エラーが1件出ただけでも調べる価値があります。本番では、評価の時間枠、最低限のトラフィック量、比率を使って、ノイズと意味のある影響を見分ける必要があります。単発の失敗のたびに呼び出すより、エラーバジェットが続けて減っていることを捉えるほうが役に立ちます。

呼び出しのルールには必ず、担当者、最初の対応、ランブックを用意します。具体的な対応が決まっていないシグナルは、その穴が埋まるまでダッシュボードに置きます。しきい値やデータ欠損時の扱いは、実際のワークロードに合わせる必要があります。

04ダッシュボードは一つ

Quickturn のダッシュボードには、リクエストレート、4xx と 5xx の件数、レイテンシのパーセンタイル、関数の所要時間とエラー、データベースのスロットリングをまとめています。パーセンタイルは平均よりもテール（遅い側の裾）をよく映しますが、影響を受けた個々のリクエストまでは特定できません。

監視する項目は意図して選び、追加するときは見直します。AI のタスクには、完了したかどうかと、最初から最後までのタイムアウトのシグナルが必要です。HTTP の応答が速く成功していても、その裏でタスクが終わっていないことがあるからです。利用者の苦情から出発し、逆算してメトリクスにたどり着きます。

3行まとめ

  1. アラームは利用者が感じる症状に対して出し、サービスには RED、リソースには USE の観点を使います。
  2. アラームは一つずつ管理された環境で鳴らし、通知が届くことを確かめ、変えた設定を元に戻します。
  3. 1件で鳴るアラームは開発環境向けです。規模が大きくなったら比率を使い、最初の対応がはっきりしているときだけ人を呼び出します。
