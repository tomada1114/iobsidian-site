Is a testing strategy just 'write more unit tests'?

After this page you can explain what each kind of test buys, and at what price. You can also say why fakes usually beat mocks, and how to test a feature whose output isn't fixed.

01What each test buys

Line coverage reports execution, not whether an assertion would detect a broken save. Different tests protect different properties: unit tests check rules, adapter contracts check integration promises, component tests check screen behavior, and smoke tests check a built path.

Quickturn's pure domain makes unit tests cheap and repeatable. Tests at the seams add confidence that those rules are wired to the actual storage and HTTP behavior.

02Pyramid or trophy

A test pyramid emphasizes many unit tests, while a testing trophy emphasizes static checks and integration. Neither is a fixed quota. The useful balance follows the code's boundaries and failure risks.

Quickturn separates fast unit and component suites from process automation, built-system smoke tests and container-based DynamoDB tests. Each has an appropriate timeout and prerequisites. A pure unit test hanging for seconds is a different failure from a container taking time to start.

03Mocks, fakes and recordings

Mocks assert interactions; fakes provide simpler working behavior; recordings replay known responses. Prefer asserting results where possible, using a fake through the same port as production. Verify that fake against shared contract cases.

Interaction assertions can be necessary when the interaction is itself the contract, but should not mirror incidental internal call order. Coverage floors reveal gaps; they do not prove the suite would catch the important defects.

04When the output isn't fixed

Nondeterministic model output needs two kinds of evidence. Deterministic tests check parsing, retry behavior, idempotent results and failures with fakes or recordings. Live evaluations estimate agreement with human labels and quality under the current configuration.

Both should exercise the production task path. A response recording cannot replace a current quality evaluation, and an evaluation score cannot replace tests of the application's failure handling.

Summary in three lines

  1. Each kind of test buys different confidence at a different price; choose the mix by where the risk is.
  2. Prefer fakes to mocks, mock only at boundaries, and assert behavior rather than calls.
  3. When output isn't fixed, tests check the plumbing and evaluations measure quality.
