How do we see what a model call costs?

After this page you can explain why a single model call is the unit to observe, and which fields its record needs. You can also say what the bill, the provider's logs and your own record each can and can't tell you.

About 8 min readThe whiteboard room

In this page

  • Why isn't the bill enough?
  • Where does each piece of the record come from?
  • What do these records cost, and where do they mislead?
  • What changes when an agent makes many calls?

The whiteboard room. Leo has been reading the worker that grades typed answers with a model.

01What the bill can't say

L

Leo: The design says "every call is observable." But AWS already tracks Bedrock usage, and there's a bill. Isn't that enough?

M

Maya: Say the bill doubles next month. What's your first question?

L

Leo: Why. Which feature got more expensive?

M

Maya: Can the bill answer that?

L

Leo: It says "Bedrock" and a total. Maybe split by model.

M

Maya: So it can't say which feature, which prompt version, or which change made it double last Tuesday.

L

Leo: No. It only tells me that something happened.

M

Maya: That's the gap. For model features, the unit you observe is one model call.

L

Leo: Not one request to our API?

M

Maya: One API request might make no model call, or several. The cost and the quality live in the call.

L

Leo: So what does a call record hold?

M

Maya: Every grade of a typed answer comes back with a call record next to it. Here's the shape:

{
  "modelId": "…haiku…",
  "promptVersion": "grade-v3",
  "feature": "grading",
  "inputTokens": 812,
  "outputTokens": 96,
  "cacheReadTokens": 640,
  "cacheWriteTokens": 0,
  "latencyMs": 1240,
  "estimatedCostUsd": 0.0013
}
L

Leo: The numbers are real?

M

Maya: Only the field names are. The values are made up for today.

L

Leo: Why does the prompt version matter so much?

M

Maya: Because it's the thing you change most. If grades get worse on Wednesday, you want to see "grade-v4 shipped Tuesday."

L

Leo: And compare grades from v3 and v4 side by side.

M

Maya: Right. Without the version on each call, the two are mixed in one pile.

L

Leo: And the feature field?

M

Maya: Grading may not be the only caller. If a hint feature shares the model, the feature field keeps their costs apart.

02Where each piece comes from

L

Leo: Where do the tokens come from? Do we count them ourselves?

M

Maya: The model's response reports its own token usage. The adapter copies it into the record.

L

Leo: And the latency? Doesn't the response report that too?

M

Maya: The adapter measures it with its own timer, around the call. We don't rely on a latency value we haven't verified.

L

Leo: So we trust our own clock.

M

Maya: For that number, yes. Then there are layers outside our code. Bedrock can log each invocation: the raw request and the response.

L

Leo: Is that on already?

M

Maya: No, it's off by default. When you turn it on, it writes to CloudWatch Logs, S3, or both.

L

Leo: And the cost split by feature?

M

Maya: Each feature calls the model through its own application inference profile, and each profile is tagged. Cost Explorer can then split spend by that tag.

L

Leo: So the bill does learn about features.

M

Maya: It does, through the tags. And a per-feature cost dashboard shows it.

L

Leo: Four layers for one call. Isn't that too much?

M

Maya: Each one answers a different question. Only our own record knows which prompt version ran.

L

Leo: Is there a standard for this? Every team seems to invent field names.

M

Maya: OpenTelemetry has GenAI semantic conventions: standard names for the model, the token usage and the operation.

L

Leo: So tools can read our traces without custom code.

M

Maya: That's the aim. It's still evolving, so check the current version before you adopt it.

L

Leo: And for the tutor agent?

M

Maya: AgentCore Observability traces its sessions and its tool calls.

03What the records cost

L

Leo: Should we just turn invocation logging on everywhere? Then we'd have everything.

M

Maya: What's in a grading prompt?

L

Leo: The learner's typed answer. Oh.

M

Maya: Right. Invocation logs store prompts and outputs. That's personal data, with its own access rules and its own retention.

L

Leo: So turning it on is a data decision, not only a debugging one.

M

Maya: Both at once. And the telemetry costs something too. Every field is more storage, on every call.

L

Leo: What about the estimated cost? It's in the record, so it's exact?

M

Maya: It's computed from the token counts and a price table. When prices change, the old numbers drift.

L

Leo: So which is the truth?

M

Maya: The token counts. Keep them, and recompute the cost when the table changes.

L

Leo: Why are cache tokens separate fields?

M

Maya: Prompt caching changes the math. Writing to the cache costs more than normal input, and reading from it costs less.

L

Leo: So a single "tokens" number would hide whether caching helped.

M

Maya: Right. Here's the whole difference in one table.

Which feature?
The bill: only with tags. The call record: always.
Which prompt version?
The bill: never. The call record: always.
Which change caused it?
The bill: no. The call record: yes, by version and time.
Per learner?
The bill: no. The usage ledger: yes.
L

Leo: Why not one shared helper, like complete(prompt)? Every feature could call it.

M

Maya: Then each caller has to remember to pass the feature and the version. One day someone forgets.

L

Leo: And that call shows up untagged.

M

Maya: So each feature gets its own typed port, and one adapter underneath fills in the record. Nobody has to remember to tag a call.

L

Leo: What if costs run away anyway?

M

Maya: A per-learner usage ledger caps each learner. And a Budgets action denies Bedrock for the whole account, as a last switch.

04Many calls, one task

L

Leo: Grading makes one call per answer. What about an agent that plans and uses tools?

M

Maya: One request can become ten model calls. Each record looks fine on its own.

L

Leo: Then how do we see the whole task?

M

Maya: Every call carries a shared session or trace id. Cost and latency then add up per task.

L

Leo: What goes wrong without it?

M

Maya: A team I know tracked tokens per call perfectly. Then the business asked, "What does one finished task cost?"

L

Leo: And they couldn't answer.

M

Maya: Not without a week of joining logs. That's the number people actually ask for.

L

Leo: So the record needs the call and the task it belongs to.

M

Maya: Right. Record per call, and roll up per task.

L

Leo: Does that change our grading records?

M

Maya: Not today. Each grade is one call, so the call and the task are the same thing. The tutor agent is where it starts to matter.

05Leo explains it back

M

Maya: Now answer your first question. Is the bill enough?

L

Leo: No. Treat each model call as the unit, and record the model, the prompt version and the feature.

L

Leo: Record the token counts including cache, the latency, and an estimated cost. The bill only gives totals.

L

Leo: Invocation logs and tagged profiles help, but only our record knows the prompt version.

M

Maya: You haven't said what's inside a prompt.

L

Leo: Prompts contain what learners typed, so logging them means logging personal data.

M

Maya: One piece is missing: the cost field is an estimate. Keep the token counts as the source of truth, and recompute when prices change.

Summary in three lines

  1. Record every model call with its model, prompt version, feature, tokens, latency and cost.
  2. The bill, invocation logs and tags help, but only your record knows the prompt version.
  3. Prompts are personal data; for agents, add a shared id so calls roll up per task.
