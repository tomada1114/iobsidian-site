What is an aggregate, really?

After this page you can explain an aggregate as a consistency boundary and show how versioned writes protect it. You can also say when it's fine to break the "one aggregate per transaction" rule.

About 4 min readQuickturn case study

  • What are entities, value objects and aggregates?

01The building blocks, quickly

An entity keeps its identity as its values change: a round remains the same round after an answer. A value object is defined by its values, such as a grade or time limit. An aggregate groups related entities and values behind one root, so specified invariants hold after a change.

For a round, answers are accepted only while it is open and only for cards in its deck. Answer IDs must not be recorded twice, and a day's portion must not be completed twice. The boundary therefore follows consistency requirements, rather than the size of an object or a set of database tables.

02How the boundary protects itself

A command reads the aggregates it needs and their versions. A pure decision function computes intended changes. The commit accepts them only if the stored versions still match those read.

If two phones act on the same round, the first write can advance its version. The second write's condition fails, so it reloads and recomputes rather than overwriting the newer state. Quickturn allows three attempts before returning a conflict.

This is optimistic concurrency: no lock is held while deciding. It suits records with infrequent contention, such as one learner's data. A heavily shared record needs a separate assessment of retry rates and throughput.

03No classes

Quickturn uses read-only data, literal types and branded identifiers. A time limit is one of 15, 20, 30, 45 or 60 seconds. A branded learner ID helps prevent accidentally passing a card ID in its place. Zod schemas validate runtime input at the HTTP boundary.

These protections have different roles. Types narrow valid code, schemas reject malformed external values, and tests check decision behavior. Plain objects still lack the full encapsulation a class with private fields could provide. The project relies on decision functions as the designated path for producing changes.

04Bending the textbook

The usual aggregate guidance favors small boundaries, references by ID and transactions that change one aggregate. Quickturn deliberately updates several learner-owned records together: the answer log, round, daily tally, card memory state and learner totals.

All belong to one learner, and contention is normally low. An atomic transaction avoids a queue solely to make a small set of counters agree. A busy shop's shared stock record is a different case: coupling every order to it can create contention, so inventory may need reservations, separate updates or compensation rules.

Transactions still have service limits. Offline answers are processed in bounded chunks, with each chunk committed separately; the implementation must count actual writes rather than assume a fixed answer count always fits. AI usage accounting has its own consistency boundary. The choice should be revisited if contention or team ownership changes.

Summary in three lines

  1. An aggregate is a consistency boundary: the data whose rules must hold after every write.
  2. Versioned, conditional commits protect it. A write that loses to another one reloads and decides again.
  3. Quickturn updates several learner-owned aggregates together because contention is low and immediate consistency matters.
