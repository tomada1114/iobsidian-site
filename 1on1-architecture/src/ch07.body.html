What is an aggregate, really?

After this page you can explain an aggregate as a consistency boundary and show how versioned writes protect it. You can also say when it's fine to break the "one aggregate per transaction" rule.

About 8 min readWhiteboard room, morning

In this page

  • What are entities, value objects and aggregates?
  • How does a write protect an aggregate's rules?
  • How do we protect the rules without classes?
  • When is it fine to bend the textbook rules?

The whiteboard room, the morning after a conflict in the logs.

01The building blocks, quickly

L

Leo: I saw an ERR_CONFLICT in the logs last night. A learner answered the same round from two phones at the same moment. One write lost and retried.

M

Maya: And what was "in conflict", exactly?

L

Leo: That's my question. The on-call engineer told me "that's the aggregate protecting itself". It didn't help.

M

Maya: What do you picture when you hear "aggregate"?

L

Leo: A big object that contains other objects. Or a table with its child tables.

M

Maya: That's the usual picture, and it isn't the important part. Let's go through the building blocks quickly. An entity has an identity that lasts while its values change.

L

Leo: Like a learner. Or a round. It's still the same round after I answer a card.

M

Maya: Right. A value object is defined only by its values. A practice day, a time limit, a grade.

L

Leo: So "missed it" is just "missed it". There's no identity to track.

M

Maya: Exactly. Now the aggregate. It's a group of entities and values with one root, the single entry point other code goes through. And it has invariants.

L

Leo: Invariants being...?

M

Maya: Rules that must be true after every change. Here are ours for a round: it takes answers only while it's open, and only for cards in its deck.

L

Leo: And an answer id is recorded only once.

M

Maya: Yes. And a day's portion is completed only once. So an aggregate isn't about size. It's about which rules must hold together.

L

Leo: So the question is "what must be consistent after one write", not "what contains what".

M

Maya: That's the whole idea. Let me draw what one learner's data looks like.

02How the boundary protects itself

L

Leo: Okay, each one has a version. What does the version do?

M

Maya: A command is one request that changes data, like recording an answer. It reads the aggregates it needs, along with their versions.

M

Maya: A pure function, code that only computes from its inputs, decides the changes. Then the commit says "write these, but only if each is still at the version I read".

L

Leo: And if another write got there first?

M

Maya: Then the condition fails. The command loads again and decides again. After three attempts, it gives up and returns a conflict.

L

Leo: That's the ERR_CONFLICT I saw. But most of the time the retry just works.

M

Maya: Right. Let me draw your two phones.

L

Leo: Why "optimistic"?

M

Maya: Because we don't lock anything in advance. We assume conflicts are rare, and handle them when they happen.

L

Leo: That fits. One learner rarely uses two phones at once.

M

Maya: Exactly why it's the right choice here. With many people editing the same thing all day, you'd think harder.

03No classes

L

Leo: In the books, an aggregate is a class with private fields. We don't have any classes.

M

Maya: We use plain read-only data instead. And literal types: a time limit can only be one of five values.

L

Leo: 15, 30, 45, 60…?

M

Maya: 15, 20, 30, 45 or 60; nothing else compiles. And a branded learner id: a string the type system won't confuse with other strings.

L

Leo: So I can't pass a card id where a learner id belongs.

M

Maya: Right. And zod schemas validate input at the HTTP edge, where requests come in. Zod is a TypeScript library that checks the shape of data, so bad data doesn't get in.

L

Leo: But what gives the guarantee a class gives? With a class, only its methods can change its fields.

M

Maya: The decide functions, the pure functions that decide changes, are the only place that produces changes. Types narrow what's possible, and tests cover each decide function.

L

Leo: That's a promise we keep, not something the language enforces.

M

Maya: It is. That's one of the trade-offs we'll get to.

04Bending the textbook

M

Maya: Vaughn Vernon wrote the simple rules most teams know. Keep aggregates small. Reference other aggregates by id.

L

Leo: And?

M

Maya: Change one aggregate per transaction, and update the others later. A transaction is a set of writes that succeed or fail together.

L

Leo: Do we follow that?

M

Maya: We bend the third on purpose. Guess what recording one answer writes.

L

Leo: The log entry. The round. Maybe the day's tally?

M

Maya: Also the item's memory state and the learner's totals. All in one DynamoDB transaction.

L

Leo: Five aggregates in one transaction. Isn't that exactly what the book says not to do?

M

Maya: It is, and here's why we do it anyway.

M

Maya: They all live in one learner's partition, the part of the table that holds only that learner's data. One learner rarely acts from two devices at once.

M

Maya: And streaks that are "eventually" right would need a queue for nothing.

L

Leo: So the usual reason for the rule, lots of writers fighting, doesn't apply.

M

Maya: Right. Picture a shop instead. An order and the stock count for a popular item.

L

Leo: Thousands of people buying the same item. If every order locked the stock count in the same transaction…

M

Maya: …they'd all fight over one record, and most orders would retry. So shops keep the order as one aggregate and update stock separately, a moment later.

L

Leo: And accept that the stock number is briefly wrong.

M

Maya: Yes, with a rule for what happens when it runs out. That's the textbook case, and there Vernon's rule is exactly right.

L

Leo: So the rule is really about contention. Many writers on one aggregate means small transactions.

M

Maya: That's the reason behind it. Know the reason, and you know when it applies.

M

Maya: But we respect one hard limit. A transaction holds a bounded number of writes.

L

Leo: So a big batch of offline answers can't go in one commit.

M

Maya: We split it into chunks of 20 answers. Each chunk is its own commit.

L

Leo: What about the usage ledger for the AI features? Is it in the same transaction?

M

Maya: No. The ledger is its own consistency boundary. Mixing billing-like counts into every answer commit would tie together two things that change for different reasons.

L

Leo: And the classes-versus-plain-data trade-off?

M

Maya: Classes enforce rules even when someone forgets. Plain data relies on discipline and tests. We chose short code and one obvious place for each rule.

L

Leo: So if the team got much bigger, you might revisit that.

M

Maya: I would. That's a decision with a condition, not a belief.

05Leo explains it back

M

Maya: The on-call engineer asks you what "the aggregate protecting itself" meant. Go.

L

Leo: An aggregate is the boundary of data whose rules must hold after every write. Like a round only taking answers while it's open.

L

Leo: Each one has a version. A command reads, a pure function decides, and the commit only succeeds if nothing changed since the read.

L

Leo: If something did, we reload and decide again, up to three tries in all. That's the conflict I saw.

M

Maya: And the rule we break?

L

Leo: One aggregate per transaction. We write several of one learner's aggregates at once, because they share a partition and one person acts on them.

M

Maya: Add the limit: a transaction holds only so many writes. So big offline batches go in chunks of 20 answers, one commit per chunk.

Summary in three lines

  1. An aggregate is a consistency boundary: the data whose rules must hold after every write.
  2. Versioned, conditional commits protect it. A write that loses to another one reloads and decides again.
  3. Bending "one aggregate per transaction" is fine when the aggregates share one partition and one actor.
