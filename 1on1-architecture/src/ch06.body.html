Why not split it into microservices?

After this page you can explain why a bounded context is not the same as a service. You can also say what a modular monolith gives a small team, and how to keep extracting a service later cheap.

About 4 min readQuickturn case study

In this page

  • What is a bounded context, and what are ours?
  • How do contexts live together in one deployable?

01Boundaries for a model

A bounded context defines where a model and its vocabulary remain consistent; it does not specify a deployment unit. Quickturn has contexts for identity, catalog, practice, learning records, learner modeling, engagement, vocabulary, assessment and entitlements.

Identity holds learner settings, the catalog supplies reviewed cards, practice owns rounds and placement, and the learning record keeps answers and memory state. Other contexts own cross-activity goals, model grading or usage accounting. References across these boundaries use IDs rather than sharing another context's internal object structures.

02A map, and one deployable

A context map shows the relationships among these models. Identity supplies information to the other contexts, and the catalog is read-only for consumers such as practice and learner modeling.

Quickturn builds an API function and a background worker from one codebase. Calls between contexts are local function calls. This is a modular monolith: modules preserve conceptual ownership while the product remains one coordinated system.

Machine-enforced boundaries currently separate domain, application, adapters and contracts. Within a layer, each context has a public entry surface, and stored keys identify the kind of record. Those conventions aid review but do not physically prevent every shortcut import.

03Why not microservices now

Turning each context into a service replaces local calls with network calls. Latency is only one cost: failures, retries, versioning, monitoring, deployment and permissions must also be handled across each connection. Independent scaling or separate team ownership can justify that cost. Quickturn's small team and traffic do not yet require it.

Validated command data, consistent handler signatures and public context surfaces make future extraction easier. They do not make it free: cross-service consistency, authorization and partial failures still need redesign. Starting with a monolith lets the team learn which boundaries deserve independent operation before paying those costs.

04What the monolith costs

A modular monolith needs discipline, and one bad release can affect the whole system. Obvious entry points, ownership names, layer checks and review help make shortcuts visible. A stored key naming a round or memory record also makes an inappropriate cross-context access easier to spot.

Quickturn kept streaks within practice until vocabulary provided a second activity. Only then did engagement's cross-activity requirements become concrete. Creating every possible context early would have meant guessing those requirements.

Services that share assumptions and must release together form a distributed monolith. They incur network costs without gaining independent operation. Team structure and real change patterns should guide the split, rather than the expectation that serious software must use many services.

Summary in three lines

  1. A bounded context is a boundary for a model and its words, not a deployment unit.
  2. A modular monolith keeps contexts as modules with public surfaces in one deployable, so calls stay function calls.
  3. Split into services when scaling or team ownership demands it, and fence a context once it has a second user.
