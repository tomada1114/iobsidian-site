Clean vs Hexagonal — what's actually different?

After this page you can answer "Clean or Hexagonal?" directly: the styles share one dependency rule, and Clean adds a prescribed inside. You can also say which parts a small team keeps and which it leaves out.

About 5 min readQuickturn case study

In this page

  • What do onion, clean and hexagonal have in common?
  • So what is actually different between them?
  • What did we take, what did we leave, and why?
  • When is the full version worth it?

01Three pictures, one rule

Onion architecture places a domain model at the center, with domain and application services around it and infrastructure outside. Domain services express rules that do not fit one object; application services coordinate tasks such as loading, deciding and saving. Clean Architecture describes entities, use cases, interface adapters, and frameworks or drivers, with source-code dependencies pointing inward.

Hexagonal architecture emphasizes the boundary between application and outside technologies. All three can protect business rules from storage and framework details. Their diagrams are useful when they explain actual dependencies rather than serve as mandatory folder layouts.

02The difference is the inside

Hexagonal architecture leaves the application's internal organization largely open. Onion and Clean offer more guidance about separating business rules from application workflows. A common Clean implementation uses interactors, input and output ports, and presenters, but the dependency rule does not require one class for every operation.

The two approaches differ in how much internal structure they describe. The tables compare representative implementations; “ceremony” means the additional interfaces, mapping and wiring a team chooses to maintain.

Conventional layering can leave policy dependent on data access. The inward styles move technology implementations outside the protected core. Teams should inspect their actual arrows, because the same style label can describe substantially different code.

03What Quickturn took and left

Quickturn adopts inward dependencies and a composition root for each executable entry point. A composition root wires the real store, catalog, authenticator, clock and ID generator together. Commands elsewhere receive those dependencies rather than locate them globally.

Commands are plain async functions such as startRound(deps, context, command). They return values without separate presenter classes or output ports. Domain types pass through the application, and request and response shapes are mapped at the HTTP boundary.

Adding a card hint illustrates the trade. Its domain type gains a field, the decision function uses it, and the API contract exposes it. Extra output objects, presenters and ring-to-ring mappers would each copy the same field unless they had a distinct responsibility. Quickturn avoids those copies because it currently needs only one presentation shape.

04When the full ceremony pays

More structure can pay for itself when several teams need explicit ownership, one use case supports several presentations, or an object model must be insulated from UI data. A report, web page and voice interface may each justify their own presenter.

The main cost is often developer attention: more files, names and mappings to update. For Quickturn's small team, a second presentation for the same use case would be a concrete reason to add a presenter. A review should state the adopted dependency rule, the omitted machinery and the condition that would justify adding it.

Summary in three lines

  1. Hexagonal, onion and clean share one rule, the core doesn't depend on technology; classic layering points at the database.
  2. Hexagonal defines only the boundary; clean also prescribes the inside with use cases, presenters and mapping.
  3. A team can adopt the rule without the ceremony, and should say what it left out and why.
