Clean vs Hexagonal — what's actually different?

After this page you can answer "Clean or Hexagonal?" directly: the styles share one dependency rule, and Clean adds a prescribed inside. You can also say which parts a small team keeps and which it leaves out.

About 8 min readCoffee in the kitchen

In this page

  • What do onion, clean and hexagonal have in common?
  • So what is actually different between them?
  • What did we take, what did we leave, and why?

The kitchen. Leo is holding a coffee and his phone.

01Three pictures, one rule

L

Leo: I did a mock interview yesterday. They asked, "Clean or Hexagonal, which did you use, and what's the difference?" I froze.

M

Maya: What did you want to say?

L

Leo: That we use Clean, I guess. But then I remembered we don't have "interactor" classes. So maybe we aren't clean at all?

M

Maya: Let's untangle it. First, what do you think Clean Architecture is?

L

Leo: A folder template. entities, usecases, interfaces, frameworks. And you pick it instead of hexagonal.

M

Maya: That's how it's often taught, and it hides the main point. Let's start with what the styles share.

L

Leo: Okay.

M

Maya: Onion architecture, from Jeffrey Palermo: the domain model in the middle, then domain services, then application services. UI, infrastructure and tests sit in the outer ring.

L

Leo: And Clean is Robert C. Martin's?

M

Maya: Yes. Entities, use cases, interface adapters, frameworks and drivers. And one rule he states plainly: source code dependencies point only inward. Let me draw his rings.

L

Leo: And hexagonal is inside versus outside, with ports between.

M

Maya: Right. So look at all three. What do they agree on?

L

Leo: The core doesn't know the database or the web framework.

M

Maya: That's the shared rule. Three pictures of it.

02The difference is the inside

L

Leo: Then what's the difference? The interviewer clearly expected one.

M

Maya: Here's the direct answer. Hexagonal says nothing about how the inside is organized. It only defines the boundary.

L

Leo: And clean does say how?

M

Maya: Onion and clean both prescribe the inside. Separate rings for enterprise rules and application rules.

M

Maya: And clean names specific parts: a use case interactor per operation, input and output ports, presenters that format the interactor's output, and data objects mapped at each ring.

L

Leo: So the short version is: clean is hexagonal plus a prescribed inside.

M

Maya: That's a good way to say it. Let me draw the two boundaries.

M

Maya: Two short tables help here, because a comparison with many attributes doesn't fit in conversation.

L

Leo: So only layered puts the database at the center of gravity. The other three push it outward.

M

Maya: Yes. And the ceremony column is where teams actually differ in practice.

03What Quickturn took and left

L

Leo: So what are we, then?

M

Maya: We took the dependency rule. And we took a composition root per deployable.

L

Leo: Composition root?

M

Maya: Mark Seemann's term. It's the one place where the real parts get wired together. We have one entry file for a local run and one for Lambda.

L

Leo: Each one passes in the stores, the catalog, the authenticator, the clock and the ids.

M

Maya: Exactly. Everything else takes what it's given.

L

Leo: And the interactor classes?

M

Maya: Left out. A command is a plain async function. It takes its dependencies, a request context and the command data.

L

Leo: Like startRound(deps, context, command).

M

Maya: Right. And no presenters or output ports: a command returns its view as a value, built by a plain function.

L

Leo: And the data objects mapped at every ring?

M

Maya: Also left out. Domain types pass straight through the application. The one mapping is at the HTTP edge, where the contracts package defines the request and response shapes.

L

Leo: Why leave all that out, though? It's in the book.

M

Maya: Because our domain is already plain functions over plain data. Extra rings would add translation code, and nothing needs a second translation.

L

Leo: Let me try it on a real case. Say we add a "hint" to each card. What changes?

M

Maya: Walk me through it.

L

Leo: The domain type gets a field. The decide function uses it. The contracts package adds it to the response schema. That's it?

M

Maya: That's it. Three places, and each one has a reason to change.

L

Leo: With full clean, I'd also touch a use case output object, a presenter, and a mapper between rings.

M

Maya: Right. Each of those would copy the same field from one shape to another. Nothing would decide anything.

L

Leo: So the ceremony isn't wrong. It's just paying for a problem we don't have.

04When the full ceremony pays

L

Leo: Is the full version ever right? Or is it always too much?

M

Maya: It pays in some places. Large teams, where the structure keeps many people from stepping on each other.

L

Leo: What else?

M

Maya: Several delivery mechanisms that need different presentation, like a web page, a report and a voice interface from one use case. Presenters earn their keep there.

L

Leo: And a domain object model you need to protect from UI shapes?

M

Maya: Yes. If your domain has rich classes, mapping at each ring stops a form field from leaking into an entity.

L

Leo: I'd have guessed the main cost is performance. All that mapping must be slow.

M

Maya: Almost never. Copying a few objects is cheap for a computer. The cost is for people: files to open, names to keep in sync, reviews that get longer.

L

Leo: So the cost is time and attention, not milliseconds.

M

Maya: Yes. That's the budget a small team runs out of first.

L

Leo: And for us?

M

Maya: For a small team, every mapping and interactor is paid on every change. A new field would touch six places instead of three.

L

Leo: So my interview answer shouldn't be "we used Clean".

M

Maya: No. Say "we used the dependency rule; here's what we left out, and why". That answer shows judgment, not just vocabulary.

L

Leo: And if they push, "then you're not really clean"?

M

Maya: Then say which condition would change your mind. "If we added a second presentation for the same use case, we'd add presenters there."

L

Leo: That's much better than freezing.

05Leo explains it back

M

Maya: Try it now. The interviewer asks again.

L

Leo: Hexagonal, onion and clean all say the core doesn't depend on the database or the framework; classic layering is the exception. Hexagonal draws only the boundary.

L

Leo: Clean and onion also prescribe the inside. Clean adds use case interactors, presenters, output ports and mapped data at each ring.

M

Maya: And your team?

L

Leo: We kept the dependency rule and one composition root per deployable. Commands are plain functions, views are values, and we map only at the HTTP edge.

L

Leo: We skipped the rest because our domain is plain data and nothing needed a second translation.

M

Maya: Good. Add one line on when you'd change: a second presentation, or a much bigger team.

L

Leo: Got it. That's the part that makes it sound like a decision.

Summary in three lines

  1. Hexagonal, onion and clean share one rule, the core doesn't depend on technology; classic layering points at the database.
  2. Hexagonal defines only the boundary; clean also prescribes the inside with use cases, presenters and mapping.
  3. A team can adopt the rule without the ceremony, and should say what it left out and why.
