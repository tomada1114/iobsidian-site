If the rules can't touch the database, who saves?

After this page you can explain how classic layering makes the rules depend on the database, and how dependency inversion flips it. You can also say when plain layering is the better choice.

About 4 min readQuickturn case study

In this page

  • What goes wrong when the rules import the database code?
  • How does inverting the dependency fix it?
  • How do we make sure nobody breaks the rule?
  • When is plain layering simpler and good enough?

01The layers everyone learns first

A conventional layered application lets pages call business logic, which calls data access, which calls the database. This is easy to explain and often adequate for CRUD tools. It also means the business rules depend on the data-access layer.

That dependency affects both change and testing: exercising a rule may need a database or a substitute, and changing storage can reach the rules. Quickturn's early SQL prototype avoided this by keeping its drill rules as plain functions. Moving to DynamoDB changed the storage implementation while those functions stayed the same.

02Flip one arrow

Dependency inversion separates high-level policy from low-level technology. The inner side defines an interface describing what the application needs, and the outer adapter implements it. Runtime calls can still reach the database even though source-code dependencies point inward.

Quickturn's application package owns a learner-store interface for reading a round, reading today's portion and committing changes. DynamoDB and in-memory adapters implement it. At startup, the HTTP application supplies the real adapter.

The domain does not call that interface. It takes values and returns decisions. The application loads the values, asks the domain to decide, then commits through the store. The application coordinates saving; the adapter performs it.

03Enforced, not just drawn

A dependency diagram needs enforcement. Quickturn's domain accepts time, time zones and randomness as inputs instead of reading them through external libraries. A test can therefore exercise 3:59 a.m. directly.

Lint checks forbidden imports, and an independent test scans the import graph and declared dependencies. Removing a lint rule does not remove the second check.

The important arrow is the one between application policy and storage implementation. Making the adapter depend on an application-owned interface lets rules be tested alone and limits what a storage change must touch.

04When plain layering wins

Inversion adds an interface, startup wiring and a search for the implementation when reading code. Mapping every object into a new shape at every layer adds another cost. Quickturn avoids most of that copying by passing domain types through the application and mapping at the HTTP boundary.

For a small admin tool whose behavior mostly follows its tables, conventional layering may be simpler. Strict layering allows calls only to the next layer; relaxed layering allows some layers to be skipped. Either needs an explicit dependency policy.

Protecting a core is particularly useful when its rules merit independent tests, storage has known alternatives, or several clients share the same behavior. Quickturn has all three. Adding an interface to every trivial operation can instead make each change larger without creating a useful boundary.

Summary in three lines

  1. Conventional downward dependencies can make business-rule tests and changes depend on data-access behavior.
  2. Dependency inversion lets the rules' side own the interface and makes the storage code implement it.
  3. Inversion costs an interface and wiring; pay it when the rules are worth protecting, not for plain CRUD.
