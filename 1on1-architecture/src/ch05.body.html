Isn't DDD just another architecture style?

After this page you can explain that domain-driven design answers "where are the boundaries and what do the words mean". Clean and hexagonal architecture answer "which way do dependencies point". You can also say how much of DDD a small team needs.

01Two halves of DDD

The word “session” can mean a card round to product staff and a login session to an authentication engineer. A folder structure cannot fix that disagreement. Domain-driven design addresses both the model's vocabulary and the boundaries within which its words have a consistent meaning.

Strategic design includes bounded contexts, a shared language and relationships between contexts. Tactical design supplies building blocks inside a context: entities, value objects, aggregates, repositories and domain events. A time limit can be a value object; “round finished” can be an event. For a small team, agreeing on the model may be more useful than adopting every tactical pattern.

02One word everywhere

A ubiquitous language is a vocabulary shared by product discussions, specifications and code. In Quickturn's practice context, a round is a short deck, a portion is the daily amount needed for a streak, and placement is the initial round that sets a level. The review log records answers, while an item's memory state determines when a card is due.

The practice context avoids “session” because it has competing meanings. A separate vocabulary activity may use that word within its own context. The boundary makes the meaning explicit.

Type and function names should carry the same language. A product request to start today's round should lead naturally to the corresponding command and decision function. This reduces translation between a requirement and its implementation.

03Two different questions

DDD and Clean Architecture answer different questions. DDD helps model the problem, choose contexts and agree on terms. Clean or hexagonal architecture helps arrange dependencies so those rules are protected from technologies.

A codebase can have perfect dependency arrows and ambiguous concepts. It can also have excellent domain names while its rules depend directly on a database. Strong modeling and useful dependency boundaries complement each other; selecting one does not eliminate the need for the other.

04How much tactical DDD?

Quickturn uses aggregates as consistency boundaries but represents data with plain values and keeps behavior in pure domain functions. The absence of methods is not, by itself, evidence that rules have been scattered outside the domain. The important question is where those rules actually live.

Plain data has a cost: callers can construct an invalid object more easily than with a class that hides its fields. Quickturn relies on decision functions as the intended change-producing path, constrained types and tests. This is a discipline supported by checks, rather than complete language-enforced protection.

A larger team or a model needing stronger encapsulation could justify richer objects. An event bus becomes useful when several independent listeners must react to one event. Neither pattern needs to be added before that responsibility exists.

Summary in three lines

  1. DDD's strategic half decides boundaries and a shared language; its tactical half gives building blocks inside one boundary.
  2. Clean and hexagonal answer a different question, which way code depends, so a system usually uses both.
  3. A small team gets most of DDD's value from the strategic half and a thin tactical slice.
