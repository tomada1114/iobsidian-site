Who stops a bad import when nobody is watching?

After this page you can explain how a monorepo with workspace packages turns architecture boundaries into checks a machine runs, and why that matters more when AI coding agents write much of the code.

About 8 min readWhiteboard room

In this page

  • Why one repository instead of several?
  • How do workspace packages make a surface explicit?
  • How are the edges enforced, and is all this config worth it?

The whiteboard room. A red CI run is on Leo's laptop.

01One repository or several

L

Leo: My coding agent wrote a change this morning that worked. It imported the DynamoDB adapter straight into a command. CI rejected it before anyone even looked.

M

Maya: Good. That's the system doing its job.

L

Leo: I know. But I'm curious why the repo is set up like this. And whether it's worth all that config.

M

Maya: Let's start one level up. Why do you think everything lives in one repository?

L

Leo: Honestly, I thought a monorepo was just one big folder. Less setup.

M

Maya: That's part of it, but not the reason. Think about a contract change. Say a new field in the answer response.

L

Leo: The contracts package changes. The API changes. The web app changes to show it.

M

Maya: In one repository, that's one commit, one review, and one set of gates. Now imagine three repositories.

L

Leo: Three pull requests. The contract gets a new version, then the API updates, then the web app. Somebody has to coordinate the order.

M

Maya: Right. Let me draw it.

L

Leo: But the other column has upsides too. Independent releases, separate permissions.

M

Maya: And separate toolchains. That's why whether the native apps live here is a real trade-off for us. Swift and Kotlin bring their own tools.

L

Leo: So neither is "more serious".

M

Maya: No. It depends on who changes what together.

02Packages with explicit surfaces

L

Leo: Okay, one repo. What makes it more than a folder?

M

Maya: pnpm workspaces. Each package declares which other packages it depends on. And pnpm's strict layout means an undeclared package can't even be resolved.

L

Leo: So if the domain doesn't declare the adapters, the import can't even resolve.

M

Maya: Exactly, type checking fails on it. That's the first fence. The second is the exports field in each package's manifest.

L

Leo: What does exports do?

M

Maya: It points at one entry file. Only what that file re-exports is public. Everything else in the package is private.

L

Leo: So each package has a front door, and the rest is locked.

M

Maya: Yes. And one more thing: "source, not builds". The entry points at the TypeScript source itself.

L

Leo: No build step per package?

M

Maya: None. Whoever uses the package compiles it: Vite for the web app, the test runner, Node's type stripping for the API. So there's no stale build to get out of sync.

L

Leo: Which package imports which, though?

M

Maya: Let me draw the layers.

L

Leo: The web app doesn't import any package?

M

Maya: None. It reaches the API only over HTTP, through types generated from the OpenAPI document. The native apps do the same, with generated clients.

03Edges enforced twice

L

Leo: So what caught my agent's import? The manifest?

M

Maya: Lint. The lint config holds the allowed edges as a table: domain to nothing, application to domain, adapters to application and domain, contracts to zod only.

L

Leo: And the import rules are generated from that table.

M

Maya: Yes. Then a separate test states the same edges again, on its own, and scans the real import graph and each package's manifest.

L

Leo: Why both, if they check the same thing?

M

Maya: So that deleting one check still fails the other. A boundary that only one layer holds is a boundary one edit removes.

L

Leo: So an agent that "fixes" the build by deleting the lint rule still fails the test.

M

Maya: Exactly the scenario. Here's what happened this morning.

L

Leo: Wait. Would the manifest alone have caught it? The application package doesn't declare the adapters.

M

Maya: Here, yes; lint just flagged it first. But a manifest is all or nothing: the API app declares several packages, so any file in it may import any of them.

L

Leo: And lint and the test can say exactly which edges are allowed, file by file.

M

Maya: Right. The manifest fences packages; the table fences the direction between them.

L

Leo: And the agent read the error and fixed it itself.

M

Maya: Yes. The error message says which edge is allowed. That's worth writing carefully.

L

Leo: What about tools like Nx or Turborepo? Would they help?

M

Maya: They solve neighboring problems. Nx has a module-boundary lint rule driven by project tags. Turborepo is mainly about running and caching tasks across packages.

L

Leo: And we don't need caching?

M

Maya: No package has its own build step, and bundling the deployables is quick. So build caching buys us little, and our own checks do the boundary job.

04Is it worth the config?

L

Leo: Okay, the honest question. It's a big lint config and a long test. Is it worth it?

M

Maya: Name the costs first. What do you see?

L

Leo: The lint config is huge. The boundary test is long. And workspace setup that a single package wouldn't need.

M

Maya: And one more: every new package needs a row in the table before it passes.

L

Leo: That sounds annoying when you're moving fast.

M

Maya: It is, a little. The first time you add a package, it fails, and you have to think about which edges it should have.

L

Leo: Which is maybe the point.

M

Maya: It is the point. Now the gain. It grows with AI agents.

L

Leo: Because agents don't read the wiki?

M

Maya: Half right. They often do read the instructions. But an agent follows what's checked more reliably than what's written. A wrong import becomes a red build, not a review comment a tired person might miss.

L

Leo: So the checks are the real documentation for agents.

M

Maya: For boundaries, yes. Neal Ford and his coauthors call a test like ours an architectural fitness function: a test for a design property, not a feature.

L

Leo: So for a small team with no agents, would you still do it?

M

Maya: The lint table, probably yes; it's cheap. The full double check pays off when many hands, human or not, touch the code every day.

L

Leo: Which is us now. My agent opens more pull requests than I do.

M

Maya: Then the config is the cheapest reviewer we have.

05Leo explains it back

M

Maya: A new hire asks why CI rejected their agent's change. What do you say?

L

Leo: One repo lets a contract and its clients change together, in one commit with one set of gates.

L

Leo: Workspaces and the exports field make each package's surface explicit. An undeclared package can't even be resolved.

L

Leo: The allowed edges are written twice on purpose. Lint checks one copy, and a separate test checks the real import graph against its own.

M

Maya: And why twice?

L

Leo: So deleting one check still fails the other. A wrong import is a failed build, whether a person or an agent wrote it.

M

Maya: Good. Add the cost: every new package needs a row first.

L

Leo: Right. That's the moment to decide its edges on purpose.

Summary in three lines

  1. One repository lets a contract and its clients change in one commit, when one team changes them together.
  2. Workspace dependencies and a single exported entry file make each package's public surface explicit.
  3. Checking the allowed edges twice, by lint and by a graph test, turns a wrong import into a failed build for people and agents alike.
