Isn't architecture just folders?

After this page you can explain architecture as two decisions: what changes together, and which way dependencies point. You can also say where structure is worth its cost and where it isn't.

About 8 min readWhiteboard room, after a review

In this page

  • Why did a small rule change touch eleven files?
  • Which way should the arrows point?
  • Why are there named styles at all?
  • When is structure worth its cost?

The whiteboard room, right after Leo's first design review.

01Eleven files for one small rule

L

Leo: Can I ask you something from the review? Someone asked why my change touched eleven files. I didn't have an answer.

M

Maya: What was the change?

L

Leo: A new rule for when a card counts as missed. If you flip the card before you say anything, it's a miss, even if the timer hasn't run out.

M

Maya: A small rule. And where did the eleven files come from?

L

Leo: The UI checked it to show the right color. The API handler checked it again. And the database code had its own version, for the stats.

M

Maya: So the same rule lived in three places. What's your guess about why?

L

Leo: Honestly? I think we picked the wrong folders. If the folders were better, the rule would sit in one place.

M

Maya: Half of that is right: the rule should sit in one place. But folders are only labels.

L

Leo: Labels for what, though?

M

Maya: For decisions you already made. You could move those eleven files into perfect folders and still touch eleven files.

L

Leo: Then what decides it, if not the folders?

M

Maya: Two words you've heard: coupling and cohesion. Coupling is how much one part must know about another. Cohesion is whether the things inside one part belong together.

L

Leo: So my rule had low cohesion. It was spread out. And the three parts were coupled, because each had to agree with the others.

M

Maya: Exactly. Here's a sharper test: a module should have one reason to change. Code that changes for the same reason lives together. Code that changes for different reasons lives apart.

L

Leo: The UI changes when design changes. The database code changes when storage changes. And the missed-card rule changes when the product rules change.

M

Maya: Right. Three reasons, so three homes. But the rule itself should have one home: the domain, the code that holds only the product's rules. Let me draw both versions.

L

Leo: So the folders would show this only if they followed the reasons to change.

M

Maya: That's it. Folders are a picture of the decision. They aren't the decision.

02Draw the arrows

M

Maya: Now the second decision. If A imports B, draw an arrow from A to B. Which way should the arrows point?

L

Leo: Toward the things that are used a lot? Like shared code?

M

Maya: Close. They should point toward the things that change least. Stable things shouldn't depend on volatile things, the ones that change often.

L

Leo: What counts as stable here?

M

Maya: The rules of the drill. How we deal cards, how streaks work, how levels move. Those change only for product reasons, never because a library or a database changed.

L

Leo: And volatile would be the web framework, the database client, AWS itself.

M

Maya: Yes. Those change for reasons that have nothing to do with learning, like a library's new major version or a table we move. Why should the streak rule care?

L

Leo: It shouldn't. But how do you stop it from caring? Somebody will import the database client one day.

M

Maya: We made that impossible to merge. Let me draw what our monorepo looks like.

M

Maya: The domain package imports no other package. No npm library, not even Node's built-in modules.

L

Leo: Not even for dates? That sounds strict.

M

Maya: Time comes in as an argument. And two separate checks guard the edge. A lint rule refuses the import, and a test reads the import graph and fails the build.

L

Leo: Why two? One seems enough.

M

Maya: Because someone can switch off a lint rule in one line. Deleting the lint rule still leaves the test failing.

L

Leo: And the native apps? They're a different codebase.

M

Maya: They call the same API. That's one reason the rules live on the server, in a package with no framework. Three clients, one copy of every rule.

03Why named styles exist

L

Leo: Okay, but then what are all the styles for? Layered, hexagonal, onion, clean. I thought I had to pick one.

M

Maya: Here's the thing: they aren't four different ideas. They're named recipes that answer the same two questions.

L

Leo: What changes together, and which way the arrows point.

M

Maya: Yes. They draw different pictures and ask for different amounts of extra code. But each one keeps the core away from the database and the framework.

L

Leo: Then why bother with the names at all?

M

Maya: Because names are short. In a review, someone says "ports and adapters", and everyone knows the rules without a lecture. A name is shared vocabulary.

L

Leo: So when I read about one of them, I should ask how it answers the two questions.

M

Maya: That's the best way to read any of them. The details differ. The two questions are the part that lasts.

Key point

Architecture is the set of decisions about what changes together and which way dependencies point. Folders and named styles are ways to show and share those decisions.

04What structure costs

L

Leo: Can I push back a little? All this sounds like a lot of files. For a small team, isn't it overkill?

M

Maya: Sometimes it is. Structure costs indirection. You follow a call through more files, and you write interfaces and wiring that a single script wouldn't need.

L

Leo: So when is it worth it?

M

Maya: Where change is frequent, or where a part must be replaced. A database, a model provider, a new client platform. Let me put it on two axes.

L

Leo: So the missed-card rule is top right. Product rules change all the time, and today a change costs eleven files.

M

Maya: Right. And a script that exports a report once a quarter?

L

Leo: Bottom left. Nobody touches it, so a clean structure gives us nothing.

M

Maya: That's YAGNI: "you aren't gonna need it". It comes from Extreme Programming. Don't build for a change you can't name.

L

Leo: But how do I know a change is coming? I can't see the future.

M

Maya: You look at history: which files changed together in the last few months? What did we replace last year? Guess from evidence, not from fear.

L

Leo: So "we might switch databases someday" isn't a reason.

M

Maya: Not by itself. "We already have two stores, one for production and one for tests" is a reason.

L

Leo: Does this apply outside apps like ours?

M

Maya: Very much. Think of a company building an AI agent. The model provider and the tool APIs change every few months. The prompts and business steps change more slowly.

L

Leo: So the provider goes at the edge, behind one adapter.

M

Maya: Yes. An adapter is one small module that talks to the provider for us, so switching providers touches only it. Teams that call the provider from everywhere rewrite half the product when prices or models change.

L

Leo: And the parts that never change stay plain.

M

Maya: That's the balance. Pay for structure where change happens, and nowhere else.

05Leo explains it back

M

Maya: Next review, someone asks you what architecture is. What do you say?

L

Leo: I'd say it's two decisions. What changes together, and which way the dependencies point.

L

Leo: My change touched eleven files because one rule lived in three places. Code should be grouped by its reason to change.

M

Maya: And the arrows?

L

Leo: The arrows should point toward stable things, like our rules, and away from frameworks and databases. At our company, a lint rule and a test check that.

L

Leo: The named styles are recipes for those two decisions. And structure costs indirection, so we only pay for it where change is frequent.

M

Maya: Careful with "frequent": say how you'd know. Check which files changed together before you say "we'll need this". Point to the history, not to a guess.

Summary in three lines

  1. Architecture is deciding what changes together and which way dependencies point; folders only show those decisions.
  2. Keep stable rules free of volatile tools, and let a machine check the direction of every import.
  3. Structure costs indirection, so spend it where change is frequent or a part must be replaced.
