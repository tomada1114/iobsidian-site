Isn't architecture just folders?

Quickturn changes one missed-card rule, but eleven files need edits. The problem is where the rule lives and what depends on it.

01Eleven files for one small rule

Quickturn is a language-learning app in which a learner answers a card before a timer ends. A product change says that flipping a card before answering counts as a miss, even while time remains. That small change touches eleven files because the UI, API handler and database statistics each contain their own version of the rule.

Moving the files into better folders would leave three copies to update. Coupling concerns how much one part must know about another. Cohesion concerns whether the things inside a part belong together. The UI changes for design reasons, storage code for database reasons, and the missed-card rule for product reasons. The rule therefore needs one home in the domain; the other parts display, carry or store its answer.

Folders become useful when they reflect those decisions. They show which code changes together, but a folder name cannot prevent duplicated rules or conflicting results.

02Draw the arrows

If module A imports B, its dependency arrow points from A to B. In this design, dependencies point toward the product rules and away from the framework, database client and deployment platform. Dealing cards, calculating streaks and changing levels should not need rewriting because an SDK releases a new version.

Quickturn makes that direction testable. The domain package imports no external package, including Node built-ins. Time arrives as an argument. A lint rule rejects forbidden imports, while a separate import-graph test also fails the build if a boundary is crossed.

The web, iOS and Android clients use the same API, so there is one server-side implementation of the rules. This boundary protects the rules shared by these clients. It does not require every project to exclude all libraries from its domain.

03Why named styles exist

Layered, hexagonal, onion and clean architecture provide vocabulary for organizing responsibilities and dependencies. Conventional layering can make business logic depend on data access. Ports and adapters and the inward dependency rule protect application policy from that direction.

A style name helps a team communicate, but it does not replace inspecting the code. Ask what each boundary protects, where dependencies point, and how much extra wiring the style requires. Those questions reveal more than a familiar folder template.

Key point

Architecture is the set of decisions about what changes together and which way dependencies point. Folders and named styles are ways to show and share those decisions.

04What structure costs

Structure costs interfaces, wiring and indirection. A reader may need to follow a call through several files that a small script would keep together. Frequent, expensive changes can justify that cost. Known alternatives, such as production and test stores, can also give an interface a clear purpose.

The missed-card rule is expensive to change because it has several copies. A rarely changed report script may gain little from additional layers. YAGNI, “you aren't gonna need it,” discourages paying for hypothetical variation: use change history and known requirements to identify the seams.

An AI application can benefit from a provider adapter when models or vendors change. The adapter concentrates provider-specific calls, although differing model behavior may still require prompt and evaluation changes. Keep stable, simple code plain, and spend structure where evidence shows that it reduces work.

Summary in three lines

  1. Architecture is deciding what changes together and which way dependencies point; folders only show those decisions.
  2. Keep stable rules free of volatile tools, and let a machine check the direction of every import.
  3. Structure costs indirection, so spend it where change is frequent or a part must be replaced.
