Should every dependency get a port?

Quickturn needs a store that production and tests can replace. Its deck composer also changes, but the two dependencies need different kinds of protection.

01Inside and outside

Hexagonal architecture, also called ports and adapters, separates the application from the technologies around it. Alistair Cockburn's hexagon leaves room for several connections; six sides are not a requirement.

A port describes an application-facing capability, and an adapter translates a particular technology to it. HTTP can drive “start a round,” while a storage adapter translates the application's writes into DynamoDB calls. A command changes state; a query reads it. The application should not need different business rules merely because a test rather than an HTTP request drives it.

02Driving and driven

Driving ports are the operations outside callers invoke: start a round, record answers, finish a round and read the home screen. Driven ports describe services the application uses, such as the learner store and card catalog. A supplied clock or ID generator can be a very small seam for controlled tests.

Quickturn's in-memory and DynamoDB stores run the same contract suite. One case writes as one learner and reads as another; the second learner must see no data. This gives evidence that the fake honors the tested contract. It does not prove that every production database behavior has been reproduced.

03Where we draw a port

An interface is valuable when it isolates meaningful variation. Storage technology differs between DynamoDB and memory. Authentication differs between Cognito and a local token verifier. Catalog data, clocks and IDs also need controlled test implementations.

The deck composer simply takes cards and returns a deck. Changing its algorithm can mean calling a different pure function; it does not automatically require an interface and implementing class.

A fake is a small working implementation, such as an in-memory store. A mock checks interactions, such as whether commit was called once with particular arguments. Interaction tests can break after a harmless refactor. A fake-based test can check the observable result: start a round, then read it back.

Quickturn uses ports at established technology or testing seams. That is a project choice, not a universal rule that a port must already have two implementations.

04When ports go wrong

Unnecessary ports make readers jump between files for little benefit. A more subtle failure is shaping an interface around the first database. Quickturn's early store was synchronous and allowed an open transaction, matching a local SQL database. A remote DynamoDB adapter could not preserve that interaction model. The revised port uses async reads and one commit carrying the intended changes.

The same principle applies to AI capabilities. “Grade an answer” and “explain a mistake” have different output schemas and evaluations. Task-specific ports keep those promises close to the application. A generic “send a prompt” port would leave every caller responsible for interpreting the response and handling provider details.

Summary in three lines

  1. Ports and adapters keep the application inside and every technology outside, behind ports that adapters translate to.
  2. Quickturn uses ports at established technology and testing seams, while pure logic remains a plain function.
  3. Shape each port for what the application needs, not for the first technology behind it.
