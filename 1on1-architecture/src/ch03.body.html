Should every dependency get a port?

After this page you can explain ports and adapters, tell driving ports from driven ones, and decide where a port belongs and where a plain function is enough.

About 8 min readWhiteboard room

In this page

  • What is hexagonal architecture actually saying?
  • What's the difference between driving and driven ports?
  • Where do we draw a port, and when is a port the wrong tool?

The whiteboard room. Leo has an interface draft on his laptop.

01Inside and outside

L

Leo: I wrote an interface for the deck composer, the function that picks a round's cards. So we can swap it later, like the store.

M

Maya: Show me. Okay, an interface with one method, and one class that implements it.

L

Leo: Right. I was thinking we could do this for every class. Ports everywhere, like hexagonal architecture.

M

Maya: Before we decide, tell me what you think "hexagonal" means.

L

Leo: Put an interface in front of everything? More ports, cleaner code?

M

Maya: That's the common reading, and it's where teams get into trouble. Let's go back to the idea itself.

L

Leo: Okay.

M

Maya: Alistair Cockburn named it hexagonal architecture, and later ports and adapters. The application sits inside. Everything outside talks to it through a port.

L

Leo: And an adapter is the thing in between?

M

Maya: Yes. An adapter translates one technology to a port. HTTP to a command. A command's writes to DynamoDB calls.

L

Leo: Why a hexagon, though? Is six important?

M

Maya: Not at all. The shape only leaves room to draw many ports. The important part is a symmetry: the app shouldn't care whether a person, an HTTP request or a test is driving it.

L

Leo: So a test is just another thing outside, like the web app.

M

Maya: Exactly. Let me draw Quickturn this way.

02Driving and driven

L

Leo: There are two groups in your drawing. Top and bottom.

M

Maya: Driving ports and driven ports. Some books say primary and secondary; it's the same split.

L

Leo: Driving means they call us?

M

Maya: Yes. Our driving side is the commands and queries: start a round, record answers, finish a round, read the home screen. The HTTP adapter calls them, and so do tests, in exactly the same way.

L

Leo: And driven is what we call out to. The store, the catalog.

M

Maya: Right. The learner store, the learner directory, the catalog. Plus the authenticator at the edge, and the clock and id generators we pass in at startup.

L

Leo: Wait, the clock is a port?

M

Maya: A tiny one. In production it's the real time. In a test it's a fixed moment, so the test is repeatable.

L

Leo: What about the in-memory store? I always worry a fake hides bugs that the real database would show.

M

Maya: Good worry. Both stores run the same contract suite. Same tests, same expected results.

L

Leo: Including the weird cases?

M

Maya: Including one I like. The test writes as one learner, then reads as another. It must get nothing back.

L

Leo: So if the fake leaked data between learners, the suite would catch it, just like with DynamoDB.

M

Maya: That's why we trust the fake in fast tests. A fake that passes the real contract is a second real implementation.

03Where we draw a port

L

Leo: So why not a port for my deck composer? It's the same idea.

M

Maya: Look at what varies. For the store, the technology varies: DynamoDB in production, memory in tests. What varies for the deck composer?

L

Leo: The way we pick cards. The algorithm.

M

Maya: And does it do any I/O?

L

Leo: No. It takes the learner's cards and returns a deck.

M

Maya: Then what you'd swap is a function, not a technology. If we want a different algorithm, we call a different function.

L

Leo: So my interface just adds a file and a name, and there will never be a second implementation.

M

Maya: Probably never. Let me put the two cases side by side.

M

Maya: Our ports sit only at seams with two real implementations. The store: DynamoDB and memory. The authenticator: Cognito, and a local stand-in where tests sign tokens with their own key pair.

L

Leo: The catalog?

M

Maya: A snapshot built with the app, and whatever cards a test hands in. Clock and ids too. The scheduler and the deck composer are plain functions.

L

Leo: So you're saying no to my interface.

M

Maya: To the interface, yes. The function is fine as it is.

L

Leo: One more thing I don't get. My old team used mocks for everything. Is the in-memory store a mock?

M

Maya: No, and the words matter here: Gerard Meszaros sorted these "test doubles" into kinds. A mock checks which calls were made. A fake is a small working implementation.

L

Leo: So a mock test says "commit was called once with these arguments".

M

Maya: Yes. And when we refactor, that test breaks even if the behavior is the same. A fake test just checks the result: start a round, then read it back.

L

Leo: And the fake is only possible because there's a port with a clear shape.

M

Maya: Right. A good port gives you good fakes. That's one more reason to put ports only where they're real.

04When ports go wrong

L

Leo: What's the real harm, though? One extra interface isn't much.

M

Maya: One isn't. A port per class is noise: two files for every idea, and interfaces nobody will ever implement twice. Readers jump around for nothing.

L

Leo: Fair. Is that the worst failure?

M

Maya: No. The subtler one is a port shaped like its first technology.

L

Leo: What does that look like?

M

Maya: Our early store interface was synchronous, and it let callers hold a transaction open. That was natural for a local database on one machine.

L

Leo: And DynamoDB is across a network. You can't hold a transaction open while your code thinks.

M

Maya: Right. The seam existed, but its shape was wrong. We had to redesign it: async reads, and one commit that carries every change at once.

L

Leo: So the lesson is to shape the port for what the app needs, not for the database you have today.

M

Maya: Yes. Here's the rule of thumb on two axes.

L

Leo: Does this apply to the AI parts? Grading typed answers with a model?

M

Maya: It does. We have one port per task: grade an answer, explain a mistake. Not one generic "call the model" port.

L

Leo: Why not generic? It would be less code.

M

Maya: Because each task has its own output schema and its own evaluation. A generic port pushes those details into every caller.

L

Leo: So the port names what the app needs, "grade this", not what the model offers, "send a prompt".

M

Maya: That's the same lesson as the store, one more time.

05Leo explains it back

M

Maya: Someone proposes a port for every class. What do you tell them?

L

Leo: Ports and adapters keep technology outside and the app inside. The app shouldn't care if HTTP or a test is calling it.

L

Leo: Driving ports are how the world calls us, our commands and queries. Driven ports are how we call the world, like the store.

L

Leo: We add a port only where there are two real implementations, like DynamoDB and memory. Pure logic stays a function.

M

Maya: And the shape?

L

Leo: Shape the port for what we need, not for the first database we had.

M

Maya: Good. One thing: mention the contract suite. It's what makes the in-memory fake trustworthy.

L

Leo: Right. Same tests for both, including the isolation test.

Summary in three lines

  1. Ports and adapters keep the application inside and every technology outside, behind ports that adapters translate to.
  2. Add a port only at a seam with two real implementations; pure logic stays a plain function.
  3. Shape each port for what the application needs, not for the first technology behind it.
