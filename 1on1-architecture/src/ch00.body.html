Engineering Readers: Architecture

Eleven short chapters about what software architecture is for. After them you can explain dependency rules, ports and adapters, DDD and aggregates. You can also choose between styles and defend the choice in a review.

11 pagesAbout 46 minEnglish, B2 · explanatory prose

The example application

Quickturn is a fictional language-learning application. A learner answers a card before a timer ends, then reviews progress and mistakes. Its web, iOS and Android clients share an API.

These chapters use that application to explain concrete engineering choices, their costs and the conditions that would justify a different design. Each chapter stands on its own; no conversation or earlier chapter is needed.

How the pages fit together

The pages

  1. Isn't architecture just folders? — Architecture decides what changes together and which way dependencies point.
  2. If the rules can't touch the database, who saves? — Dependency inversion lets the rules own the interface the database code implements.
  3. Should every dependency get a port? — Use ports where a meaningful technology or testing seam needs protection.
  4. Clean vs Hexagonal — what's actually different? — Both keep technology outside; only clean also names the parts inside.
  5. Isn't DDD just another architecture style? — DDD draws boundaries and chooses words; clean decides which way the code depends.
  6. Why not split it into microservices? — Bounded contexts can live as modules in one deployable.
  7. What is an aggregate, really? — A consistency boundary that decides what one commit protects.
  8. Where does the logic go, if not in the handler? — Load, decide in a pure function, commit.
  9. Do we need event sourcing to keep the history? — An append-only log with projections, and when to derive instead.
  10. Who stops a bad import when nobody is watching? — Workspace packages and checks that turn boundaries into failed builds.
  11. How do I defend a design decision in a review? — Decision records, rejected options, and effort that matches reversibility.

How to read this

Read a chapter in a few minutes, using the diagrams and code examples alongside the explanation. The summaries collect the main decisions; the examples show where those decisions apply.
