Do we need event sourcing to keep the history?

After this page you can place CQRS and event sourcing on a spectrum and explain an append-only log with projections. You can also decide whether a view should be stored, or derived when it's read.

About 4 min readQuickturn case study

In this page

  • What is CQRS, and how deep can it go?
  • How is a log with projections different from event sourcing?
  • When should a view be stored, and when derived?
  • What do projections cost, and who needs full event sourcing?

01The CQRS spectrum

Command-query separation distinguishes changing state from answering a question. CQRS extends that distinction to separate command and read models. It does not require two databases or event sourcing. A project can separate code paths, then add screen-shaped projections, without adopting every later step.

Quickturn's commands load, decide and commit. Queries read projections such as card memory state and learner totals. A projection is data prepared for a read need. This makes ordinary screens simple without a separate read database or command bus.

02A log is not event sourcing

An append-only log is not automatically event sourcing. In an event-sourced model, the event history is the authoritative record from which state is reconstructed, sometimes with snapshots. Quickturn normally reads stored current state and projections rather than reconstructing a round on every request.

Its review log records each answer and the card's before-and-after memory state. Related projections are updated in the same commit. The log supports rebuilding when a scheduler changes, tuning from past answers, and reproducing evaluations. Moving from Leitner boxes to FSRS can use that history without changing the system into a fully event-sourced one.

03Store it or derive it?

Current weak grammar points are derived from already-loaded card projections and catalog tags. Quickturn uses a smoothed miss rate, initially requiring three observed cards and a rate of 0.4 before ranking a point as weak. Those are tunable product values.

Storing the same result would add writes and backfills whenever the ranking rule changes, without saving a read if the underlying cards are already loaded.

A weakness trend over time has a different need: today's projection does not retain last month's result. That feature can justify a weekly weakness projection, updated on commit. Evidence from another activity might justify one too. Neither requirement alone demands event sourcing.

04What projections cost

Projections duplicate information and can drift if a write path omits an update. Contract tests and rebuild tools help detect and repair that problem. Atomic updates prevent partial success within a commit, but do not repair incorrect application logic or guarantee strongly consistent reads when the database read mode is eventual.

Updating through a queue keeps writes smaller but creates lag, retry work and stuck-queue monitoring. Quickturn favors synchronous projection updates for small learner-owned records. A large fan-out feed could make the opposite trade.

Full event sourcing adds long-lived event-schema compatibility, replay and snapshot management, and harder ad hoc queries. Audit-heavy systems may need those capabilities. Keep the log and projections that solve known problems before adding the rest.

Summary in three lines

  1. CQRS is a spectrum; most teams need separate reads from projections, not a second database.
  2. An append-only log with projections updated in the same commit keeps history without replaying it on every read.
  3. Derive a view from data you already load; store a projection when it needs history you don't keep.
