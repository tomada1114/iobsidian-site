Do we need event sourcing to keep the history?

After this page you can place CQRS and event sourcing on a spectrum and explain an append-only log with projections. You can also decide whether a view should be stored, or derived when it's read.

About 8 min readCoffee in the kitchen

In this page

  • What is CQRS, and how deep can it go?
  • How is a log with projections different from event sourcing?
  • When should a view be stored, and when derived?
  • What do projections cost, and who needs full event sourcing?

The kitchen. Leo is talking fast about something he read.

01The CQRS spectrum

L

Leo: I want to build a "weakness trend over time" screen. And I've been reading about event sourcing. We already keep every answer, so shouldn't we just switch to full event sourcing?

M

Maya: What do you think event sourcing is?

L

Leo: Keeping a log of events. Which we do. And CQRS means two databases, one for writes and one for reads.

M

Maya: Two ideas, both half right. Let's start with CQRS, because it's a spectrum, not a switch.

L

Leo: A spectrum?

M

Maya: It starts with command-query separation, from Bertrand Meyer. A method either changes state or answers a question. Never both.

L

Leo: So startRound changes things, and readHome only answers.

M

Maya: Right. Greg Young applied that idea to the whole model: CQRS. Commands go through one path, reads through another. And it has depths.

L

Leo: How many depths?

M

Maya: Let me draw four steps.

M

Maya: We sit at the second step. A command is a plain data object, handled in three steps: load, decide, commit. And every screen's query reads projections only.

L

Leo: What's a projection, exactly?

M

Maya: A read model: data shaped for a screen, kept up to date on every write. Like each card's memory state, or the learner's totals.

L

Leo: So "two databases" is just one depth of CQRS, not the definition.

M

Maya: Exactly. Most teams never need step three.

02A log is not event sourcing

L

Leo: And event sourcing is step four. We keep a log, so aren't we already there?

M

Maya: Here's the difference. Full event sourcing stores only events. To know a round's state, you replay every event for that round, applying them one by one from the start.

L

Leo: And we don't replay?

M

Maya: Not on a read. We keep an append-only review log, which means we only add to it and never change an entry. It holds every answer, with the card's memory state before and after.

L

Leo: And the projections?

M

Maya: Each card's memory state, the learner's totals, each day's tally. They're written in the same commit as the log entry.

L

Leo: Same commit, so they can't disagree.

M

Maya: Not within one commit. So a read is a key lookup, and it never lags behind. Let me put the two side by side.

L

Leo: Then why keep the log at all, if nobody replays it on reads?

M

Maya: For concrete reasons. First, when the scheduler changes: the part that decides when each card comes back. We started with simple Leitner boxes.

L

Leo: Leitner is the classic flashcard boxes, right? Get it right, move it up a box.

M

Maya: Yes. When we moved to FSRS, an open-source spaced-repetition scheduler, we replayed the log to rebuild every card's memory state.

L

Leo: And second?

M

Maya: Tuning the scheduler's parameters from real answers. And third, reproducing evaluations: rerunning old answers through a new version to compare.

L

Leo: So the log is for rebuilding and learning, not for everyday reads.

03Store it or derive it?

M

Maya: Now your screen. Where do the weak grammar points come from today?

L

Leo: I assumed there's a table of them.

M

Maya: There isn't. A pure function computes them when they're read: it only takes data in and returns a result. It uses the card projections the home screen already loads, plus the catalog's grammar tags.

L

Leo: Why not store them? It feels wasteful to compute every time.

M

Maya: Guess what storing would cost.

L

Leo: A write on every answer commit, to update the weakness numbers.

M

Maya: Yes. And a backfill every time we change the ranking rule, which means a job that recomputes the stored numbers for every learner. Without saving a single read, because we load those cards anyway.

L

Leo: What's the rule, roughly?

M

Maya: A miss rate per grammar point, smoothed so a few answers don't swing it too far. A point counts as weak once three cards have been seen and the rate reaches 0.4. We keep the top two.

L

Leo: Are those numbers fixed?

M

Maya: No, those are starting values; we tune them.

L

Leo: So when does storing win?

M

Maya: When a rule needs history the card projection doesn't keep. Here's the question as a picture.

L

Leo: A trend needs last month's numbers. The card projection only knows now.

M

Maya: Exactly. So your feature is a reason to add one projection: weakness per grammar point per week, updated on commit.

L

Leo: Not a reason to adopt event sourcing.

M

Maya: Right. Evidence from a second activity, like vocabulary, would be another reason to store one.

04What projections cost

L

Leo: Are projections free, then?

M

Maya: No. They duplicate data, so they can drift, which means they stop matching the log. If a commit path forgets to update one, it quietly goes wrong.

L

Leo: How do we catch that?

M

Maya: Contract tests on the store, a shared set of tests that every store adapter must pass. And rebuild tooling. The store can read the whole log in order, and a "rebuild projections" system job replays it.

L

Leo: So if one drifts, we rebuild it from the log.

M

Maya: Yes. That's one more reason the log is worth keeping.

L

Leo: Could we update projections later instead, from a queue? Then a commit stays small.

M

Maya: Many systems do that. Guess what the learner would see.

L

Leo: They answer a card, go back to the home screen, and the count hasn't moved yet.

M

Maya: Right. For a second or two, the screen shows old data. Then you need a way to hide that, and a way to catch a stuck queue.

L

Leo: So updating in the same commit trades a slightly bigger write for screens that never lag.

M

Maya: Yes. For one learner's small data, that's an easy trade. For a feed read by millions, you'd choose the queue.

L

Leo: And full event sourcing? What would it add?

M

Maya: More cost. Event versioning forever: old events never change, so the code must read every old shape of an event.

L

Leo: And what else?

M

Maya: Snapshots, saved copies of the state, so replays of long event streams stay fast. And ad hoc queries, the one-off questions you ask the data, get harder.

L

Leo: Why would anyone pay that?

M

Maya: Audit-heavy domains. Payments, ledgers. Systems that must answer "what was the state on day X" routinely.

L

Leo: A bank has to show a balance on any past date. We don't.

M

Maya: Right. So we took the log and the projections. We left out rebuilding state from events on every request, a separate read database and a command bus.

L

Leo: What's a command bus?

M

Maya: A shared layer that passes each command to its handler. We don't need that step. And projections in the same commit already make reads a lookup.

05Leo explains it back

M

Maya: Say the PM asks why the trend screen needs "a projection". What do you tell them?

L

Leo: CQRS is a spectrum. We separate commands from reads, and reads come from projections in the same table.

L

Leo: We keep an append-only log so we can rebuild projections and replay history when the scheduler changes. But we don't rebuild state from events on every request.

L

Leo: If a view can be computed from what we already load, like weak grammar points, we derive it. The trend needs history we don't keep, so it gets a projection.

M

Maya: And the risk?

L

Leo: Projections can drift. We have contract tests and a rebuild job for that.

M

Maya: You left out why not full event sourcing: it pays off for banks, which must show the state on any past day. Nobody here needs "the state on day X".

Summary in three lines

  1. CQRS is a spectrum; most teams need separate reads from projections, not a second database.
  2. An append-only log with projections updated in the same commit keeps history without replaying it on every read.
  3. Derive a view from data you already load; store a projection when it needs history you don't keep.
