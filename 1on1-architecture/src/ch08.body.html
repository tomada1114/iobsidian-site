Where does the logic go, if not in the handler?

After this page you can explain "functional core, imperative shell": load, decide, commit. You can say why expected failures are values, why time comes in as an argument, and what the pattern costs.

About 8 min readPairing at Leo's desk

In this page

  • How can a rule be tested without any mocks?
  • How do we handle failures and time?
  • Why does one command shape serve every caller?
  • What does the pattern cost?

Leo's desk. A long test file fills the screen.

01Load, decide, commit

L

Leo: I'm adding a rule to starting a round. My test mocks the store, the clock and the catalog. It's sixty lines, and it broke twice when I renamed things.

M

Maya: What's the rule?

L

Leo: If the learner already finished today's portion, the next round should be an "extra" round, not "today".

M

Maya: So it's one decision. How do the existing tests for starting a round work?

L

Leo: That's the thing. They have no mocks at all. I don't understand how they work without them.

M

Maya: Where do you think the logic lives?

L

Leo: In the handler? That's where I put mine. The handler reads the store, checks the portion, picks the kind.

M

Maya: That's why your test needs mocks. Starting a round is a command, one request that changes data. Let's look at how it's built: three steps.

M

Maya: The command function loads what the rule needs through ports. A port is an interface the application defines, like "load a round". An adapter implements it for one technology, like DynamoDB.

M

Maya: Then it calls a pure decide function in the domain package, with plain values. Pure means it only computes from its inputs and touches nothing outside.

L

Leo: Including "now"?

M

Maya: Including "now". Decide returns either the changes and the answer, or an expected failure. Then the command commits the changes in one write.

L

Leo: So the command is a thin shell around decide.

M

Maya: Right. Gary Bernhardt called this "functional core, imperative shell". Decisions in pure code, and side effects, like reads and writes, around the edge.

L

Leo: And my rule is a decision. So it belongs in decide.

M

Maya: Yes. And its test needs no mocks at all.

L

Leo: So my sixty lines become a few. "Portion finished, start a round, expect an extra round."

M

Maya: That's the test. Your rename wouldn't break it either, because it doesn't check which calls were made.

02Two kinds of failure

L

Leo: What happens when the rule says no? Like, the round doesn't exist.

M

Maya: That's an expected failure. The round wasn't found, or it's closed, or there aren't enough cards. Those are values of a Result type.

L

Leo: So decide returns either "ok, here's the result" or "error, round closed".

M

Maya: Yes. They're part of the function's signature, so a caller can't forget them. The API turns each one into a stable error code, like ERR_ROUND_CLOSED.

L

Leo: And when do we throw?

M

Maya: Only for bugs. A thrown error means something is broken, and there's nothing useful for a caller to do with it.

L

Leo: That's cleaner than my old job. We threw for everything, and every caller had a try-catch that guessed.

M

Maya: Now the second thing decide gets as an argument: time. Everything it needs from the world comes in. The time, generated ids, and the learner's own time zone and day-boundary hour.

L

Leo: Why the learner's time zone? Can't the server just use its own?

M

Maya: Guess what time zone a Lambda function runs in by default.

L

Leo: UTC?

M

Maya: UTC. So if decide read the process clock's zone, a Japanese learner's practice day would move by nine hours.

L

Leo: Tokyo is UTC plus nine. Their new day would start in the early afternoon.

M

Maya: Right. So each request carries the learner's time zone, and our day starts at 4 a.m. local time. Only the domain computes a practice day.

03One shape, many callers

L

Leo: Does this shape matter outside tests?

M

Maya: A lot. A command is plain data, plus a context that says who is acting. So the same function runs from anywhere.

L

Leo: From an HTTP request, obviously.

M

Maya: And from a queue worker that grades typed answers in the background. And from a tool the tutor agent calls on a learner's behalf.

L

Leo: The agent calls the same command as the web app?

M

Maya: The same one. Let me draw it.

L

Leo: What's in the context?

M

Maya: Who is acting. There are three kinds of actor: a learner, a system job, and an agent with explicit grants. Grants are a list of what the agent may do.

L

Leo: One per kind of entry point.

M

Maya: Exactly. The authorization check reads the actor, so an agent can only do what it was granted.

L

Leo: So if we add a new entry point next year, like a Slack bot for teachers, it's just a new adapter.

M

Maya: That's the payoff. The rules don't move.

04What it costs

L

Leo: This seems like it has no downside. What am I missing?

M

Maya: Three costs. First, decide can't fetch more data halfway. The shell has to load everything up front.

L

Leo: Even data a path doesn't need?

M

Maya: Sometimes. If one branch needs the catalog and another doesn't, we still load it. We pay a read to keep decide pure.

L

Leo: Couldn't we pass decide a small "fetch" function? Then it loads only what the branch needs.

M

Maya: Half right: it would save the extra read. But think about what decide becomes.

L

Leo: A function that does I/O through a callback. So it isn't pure anymore.

M

Maya: Right. Its tests need a fake fetch again, and it can fail halfway through, after deciding half the changes.

L

Leo: So we'd be back to mocks, just hidden behind a nicer name.

M

Maya: Exactly. Loading a bit too much is the cheaper mistake.

L

Leo: That's usually cheap, though. One learner's data is small.

M

Maya: For us, yes. Second, splitting a feature into load and decide takes practice. Your first instinct was the handler.

L

Leo: Yes, I did that. And the third?

M

Maya: The shell still needs its own tests. Contract tests check that each adapter does what its port promises. And a few end-to-end tests run the whole thing.

L

Leo: So "no mocks" means no mocks for the interesting logic, not no other tests.

M

Maya: Right. And when the logic is trivial, like saving a display name, a load-decide-commit split only adds steps that give nothing back.

L

Leo: So for plain CRUD, just write it directly.

M

Maya: Yes. Mark Seemann calls the same idea the "impureim sandwich": impure, pure, impure. It pays when there's something worth putting in the middle.

L

Leo: My rule is worth it. It's exactly the kind of thing the product team will change again.

M

Maya: Then put it in the middle of the sandwich.

05Leo explains it back

M

Maya: A new teammate writes a sixty-line mock test tomorrow. What do you tell them?

L

Leo: Every decision goes into a pure decide function. The command is a thin shell: it loads, calls decide, and commits.

L

Leo: Expected failures come back as values, like "round closed". Bugs throw.

L

Leo: Time, ids and the learner's time zone are arguments. That's why a test can say "it's 3:59 a.m. in Tokyo".

M

Maya: And why does the shape matter beyond tests?

L

Leo: The same command runs from HTTP, a queue worker or an agent tool. Only the actor in the context changes.

M

Maya: One piece is missing: what it costs. The shell loads everything up front, and it still needs its own tests.

Summary in three lines

  1. Keep decisions in a pure decide function, and let a thin shell load and commit around it.
  2. Return expected failures as values, throw only for bugs, and pass time and time zones in as arguments.
  3. One command shape serves HTTP, workers and agent tools; the cost is loading up front and testing the shell.
