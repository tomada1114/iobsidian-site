Why not split it into microservices?

After this page you can explain why a bounded context is not the same as a service. You can also say what a modular monolith gives a small team, and how to keep extracting a service later cheap.

About 8 min readA video call

In this page

  • What is a bounded context, and what are ours?
  • How do contexts live together in one deployable?
  • Why not microservices now?
  • What does the monolith cost?

A video call. Leo is working from home today.

01Boundaries for a model

L

Leo: I read a post last night about a startup that moved to microservices. It made me wonder. Should we split identity, the catalog and practice into separate services before the team grows?

M

Maya: What would you expect to gain?

L

Leo: Clean boundaries. Every serious system seems to use microservices. And a monolith turns into code where everything depends on everything, right?

M

Maya: You're mixing two ideas there. Let's separate them. What's a bounded context?

L

Leo: A boundary around part of the system. So... a service?

M

Maya: That's the common mix-up. A bounded context is the boundary inside which a model and its words stay consistent. It says nothing about how you deploy it.

L

Leo: So a context could be a folder, a package or a service.

M

Maya: Exactly. Want to list ours?

L

Leo: Identity, the catalog, practice. What else?

M

Maya: Identity is who the learner is: their time zone and languages. The catalog is the reviewed cards, grammar tags and levels, and it's read-only. Practice owns rounds, portions, placement, levels and deck composition.

L

Leo: And the review log?

M

Maya: That's the learning record: the append-only log of answers and each item's memory state. We only add to the log, and the memory state says when a card is due again. Then the learner model, which ranks weak grammar points.

L

Leo: I'm counting five so far.

M

Maya: Four more. Engagement keeps streaks and a daily goal across activities, and vocabulary practice is its own activity. Assessment is the LLM grading. Entitlements keeps a usage ledger, a record of how much each learner uses.

L

Leo: That's nine contexts in one codebase. How do they share data?

M

Maya: They don't share structures. They reference each other's items only by id, like "card 42" or "round abc". Never by passing one context's object into another.

02A map, and one deployable

M

Maya: A context map shows how contexts relate. Let me draw the part around the learning record.

L

Leo: And identity sits above all of them?

M

Maya: Upstream of everyone, yes, meaning the others depend on it. The learner model also reads the catalog, and the catalog is read-only for all.

L

Leo: Where do they run, though?

M

Maya: In one codebase, deployed as an API function plus a worker function for background jobs. Both are built from the same packages.

L

Leo: So calls between contexts are function calls.

M

Maya: Function calls, one deploy, one set of logs. That's a modular monolith: one deployable, meaning one thing we build and ship, with modules that keep their boundaries.

L

Leo: What stops practice from reaching into the learner model's private files?

M

Maya: Honest answer: the fences a machine checks are between layers, the domain, application, adapter and contracts packages. Lint and a test reject an import that crosses a layer the wrong way. Inside those layers, each context is a module with a public surface.

L

Leo: A public surface meaning the functions other contexts are allowed to call?

M

Maya: Yes. Other contexts go through it. And each stored key names its kind of item, like a round or a card's memory.

03Why not microservices now

L

Leo: So why not take the next step and make each context a service? The boundaries already exist.

M

Maya: Let's look at what changes when a function call becomes a network call. Guess first.

L

Leo: It gets slower?

M

Maya: That's the smallest part. Every cross-context call gets its own failures, retries and versioning. Let me put the two side by side.

L

Leo: And deployment, monitoring and permissions multiply per service.

M

Maya: Right. The usual reasons to pay that are independent scaling, and separate teams owning separate services. Do we have either?

L

Leo: We have a handful of engineers. And the traffic is small enough for one function.

M

Maya: So network boundaries would give us nothing. We wrote that down as an explicit non-goal, a thing we chose not to do.

L

Leo: But what if we grow? Wouldn't splitting later be a huge rewrite?

M

Maya: That's the real question, and we plan for it. A command is a request to change something, like "start a round". Ours are plain data, validated at the edge, where a request enters the system.

M

Maya: And handlers keep a standard request-to-response signature.

L

Leo: And contexts only talk through public surfaces.

M

Maya: Yes. So promoting one context to its own service later is mostly packaging, not a rewrite.

L

Leo: Martin Fowler's "monolith first", right?

M

Maya: That's the idea. Start with one deployable, learn where the real seams are, then split where it pays. A seam is a place where the code can be cut apart cleanly.

04What the monolith costs

L

Leo: Okay, let me push back. What's bad about our setup?

M

Maya: Two things. It needs discipline, because nothing physical stops a shortcut import between contexts. And one bad deploy takes everything down.

L

Leo: How do we keep the discipline, then? Code review?

M

Maya: Partly. My guess is you'd say "more rules in lint".

L

Leo: That was exactly my next sentence.

M

Maya: Half of it works. Lint guards the layers well.

M

Maya: Inside a layer, what helps most is making the right path the easy one. Every context has one obvious entry file, and names that say who owns what.

L

Leo: So a shortcut import looks strange in a diff, because it skips the entry file.

M

Maya: Yes. Reviewers and agents both notice what looks strange. A second protection is the data: each stored key names its kind of item, like a round.

L

Leo: So even the database shows what's being touched.

M

Maya: Right. When practice code reads a kind of item it doesn't own, it stands out in a diff.

L

Leo: Couldn't we just fence every context from day one? Then shortcuts would be impossible.

M

Maya: Fencing too early costs too. Here's a real example. We kept streaks and points inside practice until the vocabulary activity existed.

L

Leo: Why wait? A daily goal sounds like its own thing.

M

Maya: Because with only one activity, designing a cross-activity daily goal would have been guessing. We had nothing to test the design against.

L

Leo: And once vocabulary arrived?

M

Maya: Then engagement became its own context. It had a second user, so we could see what it really needed.

L

Leo: So you fence a context when a second user shows up.

M

Maya: That's a simple rule we use. Before that, you're drawing a boundary from imagination.

L

Leo: What happens to teams that split into services first?

M

Maya: Often they rebuild a distributed monolith: services that must all deploy together because they share assumptions. All the network costs, none of the independence.

L

Leo: That's the worst of both.

M

Maya: It is. Conway's law is behind a lot of it: systems end up shaped like the teams that build them. One small team tends to build one system well.

05Leo explains it back

M

Maya: Someone in the next review says "we should be on microservices". What do you say?

L

Leo: A bounded context is a boundary for a model and its words. It isn't necessarily a service.

L

Leo: We keep our contexts as modules in one deployable, plus a worker. Calls between them are function calls, with one deploy and one set of logs.

L

Leo: Network boundaries would give us nothing at our size. We keep extraction cheap with plain-data commands and public surfaces.

M

Maya: And when do you add a fence?

L

Leo: When a context gets a second user, like engagement did with vocabulary. Not before.

M

Maya: You left out the cost: it takes discipline, and one bad deploy hits everything. At our size, that's still cheaper than retries on every call.

Summary in three lines

  1. A bounded context is a boundary for a model and its words, not a deployment unit.
  2. A modular monolith keeps contexts as modules with public surfaces in one deployable, so calls stay function calls.
  3. Split into services when scaling or team ownership demands it, and fence a context once it has a second user.
