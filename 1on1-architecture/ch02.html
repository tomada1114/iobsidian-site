If the rules can't touch the database, who saves?

After this page you can explain how classic layering makes the rules depend on the database, and how dependency inversion flips it. You can also say when plain layering is the better choice.

About 8 min readPairing at Leo's desk

In this page

  • What goes wrong when the rules import the database code?
  • How does inverting the dependency fix it?
  • How do we make sure nobody breaks the rule?
  • When is plain layering simpler and good enough?

Leo's desk. A domain file is open on his laptop.

01The layers everyone learns first

L

Leo: Maya, lint just refused my import. I wanted the domain package, where our drill rules live, to save the round with the DynamoDB client.

M

Maya: What were you trying to do?

L

Leo: The round finishes, so I thought the rule could just save itself. Why aren't the rules allowed to save their own data?

M

Maya: Before I answer, how did you learn layers at your old job?

L

Leo: Top calls down. Pages call the business logic, the business logic calls the data layer, the data layer talks to the database.

M

Maya: That's classic N-tier, or layered, architecture. Let me draw it the way you described it.

L

Leo: That looks normal to me. It's easy to explain to anyone.

M

Maya: It is, and for simple apps it's fine. Now look at where the business logic's arrow goes.

L

Leo: Down into data access. So the rules import the data layer.

M

Maya: And what does that mean for testing a rule?

L

Leo: I'd need a database, or a mock of the data layer. Oh. And if the database changes, the change spreads up into the rules.

M

Maya: That's the problem in one sentence. Here's a small story. Our first prototype ran on one laptop with a local SQL database.

L

Leo: Before DynamoDB?

M

Maya: Yes. But the rules were already plain functions that didn't know about SQL. So when we moved to DynamoDB, we rewrote the storage code and didn't touch the rules.

02Flip one arrow

L

Leo: So how do the rules get saved, if they can't call the database?

M

Maya: Guess first. What would you do?

L

Leo: Maybe the domain returns what should change, and some other layer writes it?

M

Maya: Exactly the first half. The second half: that writer only knows an interface, and the interface belongs to the inner side.

L

Leo: The inner side owns the interface? I'd have put it next to the database code.

M

Maya: That's the key move. It's called the dependency inversion principle, the "D" in Robert C. Martin's SOLID.

L

Leo: I know the letters. I never knew what the D actually meant.

M

Maya: High-level policy, like our rules, shouldn't depend on low-level detail, like the database. Both depend on an abstraction, an interface, and it belongs to the high-level side. Let me draw both versions.

M

Maya: At Quickturn the application package declares a learner store interface. Read a round, read today's portion, commit a set of changes.

L

Leo: And the adapters package implements it. That's the code that talks to real tools, right?

M

Maya: Right, and it implements it twice. Once for DynamoDB, once in memory for fast tests. The HTTP app wires the real one in at startup.

L

Leo: So the domain doesn't even see the interface? It's in the application package?

M

Maya: Right. The domain has no interfaces to I/O at all. It takes plain values and returns decisions. The application loads, asks the domain, and commits through the store.

L

Leo: So "who saves" has a clear answer. The application asks, the adapter writes, and the rule just decides.

03Enforced, not just drawn

L

Leo: Okay, but an arrow on a whiteboard doesn't stop anyone. What stopped me today?

M

Maya: Two checks. The domain package imports nothing outside itself. No workspace package, no npm library, no Node built-in.

L

Leo: Not even the date library?

M

Maya: Not even that. Time, time zones and randomness arrive as arguments. That's also why a test can say "it's 3:59 a.m." without waiting.

L

Leo: And the checks?

M

Maya: A lint rule refuses the import. That's what caught you. A separate test scans the import graph, the map of who imports whom, and each package's declared dependencies.

L

Leo: Why both? The lint rule was enough for me.

M

Maya: Because a lint rule can be deleted in one line. If that happens, the test still fails the build. A boundary that only one check holds is a boundary one edit removes.

L

Leo: Can you draw the rule on its own, without our package names?

M

Maya: Sure. Here it is, stripped down to three plain layers.

L

Leo: So the whole difference is the direction of the bottom arrow.

M

Maya: Yes, and that one direction decides what you can test alone, and what a storage change touches.

04When plain layering wins

L

Leo: Let me push back. Isn't this too many extra steps? I just wanted to save a round.

M

Maya: It does cost something. You write an interface, a composition step that wires the real implementation in, and some mapping between shapes.

L

Leo: So for every store, three extra things.

M

Maya: Roughly. And a cost people forget: reading the code. You jump from the command that handles the request to the interface, then search for the implementation.

L

Leo: My guess is that the mapping is the worst part. Converting shapes at every step.

M

Maya: Half right. Mapping hurts when you copy data into new shapes at each layer. We avoid most of it: our domain types pass straight through, and the one mapping sits at the HTTP edge.

L

Leo: So the real cost is the interface and the wiring, not endless conversions.

M

Maya: For us, yes. Teams that add a copy per layer pay much more.

M

Maya: Now think of a small admin tool whose "rules" are just the database schema. Create, read, update, delete.

L

Leo: There's nothing to test alone. The logic is the table.

M

Maya: Right. There, plain layering is simpler and fine. Some teams even use relaxed layering, where a layer may skip the one below and call further down.

L

Leo: That sounds messy.

M

Maya: It's a trade. Strict layering is cleaner; relaxed layering is less typing. For a CRUD tool, less typing often wins.

L

Leo: Then when is inversion worth it?

M

Maya: Three signs. The rules are worth testing alone. The storage will change. Or several clients share the rules.

L

Leo: We have all three. Streak and level rules, a move from SQL to DynamoDB, and web plus two native apps.

M

Maya: That's why we pay for it here. If only one sign applied, I'd think harder.

L

Leo: And what goes wrong if a team inverts everything, even the CRUD parts?

M

Maya: They get interfaces with one implementation each, and every change touches the interface too. The structure starts to cost more than it saves.

L

Leo: So the question isn't "is inversion good". It's "are these rules worth protecting".

M

Maya: That's the question I ask in every review.

05Leo explains it back

M

Maya: A new teammate hits the same lint error tomorrow. What do you tell them?

L

Leo: I'd say in plain layering the rules depend on the database. So you can't test them alone, and storage changes leak into them.

L

Leo: Dependency inversion flips that. The application side owns the store interface, and the DynamoDB code implements it. The arrow points inward.

L

Leo: The domain doesn't save anything. It decides; the application commits through the interface.

M

Maya: And why couldn't they just disable the lint rule?

L

Leo: Because a separate test checks the same direction. We check it twice, on purpose.

M

Maya: You left out the cost: an interface and its wiring. It's worth paying here because our rules deserve tests of their own. For a CRUD tool, plain layers are enough.

Summary in three lines

  1. In classic layering the business rules depend on the database, so they can't be tested or changed alone.
  2. Dependency inversion lets the rules' side own the interface and makes the storage code implement it.
  3. Inversion costs an interface and wiring; pay it when the rules are worth protecting, not for plain CRUD.
