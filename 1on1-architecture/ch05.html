Isn't DDD just another architecture style?

After this page you can explain that domain-driven design answers "where are the boundaries and what do the words mean". Clean and hexagonal architecture answer "which way do dependencies point". You can also say how much of DDD a small team needs.

About 8 min readAfter the design review

In this page

  • What are the two halves of DDD?
  • Why does a shared language matter so much?
  • How do DDD and clean architecture fit together?
  • How much tactical DDD does a small team need?

After the Tuesday design review. The room is emptying.

01Two halves of DDD

L

Leo: That was a strange ten minutes. The PM kept saying "session", and a teammate who works on sign-in kept answering about login.

M

Maya: What did the PM mean?

L

Leo: One round of cards. The sign-in teammate heard "login session" and started talking about token expiry.

M

Maya: So two smart people argued for ten minutes, and each one meant something different by the same word.

L

Leo: Is that why people say "do DDD"? And honestly, is DDD an alternative to Clean Architecture?

M

Maya: What do you think DDD is?

L

Leo: A folder structure. Entities, repositories, services. A rival to clean.

M

Maya: That's the most common picture, and it's only a small part. People usually split DDD into two halves, and Eric Evans's original book covers both.

L

Leo: Two halves?

M

Maya: Strategic design and tactical design. Strategic is about boundaries and words: bounded contexts, a shared language, and a map of how contexts relate. A bounded context is a part of the system where each word has one fixed meaning.

L

Leo: And tactical is the entities and repositories?

M

Maya: Yes. Entities, value objects, aggregates, repositories, domain events. Building blocks inside one boundary.

L

Leo: I know entities and repositories. What are the others?

M

Maya: A value object is a small value with no id of its own, like a 30-second time limit. An aggregate is a group of data that one write must keep correct together. A domain event records that something happened, like "round finished".

L

Leo: Which half matters more?

M

Maya: For a small team, most of the value is strategic. Today's review is a good example: no repository class would have saved those ten minutes. Let me put the two halves side by side.

02One word everywhere

M

Maya: The strategic idea behind today's mess is the ubiquitous language. One set of words shared by product, design and code.

L

Leo: "Ubiquitous" meaning it's used everywhere?

M

Maya: Everywhere. In conversation, in specs, and in type names. Let's list ours. What's a round?

L

Leo: A short deck of cards. There are kinds: placement, today, yesterday and extra.

M

Maya: And a portion?

L

Leo: The daily amount that keeps a streak going. Placement is the first round, the one that sets your level.

M

Maya: The review log is every answer, append-only, so we only add to it. An item's memory state says when a card is due again. And the learner model ranks weak grammar points from the answers.

L

Leo: And "session"?

M

Maya: Banned inside practice. It's ambiguous, as you saw today. The vocabulary activity has its own sessions, but that lives in its own context, where the word has one meaning.

L

Leo: So the same word can mean different things in different contexts, as long as each context is strict.

M

Maya: Exactly. That's what "bounded" means in bounded context. Now, the important part: the words are the type and function names.

L

Leo: Like decideStart and decideAnswers.

M

Maya: Right. When the PM says "start today's round", you can find that sentence in the code. Let me draw one word's journey.

L

Leo: So the fix for today is boring. Agree on words and make the code use them.

M

Maya: Boring and powerful. Most design arguments I've seen were two meanings of one word.

03Two different questions

L

Leo: Okay, so where does clean architecture fit?

M

Maya: It answers a different question. DDD decides boundaries and words. Clean or hexagonal decides which way the code depends, inside and between those boundaries.

L

Leo: So they don't compete.

M

Maya: No. Let me put them on two axes, and you tell me what each corner looks like.

L

Leo: Bottom right is a clean codebase where "session" means three things.

M

Maya: I've seen it. The arrows are perfect, and nobody can tell what a class is for.

L

Leo: And top left is a great language inside a tangled codebase. Every class has a clear name, but the rules import the database.

M

Maya: Right. So in the interview, when they ask how DDD differs from clean, what do you say?

L

Leo: DDD is about modeling the problem and cutting it into contexts. Clean is about arranging code so the model doesn't depend on technology. And they combine.

M

Maya: That's the answer.

04How much tactical DDD?

L

Leo: So why not do the full tactical part too? Entity classes, a repository per aggregate, a domain event bus.

M

Maya: Full tactical DDD is heavy. It pays off in large, complex domains with many teams. Think of an insurance company, or a bank's lending rules.

L

Leo: And us?

M

Maya: We took strategic DDD and a thin slice of tactical. Aggregates only as consistency boundaries, to decide what one write must check.

M

Maya: Plain data and pure functions instead of classes. A pure function only computes a result from its inputs. It doesn't read or save anything.

L

Leo: Wait. Isn't that the anemic domain model? Data without behavior. I read that's an anti-pattern.

M

Maya: Martin Fowler named it, yes. Half right: we do have data without methods. But look at where the rules live.

L

Leo: In the domain package, as functions next to the types.

M

Maya: Right. The anti-pattern is rules that move out of the domain and end up scattered across many services. It isn't the absence of classes.

L

Leo: So if the streak rule were in the API handler, that would be anemic. Having it in a pure function beside the type is fine.

M

Maya: Exactly. What matters is that there's one home for each rule, and it's inside the domain.

L

Leo: But without classes, what stops someone from building a broken round by hand? Anyone can create the object.

M

Maya: Nothing does, and that's the real cost. A class can hide its fields so only its methods change them. Plain data can't.

L

Leo: So what do we rely on instead?

M

Maya: Three things. The decide functions are the only place that produces changes. Types narrow what's possible, like a round kind that can only be one of four words. And tests cover every decide function.

L

Leo: That sounds like discipline more than a guarantee.

M

Maya: It is. We chose discipline plus types because the code stays short. An agent or a new hire finds the rule in one place. A bigger team might choose classes.

L

Leo: What would make you add the heavier parts?

M

Maya: Several teams working in one context, or rules that must be enforced by an object hiding its fields. We don't have either.

L

Leo: And an event bus?

M

Maya: Only when many listeners need to react to one thing without the writer knowing them. Today our writers know exactly what they update.

05Leo explains it back

M

Maya: The PM asks you tomorrow what DDD has to do with the "session" mix-up. What do you say?

L

Leo: DDD tells us where to draw boundaries and which words mean what inside them. "Session" meant two things, so we banned it in practice.

L

Leo: Our words, like round, portion and placement, are the names in our code, so a PM's sentence maps onto it.

L

Leo: Clean or hexagonal is a different question: which way the code depends. We use both.

M

Maya: And the tactical half?

L

Leo: We use a thin slice: aggregates as consistency boundaries, with plain data and pure functions instead of classes.

M

Maya: Careful with "instead of classes": that doesn't make it anemic, because the rules still live in the domain. Anemic means rules outside the domain, not a missing class.

Summary in three lines

  1. DDD's strategic half decides boundaries and a shared language; its tactical half gives building blocks inside one boundary.
  2. Clean and hexagonal answer a different question, which way code depends, so a system usually uses both.
  3. A small team gets most of DDD's value from the strategic half and a thin tactical slice.
