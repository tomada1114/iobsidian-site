Can an LLM return a type instead of a paragraph?

The learner needs readable feedback, but the application needs a verdict and known error tags. Separate fields let code check shape without treating prose as instructions.

01Why free text breaks

Parsing a grade from “the first line” fails when a model adds a greeting, changes a label or merges fields. Quickturn needs a verdict and error tags for code, plus feedback for the learner. Those should be separate fields, not conventions hidden in prose.

02Constrained output

Structured output supplies a supported JSON schema to constrain the response shape. The prompt still defines meaning, such as the difference between correct and acceptable. Quickturn derives the output schema from its typed Grade definition.

const Verdict = z.enum([
  "correct", "acceptable",
  "incorrect",
]);
const Grade = z.object({
  verdict: Verdict,
  errorTags: z.array(ConceptId),
  feedback: z.string(),
});

The adapter converts that definition to the supported JSON Schema subset and parses the result. Error tags use known concept IDs so “wrong tense” and “tense error” do not become unrelated categories. Support depends on model and API, and truncation or unsuccessful response status still needs handling.

03Validate again anyway

A schema establishes shape, not truth. A well-formed reply may refer to a nonexistent concept, use the wrong feedback language or contradict its verdict. Quickturn checks those domain constraints after parsing and returns a typed task failure when they do not hold.

Retries are bounded. A persistently invalid grade remains ungraded rather than becoming a fabricated success. Feedback is displayed as text and is never used as executable code or as a machine decision hidden in free-form wording.

04What a tight schema costs

An excessively narrow label set can force a poor answer into the wrong category. Human disagreement with recurring “correct but unexpected” cases can justify an acceptable category or revised rubric. Flat schemas are easier to inspect than deeply nested responses.

Invoice extraction illustrates the same design: typed net, tax and total fields allow a separate arithmetic check. A schema makes errors detectable; domain checks and evaluations decide whether the values make sense.

Summary in three lines

  1. Ask for output that matches a schema, built from the same definitions as the API contract.
  2. Parse the response and check domain rules; a schema-conforming value can still be wrong.
  3. Typed fields drive decisions, while feedback remains text to display safely.
