Can an LLM return a type instead of a paragraph?

After this page you can explain structured output, and why a schema in the request still needs validation afterwards. You can also say where free text is allowed in the code, and where it never goes.

01Why free text breaks

L

Leo: I asked the model for the verdict on the first line, then the feedback. Most replies were fine.

M

Maya: Most?

L

Leo: One started with "Sure! Here is my assessment." My parser read that as the verdict and broke.

M

Maya: What was your plan to fix it?

L

Leo: Ask more firmly for JSON in the prompt, and wrap JSON.parse in a try/catch.

M

Maya: That's what most people try first. It works often, and fails in ways you won't see coming.

L

Leo: Like what?

M

Maya: The model adds a greeting. It renames a label, "verdict" becomes "result". Or it merges two fields into one sentence.

L

Leo: So parsing prose is guessing.

M

Maya: Right. And look at what you're really asking for. A grade, error tags, and an explanation.

L

Leo: Three things.

M

Maya: With three different readers.

L

Leo: Which readers?

M

Maya: The learner model, our record of each learner's weak grammar points, reads the grade and the tags. The screen shows the explanation. The logs keep all of it.

L

Leo: And none of them wants "Sure! Here is my assessment."

M

Maya: Let me put the two kinds of reply side by side, for the same answer.

02Constrained output

L

Leo: So how do we get the right column?

M

Maya: Structured output. The request carries a JSON schema, and the model's output is constrained to match it.

L

Leo: Constrained, not just asked?

M

Maya: Constrained. On Bedrock's Converse API, you pass the schema as a JSON schema text format. The output follows it, unless it's cut off by the max tokens limit.

L

Leo: Then the prompt doesn't need to mention the format at all?

M

Maya: It still should. The schema fixes the shape. The prompt explains the meaning, like when an answer counts as "acceptable" rather than "correct".

L

Leo: So the schema says which boxes exist, and the prompt says how to fill them.

M

Maya: Right.

L

Leo: Where does our schema come from? Do we write JSON Schema by hand?

M

Maya: No. We already describe the API contract with zod, in the contracts package. The grading output is defined there too.

L

Leo: What does it look like?

M

Maya: A simplified version. The feedback is in the learner's first language:

const Verdict = z.enum([
  "correct", "acceptable",
  "incorrect",
]);
const Grade = z.object({
  verdict: Verdict,
  errorTags: z.array(ConceptId),
  feedback: z.string(),
});
L

Leo: And ConceptId is something like en:grammar/present-perfect?

M

Maya: Exactly that format.

L

Leo: Why ids? A phrase like "wrong tense" is easier to read.

M

Maya: For a person, yes. But the learner model counts weaknesses across hundreds of answers. "Wrong tense", "tense error" and "past vs perfect" would be three different weaknesses.

L

Leo: And one id is one weakness, however the model phrases it.

M

Maya: That's why. The zod schema is converted to JSON Schema for the request. One definition, used in both places.

L

Leo: So if someone adds a verdict value, the request's schema and our checks change together.

M

Maya: Right. The prompt still needs a line saying what the new value means. Here's the whole path of one grading call.

L

Leo: Does this work with the Japan profiles and batch?

M

Maya: Yes. As of September 2026 it works with cross-region inference, batch and streaming. A tool's input schema is another way to get structured output.

03Validate again anyway

L

Leo: If the output is constrained, why the fourth step? It already matches the schema.

M

Maya: A schema guarantees shape, not meaning. Give me three ways a valid reply can still be wrong.

L

Leo: Hmm. A tag that isn't in our grammar list.

M

Maya: One. It's a string in the right format, but no such concept exists.

L

Leo: Couldn't the schema list every allowed id?

M

Maya: In theory. But the grammar list is long and grows. A huge enum makes the schema heavy, so we check ids against the list in code.

L

Leo: Feedback in English, when the learner's first language is Japanese.

M

Maya: Two. And the third is subtler.

L

Leo: A verdict of "correct", with error tags attached?

M

Maya: Three. Valid JSON, and it contradicts itself. The adapter parses with zod, then checks those domain rules.

L

Leo: And if a check fails?

M

Maya: It becomes a typed LLM error. Never an exception thrown deep inside the domain.

L

Leo: And what does the learner see then?

M

Maya: The grading job is retried. If it keeps failing, the answer stays ungraded. No verdict is better than a wrong one.

L

Leo: So where exactly is free text allowed?

M

Maya: Only in the outer ring. Let me draw the layers.

L

Leo: The feedback is free text, though. It reaches the learner.

M

Maya: It reaches the screen, as a field to display. No code decides anything based on what it says.

L

Leo: So the rule is: free text never crosses into domain code.

M

Maya: That's the rule.

04What a tight schema costs

L

Leo: Then make the schema as strict as possible?

M

Maya: Careful. A tight schema can lower quality. An enum that's too narrow forces a wrong label.

L

Leo: Like having only "correct" and "incorrect"?

M

Maya: Exactly. An answer that's fine but unusual gets forced into one of them. That's why we have "acceptable".

L

Leo: How would we notice an enum is too narrow?

M

Maya: When people review graded answers and keep disagreeing with one label. If reviewers often write "right, but not the way we expected", a value is missing.

L

Leo: And big nested schemas?

M

Maya: Harder for the model to fill well. So keep it flat, and leave one free-text field for the learner to read.

L

Leo: Has a schema ever saved a real bug?

M

Maya: At my last company, an invoice-extraction service read totals from prose output. Once it put the tax into the total, and nobody noticed.

L

Leo: Silent.

M

Maya: They moved to a schema with separate typed fields: net, tax and total. Then a check that net plus tax equals the total.

L

Leo: And when it didn't add up?

M

Maya: The job was rejected and retried. A silent error became a visible, retryable one.

L

Leo: Did many jobs fail that check?

M

Maya: A few at first, and each one was a total that would have been wrong on a customer's bill. Before, nobody could even count them.

05Leo explains it back

M

Maya: How would you describe the grader to someone joining the team?

L

Leo: I treat it like a function with a return type. Its schema comes from the same zod we use for the API.

L

Leo: The model is constrained to that schema, and we validate again, because shape isn't meaning.

L

Leo: Only typed fields reach the domain. The feedback is text to show, never text to decide on.

M

Maya: And a failure?

L

Leo: A typed LLM error from the adapter, not an exception in the domain.

M

Maya: One limit on strict schemas. If a real answer has no fitting label, the fix is a new enum value, not a stricter prompt.

Summary in three lines

  1. Ask for output that matches a schema, built from the same definitions as the API contract.
  2. Validate again, because a schema guarantees shape but not meaning.
  3. Only typed fields reach domain code; free text stays at the edge, for people to read.
