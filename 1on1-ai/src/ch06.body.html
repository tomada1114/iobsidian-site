Should the timed drill wait for the grader?

A learner answers before the timer ends, but the model is still waiting. Saving practice first lets the drill continue while grading has its own failure path.

01The hot path

A model call in the timed card path makes each answer depend on external latency. Streaming feedback does not remove the wait for a complete verdict. Offline answers also arrive later, so synchronous grading cannot be the only successful practice path.

Quickturn records the answer immediately and grades it in the background. The summary and recap show the result when it is ready, while the drill continues.

02The job and its key

A grading job key combines answer ID and rubric version. The first accepted result is stored conditionally; duplicate deliveries and retries reuse it. A new rubric version creates a distinct grading job without erasing the previous result.

Two workers can still call the provider before one wins the conditional result write. Result deduplication protects the learner-visible effect, while attempt coordination and accounting must handle any duplicate provider cost. The UI represents the grade as pending until a result or final failure is known.

03Where it runs

The job function can run inline locally and from an SQS-triggered worker in the hosted system. Standard queues can redeliver messages, so the stable key is part of normal behavior. Repeated failures move to a dead-letter queue for diagnosis and controlled replay.

A cost reservation is made before the call. Replaying a message must reuse the relevant job identity and settlement state. The saved answer remains available even when grading fails.

04What grading later costs

Background grading adds a queue, worker, result storage and pending UI states, and sacrifices immediate feedback on the card. A direct explanation request may reasonably wait synchronously because the learner has explicitly asked for it.

One call per round reduces call count but enlarges output and the failure unit. Per-answer calls isolate failure and retry. Compare measured cost, latency and recovery rather than choosing from request count alone. Keeping AI classification out of ticket creation is a similar way to preserve a core workflow during model outages.

Summary in three lines

  1. Keep model calls off a timed path; store the answer and grade it as a background job.
  2. Key the job by answer id and rubric version, and store the first result under that key.
  3. Reuse a stored accepted result for matching retries; coordinate unfinished attempts and reconcile any duplicate provider cost.
