When an agent acts for a learner, whose rights does it use?

A tutor wants to inspect weak points. The operation’s arguments can choose a query, while verified identity must choose whose protected records it may reach.

01The confused deputy

A tool that trusts getWeakPoints(learnerId) without checking ownership lets model arguments choose the owner of protected data. An attacker who influences the model can then ask a more privileged deputy to act for a different learner.

Quickturn removes that identity argument. The learner comes from a verified session, while the model supplies only the operation's permitted data.

02The identity chain

The inbound authorizer validates the token under configured issuer, client, audience and scope rules. The verified identity must then travel through Runtime, Gateway and the target on a trusted path.

Application authorization distinguishes learner, system and agent actors. An agent's operations are limited by explicit grants and the learner's own authority.

Tests inspect exposed input schemas for learner identifiers and exercise target-side ownership. An intermediate IAM signature authenticates a workload, not automatically the human learner. Confirm the actual claim propagation and revalidation requirements before building tools on that assumption.

03Memory and the system of record

Conversation memory stores session events and summaries under identifiers with enforced access rules. Quickturn's learning record stays in DynamoDB so dealing cards is reproducible, progress works without an agent, and export and deletion remain coordinated.

The agent reads progress through query tools and changes it only through granted commands. Namespace names help organize memory, but policy enforcement and trusted identifier binding create the isolation boundary.

04Costs, and the subtle part

Narrow tools require ongoing curation and may refuse useful requests, such as changing a daily goal. The tutor can direct the learner to the settings screen instead. That limitation is deliberate.

An identity propagation experiment is worthwhile because a wrong assumption affects every tool. Decode claims only within a specifically trusted, already verified path. An untrusted entry point must verify them or it can accept a forged claim. A deputy should act within the requester's rights plus explicit task limits, rather than lend its own administrative authority.

Summary in three lines

  1. No tool takes a user id; the user comes from the verified session.
  2. An agent is its own actor, acting for one user with grants no wider than theirs.
  3. Agent memory holds the conversation; the app's database stays the system of record.
