Where do evals run: in CI, at night or in production?

After this page you can explain the three places an evaluation runs, and what each one catches. You can also explain when a model can judge another model, and how production failures become tests.

A video call. Both look at the required checks on Leo's pull request.

01The pre-merge gate

L

Leo: If evals call the real model, do they run on every pull request? CI would get slow, flaky and expensive.

M

Maya: They don't. Look at the checks on your pull request. What do you see?

L

Leo: Unit, contract, isolation, infrastructure synthesis and smoke tests. They're all required.

M

Maya: And they use fakes and recordings for the model. No real calls, no cost.

L

Leo: So when does the real model run?

M

Maya: Only when a pull request changes a prompt, an output schema or the model configuration. A path filter picks those out.

L

Leo: And then it runs the whole suite?

M

Maya: A small subset, under a spend cap.

L

Leo: Picked at random?

M

Maya: Chosen on purpose: past failures, attacks, and the borderline answers that flip. Random cases would mostly be easy ones.

L

Leo: Couldn't I just run the eval on my laptop and paste the numbers into the pull request?

M

Maya: Then nobody can repeat it, and nobody knows which prompt you ran. The gate runs the committed code and records the result.

L

Leo: Here's the path, then?

M

Maya: Here it is.

L

Leo: Why a baseline, and not a target like "90% agreement"?

M

Maya: A target says nothing about whether this change made things worse. The baseline is what the current prompt scores.

L

Leo: And small subsets are noisy.

M

Maya: So there's a tolerance for noise. A tiny dip passes; a real drop fails.

L

Leo: How big is the tolerance?

M

Maya: Each metric has its own, set from how much it moves between runs of the same prompt.

L

Leo: Who changes the baseline?

M

Maya: Only a reviewed pull request. Otherwise someone could lower the bar to make their change pass.

L

Leo: And the full suite?

M

Maya: Nightly, or on demand. That's where rare failures show up.

L

Leo: And if the nightly run fails?

M

Maya: It doesn't block anyone's merge. It opens an issue, and the task's owner looks at it the next morning.

L

Leo: Does CI need AWS access to call the model?

M

Maya: Yes, through the same OIDC trust it deploys with, so no stored keys. And the gate is itself a CI change, so changing it needs approval.

02A model as the judge

L

Leo: Some things have no right answer. Is the feedback helpful? Is it in the learner's language?

M

Maya: That's where a judge helps. Another model scores the output against a written rubric. People call it LLM-as-a-judge.

L

Leo: So we can skip human labels.

M

Maya: That's the trap. A judge is a model too. First you check it against human labels, on the same outputs.

L

Leo: And if it agrees with people?

M

Maya: Then you pin it. Its model and its prompt version stay fixed, like any other dependency.

L

Leo: What can go wrong?

M

Maya: Bias. Judges often prefer longer answers, for example. So you test for that on purpose.

L

Leo: How?

M

Maya: Give it two answers of equal quality, one padded with extra words. If the padded one scores higher, the rubric needs fixing.

L

Leo: Could a judge check the language of the feedback?

M

Maya: It could, but a plain language detector in code is cheaper and never drifts. Use a judge only where code can't decide.

L

Leo: Doesn't Bedrock have evaluation built in?

M

Maya: It does. Managed evaluation supports a model as the judge, custom metrics and your own responses.

L

Leo: Then why not use it as the gate?

M

Maya: The thresholds must live in the repository, next to the code they judge. So Bedrock's evaluation supplements the harness; it doesn't replace it.

03Online evaluation

L

Leo: If the gate passes, are we done?

M

Maya: Not after release. Real inputs drift, and learners write things no gold set predicted. And agents take new paths.

L

Leo: But we already monitor errors and latency in production.

M

Maya: Those tell you it's running, not that it's good. A tutor can answer fast, with no errors, and still give wrong advice.

L

Leo: So how do we score production?

M

Maya: For the tutor agent, AgentCore Evaluations scores sessions. Online on a sample of real sessions, or on demand for chosen ones.

L

Leo: With what?

M

Maya: Built-in evaluators and custom ones, using traces as raw material. A trace is the record of every step and tool call in one session.

L

Leo: Why only a sample? Why not score every session?

M

Maya: Each score is a model call, so it costs tokens. A sample shows the trend at a fraction of the price.

L

Leo: So the harness asks "will this change make it worse?"

M

Maya: And online evaluation asks "is it getting worse out there?" Different questions, so neither replaces the other.

04Costs, and closing the loop

L

Leo: What does each one cost?

M

Maya: CI evals cost money and minutes, and small subsets miss rare failures. Judges cost tokens, and they can drift when their model changes.

L

Leo: And online evaluation?

M

Maya: It stores learners' conversations. That brings decisions about privacy and how long we keep them.

L

Leo: Is it worth that?

M

Maya: For the tutor, yes. It's the one feature where the paths aren't known in advance, so a gold set alone can't cover it.

L

Leo: Have you seen a team with only one of the three?

M

Maya: At my last company, a sales-assistant agent had only online evaluation. A prompt change passed code review.

L

Leo: And?

M

Maya: Its accuracy at choosing the right tool dropped. The dashboard showed it two days later.

L

Leo: Two days of worse answers for everyone.

M

Maya: So they built a pre-merge set from the worst online sessions. Production failures became gate cases.

L

Leo: That's a loop.

M

Maya: Let me draw it.

L

Leo: So a failure found online is only allowed to happen once.

M

Maya: That's the goal. We do the same with the tutor: its worst scored sessions feed the next gold cases.

05Leo explains it back

M

Maya: Your pull request touches a prompt. Tell me what will run, and why.

L

Leo: Fakes run on every pull request. Because I changed a prompt, a small, capped real-model eval runs too.

L

Leo: It compares with the baseline in the repository. The full suite runs nightly.

L

Leo: Once real users arrive, online scoring watches the live system. Every failure found in production becomes a test case for the gate.

M

Maya: And a judge model?

L

Leo: Only after checking it against human labels, and pinned like any dependency.

M

Maya: One gap to keep in view: online scoring stores real conversations. Decide how long we keep them before the first one is stored.

Summary in three lines

  1. Run a small, capped real-model gate only when a prompt, schema or model changes, against a recorded baseline.
  2. Run the full suite nightly, and score live sessions online once real users arrive.
  3. Check any judge model against human labels, and turn production failures into gate cases.
