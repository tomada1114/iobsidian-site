Where do evals run: in CI, at night or in production?

After this page you can explain the three places an evaluation runs, and what each one catches. You can also explain when a model can judge another model, and how production failures become tests.

01The pre-merge gate

Ordinary CI uses fakes and recordings for deterministic application checks. Changes to prompts, schemas or model configuration additionally trigger a small live evaluation using committed code and a spending cap. The subset emphasizes past failures, attacks and borderline cases.

Compare against a recorded baseline with metric-specific noise tolerance. Updating that baseline is a reviewed change, not an automatic way to make a failing candidate pass. A larger nightly or on-demand suite catches cases the small gate omits.

02A model as the judge

An LLM judge can assess qualities that deterministic code cannot easily measure. Calibrate it against human labels, pin its model and rubric versions, and test biases such as favoring longer answers.

Use code for reliably decidable properties instead of paying a judge to guess them. Managed evaluation services can supplement the harness, while repository-owned cases, thresholds and configuration keep the release criterion reviewable.

03Online evaluation

Pre-release tests cannot cover every production input. AgentCore evaluation can score selected or sampled sessions using traces, built-in criteria and custom evaluators. Quality signals complement latency and error metrics.

Sampling controls evaluation cost, and low scores need investigation rather than automatic acceptance as truth. Online evaluation asks whether deployed behavior is worsening; a merge gate asks whether a proposed change meets the current release bar.

04Costs, and closing the loop

Live gates cost money and time, judges can be biased, and production traces may contain sensitive conversations. Configure collection, access and retention deliberately.

The feedback loop promotes investigated failures into reviewed test cases. A tool-selection regression found in production should become a candidate pre-release case, with sensitive details removed and the expected behavior established by a person. The loop improves coverage without pretending a gold set is complete.

Summary in three lines

  1. Run a small, capped real-model gate only when a prompt, schema or model changes, against a recorded baseline.
  2. Run the full suite nightly, and score real sessions online after release.
  3. Check any judge model against human labels, and turn production failures into gate cases.
