Why not one complete(prompt) function for every feature?

After this page you can explain why each LLM task gets its own port, and what each task owns. You can also explain how fakes and recordings test it, and when a direct SDK call is fine.

  • What does a task port own?

01One helper for everything

A generic complete(prompt) helper centralizes transport but leaves each caller owning its prompt, parser, versions and cost attribution. When several features use it, there may be no clear unit for evaluation or investigating an old result.

A named grading task instead records its model, prompt and rubric versions and has a specific evaluation set. That responsibility boundary is more useful than simply avoiding repeated SDK calls.

02Task-level ports

The application owns a port per task, such as grade, explain or generate. A grading input contains the card, expected answers and learner response; its result is a Grade or a typed LLM error. A trusted request context identifies the learner for authorization and accounting.

interface GradeTask {
  grade(
    ctx: RequestContext,
    input: GradeInput,
  ): Promise<
    Result<Grade, LlmError>
  >;
}

Each task owns its prompt, output schema, rubric and evaluation data. A shared Bedrock adapter can implement several tasks beneath those interfaces. Transport code can be reused without collapsing their different promises into one untyped string function.

03Tests and swaps

A fixed fake exercises application behavior without a model call. A recorded real response tests parsing and integration against a known example. Live evaluations test current quality using the actual task port and adapter.

A recording proves that code handles that saved response, not that today's model is accurate. Changing a model or prompt needs a fresh evaluation. Provider replacement may also require capability or prompt changes, so the interface is a seam rather than a guarantee of interchangeable behavior.

04When a port is too much

Task ports add files and ownership work. A one-off experiment may reasonably call the SDK directly. Once a feature needs production evaluation, cost questions and failure handling, an explicit task boundary is more valuable.

Refresh recordings deliberately and review their diffs. In a migration, wrap existing model uses as named tasks, establish their expected behavior, then change providers one task at a time. That makes regressions and costs easier to attribute.

Summary in three lines

  1. Give each LLM task its own port, named for the task, not the vendor.
  2. Each task owns its prompt, schema, rubric version and evaluation set.
  3. Fakes and recordings test the code; an evaluation run approves a new model or prompt.
