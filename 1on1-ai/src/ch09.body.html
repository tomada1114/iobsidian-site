What if a learner types 'ignore your instructions'?

After this page you can explain prompt injection, direct and indirect. You can also explain why limiting an attack beats detecting it, and which layers guard each end.

01What injection is

Prompt injection attempts to turn text treated as data into instructions the model follows. Direct injection can appear in a learner answer; indirect injection can arrive through a document or tool result. Delimiters and clearer instructions can help, but are not an authorization boundary.

Quickturn therefore asks what a successfully misled model could do, rather than treating a stronger prompt as the whole defense.

02What can a successful injection do?

The grader has no tools and receives only the current task's data. Its output is limited to a grade shape, and the application binds storage to the verified learner. These choices reduce available capabilities even if the verdict is manipulated.

The remaining risks still matter: incorrect feedback, exposure of supplied context and abusive cost. Include adversarial cases in evaluation and measure whether they change verdicts. Schema compliance does not prove that the feedback or classification is safe.

03Layers at the entry and the exit

Entry controls limit size and can screen content. Bedrock Guardrails offers separately configured checks, but support, usage cost and false-positive behavior depend on the selected feature. It should be evaluated as one layer.

The exit path parses the response, checks domain rules and displays model text safely rather than inserting it as HTML or running it. Output stays untrusted data even when the prompt was authored by the team.

04The bigger risk, and the cost of guards

Token abuse needs input caps, bounded retries, a per-learner usage ledger and account-level cost containment. Content filtering also needs a policy for legitimate practice sentences that resemble an attack; a single detector hit is not a reliable grade.

Agents add tool-side consequences. An email-triage tool with arbitrary recipients could forward sensitive invoices after reading a hostile email. Constraining destinations and requiring approval for consequential actions limits that capability directly. Tool policies, identity and output handling remain necessary even with injection screening.

Summary in three lines

  1. A model can't reliably tell instructions from data, so injection can't be fully prevented.
  2. Limit what a successful injection can do: no tools, schema-bound output, the caller's own data only.
  3. Treat guardrails as one layer, and meet cost abuse with caps, a per-learner ledger and an account budget limit.
