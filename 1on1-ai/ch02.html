What am I actually paying for in one LLM call?

After this page you can explain tokens, the context window and why the same prompt can get a different answer. You can also estimate what a call costs and how long it takes, and when caching helps.

About 8 min readPairing at Leo's desk

In this page

  • What are tokens and the context window?
  • Why does the answer change, and what takes the time?
  • What does one call cost, and when does caching help?
  • How did one support bot's bill keep growing?

Leo's desk. The Bedrock playground is open on the dev account.

01Tokens and the context window

L

Leo: I sent the same grading prompt twice. Same learner answer, same verdict, but two different explanations.

M

Maya: That's normal. We'll get to why. What else did you notice?

L

Leo: The console shows input tokens and output tokens. I have no idea what they cost, or even what a token is.

M

Maya: A token is a piece of text. Often part of a word, sometimes a whole word, sometimes punctuation.

L

Leo: So a hundred words is a hundred tokens?

M

Maya: No fixed ratio. It differs by language and by model. So measure it with real text, don't guess.

L

Leo: Okay. And why so many input tokens? My learner answer was one sentence.

M

Maya: Because the model remembers nothing between calls. Every call sends the whole context: system prompt, instructions, examples, then the input.

L

Leo: The playground felt like a conversation, though.

M

Maya: The playground resends the history each time. The model itself starts from zero on every call.

L

Leo: Is there a limit on how much I can send?

M

Maya: The context window. It limits input and output together. Let me draw what fills it for grading.

L

Leo: Who decides how much room the output gets?

M

Maya: We do. The caller sets a maximum output length, called max tokens. The model stops there, even mid-sentence.

L

Leo: So set it high, to be safe?

M

Maya: Too high, and a rambling answer costs more and takes longer. Too low, and a verdict gets cut off halfway. We set it just above the longest verdict we've seen.

02Why answers change, and what takes time

L

Leo: So why two explanations for the same input?

M

Maya: The model writes one token at a time. For each one, it has a list of likely next tokens, each with a probability.

L

Leo: And it doesn't always take the most likely one?

M

Maya: Not always. Sampling settings decide how adventurous that pick is. Temperature is the best known: lower means safer choices.

L

Leo: Then I set the temperature to zero and get the same answer every time.

M

Maya: That's the common guess, and it's wrong. Even at a low temperature, providers don't promise identical output.

L

Leo: So what do we do about it?

M

Maya: Design for it. We store the first result, instead of expecting a repeat to agree. A retry must not grade the same answer twice.

L

Leo: And speed? My second call was faster than the first.

M

Maya: Latency has two parts you control little, and one you control a lot. Here's the shape of one call.

L

Leo: So a long explanation is slow even if the input is short.

M

Maya: Right. Output length drives latency. That's one reason our grader returns a short, typed verdict, not an essay.

03Price per call, and caching

L

Leo: Now the money. I assumed we pay per request, like an API gateway.

M

Maya: That's the usual guess. Two short calls can cost less than one long one. You pay for tokens, not requests.

L

Leo: How is a call priced, then?

M

Maya: Per million input tokens and per million output tokens. Output costs several times more than input.

L

Leo: Can we put a number on a grading call?

M

Maya: An illustration, with assumed token counts. Say 1,500 tokens in and 200 out, on Claude Haiku 4.5.

L

Leo: What's the price?

M

Maya: One dollar per million input tokens, five per million output, as checked in September 2026. Let me draw it.

L

Leo: A quarter of a cent. That's nothing.

M

Maya: At a hundred answers a day, it's about 25 cents. The shape matters more than the number: output is expensive, and input is sent every time.

L

Leo: Is that price the same in Tokyo?

M

Maya: We haven't verified the Tokyo price through the Japanese profiles. So I won't guess.

L

Leo: And caching? You said the top part can be cached.

M

Maya: Prompt caching. Put the stable part first, the instructions, rubric and examples. Put the changing part, the learner's answer, last.

L

Leo: And the provider reuses the stable part?

M

Maya: Yes. A cache write costs more than normal input, and a cache read costs much less. The cache is short-lived.

L

Leo: So it only helps if identical beginnings arrive close together.

M

Maya: That was our question too: grade each answer as it arrives, or a whole round at once?

L

Leo: Per answer means many calls with the same prefix, close together.

M

Maya: So we measured real latency and cost in a short experiment, a spike, before choosing. Every call records four counts: input, output, cache read and cache write.

L

Leo: And more examples in the prompt?

M

Maya: Higher quality, and a higher cost on every call. That's the trade you make on each example you add.

04A bill that grew every week

L

Leo: Where does this go wrong in practice?

M

Maya: At my last company, a customer-support agent's bill grew every week. Traffic hardly changed.

L

Leo: So what grew?

M

Maya: Each turn resent the whole history, plus the description of every tool. Long conversations cost far more than short ones.

L

Leo: Because the model remembers nothing, so you send it all again.

M

Maya: Right. And they only charted requests, so the growth was invisible.

L

Leo: Invisible how? The bill showed it.

M

Maya: The bill showed only the total, once a month. Nobody could see which conversations drove it, or when it started.

L

Leo: How did they fix it?

M

Maya: Four changes. Trim or summarize old turns. Cache the fixed prefix. Cap the output length.

L

Leo: And the fourth?

M

Maya: Chart tokens per conversation, not just requests. That's why our grading calls record the model id, prompt version, all four token counts, latency and an estimated cost.

05Leo explains it back

M

Maya: Someone asks why the playground gave two answers and what it cost. Your turn.

L

Leo: A call is billed and timed in tokens: everything I send each time, plus everything it writes back.

L

Leo: The output is the slow, expensive part. The model writes it one token at a time.

L

Leo: The model neither remembers nor repeats itself. So I send the full context with the stable part first, so it can be cached.

M

Maya: And the two explanations?

L

Leo: We store the first answer instead of hoping for the same one twice.

M

Maya: You left out when caching pays: only when identical beginnings arrive close together. That's what decided per answer against per round.

Summary in three lines

  1. Every call sends the whole context, because the model remembers nothing between calls.
  2. Output drives both latency and cost, and the same input can give a different answer.
  3. Put the stable part first so it can be cached, and record all four token counts on every call.
