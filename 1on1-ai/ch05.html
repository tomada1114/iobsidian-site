Why not one complete(prompt) function for every feature?

After this page you can explain why each LLM task gets its own port, and what each task owns. You can also explain how fakes and recordings test it, and when a direct SDK call is fine.

About 8 min readAfter the design review

In this page

  • What goes wrong with one generic helper?
  • What does a task port own?
  • How do ports make tests and swaps easy?
  • When is a port too much?

After Tuesday's design review. Leo stops by Maya's desk.

01One helper for everything

L

Leo: In the review, a teammate proposed a shared llmClient.complete(prompt) helper. One function, any prompt, less code. I liked it.

M

Maya: I argued against it. Want to know why?

L

Leo: Yes. It looked like the clean abstraction to me. Task-specific code felt like duplication.

M

Maya: Picture it a year from now. Grading, explanations and card generation all call complete. Who owns the grading prompt?

L

Leo: Whoever wrote the grading code, I guess.

M

Maya: And the output schema? The parsing?

L

Leo: Also the caller. So every caller has its own prompt, schema and parser.

M

Maya: Now a learner complains about a grade from last Tuesday. Which prompt version produced it?

L

Leo: Nobody knows, unless every caller remembered to log it.

M

Maya: With a task port, every grade records its model id, prompt version and rubric version. We can run the same answer through the same setup and see what happened.

L

Leo: So the complaint becomes something we can check, not an argument.

M

Maya: Same with cost. Tagging which feature spent the tokens depends on every caller remembering.

L

Leo: And evaluations?

M

Maya: That's the biggest gap. An evaluation needs a unit to attach to. "Any prompt" isn't a unit.

L

Leo: So the helper saves code, but nobody owns the things that matter.

M

Maya: Let me put the two designs side by side.

02Task-level ports

L

Leo: So what do we do instead?

M

Maya: The application layer declares a port per task. A port is an interface our code depends on, with no vendor in it.

L

Leo: Like the stores? The application asks for a learner's rounds, not for DynamoDB.

M

Maya: Exactly the same idea, in the same layout as the rest of our code. The domain imports nothing, and the application declares ports.

L

Leo: And the port names the task?

M

Maya: The task, not the vendor. Here's a simplified grading port. GradeInput holds the card, the expected answers and the learner's answer:

interface GradeTask {
  grade(
    ctx: RequestContext,
    input: GradeInput,
  ): Promise<
    Result<Grade, LlmError>
  >;
}
L

Leo: Why does it take a request context?

M

Maya: The context carries the learner, taken from the verified session. Cost records and the usage ledger use it to charge the right learner.

L

Leo: And the cost tag comes with the task, so no caller can forget it.

M

Maya: Right.

L

Leo: So the caller never sees a prompt.

M

Maya: Right. It passes typed input and gets a typed result, or an LLM error. Beside it sit an explain port and a generate port.

L

Leo: Couldn't complete just take a task name as a parameter? Then it's one function, with owners.

M

Maya: Then it's a port with a string instead of a type. Nothing makes the grading caller pass grading input, or get a grade back.

L

Leo: And a typo in the name is a runtime error.

M

Maya: Right. The interface makes the compiler check it for us.

L

Leo: And what does each task own?

M

Maya: Four things: its prompt, its output schema, its rubric version and its evaluation set.

L

Leo: The rubric version is the grading rules?

M

Maya: The written rules for what counts as correct or acceptable. When they change, the version changes, and every grade records which one it used.

L

Leo: And the model?

M

Maya: One Bedrock Converse adapter implements all the LLM tasks underneath. The model becomes a replaceable part.

03Tests and swaps

L

Leo: What are the three boxes at the bottom?

M

Maya: Three ways to run the same code. A fake returns fixed answers, for unit tests.

L

Leo: So a test can say "the grader returns incorrect" and check what the app does.

M

Maya: Right, with no network and no cost. It can also return an LLM error, to check that the answer stays ungraded instead of crashing. A recording is a real response saved once and replayed, for contract tests.

L

Leo: And the real model?

M

Maya: For evaluation, where we measure quality on real calls.

L

Leo: Does evaluation go through the same port?

M

Maya: Yes, the same port and the same adapter. So what we measure is exactly what learners get, not a copy of the prompt in someone's test script.

L

Leo: I'd have guessed a recording is enough for everything. It's real output.

M

Maya: It's real output from one day, with one prompt. It proves our code handles that response. It can't tell you whether today's prompt grades well.

L

Leo: And swapping a model?

M

Maya: The model id and the prompt version are configuration. Changing either is a config change plus an evaluation run.

L

Leo: Not a search through the code for every call site.

M

Maya: Right. And the evaluation has to approve it before it ships.

04When a port is too much

L

Leo: Isn't this a lot of code for a few prompts?

M

Maya: It is more code, with some repetition. For a one-off script, a direct SDK call is fine.

L

Leo: So when does the port pay?

M

Maya: Once there are several tasks, evaluations and questions about cost. That's when the owners in that table start to matter.

L

Leo: We have three: grade, explain and generate.

M

Maya: And adding a fourth means a port, a prompt, a schema and an evaluation set. That work is the point: it's the list of things someone must own.

L

Leo: Anything that gets worse?

M

Maya: Recordings become out of date when prompts change. We refresh them on purpose, not when a test happens to fail.

L

Leo: How do you refresh one?

M

Maya: Run the task once against the real model, save the new response, and review the diff like any other change. A surprising diff is worth reading.

L

Leo: Have you seen the other way go wrong?

M

Maya: At my last company, an internal assistant called the model SDK from about twenty places. Then the company changed model providers.

L

Leo: How bad was it?

M

Maya: They found three different JSON parsers. And when costs spiked, nobody could tell which feature caused it.

L

Leo: So what did they do?

M

Maya: Before migrating, they wrapped each use as a named task with its own evaluation. Then they switched providers one task at a time.

L

Leo: And each switch had an evaluation to pass.

M

Maya: Yes. That's what made the migration safe.

05Leo explains it back

M

Maya: Say it the way you'd put it in the review thread.

L

Leo: Each LLM feature is a named task, with its own prompt, schema, rubric version and evaluation set. It's declared as a port, like any other dependency.

L

Leo: The model sits behind one adapter. Tests use fakes and recordings.

L

Leo: Changing the model is configuration that the evaluation has to approve.

M

Maya: And the helper?

L

Leo: Fine for a one-off script. Not once we have several tasks to evaluate and pay for.

M

Maya: Name the upkeep in the thread too: recordings must be refreshed on purpose whenever a prompt changes.

Summary in three lines

  1. Give each LLM task its own port, named for the task, not the vendor.
  2. Each task owns its prompt, schema, rubric version and evaluation set.
  3. Fakes and recordings test the code; an evaluation run approves a new model or prompt.
