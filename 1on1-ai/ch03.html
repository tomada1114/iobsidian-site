Why does Bedrock want an inference profile, not a model?

After this page you can explain what Amazon Bedrock adds on top of a model, and what an inference profile decides. You can also say when batch inference beats calling a model on demand.

About 8 min readOn a video call

In this page

  • What is Bedrock, beyond a model's API?
  • What does an inference profile decide?
  • When does a request go to batch?
  • What do we trade for keeping data in Japan?

A video call. Both are looking at the Bedrock console in the dev account.

01What Bedrock is

L

Leo: I called a Claude model by its model id, and got an error. It told me to use an inference profile. Why does a model need a profile?

M

Maya: Let's start one step back. What do you think Bedrock is?

L

Leo: The model vendor's API, with an AWS bill. You call a model id in your region, and that's it.

M

Maya: That's the common picture, and it misses most of it. Bedrock is serverless access to models from several providers, inside your AWS account.

L

Leo: Inside the account, meaning what?

M

Maya: IAM controls who may call which model. The cost lands on your AWS bill. And invocation logging writes prompts and answers to logs in your own account.

L

Leo: Is that different from calling the vendor with an API key?

M

Maya: Quite different. You don't need a vendor's API key, and the same IAM roles and audit logs as the rest of AWS apply.

L

Leo: So we can see every prompt we sent?

M

Maya: If you turn it on. It's off by default, and it writes to CloudWatch Logs and S3 in the same account and region.

L

Leo: And the request itself? Each provider has its own format.

M

Maya: That's what the Converse API solves. One request shape across models: messages, a system prompt, inference settings, tools and an output format.

L

Leo: So switching models is mostly configuration.

M

Maya: For us, it's the model's profile id in one setting. The code that builds the request doesn't change.

L

Leo: Only mostly?

M

Maya: The other call, InvokeModel, takes each provider's own body instead. We use Converse, through one adapter that serves every LLM task.

L

Leo: Could I call any model right away?

M

Maya: No. The account must be allowed to use a model before the first call. How you enable that has changed over time, so check the console when you need it.

02Inference profiles

L

Leo: Now the profile. What is it?

M

Maya: For newer Claude models, on-demand calls don't go to a single region. They go through a cross-region profile, which picks where the request runs.

L

Leo: Picks from where?

M

Maya: Two kinds. A geographic profile, like one starting with jp., routes only between Tokyo and Osaka. A global profile can route anywhere, for more capacity.

L

Leo: So jp. keeps the text in Japan.

M

Maya: The processing stays in Japan. Our app runs in Tokyo, and the model may run in Tokyo or Osaka. Here's the path of one call.

L

Leo: Does a request sent to Osaka come back slower?

M

Maya: Sometimes a little. For a verdict of a few words, the time the model spends writing matters more than the distance.

L

Leo: Wait, two profiles?

M

Maya: The jp. one is AWS's. The other is an application inference profile: one you create yourself and tag.

L

Leo: Why create one?

M

Maya: So the bill can be split by feature. We make one per feature, each wrapping that feature's jp. profile.

L

Leo: So I can answer "what does grading cost?" without guessing.

M

Maya: Right. One catch: the tags take up to a day to appear, and they only count from when they're activated.

L

Leo: Which is why we create them before launch, not after.

M

Maya: Yes. And that error you saw? These models require a geographic or global profile for on-demand calls. A bare model id won't work.

03On demand or batch

L

Leo: Is every call on demand?

M

Maya: No. Some work can wait. Bedrock also has batch inference.

L

Leo: How is it different?

M

Maya: You put a file of requests in S3. Bedrock returns the results later, as another file.

L

Leo: Half price, just for waiting?

M

Maya: For supported models, batch costs half of on demand, as checked in September 2026.

L

Leo: So which of ours go where?

M

Maya: Grading a learner's answer is on demand. The learner is waiting for the verdict.

L

Leo: And cards?

M

Maya: Generating a hundred cards overnight is batch. Nobody is waiting, so we take the lower price.

L

Leo: What if one request in the file fails?

M

Maya: Each result in the output file carries its own status. The pipeline sends only the failed ones again.

L

Leo: So one bad card doesn't fail the whole night's run.

M

Maya: Right. The other ninety-nine are already done.

L

Leo: Does structured output still work in batch?

M

Maya: It does, and with cross-region profiles too. So the card pipeline gets the same typed results.

L

Leo: I'd have put everything on demand, to keep it simple.

M

Maya: It is simpler. But anything that can wait for hours is paying double for speed nobody needs.

04Residency against model choice

L

Leo: Why not use the global profile everywhere? More capacity sounds better.

M

Maya: Here's the trade. Let me compare the two.

L

Leo: Our learners are mostly in Japan, so residency, where the data is processed, matters.

M

Maya: Right. Grading runs on Claude Haiku 4.5 through its jp. profile. Card generation uses a Sonnet-class model through a jp. profile, where one exists.

L

Leo: Where one exists?

M

Maya: When we checked in September 2026, Sonnet 4.6 had a global profile, and no jp. profile was confirmed. So before moving past Sonnet 4.5, we check first.

L

Leo: And why Bedrock at all, instead of the vendor's own API?

M

Maya: IAM, one bill, and logs in our own account. The cost is that new features sometimes arrive on Bedrock later.

L

Leo: Has residency ever blocked a launch?

M

Maya: At my last company, an internal agent served staff in Europe. Legal review asked where the text was processed, and where the logs were.

L

Leo: What did they answer?

M

Maya: A geographic profile, and invocation logs in the same region. They settled it before launch, not after.

05Leo explains it back

M

Maya: Say how you'd explain that error to the next person who hits it.

L

Leo: Bedrock gives one API shape for many models, inside our account, with IAM, one bill and our own logs.

L

Leo: The inference profile decides where a request runs. Our jp. profile keeps processing in Japan, and our own tagged profile decides which feature pays.

L

Leo: Anything that can wait for hours goes to batch, at half price.

M

Maya: And the catch with jp.?

L

Leo: A newer model may only have a global profile at first.

M

Maya: Add the practical step: create the tagged profiles before launch. Their cost data only starts from the day they're activated.

Summary in three lines

  1. Bedrock puts many models behind one API shape, inside your account, with IAM, billing and logs.
  2. An inference profile decides where a request runs; a tagged profile per feature splits the bill.
  3. Work that can wait goes to batch at half price; residency can limit which new models you use.
