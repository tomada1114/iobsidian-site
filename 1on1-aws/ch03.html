What do we give up by running the API on Lambda?

After this page you can explain how Lambda runs requests and what a cold start is. You can also say when serverless fits, and when containers or a queue are the better choice.

A video call. Leo has the API's response times open in another window.

01How Lambda runs a request

L

Leo: I noticed something. The first request of the morning takes clearly longer than the rest. Is Lambda just slow? Should we move the API to containers?

M

Maya: Before we move anything, let's see what that first request does. What do you think happens when a request reaches Lambda?

L

Leo: Lambda runs my handler function. That's it?

M

Maya: That's the part you see. Underneath, your code runs in an execution environment, a small, isolated sandbox with the runtime and your code loaded.

L

Leo: And the environment is always there?

M

Maya: No. It's created on demand. One environment handles one request at a time. If two requests arrive together, Lambda creates a second environment.

L

Leo: So the number of environments running at once is…

M

Maya: Concurrency. After a request, the environment stays warm for a while and is reused. When it's idle long enough, it's removed.

L

Leo: Oh. So in the morning, nothing is warm.

M

Maya: Right. The first request pays for creating one. That's a cold start: load the code, start the runtime, and run the setup code outside the handler. Let me draw it.

L

Leo: What's in our setup code?

M

Maya: Our API is one function that runs the whole HTTP app. At start, it reads its configuration once and builds its clients, like the DynamoDB client. Every warm request reuses them.

L

Leo: So it's slow once, then fast. Not "Lambda is slow".

M

Maya: Exactly. And we measured the cold start rather than assuming it. It matters less than you'd think for our app.

L

Leo: Why?

M

Maya: The drill timer runs on the phone, not on the server. A slow first call doesn't eat into a learner's thirty seconds.

02The front door

L

Leo: How do requests even reach the function? Through API Gateway?

M

Maya: Yes, and there are several front doors to choose from. API Gateway has two kinds. The HTTP API is simpler and cheaper per request, and it can check a JWT, a signed sign-in token.

L

Leo: And the other kind?

M

Maya: The REST API. It has more features: API keys, usage plans, request validation and caching. We don't need those.

L

Leo: What else could sit in front?

M

Maya: A load balancer in front of containers, which bills per hour. Or a Lambda function URL, where the function gets its own address, with no gateway at all.

L

Leo: A function URL sounds simplest. Why didn't we use that?

M

Maya: We looked hard at it. You can protect a function URL so that only CloudFront can call it. But then clients must send a SHA-256 hash of every POST or PUT body.

L

Leo: Every client? The phone apps too?

M

Maya: Every client. An infrastructure detail would leak into our public contract. So we chose an HTTP API, with one catch-all route to our app.

L

Leo: And if the gateway's cost ever became a problem?

M

Maya: The fallback is a function URL that only accepts a secret header, which CloudFront adds. We'd switch only if the per-request cost really mattered.

03What serverless gives up

L

Leo: So is Lambda free of limits? "Serverless" sounds like nothing to think about.

M

Maya: That's the idea I want to clear up. Let's list what you give up. First, cold-start latency, which we just saw.

L

Leo: Second?

M

Maya: A hard limit: fifteen minutes at most per invocation. Third, no memory kept between requests. You can't hold a session in a variable.

L

Leo: Because the next request might go to another environment.

M

Maya: Right. Fourth, a concurrency quota shared by the whole account. And fifth, cost that grows with every single request.

L

Leo: How do we know if we hit the concurrency limit?

M

Maya: We have alarms on 5xx errors, function errors and throttles. We tested them by setting the function's reserved concurrency to zero. Every request was throttled, and the alarms fired.

L

Leo: You broke it on purpose to see the alarm?

M

Maya: In dev, yes. An alarm you've never seen fire is a guess. Now compare Lambda with containers.

L

Leo: So containers aren't worse. They just cost money while idle.

M

Maya: Both a load balancer and container tasks bill by the hour. That's why we ruled them out, not because of speed.

L

Leo: When would you switch?

M

Maya: Steady, high traffic, where per-request cost adds up. Long-running jobs. Long-lived connections, like websockets held for hours. Or heavy startup, where every cold start is painful.

L

Leo: So the question is the shape of the work, not which tool is newer.

M

Maya: Yes. Here are the two questions together.

04Long AI jobs

L

Leo: The top row is where AI work lands, isn't it? An agent can run for a long time.

M

Maya: Yes. One agent session can run for many minutes, with dozens of tool calls. That doesn't fit a fifteen-minute request, and a user won't hold a connection that long anyway.

L

Leo: So what do teams do?

M

Maya: Three common answers. A queue and a worker that picks jobs up. A workflow service that runs steps and waits between them. Or a managed agent runtime, where one session can last for hours.

L

Leo: Which do we use?

M

Maya: Both kinds. Grading typed answers is a background job: the API puts it on an SQS queue, and a worker Lambda picks it up.

L

Leo: A grade takes seconds, so a worker Lambda still fits.

M

Maya: Right, and the learner doesn't wait on the request. Our tutor agent is different. It runs on Amazon Bedrock AgentCore, a managed agent runtime, because its sessions are long conversations.

L

Leo: So the API stays a short-request function, and the long work moves elsewhere.

M

Maya: Yes. That's the pattern. Keep each piece in the quadrant it fits.

05Leo explains it back

M

Maya: Say the PM asks whether we should move the API to containers because the first call is slow. What's your answer?

L

Leo: Lambda runs each request in an environment created on demand. The first request after idle pays a cold start; warm requests don't.

L

Leo: Each invocation also has a hard time limit, keeps no memory between requests, and shares a concurrency quota.

L

Leo: In return, we run no servers and pay close to nothing when nobody practices.

M

Maya: And the front door?

L

Leo: An HTTP API, because it's simple and keeps signing details out of our public contract.

M

Maya: Say when you'd change your mind: steady, heavy traffic or long jobs. Then containers or a queue would win, and we'd move.

Summary in three lines

  1. Lambda creates environments on demand, so the first request after idle pays a cold start and later ones don't.
  2. Serverless gives up long requests, in-memory state and flat costs, in exchange for no servers and no idle bill.
  3. Pick by the shape of the work: short and spiky suits functions, steady or long suits containers, queues or agent runtimes.
