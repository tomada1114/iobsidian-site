01誰なのかと、何をしてよいか

JWT をデコードすればクレームは読めますが、その内容が正しいことは確かめられません。好きな subject を書いたトークンらしき文字列は、誰でも作れます。認証は呼び出し元が誰かを確かめ、認可はその呼び出し元がどの操作とデータにアクセスしてよいかを決めます。

OpenID Connect は、OAuth の認可の枠組みに ID の仕組みを加えたものです。Quickturn では、学習者がリソースオーナー、Web のバックエンドがクライアントにあたります。トークンを発行するのは Cognito で、保護されたリソースを提供するのは API です。

02PKCE を使った認可コードフロー

Quickturn は、PKCE を使った認可コードフローを採用しています。ログイン用のエンドポイントが state と verifier を作り、verifier の SHA-256 から作った challenge を Cognito に送ります。コールバックで受け取るのは最終的なトークンではなく、短時間だけ有効なコードです。

バックエンドは state を検証し、verifier と自分のクライアント認証情報を添えてコードを交換します。ネイティブのクライアントは、アプリにシークレットを埋め込まず、システムのブラウザと PKCE を使います。state、リダイレクトの扱い、verifier との結び付けは、それぞれ別の攻撃を防ぐもので、どれも正しく実装しなければなりません。

03三つのトークン

ID トークンはクライアントに認証の結果を伝え、アクセストークンは API の利用を認可し、リフレッシュトークンは新しいアクセストークンを得るために使います。Quickturn の Web のセッションが保持するのは、API へのアクセスと更新に必要なトークンです。デコードした ID トークンを、認可の根拠として持つことはしません。

検証では、信頼できる鍵による署名、有効期限、発行者、トークンの用途、想定するクライアントやリソースを確かめます。Cognito のアクセストークンには client_id が含まれ、リソースへの結び付けを要求した場合は aud クレームが入ることもあります。

Quickturn は、本番では Cognito の鍵、テストでは管理下の署名鍵で、同じ検証処理を使います。これにより、本物のサインインサービスに頼らずに、発行者、有効期限、クライアント ID が誤っている場合の否定テストを書けます。

04マネージドサービスの代償

マネージドなサインインを使えば、パスワードやアカウント復旧の作業は減りますが、プロバイダー固有の設定、料金プランの選択、移行の問題が加わります。Quickturn は、プロバイダーの subject を自分たちの学習者 ID に対応付けています。ユーザープールを入れ替えても、学習者が持つレコードの名前を変える必要はありません。ただし、ID の対応付けは移行しなければなりません。

トークンの検証は、Cookie での認証と Bearer での認証が共有する経路に置きます。ログには、どの確認で失敗したかを残し、トークン自体は含めません。読み取れるトークンは、実際の有効期限が来るか、失効の仕組みで無効になるまでは、そのまま使える認証情報になりえます。

3行まとめ

  1. OAuth は委任されたアクセスを扱い、OpenID Connect はそこに標準的なサインインと ID トークンを加えます。
  2. Quickturn の Web のバックエンドは PKCE を使ってコードを交換し、ネイティブのクライアントは自分で保護したトークンを管理します。
  3. ユーザー ID を信用する前に、アクセストークンの署名、発行者、用途、クライアント、有効期限を検証します。
