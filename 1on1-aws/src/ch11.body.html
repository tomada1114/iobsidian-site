What actually happens when a learner signs in?

After this page you can explain OAuth and OpenID Connect, and walk through the authorization code flow with PKCE. You can also say which token the API checks, and how.

About 8 min readAt the whiteboard

In this page

  • What are OAuth and OpenID Connect for?
  • How does the code flow with PKCE work?
  • Which token does the API check, and how?
  • What does a managed identity service cost us?

The whiteboard room. Leo is chasing a 401 error.

01Who you are, what you may do

L

Leo: I pasted an access token into a JWT decoder website. The user's id was right there in plain text, under sub.

M

Maya: What did you conclude?

L

Leo: That the API could just read sub and skip the verification library. It looks like a lot of machinery for reading one field.

M

Maya: Anyone can write a token that decodes. Decoding shows you what it claims, not whether it's true.

L

Leo: Hmm. Then what makes it true?

M

Maya: We'll get there. First, two words people mix up. Authentication answers "who is this?" Authorization answers "what may they do?"

L

Leo: And OAuth is the login protocol.

M

Maya: That's the common mix-up. OAuth 2.0 is about authorization: letting one program act for a user, with limits.

L

Leo: Then where does login come from?

M

Maya: OpenID Connect. It sits on top of OAuth and adds identity: a standard sign-in and an ID token.

L

Leo: Who are the players?

M

Maya: OAuth names four roles. The resource owner is the learner. The client is our web backend.

L

Leo: And the other two?

M

Maya: The authorization server is Cognito, which signs people in and issues tokens. The resource server is our API, which holds the data.

02The code flow with PKCE

L

Leo: So what happens when a learner clicks "Sign in"?

M

Maya: The authorization code flow, with PKCE. Let me draw it.

L

Leo: Walk me through the second step.

M

Maya: Our login endpoint makes two random values. One is the state. The other is the verifier, which stays on our side.

L

Leo: And what goes to Cognito?

M

Maya: A hash of the verifier, called the challenge. Cognito only supports the SHA-256 method, called S256.

L

Leo: Then the learner signs in on Cognito's page, not ours.

M

Maya: Right, the managed login page. We never see a password. Afterwards Cognito sends the browser back with a one-time code.

L

Leo: Why not send the tokens straight back?

M

Maya: Because the browser's address bar leaks. A code in a URL can end up in history or logs.

L

Leo: So the code is useless on its own?

M

Maya: Nearly. Our backend exchanges it at the token endpoint. It sends the code, the original verifier, and the client secret.

L

Leo: I'd have said the client secret is enough. The attacker doesn't have that either.

M

Maya: For our web backend, true. But the phone apps have no secret, and a leaked secret would open every code. The verifier is new for each sign-in.

L

Leo: So a stolen code only works with the verifier from that one sign-in.

M

Maya: Exactly. That's what PKCE adds. And the state stops a forged callback: if it doesn't match what we made, we refuse it.

L

Leo: What about the phone apps? They can't keep a secret.

M

Maya: They use the same flow as public clients, with no secret, through the system browser. PKCE carries the weight there.

03Three tokens

L

Leo: And what comes back?

M

Maya: Three tokens. The ID token says who signed in. The access token is for calling the API.

L

Leo: And the third?

M

Maya: The refresh token. It lives long and gets new access tokens, so the learner doesn't sign in every hour.

L

Leo: I'd have guessed the API checks the ID token. It's the one that says who you are.

M

Maya: That's the trap. The ID token is meant for the client, to learn who signed in. The access token is meant for the API.

L

Leo: Do we keep the ID token?

M

Maya: No. The web session stores only the access and refresh tokens. We don't need the ID token after sign-in.

L

Leo: Now back to my question. How does the API trust an access token?

M

Maya: Five checks, in order. Let me draw them.

L

Leo: Where do the public keys come from?

M

Maya: The user pool publishes them, as a key set called JWKS. Only Cognito holds the private key, so only Cognito can sign.

L

Leo: Why check the client id?

M

Maya: A token from another app in the same pool would pass the other checks. Cognito access tokens carry client_id instead of aud, so that's our audience check.

L

Leo: And our library does all five.

M

Maya: It does, with the token use and client id we require. In tests, we sign tokens with a local key, so the real checking code runs without calling Cognito.

L

Leo: And a cookie from the web and a Bearer header from the phone?

M

Maya: One authenticator resolves both, then runs the same checks.

04What a managed service costs

L

Leo: Why use Cognito at all, instead of our own login?

M

Maya: At our size it's cheap, and it handles passwords, email checks and account recovery. Those are easy to get wrong.

L

Leo: What's the catch?

M

Maya: Some choices are fixed when the pool is created. The sign-in identifier and its case rules are two of them.

L

Leo: What did we pick?

M

Maya: Email as the username, and case-insensitive. Otherwise "Leo@" and "leo@" could become two accounts.

L

Leo: And changing them means a new pool.

M

Maya: With new user ids. So we never use sub as our key directly. On first sign-in, we map it to our own learner id.

L

Leo: Anything we chose not to buy?

M

Maya: Advanced threat protection. It needs a more expensive plan. We'll switch it on if abuse appears.

L

Leo: Why verify in our code, not at API Gateway? It has a JWT authorizer.

M

Maya: The gateway can't read cookies. Verifying in the app keeps one path for both cookies and Bearer headers.

L

Leo: So my 401 is probably a check failing, not a bug in the library.

M

Maya: Likely. Log which check failed, never the token itself.

L

Leo: Why not the token? It would make debugging easier.

M

Maya: A logged access token works for anyone who reads the log, until it expires. The name of the failed check is enough.

05Leo explains it back

M

Maya: A new teammate asks what happens when a learner signs in. Go.

L

Leo: OAuth is about delegated access, and OpenID Connect adds who signed in.

L

Leo: We use the code flow with PKCE. The browser brings back a one-time code, and our backend swaps it for tokens with the verifier and the client secret.

L

Leo: The API trusts an access token only after checking its signature, issuer, token use and client id. Decoding alone proves nothing.

M

Maya: And after that?

L

Leo: We read sub and look up our own learner id.

M

Maya: One word on expiry too: it's the last check, and the refresh token is what spares the learner from signing in again.

Summary in three lines

  1. OAuth handles delegated access; OpenID Connect adds a standard sign-in and an ID token.
  2. The code flow with PKCE turns a one-time code into tokens on the backend, never in the browser.
  3. Verify the access token's signature, issuer, token use, client and expiry before trusting its user id.
