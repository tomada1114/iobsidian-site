AWS で自分たちが責任を持つのはどこまでか

開発中のミスの影響が、本番の学習者データにまで及んではいけません。アカウントを分ければその危険は小さくなりますが、各サービスの設定と、アカウントをまたぐ信頼関係には引き続き注意が要ります。

01リージョンとアカウント

AWS アカウントには、リソース、権限、請求情報が入っています。リージョンは地理的な区域で、互いに独立した複数のアベイラビリティーゾーンを含みます。多くのサービスはリージョン単位で動きますが、IAM や CloudFront のようにグローバルな性質を持つサービスもあります。

Quickturn は、最初の学習者が日本にいることから、リージョン単位の主なリソースを東京に置いています。アカウントの境界と地理的な配置では、扱う問題が違います。前者は所有とアクセスの問題で、後者はレイテンシ、耐障害性、データの保存場所に関する要件の問題です。

02責任共有モデル

責任共有モデルでは、AWS が基盤となるインフラを守り、利用者は自分のデータ、コード、ID、設定を守ります。どこで線を引くかは、サービスによって変わります。

マネージドな Lambda や DynamoDB を使えば、OS やデータベースの保守は減ります。しかし、実行ロールにどのテーブルへのアクセスを許すかや、あるトークンを信用してよいかまでは決めてくれません。呼び出し元がどの学習者のレコードにアクセスしてよいかも、アプリの認可が判断します。これらは引き続き、アプリとアカウントを持つ側の責任です。

03アカウントでミスの影響範囲を区切る

開発用と本番用のアカウントを分けると、日常的な開発のミスの影響が及ぶ範囲を狭められます。Quickturn は AWS Organizations を使い、小さな管理アカウントの下に別々のメンバーアカウントを置いています。人のアクセスには IAM Identity Center を使い、短時間だけ有効な認証情報を発行します。ルートユーザーには MFA を設定し、普段使うアクセスキーは作っていません。

管理アカウントには特に注意が要ります。組織のガードレールとなるポリシーは、メンバーアカウントと同じようには管理アカウントを制限しないからです。アカウントをまたぐ信頼関係も管理しなければなりません。境界をまたぐ広い権限のロールを意図して設けていれば、アカウントを分けても守りにはなりません。

分離すれば、そのぶん初期設定と運用の手間が増えます。クレジットを当てにする前に、無料プランや組織に関する適用条件を確認してください。請求上の利点と、本番の学習者データを守る必要とは、別々に考える話です。

04料金も設計の一部

料金には、固定でかかる部分と、使用量に応じてかかる部分があります。インスタンス、ロードバランサー、NAT ゲートウェイは、使われていなくても費用が発生します。Lambda の呼び出し、DynamoDB のオンデマンドの操作、ストレージへのアクセスは、おおむね使用量に比例します。ただし、保存しておくデータとログには、使われていなくても費用がかかります。

固定の部品が少なければ、使われていない開発環境は安く済みます。一方、高い負荷が続くなら、プロビジョンドの容量や常時稼働の構成のほうが安くなることもあります。「サーバーレスなら無料」と決めつけず、トラフィックがゼロのときと、現実的に伸びたときの両方で見積もってください。

3行まとめ

  1. リージョンは処理を動かす場所で、アカウントはリソース、権限、請求、そしてミスの影響を囲う単位です。
  2. AWS はクラウドの基盤を守りますが、データ、IAM、設定は、どれほどマネージドなサービスでも自分たちの担当です。
  3. 本番は専用のアカウントに分け、使われていないときの費用を重視するならリクエスト課金の部品を選びます。
