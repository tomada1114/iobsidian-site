How do we prove one learner can't see another's data?

After this page you can explain how identity, one policy and learner-bound stores keep each learner's data apart. You can also explain the test that proves it, and the silo and pool models.

About 8 min readAfter the design review

In this page

  • Where does identity enter a request?
  • How do one policy and bound stores keep learners apart?
  • How do silo and pool models compare?
  • What about an AI agent acting for a learner?

After Tuesday's design review. Leo is still thinking about one question.

01Identity enters once

L

Leo: In the review, someone asked what stops learner B from reading learner A's round. I said each handler checks the learner id.

M

Maya: What did they say?

L

Leo: "Every handler, forever?" I didn't have a better answer.

M

Maya: What happens the day someone writes a new handler and forgets the check?

L

Leo: A learner can read someone else's data. And no test fails, because nobody wrote one for the new handler.

M

Maya: Right. And signing in doesn't help there. It proves who is calling, not what they may touch.

L

Leo: So what's the better answer?

M

Maya: Make the check impossible to forget. Let me draw how a request flows.

L

Leo: Start at the top. What does "authenticate once" mean?

M

Maya: The edge checks the token or cookie, one time. Then it builds a request context: the actor, the learner, the time and a request id.

L

Leo: And below the edge?

M

Maya: Nothing reads headers or cookies again. And a learner id never comes from a request body, a path, or a tool argument.

L

Leo: Why not from the path? /learners/123/rounds looks normal.

M

Maya: Because the caller wrote it. The only learner id we trust is the one the edge got from a verified token.

L

Leo: What's an actor, exactly?

M

Maya: Who is acting. A learner, a system job working for one learner, or an agent acting for a learner with named grants.

02One policy, bound stores, one test

L

Leo: And authorize is the if-statement, just moved?

M

Maya: It's one function over one table. A learner may run learner operations. A job may run only its own.

L

Leo: And an agent?

M

Maya: Only what it was granted, and never more than the learner could do. The tutor may read a learner's history, for example, but may not delete an account. A table test checks every actor against every operation.

L

Leo: Then the store. What does "bound" mean?

M

Maya: The application can only get a store as forLearner(id). No store method takes a learner id.

L

Leo: So I can't even write "get round X for learner B".

M

Maya: Right. The adapter writes the learner's partition into every key. Ask for another learner's round, and it's simply not found.

L

Leo: What does the API answer then? 403?

M

Maya: 404. A 403 would confirm the round exists. With 404, B learns nothing about A.

L

Leo: Does that matter? Round ids look random.

M

Maya: Picture A sharing a screenshot with a round id in the address bar. B tries it and gets 403.

L

Leo: Now B knows the round is real, and that it belongs to someone.

M

Maya: Right. With 404, it looks like a typo.

L

Leo: But how do we know it holds? The reviewer will ask that next.

M

Maya: The isolation contract. Here are its steps.

L

Leo: Why write the same keys as B? Reading already failed.

M

Maya: Reading proves B can't see A. A write with the same round id could still land on A's item if the partition were missing from the key.

L

Leo: So the write half catches a store that forgets the partition.

M

Maya: Right.

L

Leo: Which stores does it run against?

M

Maya: Every one. The in-memory store and DynamoDB running locally run the same suite.

L

Leo: And above the store?

M

Maya: HTTP tests do the same with B's token. We also checked on dev with two learners an administrator created.

L

Leo: I'd have guessed the handler check was enough if we tested each handler.

M

Maya: Then every new handler needs a new test, written by someone who remembers. The contract covers every read at once.

L

Leo: So a new handler is safe by default.

M

Maya: It gets a bound store or nothing. That's the answer for the reviewer.

03Silo, pool and bridge

L

Leo: Why do we need all this? Couldn't each learner just have their own table?

M

Maya: That's a real model, called silo. Each tenant, one customer whose data must stay apart, gets its own resources: an account, a stack, or a table.

L

Leo: And ours?

M

Maya: Pool. Everything is shared, and the tenant key is in every item. Let me compare them.

L

Leo: Silo sounds safer. Why didn't we pick it?

M

Maya: For thousands of learners, a table each is heavy to run and pay for. Silo suits a few large customers, each with their own contract.

L

Leo: Is there something in between?

M

Maya: Bridge. Shared compute, say, with a table per tenant. We're pool, with one partition per learner.

L

Leo: Couldn't IAM enforce the partition? I've seen a condition on DynamoDB's leading keys.

M

Maya: It can, but only when each user calls AWS with their own credentials. Our API calls DynamoDB with one role for everyone.

L

Leo: So IAM can't tell learners apart there.

M

Maya: Right. And in that setup the key would be an identity-pool id, not the Cognito sub we map from. So the boundary lives in our code, and the test proves it.

04Agents follow the same rule

L

Leo: What about the tutor agent? It reads a learner's history.

M

Maya: Same rule. It's an agent actor with narrow grants. And the tools it can call declare no learner id parameter.

L

Leo: Why does that matter so much?

M

Maya: Because the model writes the tool arguments. A prompt injection controls what the model writes.

L

Leo: So if a tool took a learner id, a hidden instruction could say "use learner B".

M

Maya: Exactly. The learner comes from the verified session, never from anything the model writes.

L

Leo: So the tutor can only ever reach the learner who is talking to it.

M

Maya: Yes. Even if the model is tricked, the worst it can do is read that same learner's own history.

L

Leo: And the system jobs? Account deletion, export, the rebuild?

M

Maya: They go through a separate, clearly named interface in our code. So their wider reach is visible in the code, not hidden in a flag.

L

Leo: Okay. Next review, my answer is the structure and the test, not the handlers.

05Leo explains it back

M

Maya: Give me your answer for the reviewer.

L

Leo: We don't rely on each handler remembering a check. Identity is resolved once into a request context.

L

Leo: One authorize function decides what each actor may do. And the only way to get a store is already bound to one learner.

L

Leo: So a cross-learner read can't even be written. A contract test on every store proves B sees nothing of A's.

M

Maya: And why does that test matter so much for us?

L

Leo: We share one table, the pool model. So that test is our isolation.

M

Maya: Add the 404: it hides whether another learner's round exists at all.

Summary in three lines

  1. Resolve identity once at the edge, and let one authorize function decide what each actor may do.
  2. Hand out stores already bound to one learner, and prove it with a contract test on every store.
  3. In a pool model, structure and tests are the boundary; agents get the learner from the session, never from tool arguments.
