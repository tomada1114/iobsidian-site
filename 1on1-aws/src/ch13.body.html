ある学習者が他人のデータを見られないことを、どう確かめるか

学習者 B が、学習者 A のラウンド ID を指定してリクエストを送ってきたとします。信頼できる ID、共通の認可ポリシー、学習者に縛ったストアの三つで、このリクエストを B の持ち物の範囲に限らなければなりません。

01ID は入口で一度だけ決める

サインインで呼び出し元はわかりますが、それだけでは、ハンドラーがうっかりほかの学習者のレコードを読むことは防げません。Quickturn は、検証を済ませたリクエストの入口で一度だけ ID を導き出し、操作者、学習者、時刻、リクエスト ID を持つコンテキストを組み立てます。

データの持ち主となる学習者の ID は、リクエストのボディやパス、モデルが書いたツールの引数からは取りません。コマンドは、学習者、範囲を限ったシステムのジョブ、権限を付与されたエージェントのいずれかを示す、信頼できるコンテキストを受け取ります。要求されたレコードの ID は、どれもその所有のコンテキストの制約を受けます。

02一つのポリシー、縛ったストア、一つのテスト

一つの認可関数が、操作者と操作を確かめます。エージェントが受け取るのは明示的に付与された権限だけで、学習者本人より広い権限は持ちません。アプリが受け取るのは学習者に縛ったストアで、そのメソッドは別の任意の学習者 ID を受け付けません。

アダプターは、すべての操作にその学習者のキーを含めます。ほかの学習者のラウンドは存在しないものとして扱われ、多くの場合は、存在するかどうかを明かさずに 404 を返します。契約テストは、インメモリと DynamoDB の両方のストアで読み書きの分離を確かめ、HTTP のテストでは別々のトークンを使って同じシナリオを繰り返します。

縛ったインターフェースを使えば、所有の確認を書き忘れる機会は減ります。それでも、すべてのメソッドと今後の変更にはテストが必要です。今日の契約テストに通ることは、対象にしたケースについての証拠にはなりますが、ありうるすべての振る舞いを証明するものではありません。

03サイロ、プール、ブリッジ

サイロ型の分離では、テナントごとに別々のリソースを持たせます。プール型の分離では、リソースを共有し、テナントのキーで分けます。ブリッジ型の設計は、この二つを組み合わせます。小口の学習者が何千人もいるなら共有のテーブルが向き、少数の大口の顧客には専用のリソースが必要になることもあります。

Quickturn の API は AWS の実行ロールを一つしか使わないので、IAM だけでは、学習者ごとのアプリのリクエストを区別できません。テナントの境界を守っているのは、コードの中の信頼できる ID、認可、キーの組み立てです。リソースを分ければ運用の手間が増えますが、アプリのレベルで果たすべき責任がすべてなくなるわけではありません。

04エージェントも同じルールに従う

チューターも同じ所有のルールに従います。そのツールはモデルが渡した学習者 ID を受け付けず、許可された操作も狭く保たれています。プロンプトインジェクションでツールの引数を書き換えても、それだけで ID を変えることはできません。

これで学習者をまたぐアクセスは制限できますが、許可された操作の範囲内での有害な動作や、現在の学習者自身のデータの漏えいまでは防げません。学習者をまたぐ管理作業には、名前ではっきり区別した専用のインターフェースを使い、その広い影響範囲が見えて、レビューできるようにします。

3行まとめ

  1. ID は入口で一度だけ決め、各操作者に何を許すかは一つの authorize 関数に判断させます。
  2. 最初から一人の学習者に縛ったストアを渡し、すべてのストアで読み書きの分離をテストします。
  3. 共有したアクセスを守るのは、信頼できる ID、認可、キーの組み立てです。テストは対象にした経路の証拠になり、エージェントは信頼できるセッションの ID を使います。
