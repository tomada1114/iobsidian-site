How do we prove one learner can't see another's data?

Learner B requests learner A’s round ID. Trusted identity, a shared authorization policy and learner-bound stores must keep that request inside B’s ownership.

About 4 min readQuickturn case study

  • Silo, pool and bridge

01Identity enters once

Signing in identifies a caller but does not stop a handler from accidentally reading another learner's record. Quickturn derives identity once at the verified request edge and builds a context with actor, learner, time and request ID.

The owned learner ID does not come from a body, path or model-written tool argument. Commands receive a trusted context identifying a learner, a scoped system job or an agent with grants. Any requested record ID remains subject to that ownership context.

02One policy, bound stores, one test

One authorization function checks actor and operation. Agents receive only their explicit grants and no broader authority than the learner. The application obtains a learner-bound store whose methods do not accept another arbitrary learner ID.

The adapter includes that learner key in every operation. Another learner's round appears absent, commonly returning 404 without confirming its existence. Contract tests exercise read and write isolation for in-memory and DynamoDB stores, and HTTP tests repeat the scenario with distinct tokens.

A bound interface reduces opportunities to omit ownership checks. Every method and future change still needs tests. Passing today’s contract suite provides evidence for the covered cases, rather than proving every possible behavior.

03Silo, pool and bridge

Silo isolation gives tenants separate resources; pool isolation shares resources with tenant keys; bridge designs mix these choices. Thousands of small learners can favor a shared table, while a few large customers may need dedicated resources.

Quickturn's API uses one AWS execution role, so IAM alone does not distinguish each learner's application requests. The tenant boundary is enforced by trusted identity, authorization and key construction in code. Separate resources would add operations without removing all application-level obligations.

04Agents follow the same rule

The tutor follows the same ownership rule. Its tools do not accept a learner ID supplied by the model, and their granted operations remain narrow. Prompt injection cannot change the identity simply by changing a tool argument.

That limits cross-learner access; it does not eliminate harmful actions within allowed operations or disclosure of the current learner's data. Cross-learner administrative work uses a distinct, clearly named interface so its broader reach is visible and reviewable.

Summary in three lines

  1. Resolve identity once at the edge, and let one authorize function decide what each actor may do.
  2. Hand out stores already bound to one learner, and test read and write isolation on every store.
  3. Trusted identity, authorization and key construction enforce pooled access. Tests provide evidence for covered paths; agents use trusted session identity.
