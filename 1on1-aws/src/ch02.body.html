デプロイに AWS のキーを置かない理由

デプロイには AWS のリソースを変更する権限が要りますが、恒久的なアクセスキーを置けば、守るべき秘密がまた一つ増えます。一時的な認証情報を渡すロールを使うと、この損得が変わります。

01ユーザーとロール

IAM ユーザーは長く使い続ける ID で、パスワードやアクセスキーを持たせられます。ロールは引き受けて使うもので、引き受けると STS が一時的な認証情報を発行します。Quickturn は、長期のデプロイ用キーを保存する代わりに、ロールと Identity Center のセッションを使います。

IAM は暗黙の拒否から始まります。ポリシーで特定の操作を許可し、該当する明示的な拒否があれば、それが許可より優先されます。ルートユーザーでのアクセスは、それを必要とする作業のためだけに取っておきます。

02ロールの二つの面と OIDC

ロールについては、別々の二つの問いがあります。誰がそのロールを引き受けてよいかは信頼ポリシーが決め、引き受けたセッションで何をしてよいかは許可ポリシーが決めます。GitHub Actions は、リポジトリのシークレットから AWS のキーを取り出す代わりに、OIDC トークンを提示できます。

デプロイ用ロールの信頼ポリシーは、audience と、リポジトリおよびブランチまたは環境を表す subject を、完全一致で確認します。GitHub 側では、id-token: write の権限があればジョブがこのトークンを要求できます。こうして得たロールにできるのは、意図した CDK のデプロイ用ロールを引き受けることだけで、本番にはさらに承認のゲートを設けています。

Lambda も実行ロールを使います。Quickturn はこのロールを、必要なテーブル、キュー、シークレットのリソースに限り、復号には適切なサービス条件を付けています。アプリのコードがそれ以上のことをしようとしても、AWS へのアクセスはロールの範囲に制限されます。

03最小権限の代償

最小権限には保守の手間がかかります。新しいリソースを足すたびに、新しいポリシーが必要になることがあります。広いワイルドカードを使えばこの種の失敗は減りますが、望まない操作まで許すことになります。レビューの労力は、被害が最も大きくなりうる本番の権限と信頼条件に集中させてください。

OIDC の subject の条件が広すぎると、意図しないワークフローまで受け入れてしまいます。それでも、リポジトリを正確に指定する意味は残ります。正しいリポジトリの全ブランチを受け入れるのと、無関係なリポジトリまで受け入れるのとでは、危険の大きさが違います。付与した許可の一覧だけでなく、信頼の設定もデプロイの境界の一部として扱ってください。

04エージェントにもロールがある

ホスト型のエージェントにも、モデルや AWS のサービスにアクセスするための実行ロールがあります。ただし、そのロールがあるからといって、ツールがどの学習者のアプリデータを読めるかが自動的に決まるわけではありません。

Quickturn は二つの層をどちらも確認します。AWS の権限はサービスの操作を許可し、アプリの認可はその操作を、検証済みの学習者と付与された機能に結び付けます。テーブルへのアクセスを許可しても、テナントの分離の代わりにはなりません。

3行まとめ

  1. 長期のキーを持つユーザーより、一時的な認証情報を使うロールを選び、それぞれの ID には必要な権限だけを与えます。
  2. 信頼ポリシーは誰がロールを引き受けられるかを決め、OIDC を使えば CI はシークレットを保存せずに身元を証明できます。
  3. 信頼ポリシーと、データにアクセスできる権限に最も注意を払います。ロールが制限するのはリソースで、誰のデータかまでは制限しません。
