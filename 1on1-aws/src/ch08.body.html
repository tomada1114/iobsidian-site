What if the app crashes halfway through a write?

After this page you can explain why several related writes belong in one DynamoDB transaction. You can also explain version conditions, and how a transaction's limits shape commands.

01Half-done writes

Saving an answer and updating points in separate writes creates a partial-success problem. A crash between them leaves the log and derived totals disagreeing, and retrying can duplicate one side rather than repair it.

Quickturn treats the answer log as history and points, day counts and memory state as projections. The commit must include every change required for the accepted answer's meaning.

02One commit with conditions

TransactWriteItems groups up to 100 actions with a 4 MB aggregate item limit. Actions cannot target the same item twice. A new answer carries a nonexistence condition; an updated aggregate carries its expected version. A condition check can guard a record that is not being changed.

The application loads, decides and sends a complete conditional commit rather than holding an open database transaction while running its rule. On conflict it reloads and recomputes, with a bounded three-attempt policy.

The in-memory store and local DynamoDB adapter run the same contract cases. Tests reject oversized commits, duplicate target keys and attempts to mutate append-only answers. The fake provides evidence about those tested semantics, not every cloud failure mode.

03What transactions cost

Transactional capacity costs more than ordinary writes and imposes limits on command size. A shared learner-totals item can also create contention if many writers update it. Count actual actions when chunking offline answers.

Atomicity covers only the submitted actions. A forgotten projection remains a logic bug, so command tests and rebuild tooling still matter. Single-item changes may need only an atomic update; asynchronous projections can suit reports whose readers accept lag.

04Conditions that guard money

Model-call accounting has a similar conditional boundary. Reserve a maximum affordable amount before starting, record the attempt under a stable job key, then settle the actual cost or reconcile a failed attempt.

Conditions can prevent a repeated job from charging the learner twice. They do not themselves stop a provider call already in flight. Reservation expiry, attempt coordination and recovery must therefore be designed alongside the transaction.

Summary in three lines

  1. Commit a log entry and the summaries derived from it in one transaction, so all apply or none do.
  2. Conditions make it safe: new items must not exist, and updates must still be at the version read.
  3. Transactions cost double and allow 100 actions, which shapes how commands are cut.
