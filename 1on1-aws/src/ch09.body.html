インフラをコードで書くのはなぜか

コンソールで設定を変えて API が速くなっても、次のデプロイでその変更が上書きされるかもしれません。レビューを経たインフラのコードには、設定そのものと、その理由の両方を残す必要があります。

01コンソールで済ませない理由

コンソールで試すと、Lambda のメモリを増やせばレイテンシが改善する、とわかることがあります。その変更をインフラのコードに反映しなければ、次のデプロイで元に戻るか、コードとずれた設定（ドリフト）が残ります。インフラをコードで書けば、意図した構成をレビューでき、同じ構成を再現できます。

サンドボックスでの試行は役に立ちますが、そこで得た変更は、理由と一緒にソースへ書き戻すべきです。そのうえで、実際に動いているアカウントがソースと一致しているかも確かめる必要があります。

02CDK の仕組み

CDK はプログラムを実行して、CloudFormation のテンプレートとデプロイ用のアセットを合成（synthesize）します。CloudFormation は変更セットを計算して適用します。更新に失敗すると多くの場合はロールバックされますが、ロールバック自体が失敗したり、保持されたリソースが残って対応が必要になったりすることもあります。

ブートストラップは、アカウントとリージョンごとに、デプロイ用のリソースとロールを作ります。Quickturn は、基盤、デプロイ用アクセス、アプリ、エージェントの四つのスタックを使い、デプロイの順序を明示しています。開発環境へのデプロイは自動にし、本番は承認を待つようにできます。

03ツールの選択肢

CloudFormation と SAM は、AWS が管理するスタックを定義します。CDK はプログラミング言語の層を提供しますが、デプロイは引き続き CloudFormation を通して行います。Terraform などのツールは、AWS 以外も含む幅広いプロバイダーを扱え、独自の状態管理のモデルを持っています。

Quickturn が TypeScript の CDK を選んだのは、CloudFront、WAF、Cognito、関数にまたがるインフラで、言語とテストを共通にするためです。CDK を使えば CloudFormation のデプロイが一瞬で終わる、とは考えていません。関数が中心の、もっと小さなシステムなら、SAM を選ぶのも妥当です。

04代償とテストのしかた

インフラの抽象化は、作者が明示的に書いていない権限やリソースを生成することがあります。コンストラクトの名前だけを頼りにせず、合成された結果をテストしてください。特に、キースキーマ、保持の設定、課金モード、OIDC の信頼関係は確かめておきたいところです。

焦点を絞ったアサーションとリソースの許可リストを使うと、重要な変更が目に入りやすくなります。テンプレート全体のスナップショットでは、大きな差分の中に埋もれがちです。バンドルのテストはデプロイ時のパッケージングの誤りを捕まえ、デプロイ後の読み取りは実際の設定を確かめます。

コンストラクトが実環境への問い合わせ（lookup）を必要としなければ、合成はオフラインでも動きます。合成とテンプレートのテストに通っても、デプロイが受け入れられたことの確認にはなりません。動いているサービスに要求どおりの設定が入っているかは、実環境で確かめる必要があります。

3行まとめ

  1. インフラをコードで書くと、意図した環境をレビューできる形で定義できます。それでも、コンソールで生じたドリフトを見つけるには実環境の確認が要ります。
  2. CDK は CloudFormation のテンプレートを合成し、CloudFormation がそれをスタックとして適用して状態を持ちます。
  3. 合成したテンプレートで大事な点をテストし、デプロイ後には実際のリソースを読み戻します。
前へ書き込みの途中でアプリが落ちたらどうなるか 次へよく壊すものと、失ってはいけないものを分ける
