Why write infrastructure as code at all?

After this page you can explain what infrastructure as code gives you and how CDK becomes a CloudFormation stack. You can also compare the main tools, and say how to test what they produce.

About 8 min readPairing at Leo's desk

In this page

  • What's wrong with changing things in the console?
  • How does CDK code become real resources?
  • How do the tools differ?
  • What does infrastructure as code cost, and how do we test it?

Leo's desk. He has just changed a setting in the AWS console.

01Why not the console

L

Leo: I raised the API function's memory in the console, to test a slow request. It helped a lot.

M

Maya: Useful test. When's the next merge to main?

L

Leo: This afternoon, probably. Why?

M

Maya: Because the next deploy will quietly put the memory back. The code still says the old value.

L

Leo: Oh. So my change disappears, and nobody notices.

M

Maya: Or the opposite. Someone's console change stays, and the code no longer describes what's running. That gap has a name: drift.

L

Leo: I always thought the console was the real state, and code was a way to automate clicking.

M

Maya: That's the misconception. For us, the code is the source of truth. Infrastructure as code means the environment is defined in files, like any other code.

L

Leo: What does that give us, besides no drift?

M

Maya: The same environment twice: dev and prod from one source. Review in pull requests, before anything changes.

L

Leo: And after it changes?

M

Maya: History in git, so you can see who changed what and why. And a new environment from one command.

L

Leo: So a reviewer would have seen my memory change and asked why.

M

Maya: Right. And the reason would live in the commit, not in your memory.

L

Leo: Is the console useless, then?

M

Maya: No. It's fine for exploring in a sandbox account. The rule is: whatever you learn there, you write back into code.

02How CDK works

L

Leo: How does our CDK code actually become resources?

M

Maya: Let me draw it. It's a pipeline, and each step has a job.

L

Leo: What's a construct?

M

Maya: A building block in code, like "a DynamoDB table". A bigger one might be "a Lambda function with its role".

L

Leo: And cdk synth?

M

Maya: It runs our program and writes a CloudFormation template. Assets come with it, like the bundled Lambda code.

L

Leo: And cdk deploy?

M

Maya: It uploads the assets to the bootstrap bucket. Then CloudFormation computes a change set, the list of what will be created, changed or deleted.

L

Leo: And if a step fails halfway?

M

Maya: CloudFormation rolls the stack back to where it was. That's a big reason to use it.

L

Leo: Where does it remember what exists? My friend's team keeps a state file.

M

Maya: With CloudFormation, the state lives in AWS, in the stack itself. There's no file for us to keep or lose.

L

Leo: What's the bootstrap bucket?

M

Maya: Bootstrapping, done once per account, creates what CDK deploys through. That means an S3 bucket, a KMS key, IAM roles, a container repository and a parameter. After that, every deploy uses them.

L

Leo: How many stacks do we have?

M

Maya: Three in each account: foundation, deploy-access, and app. An agents stack holds the tutor agent.

L

Leo: And how do deploys run?

M

Maya: GitHub Actions deploys foundation, then app, to dev on every merge to main, with no manual step. Prod waits for a manual approval. The deploy-access stack is deployed by hand, once per account.

03The tools

L

Leo: Why CDK? My old agency used Terraform.

M

Maya: Let's compare on two questions. How do you write it: as configuration, or in a programming language? And who keeps the state: AWS, or you?

L

Leo: CloudFormation is configuration, YAML or JSON, and AWS keeps the state.

M

Maya: Right. SAM too; it's an extension of CloudFormation for functions and APIs. CDK is a real programming language, and it still compiles to CloudFormation, so AWS keeps the state.

L

Leo: And Terraform is its own configuration language, with a state file you keep.

M

Maya: You run its state store and its locking, so two people can't apply at once. In return, it has providers for many clouds and services. Let me draw the four corners.

L

Leo: So why did we land bottom right?

M

Maya: Three reasons. Our server is TypeScript, so the infrastructure shares the same language, checks and tests. Terraform would need its own state store. And SAM leaves CloudFront, WAF, Cognito and our stack split to raw CloudFormation.

L

Leo: My guess was that CDK wins because it's newer and faster to deploy.

M

Maya: Newer, yes. Faster, no. A CDK deploy is a CloudFormation deploy, so it's just as slow.

L

Leo: So speed was never the reason. The reasons are the language and not running a state store.

M

Maya: Right. And the size of what we run.

L

Leo: So SAM is great for a function and an API, but we have much more than that.

M

Maya: Right. For a small team that only runs functions, SAM would be a fine choice.

04What it costs, and how we test it

L

Leo: Does infrastructure as code have downsides?

M

Maya: Several. A learning curve. Slow deploys. CloudFormation's own limits. And abstractions that create resources and IAM policies you never wrote.

L

Leo: The last one sounds dangerous.

M

Maya: It is. A construct can add a role with more permissions than you'd choose. So we test what the code makes. Here's the ladder of checks, fastest first.

L

Leo: How do the template tests work?

M

Maya: Synthesis needs no AWS credentials. So tests synthesize every stage and assert what matters: the table's key schema, billing mode, retain policies, trust conditions, the exact permissions.

L

Leo: What about a whole-template snapshot? That's one line.

M

Maya: We avoid snapshots. A large snapshot diff gets approved without anyone reading it. We also keep an allowlist of resource types in the app stack's test.

L

Leo: So if a construct quietly adds a new kind of resource…

M

Maya: The test fails, and adding that type becomes a conscious change. One more test bundles the function exactly as a deploy does.

L

Leo: And after all that is green?

M

Maya: A green synth proves nothing about the live account. After a deploy, read the real resource back: the table's settings, the function's memory.

L

Leo: Which is exactly where my console change would have shown up.

M

Maya: Yes. Now put your memory change in the code, and let review decide.

05Leo explains it back

M

Maya: A new teammate asks why they can't just click in the console. What do you say?

L

Leo: Infrastructure as code means the environment is defined in reviewed code. Dev and prod come from the same source.

L

Leo: A console tweak can't quietly drift, because the next deploy puts the code's version back.

L

Leo: CDK is TypeScript that turns into a CloudFormation template. CloudFormation does the create, update and rollback, and keeps the state.

M

Maya: And testing?

L

Leo: We test the synthesized template for the properties we care about, and a list of allowed resource types. No snapshots.

M

Maya: One step is missing: after a deploy, check the real resource. A green template test only proves what we asked for, not what's running.

Summary in three lines

  1. Infrastructure as code makes environments reproducible and reviewable, and stops console changes from drifting.
  2. CDK synthesizes CloudFormation templates; CloudFormation applies them as stacks and keeps the state.
  3. Test the synthesized template for what matters, then read the live resource back after a deploy.
