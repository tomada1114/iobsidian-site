DynamoDB はなぜデータをすばやく見つけられるのか

API が必要とするのは一人の学習者の練習ラウンドで、全学習者のレコードではありません。パーティションキーとソートキーの範囲を使うと、DynamoDB はこの問いに的を絞って答えられます。

01アイテム、キー、パーティション

DynamoDB は、属性とプライマリキーを持つアイテムを保存します。Quickturn は、パーティションキーとソートキーの組み合わせを使います。パーティションキーで論理的なまとまりを選び、物理的な保存先への分散は DynamoDB が内部で行います。ソートキーはそのキーの中でアイテムを並べ、範囲での取得を可能にします。

キーをすべて指定すれば、GetItem で一つのアイテムを直接取り出せます。Quickturn のパーティションキーは学習者を表し、ソートキーは設定、ラウンド、回答など、その学習者が持つレコードを表します。論理的な学習者のパーティションが、物理的な保存先のパーティションと常に1対1で対応しているわけではない点に注意してください。

02Query と Scan の違い

Scan は、フィルタを適用する前にテーブルのアイテムを読みます。そのため、一人の学習者でフィルタしても、ほかの学習者を読む費用は減りません。一方の Query は、パーティションキーを指定したうえで、ソートキーの範囲や接頭辞で絞り込めます。

Quickturn は、リクエスト経路での読み取りをこれらのキーに対応させ、ページ分割にも対応します。1ページのレスポンスにはサイズの上限があるからです。一つの接頭辞でラウンドと回答の両方が返る場合は、アイテムの種類を確かめます。セカンダリインデックスを使えば別のキーのパターンにも対応できますが、書き込み、ストレージ、整合性について考えることが増えます。

03キャパシティ、整合性、サイズ

オンデマンドのキャパシティは不規則なトラフィックに、プロビジョンドのキャパシティは予測できる負荷に向きます。どちらでもスロットリングは起こりえますし、一つのキーにアクセスが集中するホットキーでも起こります。キャパシティをどう選んでも、アラームは必要です。

DynamoDB の読み取りは、デフォルトでは結果整合性です。Quickturn は、受け付けた回答をすぐに反映する必要がある場面で、強い整合性の読み取りを要求します。強い整合性の読み取りはキャパシティを多く消費し、グローバルセカンダリインデックスでは使えません。

1つのアイテムの上限は 400 KB です。際限なく増える回答の履歴は、一つのレコードを伸ばし続けるのではなく、別々のアイテムとして保存します。複数のアイテムにまたがるトランザクションを使えば、その上限の範囲内でアトミックな変更ができます。

04DynamoDB で手放すもの

DynamoDB は、マネージドなキーベースのアクセスを提供する代わりに、リレーショナルデータベースのような結合や自由な探索を手放しています。アクセスパターンは事前に計画しなければなりません。Quickturn は、広い範囲のレポートにはエクスポートを使い、学習者向けのリクエスト経路でスキャンすることはしません。

必要な問いがまだはっきりしない場合や、関係とレポートが中心になる場合は、リレーショナルデータベースのほうが育てやすいかもしれません。ポイントインタイムリカバリは、別のテーブルとして復元します。そのため、復元したデータをサービスに戻す手順を、あらかじめ試しておく必要があります。

3行まとめ

  1. パーティションキーはアイテムの置き場所を決め、ソートキーはそのパーティションの中でアイテムを並べます。
  2. キーをすべて指定して Get するか、一つのパーティションを Query します。Scan はすべてを読み、フィルタは結果を削るだけです。
  3. キャパシティモードと整合性は意図して選び、テーブルを設計する前に問いを書き出します。
