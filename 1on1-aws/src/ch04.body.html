Quickturn に VPC がないのはなぜか

Web アプリと API は、ブラウザから見て一つのオリジンにまとめたい一方で、どちらもデータベースへの非公開の接続は必要としません。この違いが、Quickturn の配信とネットワークの形を決めています。

01エッジ

CloudFront は、ブラウザ向けのアプリをエッジロケーションから配信します。オリジンの S3 バケットはパブリックアクセスをブロックし、オリジンアクセスコントロール（OAC）によって、意図したディストリビューションにだけアクセスを許可しています。ビューアーとの間も、オリジンとの間も HTTPS を必須にしています。

小さなエッジ関数が、クライアント側のルートを静的アプリの入口ページに書き換えます。これで、設定画面のルートに直接アクセスしても、バケットを公開の Web サイトにすることなく画面を表示できます。

02二つのバックエンドを一つのオリジンにまとめる

一つのドメインで、静的ファイルは S3 へ、/api は API へ振り分けます。静的なアセットはキャッシュできますが、学習者ごとに異なる API のレスポンスには、キャッシュを無効にするポリシーを使い、必要なヘッダー、Cookie、クエリ文字列を転送します。

ブラウザから見てオリジンが一つなので、Cookie の扱いが単純になり、クロスオリジンのリクエストも発生しません。ネイティブのクライアントは、ブラウザの CORS の制約を同じようには受けません。運用上の利点が Web 側の追加設定に見合うなら、API に別のホスト名を割り当てる選択肢も残っています。

03VPC は何のためにあるか

VPC は、サブネット、ルーティング、セキュリティグループを持つ AWS 上のネットワークを定義します。ルートテーブルにインターネットゲートウェイへのルートがあるサブネットが、パブリックサブネットです。ただし、実際に外から到達できるかどうかは、アドレスとセキュリティの設定にも左右されます。プライベートなリソースは、外向きの通信に NAT やサービスエンドポイントを使うことがあります。

Quickturn は、IAM で認可された署名付きのリクエストで、マネージドサービスのパブリックなエンドポイントを呼び出します。到達すべきプライベートなデータベースもありません。そのため、この経路では VPC のネットワーク費用がかかりません。ただし、エンドポイントがパブリックだからといってアプリのテーブルが公開されるわけではありませんし、IAM だけでアプリへのあらゆる脅威に対処できるわけでもありません。

04VPC が必要になるとき

VPC が役に立つのは、プライベートな RDS のデータベースや社内のサービス、VPN や Direct Connect でつないだネットワークに到達するときです。規制や組織の要件によって、通信経路が制約されることもあります。

Quickturn は現在の構成で、エッジでの制御、IAM、アプリの認証を組み合わせています。WAF のルールで乱用的なリクエストの頻度を抑えることはできますが、学習者を認証したり、ユーザーごとのモデル利用の予算を守らせたりはできません。プライベートなネットワークは、具体的なリソースやポリシーが必要としたときに追加し、その固定費とデータ転送の費用も判断に含めてください。

3行まとめ

  1. CDN は非公開のバケットを配信しつつ /api/* を API へ振り分けられるので、ブラウザからはオリジンが一つに見えます。
  2. Quickturn は IAM とアプリの認証・認可を組み合わせており、現在のリクエスト経路には自前の VPC を必要とするリソースがありません。
  3. プライベートなものに到達する必要が出たら VPC を追加し、1時間ごとに課金される NAT ゲートウェイやエンドポイントの費用を見込みます。
