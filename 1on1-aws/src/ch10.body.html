01状態を持つものと、頻繁に作り直すもの

スタックはライフサイクルで分けます。Quickturn の基盤スタックは学習者テーブルとユーザープールを持ち、アプリのスタックは、頻繁に作り直すコンピュート、静的配信、アラームを持ちます。長く残すべきデータを、アプリのリリースのたびに巻き込むような結合は避けます。

DeletionPolicy と UpdateReplacePolicy で保持を指定すると、スタックの削除や置き換えのときに既存のリソースが守られます。ユーザープールを新しくすると、プロバイダー側の ID が変わります。アプリは、内部の学習者との対応付けを維持するか、移行しなければなりません。古いプールを保持していても、新しいプールがそのまま使えるようになるわけではありません。

削除保護と、本番でのポイントインタイムリカバリは、さらに安全策を重ねます。事故は減らせますが、復旧と移行の手順が要らなくなるわけではありません。

02ゆるい結合

CloudFormation のエクスポートを使うと、スタック間の参照が検証されます。ただし、ほかのスタックにインポートされたエクスポートは、自由に削除したり変更したりできません。そこで Quickturn は、基盤の識別子を、ステージごとの Parameter Store の名前で公開しています。

これで CloudFormation 上の結合はゆるくなりますが、文字列の約束事とデプロイの順序という代償を払います。テストでは、基盤が書き込む名前と、アプリが読む名前を確かめます。それでも、値が欠けていたり誤っていたりすることは、実行時とデプロイ時の確認で見つけなければなりません。

03ステージ、設定、シークレット

一つのインフラのプログラムから、検証済みのステージ設定をもとに、開発環境と本番環境を作ります。復旧、削除保護、サインアップの方針、承認といった違いは、明示したうえで小さく保ちます。

普通の設定は起動時に解析します。シークレットは、誰でも読めるテンプレートや関数の設定に書くのではなく、取得できる相手を絞り、必要に応じてローテーションします。

Parameter Store と Secrets Manager は、想定するライフサイクルと料金体系が異なります。Quickturn は、めったに変えないクライアントシークレットに SecureString のパラメータを使い、キャッシュを通して取得します。キャッシュの有効期間は、ローテーションがいつ反映されるかに影響します。名目上の TTL が過ぎたからといって、すべての環境がすでに更新済みだという証拠にはなりません。

シークレットをコピーする独自のデプロイ用コードにも、狭い権限と、シークレットの値を出力しないログが必要です。

04分割の代償

スタックを二つにすると、順序を守ったデプロイと、両者をつなぐ識別子の保守が必要になります。保持されたリソースはスタックより長く残り、課金も続きます。そのため、削除はついでに行うのではなく、明示的でレビューを経た後片付けとして行います。

使い捨てのプロトタイプなら、同じ分割は要らないかもしれません。本番の学習者データについては、長く残すリソースを切り離すことで、アプリのデプロイ失敗が届く範囲を狭められます。ただし、それでデータが決して危険にさらされないと言えるわけではありません。

3行まとめ

  1. 状態を持つリソースは、めったに変えないスタックに置き、削除時も置き換え時も保持します。
  2. 名前付きのパラメータでスタックの結合はゆるくなりますが、識別子の約束事をテストで確かめる必要があります。
  3. すべてのステージを一つのアプリから作り、シークレットの保存先はアクセスとローテーションの要件で選びます。
