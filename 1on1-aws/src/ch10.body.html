Split what breaks often from what must never be lost

After this page you can explain why data lives in its own stack with retain policies. You can also explain how stacks find each other without locking, and where configuration and secrets belong.

About 8 min readThe morning after a failed deploy

In this page

  • Why keep the data in a separate stack?
  • How do two stacks find each other?
  • How do dev and prod differ, and where do secrets go?
  • What does the split cost?

Morning. The app stack's deploy failed overnight and rolled back.

01Stateful versus rebuilt often

L

Leo: The overnight deploy of the app stack failed and rolled back. Everything's fine now. But could a bad deploy ever delete the learner table?

M

Maya: Not from the app stack. The table isn't in it.

L

Leo: Where is it, then? I assumed one stack held everything. That seems simpler.

M

Maya: It's simpler at first. We split by one question: does this resource keep data we can't rebuild?

L

Leo: The learner table, obviously. What else?

M

Maya: The user pool. Every learner's account lives there. Those two sit in the foundation stack, which almost never changes.

L

Leo: And the rest?

M

Maya: The distribution, the bucket with the web app, the API, the function, the alarms. All of that is in the app stack, deployed on every merge.

L

Leo: So a failed deploy only touches things we can rebuild from code.

M

Maya: Right. Let me compare the two stacks.

L

Leo: How can a resource survive its stack being deleted?

M

Maya: A retain policy. CloudFormation's DeletionPolicy says: when the stack goes, keep this resource. We set it on both, in every stage.

L

Leo: Then why was I nervous? Nobody deletes stacks.

M

Maya: Deletion isn't the quiet danger. Replacement is. Some property changes make CloudFormation build a new resource and remove the old one.

L

Leo: Like what?

M

Maya: Change a table's key, and you get a new, empty table. Change certain sign-in settings on a user pool, and you get a new pool.

L

Leo: A new pool just means new accounts. Learners sign in again, right?

M

Maya: Worse. A new pool issues new user ids. Every learner's data is keyed by the old id, so it's stranded.

L

Leo: Oh. Their history is still there, but nobody can reach it.

M

Maya: So we also set UpdateReplacePolicy to retain. Then a replacement keeps the old resource instead of deleting it.

L

Leo: Anything else in prod?

M

Maya: Deletion protection on the user pool, in every stage. On the table in prod, deletion protection and point-in-time recovery.

02Loose coupling

L

Leo: If the app stack doesn't hold the table, how does the function know its name?

M

Maya: What would you guess?

L

Leo: CloudFormation exports. One stack exports a value, the other imports it.

M

Maya: That's the obvious way, and it locks both stacks. Once another stack imports an export, the exported value can't change.

L

Leo: And the exporting stack?

M

Maya: It can't be deleted while anything imports from it. You end up untangling imports before every change.

L

Leo: So what do we do instead?

M

Maya: The foundation writes its identifiers to Parameter Store, under a path for the stage. The app stack reads them by name when it deploys.

L

Leo: So the foundation publishes, and the app looks up. Nothing is locked.

M

Maya: Right. The stack outputs carry no export names at all.

L

Leo: What's the catch?

M

Maya: The name is a string contract, and nothing enforces it. Rename a parameter on one side, and the other side breaks at deploy time.

L

Leo: So the tests check both sides.

M

Maya: Yes. One test checks what the foundation writes, another checks what the app reads, from the same list of names.

03Stages, config and secrets

L

Leo: Is prod a separate CDK app?

M

Maya: No. One app builds dev or prod from a stage setting. The setting is checked before any template is written.

L

Leo: What does the stage change?

M

Maya: A short, listed set of things. Point-in-time recovery, table deletion protection, self sign-up, and the approval before deploy.

L

Leo: Why keep the list short?

M

Maya: So prod is the same design, not a second one. Every difference is a place where dev can't warn you about prod.

L

Leo: Wait, dev has no point-in-time recovery?

M

Maya: By choice. Dev holds only the team's own test data. We accept losing it in exchange for a simpler, cheaper stage.

L

Leo: And configuration inside the function?

M

Maya: Read once at startup, from one place, and validated. A missing value fails the start, not a request an hour later.

L

Leo: My last team put secrets in environment variables. Is that wrong?

M

Maya: They show up in the console and in the template. Anyone who can read the function's settings can read them.

L

Leo: So where do secrets go?

M

Maya: Two questions: is it secret, and must it rotate? Here are the two stores we use for secrets.

L

Leo: I'd have picked Secrets Manager for everything. It sounds like the proper place.

M

Maya: It's a fine place, but you pay for every secret, every month. Most of ours never rotate, so that buys nothing.

L

Leo: So SecureString by default, and Secrets Manager only when we need rotation.

M

Maya: Right. Standard parameters carry no extra charge. Secrets Manager costs a small monthly amount per secret.

L

Leo: How does a secret get into a SecureString? Surely not typed into the template.

M

Maya: CloudFormation can't create a SecureString. So a small custom resource copies the secret Cognito gave our web backend into one.

L

Leo: A custom resource?

M

Maya: A function CloudFormation runs during the deploy.

L

Leo: And the secret never appears in a template or a log.

M

Maya: Right. The function reads it through the Parameters and Secrets extension. That's a small helper running next to the function, and it caches values.

L

Leo: For how long?

M

Maya: Five minutes at most. So a changed value reaches every function within five minutes.

04What the split costs

L

Leo: This all sounds safer. What does it cost?

M

Maya: Two stacks mean deploy order: foundation first, then app. And the parameter names are a contract to keep.

L

Leo: And retained resources?

M

Maya: They outlive their stack. If you really want one gone, you remove it by hand.

L

Leo: So a dev table from an old experiment could sit there forever.

M

Maya: It could, and it would still bill for its storage. Somebody has to clean up on purpose.

L

Leo: When would you use one stack?

M

Maya: For a throwaway prototype with no data worth keeping. Nothing to lose, so nothing to protect.

L

Leo: And last night's rollback?

M

Maya: Read why it failed, fix it in code, and merge. The data was never at risk.

05Leo explains it back

M

Maya: The PM heard about the failed deploy. Explain why the data was safe.

L

Leo: The table and the user pool live in a foundation stack that rarely changes. Retain policies keep them even if that stack is deleted.

L

Leo: Everything else is in an app stack we rebuild on every merge. The app stack finds the table by parameter name, not by export.

L

Leo: Prod is the same app with a different stage setting. Secrets go in SecureString parameters unless they need rotation.

M

Maya: Anything the PM should worry about?

L

Leo: Not for last night. The app stack can't touch the table.

M

Maya: The risk worth naming is replacement. A changed key still swaps in a new, empty table, and the retain policy only keeps the old one. Our key-schema test catches that change before it ships.

Summary in three lines

  1. Keep stateful resources in a rarely changed stack, retained on deletion and on replacement.
  2. Connect stacks through named parameters, not exports, so neither locks the other.
  3. Build every stage from one app, and keep secrets in SecureString unless they must rotate.
