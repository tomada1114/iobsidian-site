Where should a web app keep its tokens?

An injected script can steal a token from browser storage. HttpOnly cookies reduce direct token theft while leaving authenticated requests and CSRF to protect.

01The risk in localStorage

JavaScript on a page can read localStorage, including injected scripts or compromised dependencies. Persisting a refresh token there can turn a browser compromise into continued access after the page closes.

An HttpOnly cookie prevents direct script reads of that cookie value. It does not make XSS harmless: injected code can still issue authenticated requests, read permitted responses and exfiltrate data. Use cookie protection together with injection defenses and appropriately scoped sessions.

02The backend and its cookies

Quickturn's API also acts as a backend-for-frontend for login, callback, refresh and logout. It keeps client secrets server-side and sets access, refresh and temporary sign-in cookies with explicit lifetimes and attributes.

A __Host- cookie requires Secure, Path=/ and no Domain attribute, reducing cookie injection from sibling subdomains. Refresh rotation and a short concurrency grace period help manage renewal, but access-token revocation behavior must be evaluated separately.

Refresh and logout are state-changing POSTs. Expired or unusable refresh credentials send the user through sign-in again. Same-origin app and API routing simplifies delivery of these cookies.

03Forged requests

Cookies are attached automatically, which creates CSRF risk. Quickturn combines SameSite=Lax with an exact Origin allowlist on state-changing requests and a validated state value for the sign-in callback. The callback needs its own protection because it is a navigation from the identity provider.

Safe reads must not change state. Bearer-token paths have different CSRF properties because another site does not automatically possess their Authorization header. XSS and token leakage remain separate threats even when CSRF checks are correct.

04What it costs

The backend now owns login, cookies and renewal, and both cookie and Bearer paths need equivalent authorization tests. Cookie size limits and local HTTPS behavior also affect implementation. Separate production origins require revisiting cookie and CORS policy rather than assuming this arrangement transfers unchanged.

An in-memory browser token can suit some threat models, while native apps use platform secure storage. Choose persistence and session design from actual risks and interaction needs. No storage choice replaces protecting the application from script injection.

Summary in three lines

  1. Tokens in localStorage can be read by any script on the page, including a compromised dependency.
  2. A backend-for-frontend keeps tokens in HttpOnly, Secure, SameSite cookies with the __Host- prefix.
  3. Cookies are sent automatically, so add CSRF defenses and rotate the refresh token.
