Web アプリはトークンをどこに置くべきか

注入されたスクリプトは、ブラウザのストレージからトークンを盗めます。HttpOnly Cookie を使えばトークンを直接盗まれる危険は減りますが、認証済みのリクエストの悪用と CSRF には、引き続き対策が要ります。

01localStorage の危険

ページ上の JavaScript は localStorage を読めます。注入されたスクリプトや、乗っ取られた依存パッケージも例外ではありません。そこにリフレッシュトークンを保存すると、ブラウザが一度侵害されただけで、ページを閉じたあとも攻撃者がアクセスし続けられるおそれがあります。

HttpOnly Cookie にすると、スクリプトはその Cookie の値を直接読めなくなります。ただし、XSS が無害になるわけではありません。注入されたコードは、認証済みのリクエストを送り、読み取りが許されたレスポンスを読み、データを外へ持ち出せます。Cookie による保護は、スクリプト注入への対策や、範囲を適切に絞ったセッションと組み合わせて使ってください。

02バックエンドと Cookie

Quickturn の API は、ログイン、コールバック、更新、ログアウトを受け持つ BFF（Backend for Frontend）も兼ねています。クライアントシークレットはサーバー側に置き、アクセストークン用、リフレッシュトークン用、サインイン中だけ使う一時的な Cookie を、有効期間と属性を明示して設定します。

__Host- の Cookie には Secure と Path=/ が必須で、Domain 属性は付けられません。これにより、兄弟関係にあるサブドメインから Cookie を注入される危険が減ります。リフレッシュトークンのローテーションと、同時更新に備えた短い猶予期間は更新の管理に役立ちますが、アクセストークンの失効がどう振る舞うかは別に評価する必要があります。

更新とログアウトは、状態を変える POST です。リフレッシュ用の認証情報が期限切れか使えない場合は、ユーザーにもう一度サインインしてもらいます。アプリと API を同じオリジンで振り分けているので、これらの Cookie の受け渡しは単純になります。

03偽造されたリクエスト

Cookie は自動で付けて送られるため、CSRF の危険が生じます。Quickturn は、SameSite=Lax に加えて、状態を変えるリクエストでは Origin を許可リストと完全一致で照合し、サインインのコールバックでは検証済みの state の値を使います。コールバックは ID プロバイダーからの画面遷移なので、専用の保護が必要です。

安全なはずの読み取りで、状態を変えてはいけません。Bearer トークンを使う経路は、CSRF に対する性質が異なります。ほかのサイトは、その Authorization ヘッダーを自動的には手に入れられないからです。CSRF の確認が正しくても、XSS とトークンの漏えいは別の脅威として残ります。

04この構成の代償

この構成では、ログイン、Cookie、更新をバックエンドが受け持つことになり、Cookie と Bearer の両方の経路に同等の認可テストが必要です。Cookie のサイズの上限や、ローカル環境での HTTPS の扱いも実装に影響します。本番でオリジンを分けるなら、この構成がそのまま通用すると考えず、Cookie と CORS の方針を見直してください。

脅威モデルによっては、ブラウザのメモリ上にだけトークンを置く方法が合うこともあります。ネイティブアプリは、プラットフォームの安全なストレージを使います。トークンの保存方法とセッションの設計は、実際の危険と操作の要件から選んでください。どの保存方法を選んでも、スクリプト注入からアプリを守ることの代わりにはなりません。

3行まとめ

  1. localStorage のトークンは、乗っ取られた依存パッケージを含め、ページ上のどのスクリプトからも読めます。
  2. BFF は、トークンを __Host- 接頭辞付きの HttpOnly、Secure、SameSite な Cookie に入れて扱います。
  3. Cookie は自動で送られるので、CSRF 対策を加え、リフレッシュトークンをローテーションします。
