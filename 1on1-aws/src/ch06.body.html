PostgreSQL ではなく DynamoDB を選んだ理由

Quickturn には、学習者ごとのレコードを分離し、エクスポートし、削除できることが求められます。使われていないときの費用も小さく抑えたいところです。データベースの比較では、製品の好みより先に、こうした要件を手がかりにします。

01製品より先に判断の軸を決める

Quickturn は、製品を比べる前に判断の軸を書き出します。学習者の分離、素直なエクスポートと削除、使われていないときの低い費用の三つです。加えて、Lambda から扱いやすいアクセス、条件付き書き込み、派生した状態を作り直せるだけの履歴も必要です。

これらはアプリの要件であって、SQL や NoSQL への好みではありません。比較が役に立つのは、どの候補も同じ要件と同じ運用の前提で評価したときだけです。

02候補を並べて比べる

候補は、オンデマンドの DynamoDB、Aurora DSQL、Aurora Serverless v2、RDS for PostgreSQL です。使われていないときのふるまい、ネットワークと接続の要件、トランザクションの意味論、ローカルでのテスト方法が、それぞれ異なります。

PostgreSQL 互換のサービスが、トランザクションや対応機能のすべてで PostgreSQL と同じとは限りません。判断の際には、実際のエンジン、バージョン、上限、必要なネットワーク経路を確かめる必要があります。このワークロードについて Quickturn が選んだのは、DynamoDB の学習者キーのモデルと、テスト済みの条件付きコミットの約束事です。ほかのワークロードなら、リレーショナルなサーバーレスサービスのほうが有利になることもあります。

03DynamoDB の代償

DynamoDB では、リクエスト経路での読み取りごとにキーを設計し、場当たり的なレポートにはエクスポートを使い、派生した集計（プロジェクション）を保守しなければなりません。回答のログが完全に残っていれば集計の修復に役立ちますが、更新を一度取りこぼせば、ずれが生じることもあります。

アクセスパターンが定まっていない場合や、多対多の関係に制約をかける必要がある場合は、リレーショナルなストレージのほうが早く始められます。SQL に慣れたチームが探索的なレポートを必要とする場合も、リレーショナルが有利です。Quickturn も、初期のローカルのプロトタイプでは SQL を使っていました。複数の学習者で運用するようになって、判断の軸が入れ替わりました。

04両方を使う場合と、選択の説明

リレーショナルデータベースとキーバリューデータベースは、それぞれ別のワークロードを受け持てます。ただし両方を動かせば、運用するシステムがもう一つ増え、二つのコピーを同期させる必要も出てきます。二つ目のストアは、実際に確認された要件があるときに追加してください。

選んだデータベースの妥当性は、判断の軸、退けた候補、見直す条件を示して説明します。Quickturn の場合、履歴のライフサイクルやレポートの要件が学習者のレコードと食い違ってくれば、別のログテーブルを設ける理由になります。新しい製品が登場するたびではなく、判断の軸が変わったときに、この判断を見直します。

3行まとめ

  1. データベースは書き出した判断の軸から選び、どの候補も同じ一覧で評価します。
  2. DynamoDB の決め手は学習者の境界を構造として持てることで、その代償はすべての問いを先にキーとして設計することです。
  3. 問いがわからないときや関係が豊富なときはリレーショナルを選び、どうなったら見直すかを書いておきます。
前へDynamoDB はなぜデータをすばやく見つけられるのか 次へテーブルより先に、問い合わせを書き出す
