小さなアプリで学ぶ AWS の基礎

小さなアプリでも、AWS で動かす以上、誰に何を触らせるか、データをどう持つか、いくらまで払うかは自分たちで決めることになります。この本では架空の学習アプリ Quickturn を例に、アカウントの境界から毎月の請求までを順にたどります。

全14章約60分解説

例に使うアプリ

Quickturn は架空の語学学習アプリです。学習者はタイマーが切れる前にカードに答え、あとで進み具合と間違えた問題を見直します。Web、iOS、Android の三つのクライアントが、一つの API を共有しています。

各章はこのアプリを使って、具体的な設計の選択と、その代償、別の設計を選ぶべき条件を説明します。どの章も単独で読めるように書いてあり、前の章を読んでいなくても話を追えます。

この本の地図

目次

  1. AWS で自分たちが責任を持つのはどこまでか — リージョンとアカウント、そして AWS が守る範囲と自分たちが守る範囲の境目。
  2. デプロイに AWS のキーを置かない理由 — ロールが短命の認証情報を渡すので、漏れて困る長期のキーがそもそも存在しない。
  3. API を Lambda で動かすと何を手放すのか — サーバーの運用がなくなる代わりに、コールドスタートと各種の上限を受け入れる。
  4. Quickturn に VPC がないのはなぜか — 現在の通信経路には、自前の VPC につなぐ必要のある資源がない。
  5. DynamoDB はなぜデータをすばやく見つけられるのか — キーの範囲を絞れば、無関係な学習者のレコードを読まずに済む。
  6. PostgreSQL ではなく DynamoDB を選んだ理由 — 学習者ごとの境界をキーに組み込めることが決め手になった。
  7. テーブルより先に、問い合わせを書き出す — アクセスパターンからキー、ページ分割、インデックスを決める。
  8. 書き込みの途中でアプリが落ちたらどうなるか — 条件付きの一つのトランザクションで、ログと集計を食い違わせない。
  9. インフラをコードで書くのはなぜか — レビュー済みのコードがあるべき状態を表し、テストと実環境の確認でずれを見つける。
  10. よく壊すものと、失ってはいけないものを分ける — 長く残す資源はライフサイクルを分け、保持ポリシーを明示する。
  11. 学習者がサインインするとき、実際に何が起きているか — ワンタイムコードがトークンと交換され、API は検証してから信用する。
  12. Web アプリはトークンをどこに置くべきか — HttpOnly Cookie なら、ページのスクリプトからトークンを読まれない。
  13. ある学習者が他人のデータを見られないことを、どう確かめるか — 一人の学習者に縛ったストアと、共通の分離テストで確かめる。
  14. 誰も使わないとき、いくらかかるか — 使った分だけ払う部品、無料枠、初日からの予算設定。
