API を Lambda で動かすと何を手放すのか

学習者が練習を始められるのは、API がカードの束を返してからです。この短いリクエストには Lambda が向いていますが、時間のかかる採点には別の実行経路が要ります。

01Lambda がリクエストを処理する流れ

Quickturn は Lambda の標準の実行モデルを使っています。実行環境はコードを読み込み、ランタイムを初期化してから、呼び出しを処理します。ウォームな環境は再利用されることがありますが、新しい環境では初期化の待ち時間が生じます。これをコールドスタートと呼びます。

API は、設定とサービスのクライアントを環境ごとに一度だけ初期化し、ウォームな呼び出しで再利用できるようにしています。ただし、永続させたい状態をこの再利用に頼ることはしません。練習のタイマーは端末で動いているので、初期化の待ち時間が、制限時間付きの回答時間を削ることはありません。

02入口の選び方

API Gateway の HTTP API は、比較的シンプルな HTTP の入口になります。REST API は、使用量プランやキャッシュなどの機能を追加で備えています。ロードバランサーや関数 URL という選択肢もあり、それぞれ運用とセキュリティの考え方が異なります。

Quickturn は、すべてのパスを受ける HTTP API のルートを選びました。CloudFront の OAC で保護した関数 URL を使うと、POST と PUT でペイロードのハッシュが必要になり、クライアントに影響が出ます。秘密のヘッダーで守る方法もありますが、その場合は明示的な検証とローテーションが要ります。推測されにくい URL を知っているだけでは、アクセス制御になりません。

03サーバーレスで手放すもの

標準の Lambda の呼び出しには、実行時間の上限と、アカウント単位の同時実行数の制約があります。メモリの内容はウォームな環境で残ることもありますが、永続的なセッションの保存先にはなりません。費用はリクエスト数と実行時間に応じて増えます。これは標準の実行モデルの話で、Lambda Managed Instances や、長時間続くワークフローの仕組みには別の特性があります。

Quickturn はエラーとスロットリングを監視し、開発環境で意図的にスロットリングを起こして、アラームが動くことを確かめています。

安定した負荷、長時間動く処理、普通のリクエスト単位の呼び出しに合わない接続のしかたには、コンテナが向くことがあります。その場合は、固定の容量とロードバランサーの費用を、実測した Lambda の使用量と比べる必要があります。コールドスタートについての思い込みも、それだけで決め手にせず、実際に測って確かめてください。

04時間のかかる AI の処理

時間のかかる AI の処理を、普通の対話的なリクエストの中に隠すべきではありません。記述式の回答の採点は SQS のキューに入れ、ワーカーが時間の上限を決めたジョブとして処理します。もっと長い一連の処理や待ち合わせは、ワークフローのサービスで調整できます。

Quickturn のチューター機能は、長いセッションのためにマネージドなエージェント実行基盤を使っています。それでもジョブやセッションには、タイムアウト、リトライ、認可、進捗の見える化が必要です。別の実行モデルを選ぶと、これらの責任は移りますが、なくなりはしません。

3行まとめ

  1. 新しい Lambda の環境では初期化が起きます。ウォームな環境を再利用できれば避けられますが、後続のリクエストでも新しい環境が必要になることがあります。
  2. 標準の Lambda では、永続的なプロセスのメモリと、無制限のリクエスト時間を手放します。リクエストの料金は使った分だけですが、残しておくリソースには費用がかかり続けます。
  3. 処理の形で選びます。短くて波があるなら関数が、安定しているか長いならコンテナ、キュー、エージェントの実行基盤が向きます。
