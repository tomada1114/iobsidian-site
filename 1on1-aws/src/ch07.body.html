List the questions first, then design the table

After this page you can design a DynamoDB table from its access patterns. You can also explain single-table design with prefixed sort keys, and when separate tables are better.

About 8 min readWhiteboard room

In this page

  • Why start from questions instead of entities?
  • How does one table hold every kind of item?
  • What does one partition per learner give us?
  • When is single-table design the wrong choice?

The whiteboard room. Leo is drawing boxes for a new practice calendar.

01Access patterns first

L

Leo: I need to show the last thirty days of practice on a calendar. I've started the data model: learners, rounds, answers, days. One table each.

M

Maya: That's an entity diagram. It's how you'd start in SQL. What happens next, in SQL?

L

Leo: I normalize, so nothing is stored twice. Then I write queries with joins.

M

Maya: And DynamoDB has no joins. So where do you think we start instead?

L

Leo: With… the questions the app asks?

M

Maya: Yes. We call them access patterns. Write each read as a plain sentence. Try the calendar.

L

Leo: "Get the day tallies for one learner, for a date window."

M

Maya: Keep going. What else does the app ask?

L

Leo: "Get a learner's settings." "Get a round and all its answers." "Get every card's memory state", for scheduling.

M

Maya: One more that people forget.

L

Leo: Hmm. "Everything for one learner", to delete or export an account?

M

Maya: That one. Now the rule: each question must map to one GetItem or one Query. If it doesn't, the keys are wrong. Let me draw the method.

02One table, overloaded keys

L

Leo: So how do all those items fit, if not in four tables?

M

Maya: In one table. Every item a learner owns shares one partition key: LEARNER# and the learner's id. The sort key says what the item is, with a prefix.

L

Leo: Like SETTINGS?

M

Maya: Yes. There are singletons: PROFILE, SETTINGS, STATS. Then ROUND# and the round id for each round, and ROUND# id #ANSWER# id for each answer.

L

Leo: So the answers sit right after their round, in sort order.

M

Maya: Right. "Get a round and all its answers" is one Query with begins_with ROUND# and the round id. This is called overloading the sort key: one key attribute, many kinds of item.

L

Leo: And the calendar?

M

Maya: Day tallies use DAY# and the date, like DAY#2026-09-29. ISO dates sort correctly as text.

L

Leo: So thirty days is one Query with BETWEEN two dates.

M

Maya: Exactly. And the memory state of each card is ITEM#, a kind and an id. There are also items for portions, levels, titles and the learner's usage ledger.

L

Leo: What if an id contains a #? It would look like a separator.

M

Maya: Every id inside a key is escaped with encodeURIComponent. A # becomes %23, so an id can never fake a separator.

L

Leo: Is there anything to watch out for with prefixes?

M

Maya: One thing. ROUND# matches rounds and answers alike. So the reader checks each item's type before using it. Let me draw one learner's partition.

03One partition per learner

L

Leo: What's the identity item outside the partition?

M

Maya: When someone signs in, we get their sign-in id, the sub from Cognito. The item IDENTITY# sub maps it to our own internal learner id.

L

Leo: Why not use the sign-in id as the learner id directly?

M

Maya: Keeping our own id means the sign-in provider can change without renaming every item.

L

Leo: Okay. And how does one learner stay out of another's data?

M

Maya: The store adds the learner's partition to every key. Code above the store never writes a partition key by hand.

L

Leo: So a bug in a command can't ask for someone else's partition.

M

Maya: Right. And look what deletion becomes. To delete or export an account, we Query one partition, plus the identity item.

L

Leo: No hunting across four tables.

M

Maya: None. Let me compare the two designs on the questions we listed.

L

Leo: Won't the calendar need an index on due dates, for scheduling?

M

Maya: No. One learner holds a few thousand items at most. Reading all their item states is one small Query, so no index is needed.

04When single-table is wrong

L

Leo: The bottom row worries me. "Needs the list."

M

Maya: It should. Single-table design is hard to read without the list of access patterns. The list is part of the schema.

L

Leo: And a new question?

M

Maya: A new question means a new key shape, a secondary index, or a backfill.

L

Leo: Backfill?

M

Maya: Rewriting existing items so they have the new key shape. It's a migration you run over old data.

L

Leo: Say the PM wants a weekly leaderboard: the learners who practiced most. I'd add a secondary index on day items, keyed by date.

M

Maya: What kind of question is that, compared with our list?

L

Leo: It crosses learners. Every question on our list stays inside one learner.

M

Maya: Right, and that's the warning sign. An index would copy every learner's day items into one date key, and that key gets busy every evening.

L

Leo: So what would you do?

M

Maya: Build the leaderboard from the export, once a night, and store the result as its own small item. The live table keeps answering per-learner questions only.

L

Leo: So the list tells me when a question doesn't belong in the table at all.

M

Maya: Yes. Reading the list is how you notice that early, before an index exists.

L

Leo: So when would you use separate tables?

M

Maya: When access patterns, lifecycles, backups or owners diverge. If one kind of data is deleted on a different schedule, or another team owns it, a separate table is cleaner.

L

Leo: Is anything at Quickturn close to that line?

M

Maya: The usage ledger. It's one item in each learner's partition. But money-like state with its own lifecycle is exactly the kind of data that can justify a table of its own.

L

Leo: Doesn't one learner's partition become a hot spot? Everything they do hits one key.

M

Maya: For a huge single key, like "all learners", yes. A per-learner partition doesn't, because each learner's traffic is small.

L

Leo: So the partition choice also spreads the load.

M

Maya: Yes. Thousands of learners means thousands of small partitions, not one busy one.

05Leo explains it back

M

Maya: Suppose you explain the calendar design at the Tuesday review. What do you say?

L

Leo: I wrote the questions down first. Then I gave each one a key so it's a single get or query.

L

Leo: Everything a learner owns shares one partition key. The sort key says what the item is.

L

Leo: Prefixes for rounds and answers, and dates for day tallies, so thirty days is one range query.

M

Maya: And ids?

L

Leo: Escaped, so an id can't break the separators. And deleting a learner is one partition, plus the identity item.

M

Maya: You left out the cost: a new kind of question means a new key design, an index or a backfill. That's why the list of questions lives next to the schema.

Summary in three lines

  1. List every access pattern first, and shape the keys so each is one GetItem or one Query.
  2. One partition per learner with prefixed sort keys makes isolation, deletion and export each one key.
  3. The access-pattern list is part of the schema; use separate tables when lifecycles or owners diverge.
