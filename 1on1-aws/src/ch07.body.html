01先にアクセスパターンを決める

まず問いから書き出します。学習者の設定を取得する、ラウンドとその回答を取り出す、カードの記憶状態を読む、といった問いです。そこに、日付の範囲での集計と、アカウントのエクスポートや削除を加えます。エンティティの名前を並べただけでは、これらの読み取りがどう実行されるかはわかりません。

Quickturn は、普段の読み取りがすべて GetItem か、範囲を絞った Query になることを目指しています。キーに収まらないパターンが出てきたら、設計上の判断が抜けている合図です。黙ってフィルタ付きの Scan を足す理由にはなりません。

02一つのテーブルでキーを使い分ける

学習者が持つアイテムは、LEARNER# で始まる同じパーティションキーを共有します。ソートキーの接頭辞で、一つしかない設定、ラウンド、回答、日ごとの集計、アイテムの記憶状態を区別します。日付を ISO 形式の固定の書式で持てば、時系列の範囲で取り出せます。

ラウンドの接頭辞はラウンドの見出しとその回答をまとめ、アイテムの種別を示す属性で、返ってきたレコードが何かを判別します。ID は区切り文字でつなぐ前にエンコードしておくので、# を含む ID がキー構造の一部になりすますことはありません。

03学習者ごとに一つのパーティション

検証済みの ID プロバイダーの ID は、内部の学習者 ID に対応付けられます。この対応付けを分けておけば、ID プロバイダーを入れ替えるときにも、学習者が持つすべてのレコードの名前を変えずに済みます。学習者に縛ったストアは、すべての読み書きにパーティションキーを差し込みます。

アカウントのエクスポートや削除では、学習者のパーティションを Query し、ID の対応付けも削除します。その際はすべてのページをたどり、バッチの上限にも対応します。現在のアクセスパターンがプライマリキーに収まっているなら、共有のテーブルにセカンダリインデックスがなくてもかまいません。この判断は、学習者の実際のデータ量とリクエストの要件によって変わります。

04単一テーブルが合わないとき

アクセスパターンの一覧は、スキーマのドキュメントの一部です。新しい問いには、別のキー、インデックス、データ移行が必要になることがあります。その場合のバックフィルは、既存のデータを新しい形に書き直す作業です。

学習者をまたぐランキングは、性質の違うワークロードです。Quickturn は、すべての書き込みを多くの学習者が共有する日付のキーに集中させるのではなく、エクスポートから定期的に結果を作れます。持ち主、保持期間、バックアップの要件が違えば、テーブルを分ける理由になります。単一テーブル設計が役に立つのは、データとアクセスのライフサイクルがそろっているときで、ライフサイクルが食い違うなら、レコードを別のテーブルに移すことを検討します。

3行まとめ

  1. 先にアクセスパターンを書き出し、普段の読み取りは、結果のページ分割も含めて GetItem か Query で済むようにします。
  2. 学習者のキーと学習者に縛ったストアが分離を支え、エクスポートと削除は、選んだアイテムをページとバッチをまたいでたどります。
  3. アクセスパターンの一覧はスキーマの一部です。ライフサイクルや持ち主が食い違うなら、テーブルを分けます。
