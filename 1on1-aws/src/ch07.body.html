List the questions first, then design the table

After this page you can design a DynamoDB table from its access patterns. You can also explain single-table design with prefixed sort keys, and when separate tables are better.

About 4 min readQuickturn case study

In this page

  • Why start from questions instead of entities?
  • How does one table hold every kind of item?
  • What does one partition per learner give us?
  • When is single-table design the wrong choice?

01Access patterns first

Start DynamoDB design with access patterns: get a learner's settings, retrieve a round and its answers, read card memory state, show day tallies in a range, and export or delete an account. Entity names alone do not say how those reads will run.

Quickturn aims to make each ordinary read a GetItem or a bounded Query. A pattern that cannot fit the keys signals a missing design decision, not a reason to add a filtered Scan silently.

02One table, overloaded keys

Learner-owned items share a LEARNER# partition key. Sort-key prefixes distinguish singleton settings, rounds, answers, day tallies and item memory state. ISO dates make chronological ranges possible in a fixed date format.

A round prefix groups its header and answers, while an item discriminator identifies which records were returned. IDs are encoded before joining separators so an ID containing # cannot masquerade as part of the key structure.

03One partition per learner

A verified provider identity maps to an internal learner ID. Keeping that mapping separate makes replacing the identity provider possible without renaming all owned records. A learner-bound store inserts the partition key into every read and write.

Account export or deletion can query the learner partition and remove its identity mapping, following all pages and handling batch limits. A shared table need not have secondary indexes if current access patterns already fit the primary key. That choice depends on actual learner data volume and request requirements.

04When single-table is wrong

The access-pattern list is part of the schema documentation. A new question may need another key, index or migration. Backfilling means rewriting existing data into the new shape.

A cross-learner leaderboard has a different workload. Quickturn can build a periodic result from an export rather than force every live write into a heavily shared date key. Different owners, retention or backup needs can justify separate tables. Single-table design is useful when data and access lifecycles align; it is not a requirement to keep every kind of record together forever.

Summary in three lines

  1. List every access pattern first, and shape the keys so each is one GetItem or one Query.
  2. One partition per learner with prefixed sort keys makes isolation, deletion and export each one key.
  3. The access-pattern list is part of the schema; use separate tables when lifecycles or owners diverge.
