How does DynamoDB find my data so fast?

After this page you can explain partition keys, sort keys and why a Query is fast and a Scan is not. You can also name the capacity, consistency and size choices a table needs.

About 8 min readPairing at Leo's desk

In this page

  • How does DynamoDB decide where an item lives?
  • Why is a Scan with a filter a problem?
  • What else do you choose for a table?
  • What does DynamoDB cost you in flexibility?

Leo's desk. A new query passes his local tests.

01Items, keys and partitions

L

Leo: Can you approve this? I needed to list a learner's rounds.

M

Maya: Show me how.

L

Leo: I wrote a Scan with a filter on the learner id. It works fine locally.

M

Maya: How many items are in your local table?

L

Leo: About twenty.

M

Maya: And in prod?

L

Leo: Every learner's data. Hmm. More than twenty.

M

Maya: Let's see why that matters. How do you picture a DynamoDB table?

L

Leo: Like a SQL table, just without joins. And the filter narrows down what the database reads.

M

Maya: Two parts of that don't hold here. Let's start with how DynamoDB stores things.

L

Leo: Okay. What's inside a table?

M

Maya: Items. Each item is a set of attributes, with no fixed schema beyond its key.

L

Leo: And the key is the primary key.

M

Maya: Right. The primary key is either a partition key alone, or a partition key plus a sort key. We use both.

L

Leo: What does the partition key do?

M

Maya: DynamoDB hashes it, turns it into a number, and uses that to choose a partition. A partition is a slice of storage and throughput on AWS's side.

L

Leo: So the partition key decides which slice an item lives in.

M

Maya: Yes. And inside a partition, items are kept in sort-key order. Let me draw our table.

L

Leo: So the sort keys are strings like SETTINGS and ROUND# plus an id.

M

Maya: Yes, and the partition key names the learner. Our key attributes are just called PK and SK.

L

Leo: And to read one item?

M

Maya: A GetItem, with the full key: partition key and sort key. That's the fastest read there is.

02Query versus Scan

L

Leo: Then what's wrong with my Scan? It finds the right rounds.

M

Maya: It finds them by reading every item in the table. A Scan reads the whole table, page by page.

L

Leo: But I have a filter on the learner id.

M

Maya: Here's the second surprise. The filter is applied after the items are read. You pay for everything read, and it gets slower as the table grows.

L

Leo: So with twenty items it's instant, and with every learner's data…

M

Maya: It reads every learner's data to return one learner's rounds. What would a Query do instead?

L

Leo: A Query names one partition key. So it goes straight to that learner's partition.

M

Maya: Right. And you can add a condition on the sort key: equals, begins_with, or between.

L

Leo: So begins_with "ROUND#" gets the rounds in one Query, plus their answers, since those sort under each round.

M

Maya: Right. The reader keeps only the round items. That's the whole fix: one partition, one range. Let me put the two side by side.

L

Leo: Does a Query return everything at once?

M

Maya: In pages of up to 1 MB. Our store follows the pages until it has them all.

L

Leo: What if we needed a different question, like "all rounds from yesterday, for every learner"?

M

Maya: Then you'd need a secondary index, a second copy of the data keyed another way. We have none.

L

Leo: None? That surprises me.

M

Maya: Every question our app asks fits inside one learner's partition. So the main key is enough. There's no Scan in any request path either.

03Capacity, consistency and size

L

Leo: What else do I choose when I make a table?

M

Maya: Three things. First, capacity mode. On-demand bills per request, with nothing to plan. Provisioned means you set read and write capacity ahead.

L

Leo: Which is cheaper?

M

Maya: Provisioned, at steady load, and it can scale automatically. On-demand wins when traffic is spiky or near zero, like ours. We use on-demand.

L

Leo: Can we still hit limits?

M

Maya: Either way, a "hot" partition can throttle. That's one partition getting far more traffic than the rest. We have alarms on read and write throttles.

L

Leo: Second choice?

M

Maya: Consistency. Reads are eventually consistent by default: right after a write, a read might still see the old value for a moment.

L

Leo: That sounds bad for a drill. I answer a card and then see old data?

M

Maya: So we read everything strongly consistent. A strongly consistent read costs twice as much, and it isn't available on global secondary indexes.

L

Leo: Another reason not to have one.

M

Maya: It fits our design.

L

Leo: Why not always read eventually consistent and save the money?

M

Maya: For a feed of news, I would. For a learner who just finished a round and opens the results, a stale read looks like lost answers.

M

Maya: Third: size. One item holds at most 400 KB. And writes across several items can be made atomic with transactions, all or nothing.

L

Leo: 400 KB is a lot for a round.

M

Maya: It is. But it's a hard limit, so we never let one item grow without end, like a list of every answer ever given.

04What you give up

L

Leo: So what's the catch with DynamoDB overall?

M

Maya: What you get is predictable speed at any size. No servers, no connections to manage, and on-demand costs nothing when idle.

L

Leo: And what you pay?

M

Maya: Flexibility. No joins. No ad hoc queries, the kind you type in to explore data. You decide the access patterns before the data exists.

L

Leo: What if the PM wants a report, like "how many learners practiced yesterday"?

M

Maya: Not from the live table. We export the table to S3, and reports run on the export.

L

Leo: So the live table only answers the app's questions.

M

Maya: Exactly. And that tells you when not to use it. If you can't list your questions yet, stay relational for now.

L

Leo: What about backups? If everything is in one table, one bad write is scary.

M

Maya: Prod has point-in-time recovery. We can restore a copy of the table as it was at any second in the last few weeks.

L

Leo: Okay. I'll rewrite mine as a Query on the learner's partition, with begins_with.

M

Maya: And add a test with more than one learner in it. Your twenty items were all one learner, weren't they?

L

Leo: They were. So a Scan looked correct by accident.

05Leo explains it back

M

Maya: A teammate writes the same Scan next month. What do you tell them?

L

Leo: DynamoDB hashes the partition key to find where the data lives. Inside a partition, items are kept in sort-key order.

L

Leo: So the fast operations are a get by the full key, or a Query on one partition key with a sort-key condition.

L

Leo: A Scan reads the whole table, and a filter only trims the result afterwards. So it's out for request paths.

M

Maya: And the table's other choices?

L

Leo: We use on-demand capacity and strongly consistent reads, and items stay well under 400 KB.

M

Maya: Add the cost of all this speed: we decide our questions before the table exists. When the questions aren't known yet, a relational database is the better start.

Summary in three lines

  1. The partition key picks where an item lives; the sort key orders items inside that partition.
  2. Get by full key or Query one partition; a Scan reads everything, and a filter only trims the result.
  3. Choose capacity mode and consistency on purpose, and list your questions before you design the table.
