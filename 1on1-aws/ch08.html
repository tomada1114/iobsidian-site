What if the app crashes halfway through a write?

After this page you can explain why several related writes belong in one DynamoDB transaction. You can also explain version conditions, and how a transaction's limits shape commands.

About 8 min readPairing at Leo's desk

In this page

  • What goes wrong with two writes in a row?
  • How does one commit with conditions fix it?
  • What do transactions cost, and what are the alternatives?
  • How do the same conditions guard money?

Leo's desk. His feature writes an answer, then updates the learner's points.

01Half-done writes

L

Leo: Quick question about my code. It writes the answer, then in a second call adds to the learner's points. What if the function times out between the two?

M

Maya: What do you think happens?

L

Leo: The answer is saved, but the points aren't. Then the client retries, and it's fine?

M

Maya: Let's follow the retry. The client resends the answer. What does your first call do with it?

L

Leo: It writes it again. Oh. Two answers, and then the points are added once. Or twice, if the first attempt had got further.

M

Maya: Right. A retry doesn't repair a half-done write. It can make it worse. Let's step back and look at what we store.

L

Leo: The answers, and the points.

M

Maya: The answers are an append-only log. We only ever add to it. The points are a projection: a summary derived from the log.

L

Leo: Why store the summary at all? We could add up the log every time.

M

Maya: Because reads should stay point lookups, one key each. So we keep projections: the learner's points, each day's tally, and each card's memory state.

L

Leo: And those must always agree with the log.

M

Maya: That's the job. Two separate writes can leave them disagreeing, forever. Let me compare the two ways.

02One commit with conditions

L

Leo: So how do we write both at once?

M

Maya: With TransactWriteItems. It applies up to 100 actions, all or nothing. One rule: no two actions may touch the same item.

L

Leo: And "all or nothing" solves the crash. What solves the resend?

M

Maya: Conditions. A new answer is a Put with the condition attribute_not_exists: only write it if no item has this key yet.

L

Leo: So a resent answer fails its condition, and nothing is counted twice.

M

Maya: Right. Our code reads again, sees the answer is already saved, and skips it. The client gets success, not an error.

L

Leo: And the points?

M

Maya: Two devices might add points at the same time.

L

Leo: Last one wins, and one update is lost.

M

Maya: So each summary carries a version number. We read it with its version, and the Put says: only write if the version is still the one I read.

L

Leo: And if someone else wrote first?

M

Maya: The condition fails, and the whole transaction fails with it. That's optimistic concurrency: no lock, just a check at the end.

L

Leo: What about items we read but don't change? Like checking the round is still open?

M

Maya: Those get a ConditionCheck, an action that writes nothing and only checks a condition. If the round closed meanwhile, the commit fails.

L

Leo: This sounds like a SQL transaction.

M

Maya: Here's the big difference. In SQL you often open a transaction, run code, and commit.

L

Leo: And in DynamoDB?

M

Maya: Nothing stays open while code runs. Let me draw the cycle.

L

Leo: So: read with versions, decide in pure code, submit one commit.

M

Maya: And on a conflict, read again and decide again. We try at most three times in total. After that the client gets a conflict code.

L

Leo: Is there anything the store refuses before sending?

M

Maya: Yes. A commit over 100 items, one that names a key twice, or one that tries to change an existing answer. Answers are append-only, so updating one is always a bug.

L

Leo: And how do we know the in-memory store behaves the same?

M

Maya: The same contract suite runs against the in-memory store and against DynamoDB running locally. Both must refuse and accept the same commits.

03What transactions cost

L

Leo: Why not put every write in a transaction, then?

M

Maya: Transactional writes cost twice the write capacity of plain writes. That's the first cost.

L

Leo: And the 100-action limit?

M

Maya: It shapes how we cut commands. Answers are committed as they arrive, a batch at a time. Finishing a round commits only the aggregates, not every answer again.

L

Leo: What if many answers arrive for the same learner at once?

M

Maya: They all update the learner's stats item. A busy shared item like that causes conflicts and retries. It's fine at our size, but it's the first thing I'd watch.

L

Leo: Can the summaries still drift from the log?

M

Maya: Yes, if a new code path forgets a projection. The transaction only protects what you put in it.

L

Leo: So what catches that?

M

Maya: Two safety nets. A job that rebuilds the summaries from the log. And contract tests that check each command's commit contains every projection it should.

L

Leo: Are there cases where a transaction is too much?

M

Maya: When only one item changes, a single-item atomic update is enough, like adding to a counter. And when summaries can lag a little, a stream can update them asynchronously.

L

Leo: A stream meaning DynamoDB tells another function about each change?

M

Maya: Right. The summary updates a moment later. That's fine for a weekly report, not for a points number the learner just earned.

04Conditions that guard money

L

Leo: Where else does this pattern show up?

M

Maya: Anywhere money moves. Think of a usage ledger for paid AI calls. We have one per learner, for grading typed answers.

L

Leo: How does it work?

M

Maya: Four steps. Let me draw them.

L

Leo: Why reserve the maximum, not the real cost?

M

Maya: We don't know the real cost until the model answers. Reserving the maximum means we never overspend, even if the answer is long.

L

Leo: And if the call is retried?

M

Maya: A job key makes a retried call charge once. It's the same idea as the answer ids: the condition guards the money.

L

Leo: So "attribute_not_exists" and version checks aren't just database details.

M

Maya: No. They're how you make "this happens once" true, whether it's an answer or a charge.

05Leo explains it back

M

Maya: So how would you explain your fix in the pull request?

L

Leo: One answer changes the log and three summaries. So all of them go in one transaction: everything is written, or nothing is.

L

Leo: Conditions do the real work. A new answer must not already exist, and a summary must still be at the version we read.

L

Leo: If someone else wrote first, we reload and decide again, instead of holding a lock.

M

Maya: And the limits?

L

Leo: 100 actions, and one action per item. They decide how we cut commands, like committing answers as they arrive.

M

Maya: Your fix still leans on a safety net: a transaction only covers what you put in it. The rebuild job and the contract tests catch a projection someone forgot.

Summary in three lines

  1. Commit a log entry and the summaries derived from it in one transaction, so all apply or none do.
  2. Conditions make it safe: new items must not exist, and updates must still be at the version read.
  3. Transactions cost double and allow 100 actions, which shapes how commands are cut.
