Why a static SPA instead of server rendering?

After this page you can choose between server rendering, static generation and a single-page app. You can also explain why API data in the browser is a cached copy, not app state.

About 8 min readCoffee in the kitchen

In this page

  • What are the ways to render a web app?
  • Why did Quickturn choose a static SPA?
  • What's server state, and who manages it?
  • When does server rendering win?

The office kitchen, standing with coffee.

01Four ways to render

L

Leo: Can I ask about the web app? At my agency, everything used a server-rendered React framework. I thought that was the modern default.

M

Maya: And you heard we used one once?

L

Leo: Yes, and that we replaced it with a plain single-page app. Wasn't that a step backwards?

M

Maya: Let's list the options first. What does server rendering do, exactly?

L

Leo: The server builds the HTML for each request, so the page shows up with content.

M

Maya: Right, that's SSR, server-side rendering. SSG, static site generation, builds the pages once at build time. And an SPA ships a static shell, then renders in the browser after the JavaScript loads and the API answers.

L

Leo: And the new mixes? Streaming, server components?

M

Maya: Hybrids. They combine the three in different ways. For each option, ask what you pay: a server to run and patch, a caching plan, and where data fetching lives.

L

Leo: With SSR, the fetching happens on the server.

M

Maya: So the server needs the database, or an API, plus sign-in, plus its own deploys. It's a real backend.

L

Leo: And with an SPA, the browser fetches from the API directly.

M

Maya: Right. The files themselves are just static, like images.

02Why Quickturn serves static files

L

Leo: So why did the framework go?

M

Maya: Think about where our rules live.

L

Leo: Behind the one API. The native apps use it too.

M

Maya: So a web server tier would be a second backend in front of it. A second place that checks sign-in, and a second thing to deploy and patch.

L

Leo: But SSR helps with search engines. Doesn't that matter?

M

Maya: Who can see our app?

L

Leo: Only signed-in learners. Oh. A search engine never gets in.

M

Maya: Right. The public landing page is a separate static page. The app itself has no reason to be crawled. Let me draw how the choice falls out.

L

Leo: What about sign-in? How does the SPA send the session?

M

Maya: The API sets an HttpOnly cookie, one that page scripts can't read. And the web app and the API share one origin: the API lives under /api on the same domain.

L

Leo: So the cookie just travels with each call.

M

Maya: With no CORS setup and no third-party cookie rules. CORS is the browser's rule for calls to another origin. Here's the shape.

L

Leo: So what does the SPA cost? It can't all be good.

M

Maya: First paint. Let me walk through the first load.

L

Leo: So a skeleton on every first load.

M

Maya: Yes, it's the price, and we accept it. The learner is signed in and about to practice for minutes, not deciding in one second whether to stay.

L

Leo: Couldn't we render only the home screen on a server? Just to hide that first wait.

M

Maya: What would that server need, to render your home screen?

L

Leo: My streak and my weak points. So it would call the API with my cookie.

M

Maya: Which means it handles sessions, runs somewhere, and needs deploys and patches. One screen brings back the whole second backend.

L

Leo: For a skeleton that shows for a moment.

M

Maya: That's how we weighed it. If the wait grew long, we'd first make the bundle smaller or the home view faster. A server tier is the last option, not the first.

03Server state is a copy

L

Leo: In my agency apps, API data went into a big global store. Is that what we do?

M

Maya: What is that data, really? Who owns the truth about your streak?

L

Leo: The server. The browser only has what it fetched last.

M

Maya: So it's a cached copy of the server's truth, not app state to manage by hand. People call it server state.

L

Leo: And we use a library for that?

M

Maya: TanStack Query. It keys each read, tracks loading and errors, and refetches after a change. Here's the home view.

const homeQuery = queryOptions({
  queryKey: ["home"],
  queryFn: () => api.getHome(),
});

const queryClient = new QueryClient({
  defaultOptions: {
    queries: { retry: false, refetchOnWindowFocus: false },
  },
});
L

Leo: Why turn retries off? Retries sound helpful.

M

Maya: We want each call the learner triggers to be made once. If a read fails, the screen shows it, and the learner decides.

L

Leo: And refetching when I switch back to the tab?

M

Maya: Off too, for the same reason: no surprise calls. And resending writes is the answer queue's job, not the cache's. Two retry systems would fight.

L

Leo: So the cache is for reads, and the queue is for answers.

M

Maya: Exactly that split.

04When server rendering wins

L

Leo: So is SSR just worse?

M

Maya: No. For public content, it's often better. Search engines, slow devices, and pages where the content is the product, like a blog or a store.

L

Leo: So my agency wasn't wrong. Those were public marketing sites.

M

Maya: Probably the right call there. An SPA wins for an app behind sign-in, with rich interaction, on an API shared with native apps.

L

Leo: What about AI chat screens? Our tutor's chat is in the same app.

M

Maya: That's a different shape. The tutor's answers stream in piece by piece, through Server-Sent Events or a streamed fetch.

L

Leo: Server-Sent Events being…?

M

Maya: A standard browser API. The server keeps a connection open and pushes small messages as they're ready.

L

Leo: Can the query cache hold a stream?

M

Maya: Not well. A stream isn't a finished answer you can cache. The UI needs to render text as it arrives, offer a stop button, and handle an answer that ends halfway.

L

Leo: So request and response for most screens, and a stream for the chat.

M

Maya: Right. Pick the shape per screen, not per framework.

05Leo explains it back

M

Maya: Suppose a friend at your old agency asks why we dropped server rendering. What do you tell them?

L

Leo: Server rendering is a tool for public pages, search and fast first paint.

L

Leo: Our app is behind sign-in, and all the rules are in an API that the native apps share. So a static SPA is the simplest client, with no web server to run.

L

Leo: The app and the API share one origin, so the HttpOnly cookie just travels with each call.

M

Maya: And the data in the browser?

L

Leo: A copy of the server's truth, in a query cache. Retries are off; the answer queue handles resending.

M

Maya: You skipped the cost: first paint waits for the bundle and one API call, so skeletons are normal. We chose that wait on purpose, and we'd choose differently for a public page.

Summary in three lines

  1. Server rendering and static generation earn their cost for public pages, search and content-first screens.
  2. Behind a sign-in, with rules in a shared API, a static SPA on the same origin is the simplest client.
  3. Treat API data as a cached copy of server state, and give streams like chat their own shape.
