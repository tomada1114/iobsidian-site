REST, GraphQL or RPC: how do you choose?

After this page you can explain what REST really describes and how it differs from GraphQL and RPC. You can also pick a style from your clients instead of from taste.

About 8 min readAfter the design review

In this page

  • What does REST actually mean?
  • How do the three families compare?
  • Why did Quickturn pick REST with OpenAPI?
  • How does an AI agent call the same API?

The Tuesday design review has just ended. A new hire suggested tRPC, and Leo stays behind.

01What REST really is

L

Leo: I liked the tRPC idea in there. I used it on a side project. The types just flow from server to client. No generated files.

M

Maya: What's your question about it?

L

Leo: Why do we keep an OpenAPI document and a generation step at all? tRPC seems strictly better.

M

Maya: Before we compare, what do you think REST means?

L

Leo: JSON over HTTP, with verbs. GET to read, POST to create. The rest is taste.

M

Maya: That's the common version. The idea comes from Roy Fielding's doctoral dissertation. He described an architectural style, a set of rules for how parts of a system talk.

L

Leo: Which rules?

M

Maya: Resources are named by URLs. Every resource uses the same small set of methods; he called that a uniform interface.

L

Leo: And the others?

M

Maya: Each request carries everything it needs, so it's stateless. And responses can be cached.

L

Leo: Our URLs look like that. /v1/rounds, and /v1/rounds/{roundId}/answers.

M

Maya: Right. Rounds are resources, answers belong to a round, and we use standard status codes.

L

Leo: I've read that "real" REST also needs links in every response. We don't do that.

M

Maya: That part is called hypermedia. Most teams skip it, and so do we.

L

Leo: Is that still REST, then?

M

Maya: A useful subset of it. The part that matters to us is resources plus a published contract.

L

Leo: The contract being the OpenAPI document.

M

Maya: Yes. A description of every path and every body, in a format any language can read.

02Three families side by side

M

Maya: There are three families worth knowing. Here's how they differ.

REST with OpenAPI
Any client language. The contract is an OpenAPI document. The server fixes each read's shape. HTTP caching works as normal. The server team runs ordinary HTTP routes.
GraphQL
Any client language. The contract is a GraphQL schema. The client asks for exactly the fields it wants. HTTP caching is harder, since most queries are POSTs to one URL. The server team runs resolvers, one small function per field.
RPC
The tRPC library serves TypeScript clients only. It shares types straight from the server code. The gRPC framework serves many languages, with a contract in protocol buffers. Browsers need a proxy or a special protocol to call it.
M

Maya: Now try each one on our clients. Who calls our API?

L

Leo: The web app, in TypeScript. The iOS app in Swift, and the Android app in Kotlin.

M

Maya: So tRPC?

L

Leo: Only the web app could use it. Swift and Kotlin can't import TypeScript types. Okay, that's a problem.

M

Maya: GraphQL?

L

Leo: All three could use it. And each screen could ask for exactly what it needs.

M

Maya: How many different read shapes do our screens need?

L

Leo: Not many. The home screen, records, settings, and the drill itself.

M

Maya: So GraphQL's main strength would sit unused. That doesn't rule it out, but it's a clue. Let me draw the whole question.

03Why we chose REST

L

Leo: So we're bottom right. Several languages, a few fixed commands.

M

Maya: And clients that live for years. A phone app from last year still calls us today. Each language generates its own typed client from the same OpenAPI document.

L

Leo: What would GraphQL have cost?

M

Maya: A schema language, resolvers, and a new caching story. All for flexibility our screens don't use. We looked at GraphQL on a managed AWS service, and at gRPC, before choosing.

L

Leo: And gRPC fails on the browser.

M

Maya: Not fails, but it needs a proxy or a special protocol. More moving parts for the web app.

L

Leo: What does REST cost us, then? It can't be free.

M

Maya: Over-fetching and under-fetching. A resource endpoint returns more than a screen needs, or less, so the app makes three calls.

L

Leo: GraphQL solves exactly that.

M

Maya: We solve it more simply: one view endpoint per screen. The home view returns everything the home screen shows, in one call.

L

Leo: A GraphQL query, but fixed on the server.

M

Maya: Yes, a fixed query per screen. The other cost is more endpoints to keep compatible across versions.

L

Leo: So was my side project wrong to use tRPC?

M

Maya: No. If one team owns both ends, and every client is TypeScript, tRPC is great. An internal admin tool used only by our web app would be a good fit.

L

Leo: So the style follows the clients, not the other way round.

M

Maya: Right. The question isn't which is best. It's who calls you, in what language, and for how long.

04An agent calls the same commands

M

Maya: There's one more client that isn't an app. Our tutor agent.

L

Leo: The one on AgentCore. How does it call the API?

M

Maya: It calls a chosen set of our commands and queries as MCP tools. MCP, the Model Context Protocol, is an open protocol for giving a model tools it can call.

L

Leo: So there's a second API just for the agent?

M

Maya: No. The tools go through a gateway to the same commands the apps use. Let me draw it.

L

Leo: How can the same command come in from HTTP and from a tool call?

M

Maya: Because commands are plain data, checked by schemas, behind one authorization decision. HTTP, a queue message or a tool call all turn into the same data.

L

Leo: So the transport doesn't matter to the command.

M

Maya: Right. Now the pitfall I've seen teams hit. What does a tool need to know about the user?

L

Leo: The learner id, I guess. So the model passes it as an argument?

M

Maya: That's exactly the mistake. Then the model decides whose data it touches, and a prompt can talk it into another user's id.

L

Leo: So where does the user come from?

M

Maya: From the verified session. The agent acts on behalf of the signed-in learner, and no tool takes a learner id at all.

05Leo explains it back

M

Maya: Say the new hire asks you why we didn't pick tRPC. What's your answer?

L

Leo: I'd pick the style from the clients. We have a few fixed commands, and clients in three languages that live for years.

L

Leo: REST with a generated OpenAPI contract fits that. Any language can generate a client from it.

L

Leo: GraphQL earns its cost when many clients want many read shapes. The tRPC library fits when everything is TypeScript. One team must own both ends, too.

M

Maya: And REST's weak spot?

L

Leo: Over-fetching. We answer it with one view endpoint per screen.

M

Maya: The agent belongs in the answer too: because commands are plain data, its tools call the same ones as the apps. And the learner always comes from the session, never from a tool argument.

Summary in three lines

  1. REST names resources with URLs and uses standard methods; a published contract makes it work across languages.
  2. Choose from your clients: several languages and few fixed reads favor REST, varied reads favor GraphQL, TypeScript-only favors tRPC.
  3. Commands as plain data let apps and an agent's tools share one set of rules and one authorization check.
