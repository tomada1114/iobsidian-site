Trust nothing at the boundary: parse it once

After this page you can list where outside data enters a program. You can also explain why we parse it once into a precise type instead of validating it again and again.

About 8 min readWhiteboard room

In this page

  • Why check data our own app just wrote?
  • What's the difference between validating and parsing?
  • Where exactly does the parsing happen?
  • What does parsing cost?

The small meeting room. Leo's laptop shows the web app's answer queue.

01Where outside data comes in

L

Leo: Something looks odd in the answer queue. The web app writes answers to session storage. A second later it reads them back, and it checks every one.

M

Maya: What seems odd about that?

L

Leo: It's our own data. We wrote it. Why would anyone validate their own data?

M

Maya: Who else can write to session storage?

L

Leo: Nobody. Well, the user could, in the browser's dev tools.

M

Maya: And a browser extension. And an older version of our app, loaded in this tab before a deploy, that queued answers in a different shape.

L

Leo: Oh. So it's the browser's storage, not ours.

M

Maya: Right. The storage lives outside our program's memory. Once data leaves memory, we can't be sure what comes back.

L

Leo: Where else does that happen?

M

Maya: Let's list them. A request body. Browser storage. Environment variables. A file. Another service's reply.

L

Leo: And a model's reply. That's outside too.

M

Maya: Yes. Everything that comes from outside the process's own memory is unknown on the way in. That's the TypeScript type that allows nothing until you check it.

L

Leo: So the queue is right to check. What does it do with a bad answer?

M

Maya: A small type guard checks each one, and anything that doesn't fit is dropped. The rest of the app only ever sees real answers.

02Parse, don't validate

L

Leo: I'd have called that validation. A function that returns true or false.

M

Maya: That's the half that's missing something. Alexis King has a phrase for this: parse, don't validate.

L

Leo: What's the difference? Both check the data.

M

Maya: A validator answers yes or no, and then the answer is gone. The value is still unknown. What does the next function do?

L

Leo: It doesn't know the value was checked… so it checks again.

M

Maya: Exactly. A parser returns something new: a more precise type, or a failure. The type carries the proof forward, so nobody checks again.

L

Leo: So "validated" becomes part of the type.

M

Maya: That's the idea. Let me put them side by side.

L

Leo: How do we parse a request body in practice?

M

Maya: With a schema library, zod. One schema gives two things: a runtime check and a static type.

const StartRound = z.object({
  kind: z.enum(["first", "retry"]),
  roundId: z.string().uuid(),
});
type StartRound = z.infer<typeof StartRound>;

const parsed = StartRound.safeParse(body); // body: unknown
if (!parsed.success) return badRequest();
parsed.data.kind; // "first" | "retry"
L

Leo: safeParse doesn't throw. It returns success or failure, like a Result.

M

Maya: Right. And z.infer makes the type from the schema, so they can't disagree.

L

Leo: I've also seen satisfies in our code. Is that a parser too?

M

Maya: No, it's for values we write ourselves. The keyword as tells the compiler, "trust me". satisfies checks the value against a type, but keeps the value's own narrower type.

L

Leo: So satisfies is a check, and as is only a claim.

M

Maya: Yes. And for a tiny shape where we don't want a library, a hand-written type guard is a parser too. It's a function that returns value is Answer.

L

Leo: That's what the answer queue uses.

03Once, at the edge

M

Maya: Now, where does the parsing happen? Let me draw a request's path into the API.

L

Leo: And a failed schema parse gives a bad-request code?

M

Maya: With one fixed sentence. The message never quotes what the client sent.

L

Leo: Why not? Quoting the bad field would help.

M

Maya: Because the input might hold a password, or a script tag that ends up in a log viewer. An error never carries the input back.

L

Leo: Is the environment the same? It's just a few settings.

M

Maya: It's the best example. Our API reads process.env in exactly one module. Nothing else touches it.

L

Leo: And checks it when?

M

Maya: Once, at startup. Small hand-written parse functions check every variable. If any are bad, it reports all their names in one error, and refuses to start.

L

Leo: Names, but not values?

M

Maya: Never values. A value might be a secret. And the sign-in client secret isn't allowed as a plain variable at all in the hosted app. It comes from a parameter store.

L

Leo: Why refuse to start? It could run until a request needs the value.

M

Maya: Then the crash comes at 2 a.m., on the first request that needs it. Failing at start shows up during the deploy, while someone is watching.

L

Leo: So every door has one place that parses.

M

Maya: Right. Here are our doors.

04What parsing costs

L

Leo: Why not parse everywhere, to be safe?

M

Maya: Parsing costs code and CPU time. If every function parses again, you pay many times for the same proof. Once at the edge is enough.

L

Leo: What about fields we don't expect? A newer app might send an extra field.

M

Maya: You have to decide that on purpose. Strip it, refuse it, or keep it. A strict object refuses it, and then a newer client breaks against an older server.

L

Leo: I'd have guessed refusing unknown fields was the careful choice.

M

Maya: Inside one version, it is. But phones update on their own schedule, so refusing new fields can break real users.

L

Leo: So strict isn't always safer.

M

Maya: Not across versions. There's another cost too: a schema library adds weight to the browser bundle.

L

Leo: Is that why the answer queue uses a type guard, not zod?

M

Maya: That's one reason. And our environment module uses small hand-written functions, so that package doesn't need a schema library at all.

L

Leo: Where else does this matter?

M

Maya: Anywhere a model returns structured output. Our grader for typed answers asks the model for a shape, and a schema parses the reply the same way.

L

Leo: And if the parse fails?

M

Maya: It's a retry, or a fallback grade. Never an as to make the compiler quiet. Teams that cast model output find out in production.

05Leo explains it back

M

Maya: A teammate removes the check in the answer queue, saying "it's our own data". What do you tell them?

L

Leo: Anything from outside our process is unknown: a request, browser storage, environment variables, a model's reply. Session storage is the browser's, not ours.

L

Leo: We parse it once at the edge into a real type, or refuse it. Then everything inside trusts the type.

L

Leo: A validator only says yes or no, so the next function checks again. A parser returns proof in the type.

M

Maya: And satisfies?

L

Leo: satisfies checks a value against a type. as only asserts. Config gets the same rule: one module, checked at startup, every bad name reported, and no start if anything's wrong.

M

Maya: Don't forget the refusals: a refusal never quotes the input back. The bad value might be a secret, or something dangerous in a log.

Summary in three lines

  1. Every value from outside the process, even browser storage, is unknown on the way in.
  2. Parse it once at the edge into a precise type or a refusal, so the inside never checks again.
  3. Read configuration in one module at startup, and refuse to start with every bad name listed.
