Which compiler flags change how I write code?

After this page you can explain what strict leaves out, and which extra flags catch real bugs. You can also say why a team keeps a gate closed when outside code can't pass it.

About 8 min readVideo call, screen shared

In this page

  • Doesn't strict already turn everything on?
  • What bug does each extra flag catch?
  • What do the flags cost, and when do we keep them?

A video call. Maya is working from home; Leo shares his screen, where a red line sits under cards[0].id.

01What strict leaves out

L

Leo: Can you see my screen? I check cards.length > 0 on the line above. The compiler still says cards[0] is possibly undefined.

M

Maya: I see it. That's the noUncheckedIndexedAccess flag.

L

Leo: Can I just turn it off for my package? We already have strict: true. I thought that was every strict check.

M

Maya: That's what most people think. What do you think strict turns on?

L

Leo: Null checks, for sure. No hidden any. And… everything else strict?

M

Maya: The first two are right. strict is a bundle of checks. It includes null checks and bans implicit any, where the compiler would silently guess any for a missing type.

L

Leo: And the rest of the bundle?

M

Maya: A few more, like unknown for the error in a catch block. But some checks were never added to the bundle, because they would break too much old code.

L

Leo: So strict is more like a minimum.

M

Maya: A floor, yes. We add flags on top of it. Let me draw where they sit.

L

Leo: So my error comes from a flag that strict doesn't even know about.

M

Maya: Right. Here are the four, and the bug each one catches.

noUncheckedIndexedAccess
arr[i] may be undefined. Catches reading past the end.
exactOptionalPropertyTypes
"Missing" and "undefined" differ. Catches clearing a field by accident.
noPropertyAccessFromIndexSignature
Map lookups need brackets. Catches a lookup that looks like a field.
verbatimModuleSyntax
Imports are emitted as written. Catches a module that runs by surprise.
M

Maya: None of these are style rules. Each one stops a bug that only shows up while the program runs.

02One flag, one bug

L

Leo: Start with mine. I checked the length. Why isn't that enough?

M

Maya: Because the compiler doesn't connect a length check to an index. It can narrow a variable, but cards.length > 0 says nothing it can use about cards[0].

L

Leo: So it treats every index read as maybe missing.

M

Maya: Yes, every arr[i] and every record[key]. The fix is to take the element once and check the element itself.

const first = cards[0];
if (first === undefined) return noCards();
first.id; // first: Card

type Settings = { sound?: boolean };
const a: Settings = {};                 // ok: field absent
const b: Settings = { sound: undefined }; // error
L

Leo: The top half makes sense. What's the bottom half?

M

Maya: That's exactOptionalPropertyTypes. With it, sound?: boolean means "the field may be absent". It does not mean "the field may hold undefined".

L

Leo: Is there a real difference? Both give you undefined when you read it.

M

Maya: Think of a PATCH request, the kind that changes only some fields. What does a missing field mean there?

L

Leo: "Don't touch it. Keep the old value."

M

Maya: And a field set to undefined?

L

Leo: Oh. It could mean "clear it". Or a bug where some code forgot to fill it in.

M

Maya: Right. Without the flag, both look the same to the compiler. A form sends sound: undefined by mistake, and a learner's setting gets wiped.

L

Leo: Okay. The third one, the index signature flag?

M

Maya: Say you have a map with string keys, like Record<string, number>. Without the flag you can write counts.verbs. It looks like a field the type promises.

L

Leo: But it's really a lookup that can miss.

M

Maya: So the flag makes you write counts["verbs"]. The brackets tell the next reader, "this key may not be there".

L

Leo: And the last one? Imports?

M

Maya: When you import only a type, the import should vanish from the JavaScript. If it isn't marked type, verbatimModuleSyntax keeps it. Then that module loads and runs its top-level code.

L

Leo: So I write import type { Card } when I only need the type.

M

Maya: Yes. The rule is simple: what you write is what comes out.

L

Leo: I see why each one exists. But my screen is full of red now.

03What the flags cost, and the gate

M

Maya: That's the cost, and it's real. Turning these on in an old codebase gives you many errors on day one. After that you write more ?? fallback and more undefined checks.

L

Leo: And some libraries weren't written for them.

M

Maya: Some weren't. So I wouldn't use them for a script I'll delete next week.

L

Leo: Then why here?

M

Maya: Two reasons. Quickturn is code we'll live with for years. And a lot of it is written fast, some by AI agents. A compiler gate catches what a tired reviewer misses.

L

Leo: A gate meaning a check that has to pass before a merge?

M

Maya: Yes. Type checking is a required check in our CI. Every package extends one shared base config with these flags. Nobody gets a softer copy.

L

Leo: Even when a library can't pass?

M

Maya: We had exactly that case. Our OpenAPI generator can produce a ready-made client, a small SDK for calling our API. Its own source failed to compile under exactOptionalPropertyTypes.

L

Leo: How badly?

M

Maya: About a dozen errors. Nothing we could fix from our side.

L

Leo: I'd have turned the flag off for the generated folder. It's generated code, nobody reads it.

M

Maya: That was one option on the table. Let's put both side by side.

L

Leo: So you generate only the types, and write the calls yourselves?

M

Maya: In one small module. Each call is plain fetch, and its request is checked with satisfies against the generated request type.

L

Leo: What does satisfies do, exactly?

M

Maya: It checks that a value fits a type, without changing the value's own type. So if the contract changes, our request object stops fitting, and the build fails.

L

Leo: That's the row you colored. With the loose folder, a changed contract would just slip through.

M

Maya: Right. The hand-written module costs us some upkeep. We'll look again when a generator release compiles under the flag.

L

Leo: Still, one exception for generated code doesn't sound dangerous.

M

Maya: The first one never does. But a gate you loosen for one caller stops being a gate. The next person points at your exception.

L

Leo: And turning off my flag for my package is the same move.

M

Maya: It's the same move. Take the element once and check it, and the red line goes away.

04Leo explains it back

M

Maya: A new teammate asks why their fresh package needs more than strict. What do you say?

L

Leo: strict is a floor, not the whole set. Some flags were never put in the bundle.

L

Leo: noUncheckedIndexedAccess makes an array or map read possibly undefined, so you check the element itself.

L

Leo: exactOptionalPropertyTypes keeps "missing" apart from "undefined". That matters for a PATCH, where missing means keep the old value.

M

Maya: And the other two?

L

Leo: Map lookups have to look like lookups, with brackets. And imports come out exactly as written, so a type-only import never runs a module.

L

Leo: They cost some friction, so they fit code we keep for years.

M

Maya: You left out the hard case: code you don't control that can't pass. You change what you generate, or wrap it, like our hand-written calls. You never lower the gate for it.

Summary in three lines

  1. strict is a floor; flags like noUncheckedIndexedAccess and exactOptionalPropertyTypes are separate opt-ins.
  2. Each extra flag turns a runtime surprise into a compile error, at the cost of more checks in everyday code.
  3. When outside code can't pass a gate, change what you generate or wrap it; don't loosen the gate.
