同じリクエストが二度届いたらどうなるか

サーバーは回答を受け付けたのに、スマートフォンにはレスポンスが届きませんでした。送り直せば完了済みの操作を繰り返すかもしれず、諦めれば受け付けられていない操作が失われるかもしれません。

01重複はふつうに起こる

タイムアウトしても、サーバーがリクエストをコミットしたかどうかはクライアントにはわかりません。成功したあとで応答が失われた可能性もあります。リトライすれば重複のおそれがあり、リトライしなければ操作が失われるおそれがあります。キューやリトライするクライアントがあれば、同じものが繰り返し届くのはよくあることです。

冪等性とは、同じ操作を繰り返しても、一回行ったときと同じ意図した効果になる性質です。HTTP は安全な読み取りや、PUT・DELETE などのメソッドを意味のうえで冪等と定めていますが、アプリケーションの POST には独自の設計が必要です。配信の保証は仕組みによって異なるので、繰り返しが起こりうる場所では、アプリケーションの側で対処します。

02クライアントが作る ID と条件付き書き込み

Quickturn では、回答とラウンドの ID を送信前に端末で作ります。同じ回答 ID が繰り返し届けばスキップし、同じ開始リクエストが繰り返し届けば既存のラウンドを返します。受付済みの回答だけを含むバッチは、カウンターをもう一度変えることなく成功として扱えます。

POST /v1/rounds/7c1e…/answers
{ "answers": [
  { "id": "a41f…", "cardId": "c-203", "grade": "got" },
  { "id": "b8d2…", "cardId": "c-118", "grade": "missed" }
] }

「存在しないことを読んでから書く」という別々の手順は安全ではありません。二つのリクエストが、どちらも「存在しない」と読んでしまう可能性があるからです。存在しないこと、あるいは期待するバージョンであることを、書き込みそのものの条件にします。

トランザクションは、これらの条件をアトミックに検査します。競合が起きたら回数を限って読み直しと再計算を行い、あとのリトライで受付済みの回答を見つけられます。こうすれば、Lambda の実行をまたいで分散ロックを持ち続けずに済みます。同じ ID が異なる内容で再利用された場合にどうするかも、契約で定めておく必要があります。

03冪等キーと最初の結果

自然に決まる安定した ID がない操作では、冪等キー（idempotency key）で一つの意図した操作を識別できます。キーの範囲は認証済みの呼び出し元に限り、リクエストの識別情報と最初の結果を、保持期間を明示した方針のもとで保存します。

同じキーで異なるリクエストが届いたら拒否します。最初の操作の実行中に繰り返しが届いた場合の振る舞いも決めておく必要があります。完了済みのラウンドをもう一度完了させようとしたら、別の結果を計算し直すのではなく、保存しておいた集計を返します。HTTP API で冪等キーを採用するなら、特定の標準化ドラフトの状況に頼らず、サービスの契約としてドキュメントに定めて扱います。

04コストと、リトライするエージェント

キーと保存した結果はストレージを消費し、有効期限のルールも必要です。結果が毎回同じにならない処理には、別の問題もあります。モデルを二回呼べば、採点結果が二通り出るかもしれません。最初に受け付けた採点を保存して再利用し、それとは別に試行を調整して、不要な重複呼び出しとそのコストを避けます。

メールを送るツールやカードに課金するツールを持つエージェントにも、同じ保護が必要です。オーケストレーションの層が、一つの意図した操作に安定したキーを割り当て、それを下流のサービスに渡します。モデルがリトライのたびに新しいキーを作ってしまうと、重複の排除が働きません。

3行まとめ

  1. リトライによって、完了済みのリクエストが繰り返されることがあります。繰り返し届く可能性がある場所では、操作に安定した識別子を持たせます。
  2. 条件付き書き込みで重複を防ぎ、同じ内容の繰り返しには、受け付けた結果を再利用します。
  3. ID のない作成操作には Idempotency-Key を使います。エージェントの場合、キーはモデルではなく操作に属します。
