What if the same request arrives twice?

The server accepts an answer, but the phone never receives the response. Resending may repeat a completed action; giving up may lose an unaccepted one.

01Duplicates are normal

A timeout does not tell a client whether the server committed its request. The reply may have been lost after success. Retrying risks duplication; refusing to retry risks losing the action. Queues and retrying clients commonly produce repeated deliveries.

Idempotency makes repetition have the same intended effect as one action. HTTP defines safe reads and methods such as PUT and DELETE as idempotent in semantics; an application's POST needs its own design. Delivery guarantees vary, so the application should handle repeats where they are possible.

02Client-made ids and conditional writes

Quickturn creates answer and round IDs on the device before sending. A repeated answer ID is skipped, and a repeated start returns the existing round. A batch containing only previously accepted answers can succeed without changing counters again.

POST /v1/rounds/7c1e…/answers
{ "answers": [
  { "id": "a41f…", "cardId": "c-203", "grade": "got" },
  { "id": "b8d2…", "cardId": "c-118", "grade": "missed" }
] }

A separate “read absent, then write” sequence is unsafe: two requests can both observe absence. Put the condition in the write, using nonexistence or an expected version.

The transaction atomically checks those conditions. A conflict causes a bounded reload and recomputation; a later retry can discover the already accepted answer. This avoids holding a distributed lock across a Lambda execution. The contract must also define what happens if the same ID is reused with different content.

03Idempotency keys and first answers

For an action without a natural stable ID, an idempotency key can identify one intended operation. Scope it to the authenticated caller and store the request identity and first result under an explicit retention policy.

A repeated key with a different request should be rejected. A repeat while the first action is running also needs defined behavior. Completing an already completed round returns its stored summary rather than recomputing a different outcome. HTTP API adoption of idempotency keys should be treated as a documented service contract, without depending on a particular standards-draft status.

04Costs, and agents that retry

Keys and saved results consume storage and require expiry rules. Nondeterministic work adds another issue: calling a model twice may produce two grades. Store and reuse the first accepted grade, while separately coordinating attempts to avoid unnecessary duplicate calls and cost.

Agent tools that send email or charge a card need the same protection. An orchestration layer supplies a stable key for one intended action and forwards it to the downstream service. A model inventing a new key on every retry would defeat deduplication.

Summary in three lines

  1. Retries can repeat a completed request; use a stable operation identity where repeated delivery is possible.
  2. Use conditional writes to prevent duplicates, and reuse an accepted outcome for matching repeats.
  3. For creates without an id, use an Idempotency-Key; for agents, the key belongs to the action, not the model.
