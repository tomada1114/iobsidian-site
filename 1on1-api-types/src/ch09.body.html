What if the same request arrives twice?

After this page you can explain why duplicate requests are normal. You can also make a write idempotent with client-made ids, conditional writes and stored first answers.

About 8 min readThe morning after an alarm

In this page

  • Why do duplicates happen at all?
  • How do client-made ids and conditional writes stop them?
  • What's an Idempotency-Key for?
  • What does it cost, and what changes with agents?

The morning after an alarm. Last night the API returned a short burst of 5xx errors, and web clients resent their answers.

01Duplicates are normal

L

Leo: I read the alarm notes. During the 5xx burst, the web app resent answers and some "finish round" calls. Do some learners now have answers counted twice?

M

Maya: What do you think?

L

Leo: I'm worried they do. Maybe the fix is to stop retrying?

M

Maya: Let's think about what the client knew. A request timed out. Did the server do the work?

L

Leo: It… failed? It timed out.

M

Maya: That's the trap. A timeout only tells the client that no answer came back. The server may have saved everything, and the reply got lost on the way.

L

Leo: So the client can't know. If it doesn't retry, the answers might be lost. If it does, they might be saved twice.

M

Maya: Right. And it's not only our retries. Mobile networks resend, SDKs resend, queues deliver a message again, and offline answers are replayed later.

L

Leo: So duplicates aren't a bug in the client. They're normal.

M

Maya: Networks deliver "at least once". "Exactly once" is not something you can buy. What you can build is an exactly-once effect.

L

Leo: How?

M

Maya: From at-least-once delivery plus idempotency. Idempotent means doing it twice has the same effect as doing it once.

L

Leo: Like setting a value, instead of adding to it.

M

Maya: Yes. HTTP already says GET, PUT and DELETE are idempotent by definition. POST is not, unless you make it so. Our answers are POSTs.

02Client-made ids and conditional writes

L

Leo: So how do we make a POST idempotent?

M

Maya: Give each thing an identity before it's sent. The client makes each answer's id, and each round's id, with a random UUID.

POST /v1/rounds/7c1e…/answers
{ "answers": [
  { "id": "a41f…", "cardId": "c-203", "grade": "got" },
  { "id": "b8d2…", "cardId": "c-118", "grade": "missed" }
] }
L

Leo: And the server remembers which ids the round already holds?

M

Maya: Yes. A repeated id is skipped. If the whole batch is repeats, nothing changes and the answer is success, even after the round is finished.

L

Leo: And a retried "start round" with the same round id?

M

Maya: It returns the round it already made. Here's what happened last night, for one learner.

L

Leo: So nobody was counted twice. But how does the server "skip" a repeat?

M

Maya: How would you do it?

L

Leo: I'd check if the id exists. If not, write it.

M

Maya: That's the second trap. Picture two copies of the same request, arriving a millisecond apart.

L

Leo: Both check. Both see "absent". Both write. Oh.

M

Maya: A duplicate, exactly the thing you were checking for. Reading first and writing later leaves a gap, and two requests fit into it.

L

Leo: So the check has to be inside the write.

M

Maya: Yes. The database write itself carries the condition: this item must not exist, or it must still be at the version I read. Let me compare.

L

Leo: What happens to the request that loses?

M

Maya: Each commit is one transaction of conditional writes. A lost race is retried a few times, and then it gets a conflict code.

L

Leo: Does the web client resend on a conflict?

M

Maya: Yes. It's the one refusal the web client sends again; every other refusal is final.

M

Maya: And on the resend the server sees the answers already held, so the client gets the same success.

L

Leo: Couldn't we just lock the round while one request writes? Then nobody races.

M

Maya: Locks across a network have their own problems. A Lambda that holds a lock can time out, and the lock stays until it expires.

L

Leo: And every other request waits behind it.

M

Maya: Yes. A conditional write never waits. One request wins, the other fails at once and tries again. For short writes like ours, that's cheaper than a lock.

03Idempotency keys and first answers

L

Leo: Answers have natural ids. What about a create that doesn't? Something with no obvious identity?

M

Maya: Then the client sends an Idempotency-Key header, a random value for that one intended action. Stripe made the pattern well known.

L

Leo: Is the header a web standard?

M

Maya: No. The IETF, the group that writes internet standards, had a draft for it, and the draft expired. The pattern is widely used anyway. Here's what the server does with the key.

L

Leo: Why "for this caller"?

M

Maya: Keys are scoped to the signed-in user. Otherwise one user could guess another's key and read their stored response.

L

Leo: What else do you have to decide?

M

Maya: How long keys live. What a repeat with the same key but a different body gets; usually an error. And what happens while the first request is still running.

L

Leo: Do we store first outcomes anywhere else?

M

Maya: Where it matters. Finishing a round that's already finished returns the summary it kept, not a new one.

04Costs, and agents that retry

L

Leo: This isn't free, though.

M

Maya: No. Keys and results take storage. You need an expiry policy. And non-deterministic work needs care.

L

Leo: Non-deterministic, like a model's grade?

M

Maya: Yes. Our grading of typed answers runs as a background job on a queue, and queues deliver at least once. Would the model give the same grade twice?

L

Leo: Not necessarily. So idempotent can't mean "same output".

M

Maya: Right. For a model, idempotent means: store the first grade, and return it on every repeat.

L

Leo: What about agents? They call tools.

M

Maya: That's where it gets serious. An agent retries a tool call that charges a card, or sends an email. Or the model simply calls the tool twice.

L

Leo: So the tool needs a key. Can the model make one up?

M

Maya: Never. A model could make a new key on every call, and every call would look new. The key comes from the orchestration layer, the code that runs the agent.

L

Leo: One key per intended action.

M

Maya: Yes. And the payment API has to receive that key, or it protects nothing.

05Leo explains it back

M

Maya: The on-call engineer asks you whether to turn off retries. What do you say?

L

Leo: No. Retries will happen anyway. A timeout doesn't say whether the work was done.

L

Leo: So every write that can be resent carries an id the client made. Answers and rounds have them.

L

Leo: The database write is conditional on that id. So a duplicate is skipped, even if two arrive at the same moment.

M

Maya: And what does the repeat get back?

L

Leo: The same answer as the first time. For creates with no natural id, an Idempotency-Key does the same job, with the first response stored.

M

Maya: With agents, one more rule: the key belongs to the intended action, made by the code that runs the agent. Never let the model make it up.

Summary in three lines

  1. Networks deliver at least once, so every write that may be resent needs an identity the client chose.
  2. Put the check inside the write as a condition, and answer every repeat with the first outcome.
  3. For creates without an id, use an Idempotency-Key; for agents, the key belongs to the action, not the model.
