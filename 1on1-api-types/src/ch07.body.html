Where does the API contract actually live?

After this page you can explain how one set of schemas becomes the API document and the clients' types. You can also say why generated files are committed and tested for drift.

About 8 min readPairing at Leo's desk

In this page

  • Where does the OpenAPI document come from?
  • Should the spec come before the code, or from it?
  • Why commit generated files, and test them?
  • What does owning the chain cost?

Leo's desk. His pull request shows a red CI run, on a test he never touched.

01One chain from one source

L

Leo: I added one field to a response schema. Now CI fails. It says "the OpenAPI document differs from the committed file".

M

Maya: And the second failure?

L

Leo: Same thing, for the web client's types. Why are generated files even in git? I thought generated output never belongs there.

M

Maya: Let's start earlier. Where do you think the OpenAPI document comes from?

L

Leo: Someone writes it? Or updates it after the code is done, like documentation?

M

Maya: That's how many teams do it. Ours is generated from the same schemas the server checks requests with. Let me draw the chain.

L

Leo: What's JSON Schema?

M

Maya: A standard way to describe the shape of JSON. zod can turn its own schemas into it. An OpenAPI 3.1 document uses JSON Schema for every body, so the conversion is direct.

L

Leo: And what builds the document around the schemas?

M

Maya: A small function we own. It reads a route table: for each operation, the method, the path, the request, the success response and the error codes.

L

Leo: Then the types for the web app are generated from the document.

M

Maya: Right, and the calls are written by hand. Each one is checked with satisfies against the generated request type.

// breaks if the path or the request shape changes
const settings = await call<GetSettingsResponses>(
  "GET",
  { url: "/v1/settings" } satisfies GetSettingsData,
);
L

Leo: The Swift and Kotlin apps too?

M

Maya: They generate their clients from the same document. And the contract package depends on zod only. It's neither server code nor client code, so both sides can use it.

02Design-first or code-first

L

Leo: I've read that you should write the spec first. Design-first. Isn't generating it backwards?

M

Maya: Both are real options. Design-first means you write the OpenAPI document before any code. Code-first means you derive it from code.

L

Leo: When is design-first better?

M

Maya: When several teams must agree before anyone builds. They review a spec, and one team can run a mock server from it while the other builds the real one.

L

Leo: And code-first?

M

Maya: There's no gap between the spec and the validator. The thing that checks requests is the thing that writes the spec. That's good for one team.

L

Leo: Which one are we?

M

Maya: In between. Our schemas are code, but they sit in their own package, and we write them before any handler. Let me compare the two.

L

Leo: So code-first still has a drift problem. Between the generated files and the schemas.

M

Maya: Exactly. And that's the test that just failed on you.

03Commit it, then test it

L

Leo: Okay, but why commit the generated document at all? CI could generate it fresh every time.

M

Maya: Who reads your pull request?

L

Leo: A reviewer.

M

Maya: If you change a response, what should the reviewer see?

L

Leo: The schema change, I guess.

M

Maya: The schema change is in TypeScript, in one file. The committed document shows what every client will actually see: the path, the field, whether it's required. That diff is what a reviewer reads.

L

Leo: So committing it turns a contract change into something you can review.

M

Maya: Right. Now the test. It regenerates the document and compares it with the committed file. In CI, it never rewrites the file. A stale file just fails.

L

Leo: And locally?

M

Maya: One command rewrites it. You run it, commit the new file, and CI passes. Here's the loop.

L

Leo: Couldn't CI just regenerate the file and commit it for me? That would save a step.

M

Maya: It would. What would the reviewer see then?

L

Leo: My schema change, and then a bot commit after the review started. Hmm.

M

Maya: And the bot might commit a change nobody meant to make. Say you renamed a field in a schema to tidy the code.

L

Leo: Then every app that reads the old name breaks, and the only sign is a commit from CI.

M

Maya: That's why the test only compares. A person runs the command, looks at the diff, and decides it's intended.

L

Leo: So the extra step is where the decision happens.

M

Maya: Yes. It costs you a minute, and it makes every contract change a choice someone made on purpose.

L

Leo: So my red build isn't a bug. It's the test telling me I forgot to regenerate.

M

Maya: Exactly that. The web client's types follow the same rule, with their own test.

L

Leo: Is there anything the tests can't catch?

M

Maya: One thing. We check the response schemas against the application's view types at compile time, in both directions. But an optional field that the code never actually fills in passes that check.

L

Leo: Because optional means "may be missing", and it's always missing.

M

Maya: Right. A compile-time check sees shapes, not behavior.

04What owning the chain costs

L

Leo: Why write our own document builder? There are libraries for this.

M

Maya: There are. We chose a small function over one more dependency. The cost is that anything the document doesn't express yet is our job.

L

Leo: Like what?

M

Maya: A security scheme, a header, examples. Each one is an edit to our builder. And generated files add noise to diffs.

L

Leo: Would you choose the same at a big company?

M

Maya: Maybe not. With several consumer teams, I might prefer design-first and a formal spec review. The teams need to agree before code exists.

L

Leo: So the choice depends on how many teams have to agree.

M

Maya: Yes. But one setup never works, at any size.

L

Leo: Which?

M

Maya: A spec written by hand next to separate validators. Two sources of truth, and nothing checks that they agree. They drift, and nobody notices until a client breaks.

05Leo explains it back

M

Maya: A new teammate asks you where our API contract lives. What do you say?

L

Leo: In one place: the schemas the server validates with. They're in their own package, and they depend only on zod.

L

Leo: Everything else is generated from them. zod makes JSON Schema, and our builder makes the OpenAPI document. The clients' types come from that.

L

Leo: The generated files are committed, so a contract change shows up as a diff in review.

M

Maya: And if someone forgets to regenerate?

L

Leo: A test regenerates each copy and fails in CI if it's stale. One command fixes it locally.

M

Maya: Name the alternative, so they know it's a choice: design-first is right when several teams must agree before anyone builds. What never works is a hand-written spec next to separate validators.

Summary in three lines

  1. Keep one source of truth: the schemas the server validates with generate the document and the client types.
  2. Commit the generated files so every contract change is a diff that reviewers read.
  3. Test every generated copy for drift; design-first fits when several teams must agree first.
