Where does the API contract actually live?

After this page you can explain how one set of schemas becomes the API document and the clients' types. You can also say why generated files are committed and tested for drift.

About 4 min readQuickturn case study

In this page

  • Where does the OpenAPI document come from?
  • Should the spec come before the code, or from it?
  • Why commit generated files, and test them?
  • What does owning the chain cost?

01One chain from one source

Quickturn derives its OpenAPI document from the schemas used to parse requests. A route table supplies method, path, request, success response and error codes. The document then feeds client generation.

OpenAPI 3.1 uses JSON Schema for body shapes. The schema conversion must support the features the project uses; runtime-only transformations need special care. Web request objects are checked with satisfies against generated types, while Swift and Kotlin consume the same published contract.

// breaks if the path or the request shape changes
const settings = await call<GetSettingsResponses>(
  "GET",
  { url: "/v1/settings" } satisfies GetSettingsData,
);

02Design-first or code-first

Design-first starts with a specification that several teams can review before implementation. Code-first derives it from code and reduces duplication between the validator and document. Quickturn writes schemas in a dedicated contract package before handlers, combining an early contract discussion with generation from executable definitions.

Generation still leaves a possible gap between source and committed artifacts. A schema edit does not automatically mean the published document or client types have been refreshed. That gap needs a check.

03Commit it, then test it

Committed generated files make the externally visible change reviewable. CI regenerates the document and client types in a temporary location and compares them with their committed versions. It fails on drift instead of silently rewriting or committing output.

Locally, a regeneration command updates the files so the author can inspect and commit the intended contract diff. That step prevents an accidental rename from appearing only as an unreviewed bot correction.

Compile-time agreement between response schemas and application view types checks shape, not population. An optional field that is never actually filled still requires a behavioral test.

04What owning the chain costs

Owning a small document builder avoids another integration dependency but creates maintenance work. Security schemes, headers and examples must be represented explicitly, and generated diffs need review.

Several consumer teams may favor specification-first review. Either approach needs a checked chain from agreed contract to validator and client output. A handwritten specification beside independent, unchecked validators leaves two sources that can drift.

Summary in three lines

  1. Keep one source of truth: the schemas the server validates with generate the document and the client types.
  2. Commit the generated files so every contract change is a diff that reviewers read.
  3. Test every generated copy for drift; design-first fits when several teams must agree first.
