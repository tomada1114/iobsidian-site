API の契約は、実際にはどこにあるのか

リクエストのスキーマを変えたのに、コミット済みの API ドキュメントは以前の形のままです。共有の定義元が役に立つのは、そこから生成したコピーと実装が一致しているときだけです。

01一つの定義元からつながる流れ

Quickturn は、リクエストのパースに使うスキーマから OpenAPI のドキュメントを導き出しています。ルート表には、メソッド、パス、リクエスト、成功時のレスポンス、エラーコードを書きます。そのドキュメントから、クライアントのコードを生成します。

OpenAPI 3.1 は、ボディの形を表すのに JSON Schema を使います。スキーマの変換は、プロジェクトが使う機能に対応していなければならず、実行時にしか働かない変換には特に注意が必要です。Web のリクエストオブジェクトは生成された型に対して satisfies で検査し、Swift と Kotlin は同じ公開済みの契約を使います。

// パスかリクエストの形が変わるとコンパイルが通らなくなる
const settings = await call<GetSettingsResponses>(
  "GET",
  { url: "/v1/settings" } satisfies GetSettingsData,
);

02デザインファーストかコードファーストか

デザインファーストでは、まず仕様書を書き、実装の前に複数のチームでレビューします。コードファーストでは、仕様をコードから導き出し、バリデーターとドキュメントの重複を減らします。Quickturn は、ハンドラーより先に専用の契約パッケージでスキーマを書きます。早い段階で契約について議論しつつ、実行可能な定義から生成するという、両方の利点を組み合わせたやり方です。

生成を使っても、定義元とコミットされた生成物のあいだには隙間が残りえます。スキーマを編集しても、公開されるドキュメントやクライアントの型が自動で更新されるとは限りません。この隙間にはチェックが必要です。

03コミットしてテストする

生成したファイルをコミットしておけば、外から見える変更をレビューできます。CI はドキュメントとクライアントの型を一時的な場所に生成し直し、コミット済みのものと比較します。ずれがあれば、出力を黙って書き換えたりコミットしたりせず、失敗として報告します。

ローカルでは、生成コマンドでファイルを更新し、意図どおりの契約の差分になっているかを作成者が確かめてからコミットします。この手順があるので、うっかりした名前の変更が、誰もレビューしていないボットの修正としてだけ現れることを防げます。

レスポンスのスキーマとアプリケーションのビューの型がコンパイル時に一致していても、確かめられるのは形だけで、値が実際に入るかどうかではありません。省略可能なフィールドに実際には一度も値が入らないといった問題は、振る舞いのテストで確かめる必要があります。

04流れを自前で持つコスト

小さなドキュメント生成の仕組みを自前で持てば、連携のための依存を一つ増やさずに済みますが、保守の仕事が生まれます。セキュリティスキーム、ヘッダー、例を明示的に表現する必要があり、生成された差分のレビューも欠かせません。

利用する側のチームが複数あるなら、仕様書を先に書いてレビューするやり方が向くかもしれません。どちらの方式でも、合意した契約からバリデーターとクライアントの出力までが、チェックされた流れでつながっている必要があります。手書きの仕様書の横に、チェックされていない独立したバリデーターがあると、ずれうる定義元が二つ残ります。

3行まとめ

  1. 共有のスキーマとルート定義から、ドキュメントとクライアントの型を生成します。ずれのチェックと振る舞いのテストは、その流れの別々の部分を確かめます。
  2. 生成したファイルをコミットし、契約の変更がすべて、レビューで読まれる差分になるようにします。
  3. 生成したコピーはすべてずれをテストします。複数のチームが先に合意しなければならないなら、デザインファーストが向いています。
