Why not just add another boolean flag?

After this page you can model cases that exclude each other as a discriminated union. You can also explain why the compiler then finds every place a new case must be handled.

About 8 min readWhiteboard room

In this page

  • What does a discriminated union look like?
  • How does the compiler find every switch, and why no enums?
  • When is a union the wrong shape?

The small meeting room. Leo puts his laptop on the table, next to the whiteboard.

01A bag of flags

L

Leo: I'm adding the background job that rebuilds a learner's stats. It needs to say who is acting. Here's my draft type.

type Actor = {
  learnerId?: string;
  isSystem?: boolean;
  jobName?: string;
  onBehalfOf?: string;
};
M

Maya: Let me ask one thing. What does { isSystem: true } mean, with nothing else set?

L

Leo: A system job… for no learner? That can't happen.

M

Maya: But the type allows it. How many combinations does it allow, just by which fields are set?

L

Leo: Four optional fields, each there or not. Two to the fourth. Sixteen.

M

Maya: And how many of those make sense?

L

Leo: Maybe three. A learner. A system job for a learner. Hmm, and later an agent.

M

Maya: So thirteen are nonsense. Who stops them?

L

Leo: I'd add a few if checks. If isSystem, then onBehalfOf must be set.

M

Maya: Where?

L

Leo: Wherever we read an actor.

M

Maya: That's the problem. Every reader has to check the combination again, and one day one reader forgets. There's a phrase for the fix, often credited to Yaron Minsky: make illegal states unrepresentable.

L

Leo: Meaning the bad combinations can't even be written?

M

Maya: Right. Not caught later. Impossible to type in the first place. Let me draw both.

02One tag, exact fields

L

Leo: So how do I write the right side?

M

Maya: As a discriminated union. It's a union of object types, and each one has a tag field with a literal value. We call ours kind.

L

Leo: And each member has only the fields it needs.

M

Maya: Exactly those fields, all required. Here's Quickturn's actor.

type Actor =
  | { kind: "learner"; learnerId: LearnerId }
  | { kind: "system"; job: SystemJob;
      onBehalfOf: LearnerId }
  | { kind: "agent"; onBehalfOf: LearnerId;
      grants: readonly OperationKind[] };
L

Leo: A system actor without a learner… I literally can't write it. onBehalfOf is required.

M

Maya: And once you check actor.kind === "system", the compiler narrows to that member. You get job and onBehalfOf, and nothing else.

L

Leo: What are the grants on the agent?

M

Maya: The list of operations the agent may do. Our tutor agent runs as that member, so it always acts for one learner, and only within its grants.

L

Leo: Where does OperationKind come from? Is it written out by hand?

M

Maya: From a list. We declare the operation names as const. That keeps the exact strings, not just "string".

L

Leo: And then a type from the list?

M

Maya: (typeof LIST)[number] turns the list into a union of its strings. So the list and the type can never disagree.

L

Leo: So when I add a name to the list, the type grows by itself.

M

Maya: Right. Let me draw what the actor looks like as a whole.

03Exhaustive, and no enums

L

Leo: Okay, but next year someone adds a fourth kind. How do we find all the code that reads actors?

M

Maya: Where does our code decide what an actor may do?

L

Leo: In authorize, I guess. And anywhere else that switches on kind.

M

Maya: Those switches are written to be exhaustive. That means one case per member, and a check that fails if a member is missing.

switch (actor.kind) {
  case "learner": return actor.learnerId;
  case "system":  return actor.onBehalfOf;
  case "agent":   return actor.onBehalfOf;
  default: {
    const unreachable: never = actor;
    return unreachable;
  }
}
L

Leo: What's never doing there?

M

Maya: never is the type with no values. If every case is handled, actor is never at that point. Add a fourth member, and it isn't anymore, so the line fails to compile.

L

Leo: That's clever. Is that what we use?

M

Maya: We use a lint rule that does the same job, and we forbid a plain default branch on unions.

L

Leo: Why forbid it? A default seems safe.

M

Maya: A default quietly accepts the new case. The code compiles, and the new actor gets whatever the default does. Here's the flow we want instead.

L

Leo: Why do we use string unions instead of enum? My old team used enums for this.

M

Maya: Our lint blocks enum, and its message says why. An enum is the one TypeScript feature that creates a real object in the JavaScript output. It can't just be erased.

L

Leo: Does that matter?

M

Maya: Tools that strip types without compiling, like Node's built-in type stripping, don't support enums at all. And numeric enums accept any number, even one you never listed.

L

Leo: And a string union is already the value we send in JSON.

M

Maya: Right. "system" in the code is "system" on the wire. No mapping in between.

04When a union is the wrong shape

L

Leo: Should everything with a kind be a union, then?

M

Maya: No. If the cases share almost every field and differ in one, a union repeats everything. Then keep one type with one tagged field, or a shared base.

L

Leo: And a union with ten members?

M

Maya: Often it's two ideas mixed together. Try splitting it first.

L

Leo: What about data from outside? A request can't promise it's a valid actor.

M

Maya: Right, so it's parsed into the union by a schema. Our schemas can check a discriminated union too.

L

Leo: Then the exhaustive rule works everywhere?

M

Maya: Inside our program, yes. The API is the tricky place. Our home view in the contract is a tagged union, like kind: "onboarding" | "placement" | "ready".

L

Leo: So a client switches on it, exhaustively.

M

Maya: And next month the server adds a new kind. What happens to an installed app that was exhaustive?

L

Leo: It hits a case it doesn't know. Oh. It breaks.

M

Maya: So clients of a public API keep a default branch. Inside, exhaustive; across the wire, forgiving.

L

Leo: That's the opposite of the rule for our own switches.

M

Maya: Because the owner changes. We control our code, not the apps already on phones.

L

Leo: Does this idea matter outside apps like ours?

M

Maya: A lot in agent systems. Think of the states you'd never want: an agent acting for no one, or an agent with wider rights than its user.

L

Leo: With our actor type, the first one can't be written. The second is limited by the grants.

M

Maya: Right. In an agent system, those are exactly the illegal states worth making unwritable.

05Leo explains it back

M

Maya: A reviewer asks why you threw away your four flags. What's your answer?

L

Leo: Four optional flags allow sixteen shapes, and most are nonsense. Every reader has to check the combination again.

L

Leo: A discriminated union lists only the real cases. Each has a literal kind and exactly its own fields, so a system job without a learner can't be written.

L

Leo: Checking kind narrows to one member. And when someone adds a case, the exhaustive check lists every switch to update.

M

Maya: And the enum question?

L

Leo: We use unions of strings. An enum makes a runtime object, and the string is already the value in the JSON.

M

Maya: One limit to add: across the wire it flips. The server may add a case later, so clients of a public API keep a default branch.

Summary in three lines

  1. A discriminated union with a literal kind makes nonsense combinations impossible to write.
  2. Exhaustive switches let the compiler list every place a new case must be handled; a default branch hides them.
  3. Inside your code stay exhaustive, but clients of a public API keep a default branch for new cases.
