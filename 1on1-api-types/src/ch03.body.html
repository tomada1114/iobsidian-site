真偽値フラグを足すだけでは、なぜ足りないのか

システムフラグが立っているのにジョブ名がなかったり、無関係な学習者 ID と並んでいたりすることがあります。省略可能なフィールドを並べた型では、アクターのモデルが排除すべき組み合わせまで表せてしまいます。

01フラグの寄せ集め

アクターを、省略可能な学習者 ID、システムフラグ、ジョブ名、代理対象の ID で表すと、意味のない組み合わせがいくつも作れます。システムフラグだけでは、どのジョブが動いているのか、どの学習者のための処理なのかがわかりません。読む側は毎回、こうした制約を頭の中で組み立て直すことになります。

「不正な状態を表現できないようにする（Make illegal states unrepresentable）」とは、正しい選択肢を中心に型を設計することです。これで検査済みコードの中のモデルは改善されます。ただし、実行時の入力には引き続きパースが必要で、安全でないアサーションを使えばこの仕組みは迂回されてしまいます。

type Actor = {
  learnerId?: string;
  isSystem?: boolean;
  jobName?: string;
  onBehalfOf?: string;
};

02タグ一つで、必要なフィールドを決める

Quickturn のアクターは判別可能なユニオン型です。kind が学習者・システムジョブ・エージェントのどれかを示し、各メンバーはそれぞれに必要なフィールドを必須にしています。タグを検査すると、使えるフィールドが絞り込まれます。

エージェントのアクターは、学習者を一人指定し、操作の許可（grants）を持ちます。実行時の操作名は as const を付けた配列で用意し、そのインデックスアクセス型 (typeof LIST)[number] から、対応する静的なユニオン型を得ます。型は許可の内容を表すだけなので、実際に許可を強制するのは認可の処理です。

type Actor =
  | { kind: "learner"; learnerId: LearnerId }
  | { kind: "system"; job: SystemJob;
      onBehalfOf: LearnerId }
  | { kind: "agent"; onBehalfOf: LearnerId;
      grants: readonly OperationKind[] };

03網羅性チェックと、enum を使わない理由

網羅的な switch は、ユニオン型のすべてのメンバーを扱います。残った値を never 型に代入しておくと、新しいケースを追加したときにコンパイルが失敗します。網羅性を検査する lint ルールでも、同じ目的を果たせます。

switch (actor.kind) {
  case "learner": return actor.learnerId;
  case "system":  return actor.onBehalfOf;
  case "agent":   return actor.onBehalfOf;
  default: {
    const unreachable: never = actor;
    return unreachable;
  }
}

自分たちが管理するコードでは、何でも受け止める default 節が、振る舞いの抜けを隠してしまうことがあります。一方、公開 API の向こう側では、インストール済みのクライアントが、自分のリリース後に追加された選択肢を受け取る可能性があります。そのため、安全なフォールバックが必要です。

Quickturn が enum ではなく文字列のユニオン型を使うのは、ランタイムが消去可能な TypeScript 構文を前提にしているためです。enum は JavaScript のコード出力を必要とすることがあり、型を取り除くだけのランタイムはそれを生成しません。特定の文字列なら、そのまま JSON にも対応します。

04ユニオン型が合わない場合

ユニオン型が最も役立つのは、ケースごとに必須フィールドが異なるときです。ほとんどのフィールドが共通なら、オブジェクト全体を繰り返さず、共通の形や基底を使います。ユニオン型が極端に大きくなったら、独立したいくつかの概念が混ざっている兆候かもしれません。

絞り込みに頼る前に、外部データをユニオン型へパースします。一つのバージョンで管理しているコードの中では網羅的に扱い、別々にデプロイされるクライアントとのあいだでは、未知の選択肢を安全に受け流せるようにします。アクターの型は、ID や許可の欠落を見つける助けになります。ただし、ID は信頼できる認証からサーバーが導き出し、権限もサーバーが確認しなければなりません。

3行まとめ

  1. 判別可能なユニオン型は、検査済みコードの中で、各選択肢に必要なフィールドを必須にします。外部からの入力には引き続きパースが必要です。
  2. 網羅性チェックは switch のケースの漏れを明らかにします。何でも受け止める分岐は、追加すべき振る舞いを隠してしまうことがあります。
  3. 自分たちのコードの中では網羅的に扱い、公開 API のクライアントでは新しいケースに備えて default 分岐を残します。
