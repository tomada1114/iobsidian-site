Should a function throw, or return its failure?

After this page you can decide when a failure is a returned value and when it is a thrown error. You can also explain how a branded type stops two string ids from being swapped.

About 8 min readPairing at Leo's desk

In this page

  • Why didn't the compiler stop a card id posing as a learner id?
  • What does returning a failure look like?
  • Which failures are values, and which are bugs?
  • What does all this cost?

Leo's desk. A review on his pull request is open, with two comments.

01Two strings that look the same

L

Leo: I got two review comments on one pull request. Can we go through them?

M

Maya: Sure. Read me the first.

L

Leo: A test caught a bug where I passed a card id where a learner id belonged. The reviewer asked why the compiler didn't.

M

Maya: What's the type of a learner id in your code?

L

Leo: type LearnerId = string. I thought that made it safe.

M

Maya: What does a type alias like that create?

L

Leo: A new type?

M

Maya: Only a new name. LearnerId and string are the same thing to the compiler. And a card id is also a string.

L

Leo: And the compiler compares shapes, not names?

M

Maya: Yes, that's called structural typing. Same shape, so it fits.

M

Maya: Right. The fix is called a brand. You add a marker that exists only at compile time.

type LearnerId = string & {
  readonly __brand: "LearnerId";
};

function learnerId(raw: string): LearnerId {
  if (raw === "") throw new Error("empty learner id");
  return raw as LearnerId;
}
L

Leo: No real string has a __brand field. So a plain string doesn't fit anymore.

M

Maya: Exactly. Only a value that went through learnerId() fits. That constructor is the one place with an as, and it checks the value first.

L

Leo: Does the brand survive into JSON?

M

Maya: No. It's a type, so it's erased like every type. A value is branded again wherever it enters. Our API builds the learner id once per request, at the edge, from the signed-in user.

L

Leo: So inside the program, a card id can never go in a learner id's place.

M

Maya: The compiler will refuse it. What's the second comment?

02A failure you can see

L

Leo: My command throws new Error("round closed"). The handler catches it and checks the message. The reviewer wrote that the caller can't see this failure in the signature, and the message will change.

M

Maya: Both true. Tell me: when you call a function in TypeScript, how do you know what it throws?

L

Leo: I read the code. Or the docs, if there are any.

M

Maya: The signature doesn't say. TypeScript has no checked exceptions and no throws clause. And in a catch, the value is unknown.

L

Leo: So a caller can forget the failure completely.

M

Maya: Right. The alternative is to return the failure as a value. We use a type called Result.

type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

const result = finishRound(round, now);
if (!result.ok) return handle(result.error);
result.value; // the finished round
L

Leo: It's a union with a tag. Checking ok narrows it.

M

Maya: Yes, and small ok() and err() helpers build the two members. Now the failure is in the return type. Let me compare the two.

L

Leo: What's the "stable code"?

M

Maya: Each error carries a code, like ERR_ROUND_CLOSED. The caller branches on the code. The message is prose for a human, and we may reword it any day.

L

Leo: So matching on "round closed" was the real bug in my handler.

M

Maya: It would break the first time someone fixed a typo.

03Expected failures and bugs

L

Leo: Should everything return a Result, then? Nothing throws?

M

Maya: No. Ask one question: can the caller do something useful about it?

L

Leo: For "round already closed", yes. The app can show the results screen.

M

Maya: "Not enough cards"? "Forbidden"?

L

Leo: Also yes. Show a message, or sign in again.

M

Maya: Those are expected failures. They happen in normal use, and the caller can act, so they're values with a code. Now, what if a round has more answers than cards?

L

Leo: That should never happen. It means our own code is wrong.

M

Maya: That's a bug. A broken invariant, a rule our code promised to keep. No caller can fix it, so it throws, and our error handler turns it into a 500 and a log line.

L

Leo: So the question is really about the caller, not about how bad it is.

M

Maya: Right. Here are the two answers side by side.

L

Leo: And the code travels all the way to the app?

M

Maya: Unchanged. Let me show the path of "round closed".

L

Leo: What stops someone from adding a code and forgetting its HTTP status?

M

Maya: There's one list of error codes, shared by every layer. The status table and the message table are both checked against the full list, with satisfies Record<ErrorCode, …>.

L

Leo: So a new code without a status doesn't compile.

M

Maya: Right. It's the same trick as the exhaustive switch, applied to a table.

04What it costs

L

Leo: I like it. But if (!r.ok) return r on every call looks tiring.

M

Maya: It is. Rust has a ? operator that does that in one character. TypeScript has nothing like it, so the line repeats.

L

Leo: Could we use a library that adds nicer helpers?

M

Maya: Some teams do. But then everyone must learn that library's style, a dialect on top of TypeScript. We kept our Result small.

L

Leo: And a function that returns a Result can still throw, right?

M

Maya: Yes. A Result is a promise about expected failures, not a proof that nothing throws. Brands have a cost too: you build them at every boundary.

L

Leo: So where is it worth it?

M

Maya: In the core, the domain and the commands, where the rules live. Not in thin glue code in the UI.

L

Leo: What does the web app do? It gets codes back from the API.

M

Maya: It keeps its own small Result copy. But our query library, the one that caches server data, expects a thrown error when a request fails.

L

Leo: So it throws just for the library?

M

Maya: Only there. It turns a failed Result back into a thrown error at that one spot. Fighting the library would cost more.

L

Leo: Is this a TypeScript idea, or do other languages do it?

M

Maya: Go returns errors as ordinary values. Rust has a Result type in the standard library.

L

Leo: And Java?

M

Maya: Java tried checked exceptions, which put failures in the signature. The need is the same everywhere.

05Leo explains it back

M

Maya: Suppose you reply to the reviewer. What do you write?

L

Leo: If a failure is expected and the caller can act on it, I return it as a Result. Then it's in the signature, and it's hard to forget.

L

Leo: The error has a stable code, and callers branch on the code. The message is for people and can change.

L

Leo: Bugs, like a broken invariant, still throw. No caller can fix them.

M

Maya: And the first comment?

L

Leo: A type alias is just a name. A brand makes the compiler refuse a card id where a learner id belongs, and one constructor checks and builds it.

M

Maya: Say where you'd stop, too: in thin UI code, or where a library expects throws, a plain throw is the cheaper choice. Keep Result and brands for the core.

Summary in three lines

  1. Return an expected failure as a Result with a stable code; throw only for bugs no caller can handle.
  2. Callers branch on the code, never the message, and every table keyed by code is checked against the full list.
  3. A brand makes same-shaped ids different types; use brands and Result in the core, not in thin glue.
