01見分けのつかない二つの文字列

type LearnerId = string のような型エイリアスは、わかりやすい名前を付けてくれますが、カード ID との区別は生みません。構造的型付けでは、どちらの文字列も受け入れられてしまいます。ブランド型はコンパイル時の目印を加え、通常の型検査が効くコードで、この二つの役割を取り違えないようにします。

コンストラクターは、監査の対象となるアサーションの置き場所です。生の値を検証してから、ブランド付きの型を返します。目印は実行時にも JSON にも残らないので、外から入ってきた値はもう一度検査してブランドを付け直す必要があります。ブランド型そのものがユーザーを認証するわけではありません。

type LearnerId = string & {
  readonly __brand: "LearnerId";
};

function learnerId(raw: string): LearnerId {
  if (raw === "") throw new Error("empty learner id");
  return raw as LearnerId;
}

02シグネチャに表れる失敗

TypeScript では、関数が投げる例外はシグネチャに現れません。「ラウンド終了済み」のような想定内の結果は、タグ付きの Result<T, E> として返したほうが、呼び出し側で扱いやすくなります。ok フィールドを検査すれば、値かエラーのどちらかに絞り込まれます。

type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

const result = finishRound(round, now);
if (!result.ok) return handle(result.error);
result.value; // 終了したラウンド

エラーには、ERR_ROUND_CLOSED のような機械が読むための安定したコードを持たせます。人が読むメッセージは、呼び出し側を壊さずに変更できます。メッセージの文字列で分岐していると、文面を直しただけで意図しない API の変更になってしまいます。

03想定内の失敗とバグ

想定内の拒否とは、呼び出し側が対処できるものです。終了したラウンドを表示する、入力を直す、権限を求めるといった対処がこれにあたります。不変条件が崩れるのは想定外の欠陥なので、学習者のふつうの行動として扱わず、ログに記録してサーバーエラーを返します。

同じ安定したコードを、ドメインから API、クライアントまでそのまま渡せます。各境界はそれぞれの見せ方を加えるだけで、例外メッセージから推測することはありません。

Quickturn はエラーコードの一覧を一つだけ持ち、ステータスやメッセージの対応表を satisfies Record<ErrorCode, …> で検査しています。対応を書かずにコードを追加すると、型チェックで失敗します。これで確かめられるのは表に漏れがないことまでで、意図したステータスや振る舞いはテストで確かめます。

04この方法のコスト

Result を使うと失敗を明示的に伝播させる必要があり、TypeScript では似た記述の繰り返しになりがちです。小さな自前の Result なら大きなヘルパーライブラリを覚えずに済みますが、関数が絶対に例外を投げないことまでは保証しません。ブランド型も同様に、値が入ってくる境界ごとにコンストラクターを通す必要があります。

これらの道具は、ドメインの判断やコマンドのように、ミスの影響が大きい場所で使います。クエリライブラリが例外を前提としているなら、その連携部分で、失敗した Result を例外に変換します。そうすれば、周りのライブラリの流儀と争わずに、アプリケーションの中では想定内の失敗を明示したままにできます。

3行まとめ

  1. 想定内のドメインの失敗は、安定したコード付きの Result として返します。想定外の欠陥やインフラの障害は別に扱います。
  2. 呼び出し側はメッセージではなくコードで分岐し、コードをキーにした表はすべて、一覧全体と照合して検査します。
  3. ブランド型は同じ形の ID を別の型にします。ブランド型と Result は中核のロジックで使い、薄いつなぎのコードには持ち込みません。
