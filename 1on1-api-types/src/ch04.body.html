Should a function throw, or return its failure?

A closed round is an expected refusal; a broken invariant signals a defect. Callers need to distinguish those outcomes without guessing from error messages.

01Two strings that look the same

A type alias such as type LearnerId = string creates a useful name but no distinction from a card ID. Structural typing still accepts either string. A brand adds a compile-time marker so those roles cannot be accidentally swapped in normally checked code.

The constructor is the audited assertion point: it validates the raw value before returning the branded type. The marker disappears at runtime and in JSON, so incoming values must be checked and branded again. A brand does not independently authenticate a user.

type LearnerId = string & {
  readonly __brand: "LearnerId";
};

function learnerId(raw: string): LearnerId {
  if (raw === "") throw new Error("empty learner id");
  return raw as LearnerId;
}

02A failure you can see

TypeScript does not list thrown exceptions in a function signature. Expected outcomes such as “round closed” are easier for callers to handle when returned as a tagged Result<T, E>. Checking its ok field narrows to either a value or an error.

type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

const result = finishRound(round, now);
if (!result.ok) return handle(result.error);
result.value; // the finished round

Errors carry stable machine codes such as ERR_ROUND_CLOSED. Human-readable messages can change without breaking callers. Matching a message string would turn editing its prose into an accidental API change.

03Expected failures and bugs

An expected refusal is one the caller can act on: show a finished round, fix input or request permission. A broken invariant is an unexpected defect and needs logging and a server error, rather than being treated as ordinary learner behavior.

The same stable code can pass from the domain to the API and client. Each boundary adds its presentation without guessing from an exception message.

Quickturn keeps one error-code list and checks status and message tables with satisfies Record<ErrorCode, …>. Adding a code without its mapping then fails type checking. This verifies table coverage, while tests must still verify the intended status and behavior.

04What it costs

Results require explicit propagation, which can become repetitive in TypeScript. A small local Result avoids teaching a large helper library, but does not guarantee that a function never throws. Brands likewise require constructors at incoming boundaries.

Use these tools where mistakes have meaningful consequences, such as domain decisions and commands. If a query library expects exceptions, translate a failed Result at that integration point. The application can keep explicit expected failures without fighting every surrounding library's conventions.

Summary in three lines

  1. Return expected domain failures as Results with stable codes. Handle unexpected defects and infrastructure faults separately.
  2. Callers branch on the code, never the message, and every table keyed by code is checked against the full list.
  3. A brand makes same-shaped ids different types; use brands and Result in the core, not in thin glue.
