古いアプリを壊さずに API を変えるには

現在の Web アプリがもう読んでいないレスポンスのフィールドを、サーバーから削除したとします。インストール済みのスマートフォンアプリは、まだそのフィールドに依存しているかもしれません。

読了 約4分Quickturn の事例

このページの内容

  • メッセージではなくコードで

01メッセージではなくコードで

インストール済みのアプリは、サーバーとは別のタイミングで更新されます。重複したレスポンスのフィールドを削除すると、現在の Web アプリがもう読んでいなくても、古いクライアントが壊れることがあります。API は、すでに配布されている利用側のアプリのことも考えなければなりません。

エラーはこの契約のよい例です。安定したコードはプログラムの振る舞いを決め、メッセージは人に向けて状況を説明します。クライアントは、自分のリリース後に追加されたコードに備えて、汎用のフォールバックを残しておきます。リトライするかどうかも、メッセージの文面ではなく、ドキュメントに定めたエラーの分類で決めます。

{ "error": {
    "code": "ERR_ROUND_CLOSED",
    "message": "This round is already finished." } }

switch (error.code) {
  case "ERR_UNAUTHENTICATED": return signInAgain();
  case "ERR_ROUND_CLOSED":    return showResults();
  default:                    return showGenericError();
}

02/v1 の中では追加だけ

Quickturn は、/v1 の中では追加による変更だけを行います。寛容な読み手（tolerant reader）は必要のないレスポンスのフィールドを無視するので、フィールドを追加しても互換性が保たれる場合が多くあります。既存のフィールドの名前を変えたり削除したりすると、古いクライアントが読めるものが変わってしまいます。

次の表では、一見追加に見えるだけの変更と、既存のクライアントが実際に受け入れられる変更を区別しています。

変更/v1 で安全か理由
エンドポイントの追加通常は安全古いアプリは呼ばない
省略可能なリクエストフィールドの追加通常は安全既存のリクエストは引き続き受け付けられる
レスポンスフィールドの追加寛容なら安全古いアプリが未知のフィールドを受け入れる必要がある
フィールドの削除・名前の変更安全でない古いアプリが何も読めない
フィールドの意味の変更安全でない古いアプリが誤って読む
省略可能なフィールドを必須にする安全でない古いリクエストが拒否される
閉じた選択肢への値の追加安全でない網羅的に扱うクライアントが壊れる

以前は省略可能だったリクエストのフィールドを必須にすると、それを送らない古いアプリのリクエストが拒否されることがあります。ユニオン型に選択肢を追加した場合も、既知の集合が完全だと想定している生成クライアントが壊れる可能性があります。将来の拡張を想定している箇所では、レスポンスのスキーマと、生成される利用側のコードを開いた形にしておき、実際の利用側の振る舞いで互換性をテストします。

03非推奨にしてから、バージョンを上げる

重複したフィールドは、既存の値を返し続けたまま非推奨としてマークできます。ドキュメントには代わりのフィールドを書きます。削除は破壊的なバージョンで行い、以前のバージョンは、明示した非推奨期間のあいだサポートを続けます。

Deprecation と Sunset のレスポンスヘッダーで、非推奨であることと終了予定日を伝えます。利用状況を観察すれば、どの利用者がまだ古い契約に依存しているかがわかります。期間はインストール済みのクライアントを念頭に置いて決めます。また、生成されたクライアントがすべて警告を表示すると決めつけず、ジェネレーターの対応状況を確かめます。

04互換性を守るコスト

互換性を守る規律は、整理を遅らせます。よくない名前がメジャーな変更まで残ることもありますし、複数のバージョンを並行して持てば、コード、テスト、注意力のコストがかかります。それでも、リリース前に契約をレビューするほうが、あとから約束を修復するより安く済みます。

パスにバージョンを入れる方法は目に見えてわかりやすく、ヘッダーやメディアタイプでバージョンを伝えることもできます。Problem Details は、標準化された別のエラー形式です。どの形式を選ぶにしても、レスポンスの外枠が流行りの形かどうかより、機械が読む安定したフィールドと安全なフォールバックのほうが重要です。

3行まとめ

  1. 失敗には、プログラム向けの安定したコードと、人向けの読めるメッセージを持たせます。別々に更新されるクライアントには、安全なフォールバックが必要です。
  2. 追加による変更でも、利用側に互換性が必要です。フィールドの削除、意味の変更、入力の制約の強化は、インストール済みのアプリを壊すことがあります。
  3. まずフィールドを非推奨にし、破壊的な変更は新しいバージョンとして出し、古いバージョンは期間が過ぎてから廃止します。
