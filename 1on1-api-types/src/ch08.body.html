How do you change an API without breaking old apps?

The server removes a response field that the current web app no longer reads. An installed phone app may still depend on it.

01Codes, not messages

Installed apps update independently of the server. Removing a duplicate response field can break an older client even if the current web app no longer reads it. The API must account for those deployed consumers.

Errors illustrate the contract: a stable code directs program behavior, while a message explains it to a person. Clients retain a generic fallback for codes introduced after they shipped. Retry behavior follows the documented error category rather than message text.

{ "error": {
    "code": "ERR_ROUND_CLOSED",
    "message": "This round is already finished." } }

switch (error.code) {
  case "ERR_UNAUTHENTICATED": return signInAgain();
  case "ERR_ROUND_CLOSED":    return showResults();
  default:                    return showGenericError();
}

02Additive only inside /v1

Quickturn uses additive changes within /v1. A tolerant reader ignores response fields it does not need, so adding one is often compatible. Renaming or removing an existing field changes what an old client can read.

The compatibility table distinguishes changes that only appear additive from those existing clients can actually accept.

ChangeSafe in /v1?Why
New endpointUsuallyOld apps do not call it
New optional request fieldUsuallyExisting request behavior remains accepted
New response fieldIf tolerantOld apps must accept unknown fields
Remove or rename a fieldNoOld apps read nothing
Change what a field meansNoOld apps read it wrongly
Make an optional field requiredNoOld requests are refused
New value in a closed listNoExhaustive clients break

Making a previously optional request field required can reject older apps that never sent it. Adding a union variant may also break a generated client that assumes its known set is complete. Keep response schemas and generated consumers open where future extensions are intended, and test compatibility with real consumer behavior.

03Deprecate, then version

A duplicate field can be marked deprecated while continuing to serve its existing value. The document names the replacement. Removal belongs in a breaking version, with the earlier version supported for an explicit deprecation period.

Deprecation and Sunset response headers communicate status and a planned end date. Usage observations reveal which consumers still depend on the old contract. Choose the window with installed clients in mind, and verify generator support rather than assume every generated client displays a warning.

04What the discipline costs

Compatibility discipline slows cleanup: a poor name may remain until a major change, and parallel versions cost code, tests and attention. Reviewing the contract before release is cheaper than repairing a promise afterward.

Path versions are visible and simple, while headers or media types can carry versions too. Problem Details is a standardized alternative error format. Whichever format is chosen, stable machine fields and safe fallbacks matter more than whether a response envelope looks fashionable.

Summary in three lines

  1. Failures carry stable codes for programs and readable messages for people; independently updated clients need a safe fallback.
  2. Additive changes still need compatible consumers; removing fields, changing their meaning or tightening input can break installed apps.
  3. Mark a field deprecated first, ship breaking changes as a new version, and retire the old one after a window.
