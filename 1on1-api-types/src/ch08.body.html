How do you change an API without breaking old apps?

After this page you can tell a safe API change from a breaking one. You can also explain error codes, additive changes and deprecation as promises to apps you can't update.

About 8 min readVideo call

In this page

  • What should a client branch on when a call fails?
  • Which changes are safe inside one version?
  • How do you remove something for real?
  • What does this discipline cost?

A video call. Maya is at home; Leo has a small cleanup pull request open.

01Codes, not messages

L

Leo: Quick one. The settings response has the learner's level twice: a top-level toeic field and one inside difficulty. I want to delete the duplicate. Only our web app reads it.

M

Maya: Only our web app reads it today. Who reads it next year?

L

Leo: Next year? The web app, still.

M

Maya: And the iOS app installed on a phone that hasn't updated in eight months?

L

Leo: Oh. I was thinking of the web app, which we deploy whenever we want.

M

Maya: That's the key difference. A web app updates as soon as the browser reloads it. An installed app updates when the store approves it and the learner taps "update". Some never do.

L

Leo: So the API has to keep working for apps we can't change.

M

Maya: Right. A public API is a promise. Let's start with the part clients rely on most: failures. How does the web app decide what went wrong?

L

Leo: I've seen code that checks the error message.

M

Maya: That's the habit to break. Every failure we send has the same shape.

{ "error": {
    "code": "ERR_ROUND_CLOSED",
    "message": "This round is already finished." } }

switch (error.code) {
  case "ERR_UNAUTHENTICATED": return signInAgain();
  case "ERR_ROUND_CLOSED":    return showResults();
  default:                    return showGenericError();
}
L

Leo: The code is for the program, the message is for a person.

M

Maya: Yes. The code is a stable string. The message is one fixed sentence, and it never quotes the request back.

L

Leo: Why is there a default branch? I thought exhaustive switches were the good kind.

M

Maya: Inside our own code, they are. But new codes may appear inside a version. So the document types code as a plain string, not a closed list, and every client keeps a default.

L

Leo: And the HTTP statuses?

M

Maya: They're grouped by what a client can do: sign in again, fix the request, reload, or retry. Our web client treats every refusal as final, except the one code the contract names as worth sending again.

02Additive only inside /v1

L

Leo: So what can I change inside /v1?

M

Maya: Guess first. Is adding a new field to a response safe?

L

Leo: I think so. An old app doesn't know about it, so it ignores it.

M

Maya: Right. That idea has a name, the tolerant reader, from Martin Fowler. A client reads what it needs and ignores the rest.

L

Leo: And renaming a field?

M

Maya: What does the old app do when toeic becomes toeicScore?

L

Leo: It reads toeic, finds nothing, and shows an empty level. Or crashes.

M

Maya: Let me draw the two cases.

M

Maya: Here are the common cases in one list.

ChangeSafe in /v1?Why
New endpointYesOld apps never call it
New optional request fieldYesOld apps just don't send it
New response fieldYesOld apps ignore it
Remove or rename a fieldNoOld apps read nothing
Change what a field meansNoOld apps read it wrongly
Make an optional field requiredNoOld requests are refused
New value in a closed listNoExhaustive clients break
L

Leo: The "required" row surprises me. Our web app always sends the time zone, so making it required felt harmless.

M

Maya: What does last spring's Android app send?

L

Leo: I don't know. Maybe nothing, if the field didn't exist yet.

M

Maya: Then every answer batch from that app is refused as a bad request. The learner sees an error on every round.

L

Leo: So I'd check what old clients send, not what our newest one sends.

L

Leo: The last row is sneaky. Adding a value sounds additive.

M

Maya: It is, for clients with a default branch. For a client that switches over every value it knows, it's a break. That's why codes are open strings.

L

Leo: How do generated clients handle new fields? Some generators reject unknown properties.

M

Maya: We leave response objects open in the document. So a generated client accepts a field that's added later, instead of refusing the whole response.

03Deprecate, then version

L

Leo: So I can never remove the duplicate toeic field?

M

Maya: Not inside /v1. When something really must break, it ships as /v2. And /v1 keeps working for a deprecation window.

L

Leo: How long is the window?

M

Maya: Long enough for installed apps. Store review takes time, and some people never update. We decide it per change.

L

Leo: And before /v2 exists?

M

Maya: We mark the field deprecated in the document now. Generated clients show a warning, and the note names the replacement: the value inside difficulty.

L

Leo: So the field is still served, unchanged. It just carries a warning.

M

Maya: Right. That's where your cleanup belongs today. Here's the whole path to removal.

L

Leo: How does an app even know a version is going away?

M

Maya: HTTP has standard response headers for it. A Deprecation header says "this is deprecated", and a Sunset header gives the date it stops.

L

Leo: And we watch the traffic so we know when it's safe.

M

Maya: Yes. Usage tells you who still depends on it. Dates alone don't.

04What the discipline costs

L

Leo: This all sounds slow.

M

Maya: It is slower. Additive-only means a naming mistake stays until the next major version. The duplicate field is exactly that kind of mistake.

L

Leo: So the review has to happen before release, not after.

M

Maya: Right. We review contract changes before they ship, because after that they're promises. And running two versions costs code, tests and attention.

L

Leo: Are there other ways to version? I've seen a version in a header.

M

Maya: Some teams put it in a header or a media type. Stripe uses dated versions, where each account is pinned to a date. A version in the path is simply the easiest to see.

L

Leo: And the error format? Is ours standard?

M

Maya: There's a standard alternative called Problem Details. We kept a smaller envelope, but the idea is the same: a stable machine field, and prose for people.

L

Leo: So why do so many web teams skip all this?

M

Maya: A web-only product can move faster. Every user gets the new code on reload. So the discipline feels useless.

L

Leo: Until the day a native app ships.

M

Maya: That's the day they pay for it. Every response shape from before becomes a promise they didn't know they made.

05Leo explains it back

M

Maya: So what do you write on your pull request, instead of the delete?

L

Leo: Once apps are installed, we can't make them update. So the API has to stay compatible.

L

Leo: Clients branch on the error code, never the message, and they always keep a default branch.

L

Leo: Inside /v1 we only add things: new endpoints, new optional fields, new response fields. Clients ignore what they don't know.

M

Maya: And the duplicate field?

L

Leo: It stays, marked deprecated with its replacement named. If something must break, it goes to /v2, and /v1 stays up for a deprecation window.

M

Maya: One thing to add: watch the traffic. We remove /v1 when usage says nobody needs it, not just when a date passes.

Summary in three lines

  1. Failures carry a stable code for programs and a fixed message for people; clients always keep a default branch.
  2. Inside one version, only add things; renaming, removing or tightening anything breaks installed apps.
  3. Mark a field deprecated first, ship breaking changes as a new version, and retire the old one after a window.
