ルールをサーバーが持つアプリは、オフラインで動けるか

取得済みのデッキに答えている途中で、学習者の通信が切れます。出題スケジュールや連続記録のルールがサーバーにあっても、端末はその回答を手元に残しておけます。

01オフライン対応の二つの方法

オフラインで動かすために、ビジネスルールを端末に複製しなければならないとは限りません。一つは、端末でルールを実行し、あとで状態をマージする設計です。データの性質が合えば CRDT を使うこともあります。もう一つは、端末では事実だけを記録し、接続が戻ったときにその意味をサーバーが決める設計です。

Quickturn は二つ目の方法をとっています。ラウンドのデッキはオンラインで取得し、そのカードへの回答を、オフラインのあいだ端末に記録します。カードの配布、スケジュール、連続記録のルールは、Web、ネイティブ、エージェントのどの呼び出し元に対してもサーバーに置いたままです。

02キューと再送

各回答には端末で作った ID が付き、順序付きのキューに入ります。Web のキューはセッションストレージを使うので、タブを再読み込みしても残ります。タブを閉じたりストレージを消去したりすると、キューは失われることがあります。ネイティブのクライアントには、端末上の適切な永続ストアが必要です。

送信に失敗した回答は、キューの先頭に残ります。リトライでは同じ ID を使うので、元のレスポンスが失われた回答を、サーバーはスキップできます。

オンラインの回答も再送された回答も、同じバッチ用エンドポイントを使います。サーバーはバッチを時刻順、次に ID 順に並べ、再開用のエンドポイントはすでに受け付けた回答を返します。そのため、再開はローカルのキューだけでなく、サーバーが受付を確認した状態にも依存します。

03信用できない時刻

端末の時計はずれることも、変更されることもあります。Quickturn は、報告された回答時刻を、ラウンドの開始時刻とサーバーの現在時刻のあいだに収めます。時刻が送られてこなければ現在時刻を使います。これはありえない値を抑えるための処理で、実際に練習した正確な時刻を証明するものではありません。

const answeredAt = Math.min(
  Math.max(reported ?? now, round.startedAt), // ラウンド開始より前にはしない
  now,                                        // サーバーの「現在」より後にはしない
);

遅れて届いた回答は、元のラウンドの練習日に属します。新しい回答によってすでに更新されたカードのスケジュールを巻き戻さずに、記録だけを残せます。たとえば、月曜日にオフラインでした回答が水曜日のオンラインの回答よりあとに届いたら、月曜日の回答は履歴に残し、スケジュールは水曜日の状態を有効のままにします。

このルールでは、途中で放棄されたラウンドにも、練習した回答を受け付けます。プロダクトとしての意味、タイムスタンプの扱い、スケジュールの順序は、明示的なテストで確かめる必要があります。

04この設計で諦めること

この設計で対応できるのは取得済みのデッキを続けることで、新しいデッキをオフラインで手に入れることではありません。連続記録は回答が届くまで暫定のままで、セッションストレージの永続性にも限りがあります。時刻の補正は、時計の異常を理由に回答を拒否するより、練習の記録を残すことを優先しています。そのため、報告された時刻は不正対策の強い根拠にはなりません。

遅れて届いた回答に期限を設けない Quickturn の方針は、復旧を重視した意図的な選択です。ユーザーが所有するドキュメントや、オフラインでの独立した作成が中心的な要件なら、ローカルファーストの設計のほうが適している場合があります。どのモデルが正しいかは、ユーザーがサーバーなしで何をできなければならないかで決まります。

3行まとめ

  1. ルールをサーバーが持つ場合、オフライン対応とは、クライアントが事実をキューに入れ、届いた時点でサーバーが判断することを指します。
  2. クライアントが作る ID によって再送は無害になり、送信に失敗した回答はキューの先頭に残ります。
  3. 報告された時刻はラウンドの範囲に収め、遅れた回答はラウンドの日に数え、スケジュールは巻き戻しません。
