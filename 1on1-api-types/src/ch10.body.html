Can an app work offline if the server owns the rules?

After this page you can explain offline support where the client records facts and the server applies the rules. You can also say how to replay those facts safely and which times to trust.

About 4 min readQuickturn case study

In this page

  • Does offline mean running the rules on the phone?
  • How are queued answers replayed safely?
  • Which time do we believe?

01Two ways to be offline

Offline operation does not always require copying the business rules onto a device. One design runs local rules and later merges state, perhaps using CRDTs for suitable data. Another records facts locally and lets the server decide their meaning when connectivity returns.

Quickturn takes the second approach. A round's deck is fetched online, then the device records answers to those cards offline. Dealing, scheduling and streak rules remain on the server for web, native and agent callers.

02The queue and the replay

Each answer receives a device-generated ID and enters an ordered queue. The web queue uses session storage, which survives a tab reload but is not guaranteed to survive closing the tab or clearing storage. Native clients need an appropriate durable device store.

A failed send stays at the queue head. Retries reuse its ID, allowing the server to skip an answer whose original response was lost.

Online and replayed answers use the same batch endpoint. The server orders a batch by time and then ID, and a resume endpoint returns the answers already held. Resuming therefore depends on acknowledged server state as well as the local queue.

03Time you can't trust

Device clocks can drift or be changed. Quickturn clamps a reported answer time between the round's start and the server's current time, using current time if none was supplied. This limits implausible values without claiming to prove the exact moment of practice.

const answeredAt = Math.min(
  Math.max(reported ?? now, round.startedAt), // not before the round began
  now,                                        // not after the server's "now"
);

A late answer belongs to its original round's practice day. It can be logged without rewinding a card schedule already updated by a newer answer. For example, Monday's offline answer arriving after Wednesday's online answer should remain in history while Wednesday's scheduling state remains effective.

The rules also allow an abandoned round to receive practiced answers. Product meaning, timestamp handling and scheduling order need explicit tests.

04What this design gives up

This design supports continuing a fetched deck, not obtaining a new one offline. Streaks remain provisional until answers arrive, and session storage has limited durability. Clamping favors retaining practice over rejecting clock anomalies; it also means the reported time is not strong anti-cheat evidence.

Quickturn's no-expiry policy for late answers is a deliberate recovery choice. A local-first design can be better when user-owned documents and independent offline creation are central requirements. The right model follows what users must be able to do without the server.

Summary in three lines

  1. With server-owned rules, offline means the client queues facts and the server decides when they arrive.
  2. Client-made ids make replay harmless, and a failed send stays at the head of the queue.
  3. Clamp reported times to the round's window, count late answers on the round's day, and never rewind a schedule.
