If types vanish at runtime, what are they for?

After this page you can explain what TypeScript checks and what it never checks. You can also say where a runtime check must go, and why a cast is not one.

About 8 min readPairing at Leo's desk

In this page

  • Why does a type match by shape, not by name?
  • How does the compiler follow my checks?
  • What can types never do for me?
  • Is a model's reply any different from a request body?

Leo's desk. A request handler is open in the editor, with a review comment next to one line.

01Shapes, not names

L

Leo: Maya, can you look at this? I wrote const body = (await request.json()) as StartRoundRequest. A reviewer wrote "this cast proves nothing".

M

Maya: What do you think they meant?

L

Leo: I'm not sure. It compiled. If it proves nothing, why did the compiler accept it?

M

Maya: That's the right thing to be confused about. Before we answer it, tell me what you think a type is while the program runs.

L

Leo: Like in Java or Swift, I guess. The object carries its class. If it says StartRoundRequest, it is one.

M

Maya: Half of that is right for Java. In Java a class name is part of the object, and the runtime can check it. TypeScript works another way, in two places.

L

Leo: Two places?

M

Maya: First, it compares shapes, not names. That's called structural typing. Two types fit together when their fields match, whatever they are called.

L

Leo: So the name StartRoundRequest doesn't matter?

M

Maya: Not to the compiler. Look at this.

interface HasLearner { learnerId: string }

function greet(x: HasLearner) { return x.learnerId }

// this object never mentions HasLearner
const req = { learnerId: "L1", deckSize: 10 };
greet(req); // compiles: the shape fits
L

Leo: The object never says it's a HasLearner, but it has a learnerId, so it passes.

M

Maya: Right. Java would call that nominal typing: you must say implements HasLearner. TypeScript only asks, "does it have the fields I need?"

L

Leo: And I didn't write a type on req. The compiler worked it out?

M

Maya: That's inference. Inside a function body, the compiler fills in most types for you. So we write types where code meets other code: parameters and exported return types.

L

Leo: At the edges of a function, not on every line.

M

Maya: Yes. Those are the promises other code depends on. The inside can take care of itself.

02Unions and narrowing

L

Leo: Okay, shapes. What's the second place it's different?

M

Maya: Hold that for a minute. First, the part TypeScript is really good at.

L

Leo: Which is?

M

Maya: Unions. A value can be one of several types, and we write that with a bar: string | null.

L

Leo: A union. We have those for the round kind, right? 'first' | 'retry'.

M

Maya: Right. Those are literal types. The type is not "any string", it's exactly one of these two strings. Now watch what the compiler does with a union when you check it.

function label(name: string | undefined) {
  // name: string | undefined
  if (name === undefined) {
    return "Guest"; // name: undefined
  }
  // name: string
  return name.toUpperCase();
}
L

Leo: After the early return, it knows name is a string. I never told it.

M

Maya: It followed your check. That's called narrowing. The compiler reads typeof, === and in checks, and gives each branch a narrower type.

L

Leo: So the check I write for my own logic also teaches the compiler.

M

Maya: Exactly. Let me draw what narrowing looks like with our round kinds.

M

Maya: Each box is a set of possible values. Every check moves you one box in.

L

Leo: And inside the 'first' branch, I can't accidentally handle a retry.

M

Maya: Right. Add a third kind later, and the compiler shows you every switch that forgot it. That's the real payoff of unions.

03What types cannot do

L

Leo: Okay, now the second place. Why does my cast prove nothing?

M

Maya: Because of what happens when you build. TypeScript compiles to JavaScript, and every type is removed. The term for that is "erased".

L

Leo: Removed completely? Not kept somewhere for checking?

M

Maya: Completely. Let me draw the path from your file to a real request.

L

Leo: So when a request arrives, the JSON is just bytes. Nobody compares it with StartRoundRequest.

M

Maya: Nobody. as is a promise you make to the compiler: "trust me, it's this shape". The compiler believes you and checks nothing.

L

Leo: Then why did it let me make the promise at all?

M

Maya: Because request.json() returns any. JSON.parse does too. any means "switch checking off". The compiler will accept any promise about it.

L

Leo: And from that line on, everything I do with body is trusted?

M

Maya: Everything downstream. If a client sends deckSize: "ten", your code gets a string where it expects a number. The crash happens far from the cause.

L

Leo: So what should the type be instead?

M

Maya: unknown. It's the honest type for outside data. It allows nothing until you check it. You can't even read a field.

L

Leo: That sounds annoying.

M

Maya: It's meant to be. It forces one check, once, at the edge. Here's the difference side by side.

L

Leo: So at Quickturn, the API never casts a body?

M

Maya: Never. It reads every body as unknown, with a size limit, and parses the JSON. Then a schema checks it before any command sees it.

L

Leo: And if it fails?

M

Maya: The client gets a bad-request error with a fixed code. The command never runs.

L

Leo: Okay. Is there anything else the compiler can't see, even inside our code?

M

Maya: One blind spot comes from structural typing. A learner id and a card id are both string. Same shape, so the compiler lets you swap them.

L

Leo: Oh. recordAnswer(cardId, learnerId) with the arguments reversed would compile.

M

Maya: It would. There's a fix called a brand, a tag that makes two strings different types. That's a topic of its own.

L

Leo: So what does all this checking cost?

M

Maya: Inside the program, compile-time checks are free. They cost nothing when the code runs. Runtime checks cost code and a little time, so you place them on purpose: at the edges, once.

04Beyond Quickturn

M

Maya: This matters more now that teams call language models. What's a model's reply, from the program's point of view?

L

Leo: Text that comes back from an API. So it's outside data too.

M

Maya: Right. Say you ask a model for JSON with a score and a reason. Does the reply have that shape?

L

Leo: Usually. But nothing forces it.

M

Maya: Exactly. Teams write as GradeResult on the parsed reply. It works for weeks. Then the model returns score: "high", and something far away crashes.

L

Leo: And the stack trace points at the place that used the score, not the place that trusted it.

M

Maya: That's the painful part. At Quickturn, the grader for typed answers asks for structured output. The reply is still unknown until a schema has checked it.

L

Leo: Same rule as a request body. A request, a model reply, a file someone uploads: all unknown at first.

M

Maya: Same rule. The source doesn't matter. What matters is whether our own code produced the value.

05Leo explains it back

M

Maya: Say the reviewer asks you why you changed the line. What do you tell them?

L

Leo: Types are a proof about our own code, checked before it runs. They compare shapes, not names, and the compiler infers most of them.

L

Leo: Unions say a value can be one of several things. The compiler follows our checks and narrows each branch.

L

Leo: But types are erased. At runtime nothing checks them, so as is only a promise, and request.json() gives any, which turns checking off.

M

Maya: So what's the type of the body?

L

Leo: unknown. Then a schema checks it once, at the edge, and a bad body is refused before any command runs.

M

Maya: Add where else it applies: a model's reply is outside data too. Asking for a shape does not give you that shape, so it gets the same schema check as a request body.

Summary in three lines

  1. TypeScript checks shapes, infers most types and narrows unions as your code checks them.
  2. Every type is erased at build time, so as and any check nothing while the program runs.
  3. Treat anything from outside, including a model's reply, as unknown and check it once at the edge.
