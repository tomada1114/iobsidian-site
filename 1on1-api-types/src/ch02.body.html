Which compiler flags change how I write code?

An array lookup may have no value, even when its element type looks precise. Compiler options determine which missing cases the code must handle.

01What strict leaves out

The strict compiler option enables a family of checks, including strict null checks and restrictions on implicit any. It does not enable every additional safety option. Quickturn adds four options for indexing, optional fields, index signatures and import syntax.

These options address different failure modes. They make potentially missing values and erased type imports more explicit, rather than merely prescribe formatting.

noUncheckedIndexedAccess
arr[i] may be undefined. Catches reading past the end.
exactOptionalPropertyTypes
"Missing" and "undefined" differ. Catches clearing a field by accident.
noPropertyAccessFromIndexSignature
Map lookups need brackets. Catches a lookup that looks like a field.
verbatimModuleSyntax
Imports are emitted as written. Catches a module that runs by surprise.

A shared compiler configuration gives every package the same expectations. The following examples explain what those expectations change in everyday code.

02One flag, one bug

With noUncheckedIndexedAccess, an array or dictionary lookup may return undefined. A length test does not generally establish that a separately indexed expression is present. Read the element into a variable and narrow that value before using it.

exactOptionalPropertyTypes distinguishes an absent optional field from explicitly assigning undefined unless the type includes it. This is useful for update objects, although JSON omits undefined values and an API must separately define how clearing a field works.

The noPropertyAccessFromIndexSignature flag requires bracket notation for fields supplied only by an index signature. The verbatimModuleSyntax flag makes type-only imports explicit, avoiding guessed import removal and unexpected module side effects.

const first = cards[0];
if (first === undefined) return noCards();
first.id; // first: Card

type Settings = { sound?: boolean };
const a: Settings = {};                 // ok: field absent
const b: Settings = { sound: undefined }; // error

03What the flags cost, and the gate

Enabling these options in an existing codebase creates migration work: missing-value checks, fallbacks and library incompatibilities must be handled. Quickturn accepts that cost for long-lived code and requires type checking in CI.

A generated client once failed under exact optional-property checks. The choices were to relax the configuration for that output or change what was generated.

Quickturn generated types only and kept a small fetch module checked with satisfies. That operator tests compatibility without replacing the value's inferred type. The module needs maintenance, and a compatible generator release could make the choice worth revisiting.

A failing index read should normally be fixed by handling absence, rather than removing the check for an entire package. Exceptions require understanding which protection is being lost.

Summary in three lines

  1. strict is a floor; flags like noUncheckedIndexedAccess and exactOptionalPropertyTypes are separate opt-ins.
  2. Each extra flag catches a class of mistakes before runtime, at the cost of more checks in everyday code.
  3. Quickturn retains its checks by generating types and maintaining a small fetch module; a compatible generator could change that trade.
