Trust nothing at the boundary: parse it once

After this page you can list where outside data enters a program. You can also explain why we parse it once into a precise type instead of validating it again and again.

01Where outside data comes in

Data written to browser storage does not remain under the running program's sole control. An older app version, developer tools or another same-origin script can change its shape. Reading it back is a new boundary crossing.

The same applies to request bodies, environment variables, files, service responses and model replies. Start with unknown, then produce a trusted representation. Quickturn's answer queue checks stored entries and drops malformed ones according to its recovery policy.

02Parse, don't validate

A parser returns a useful typed value or a failure. A bare yes/no check can leave later code without a representation of what was established. “Parse, don't validate” encourages carrying the result forward so callers do not repeatedly reconstruct the same guarantee.

A Zod schema supplies a runtime parser and an inferred static type. Successful safeParse yields checked data; failure remains explicit. A hand-written type guard can narrow a small shape without a schema-library dependency, but its correctness is the programmer's responsibility.

satisfies checks values authored in code. It does not parse runtime JSON. An assertion with as makes a claim rather than performing a check.

const StartRound = z.object({
  kind: z.enum(["first", "retry"]),
  roundId: z.string().uuid(),
});
type StartRound = z.infer<typeof StartRound>;

const parsed = StartRound.safeParse(body); // body: unknown
if (!parsed.success) return badRequest();
parsed.data.kind; // "first" | "retry"

03Once, at the edge

Quickturn parses requests before calling commands and returns fixed error messages that do not echo raw input. This reduces the chance that secrets or hostile content are carried into responses and log viewers.

Environment settings are read in one startup module. It reports invalid variable names together, without revealing values, and refuses to start with unusable configuration. Hosted secrets come from the chosen secret or parameter service, with access controls, rather than being treated as ordinary public settings.

Parsing at each entry point lets the core use checked values. A new boundary still needs its own check; “once” applies within a trusted path, not forever after data was first written.

04What parsing costs

Repeated parsing adds code and CPU cost without necessarily adding new evidence. Unknown fields also need an explicit compatibility policy: reject, strip or preserve them. Rejecting a field from a newer client can break an otherwise compatible request.

Schema libraries add browser weight, so small stored shapes may use a careful type guard. Model output is parsed at its incoming boundary too. A failed parse requires a bounded retry, a safe fallback or a visible failure, rather than a cast that hides invalid data.

Summary in three lines

  1. Every value from outside the process, even browser storage, is unknown on the way in.
  2. Parse it once at the edge into a precise type or a refusal, so the inside never checks again.
  3. Read configuration in one module at startup, and refuse to start with every bad name listed.
