01外部データはどこから入るか

ブラウザのストレージに書いたデータは、実行中のプログラムだけが管理しているわけではありません。古いバージョンのアプリや開発者ツール、同じオリジンの別のスクリプトが、その形を変えることがあります。読み戻す操作は、境界をもう一度越えることになります。

リクエストボディ、環境変数、ファイル、他サービスの応答、モデルの応答も同じです。まず unknown として受け取り、そこから信頼できる表現を作ります。Quickturn の回答キューは保存されたエントリーを検査し、形の崩れたものは復旧方針に従って捨てます。

02検証ではなくパースする

パーサーは、型の付いた使える値か、失敗のどちらかを返します。はい・いいえだけを返すチェックでは、何が確かめられたのかを表すものが後続のコードに残りません。「Parse, don't validate（検証せずにパースせよ）」は、パースの結果を後続の処理へ渡し、呼び出し側が同じ保証を何度も組み立て直さずに済むようにする考え方です。

Zod のスキーマは、実行時のパーサーと推論された静的な型の両方を提供します。safeParse が成功すれば検査済みのデータが得られ、失敗した場合もそれが明示されます。小さな形なら、手書きの型ガードでスキーマライブラリに依存せずに絞り込めますが、その正しさはプログラマーの責任になります。

satisfies が検査するのは、コードの中で書いた値です。実行時の JSON はパースしません。as によるアサーションは、検査をせずに主張をするだけです。

const StartRound = z.object({
  kind: z.enum(["first", "retry"]),
  roundId: z.string().uuid(),
});
type StartRound = z.infer<typeof StartRound>;

const parsed = StartRound.safeParse(body); // body: unknown
if (!parsed.success) return badRequest();
parsed.data.kind; // "first" | "retry"

03入口で一度だけ

Quickturn は、コマンドを呼ぶ前にリクエストをパースし、生の入力を含まない固定のエラーメッセージを返します。こうすると、秘密情報や悪意のある内容がレスポンスやログビューアーに運ばれる可能性を減らせます。

環境設定は、起動時に一つのモジュールで読み込みます。不正な変数名は値を表に出さずにまとめて報告し、使えない設定のままでは起動を拒否します。ホスティング環境の秘密情報は通常の公開設定として扱わず、アクセス制御のある秘密情報管理サービスやパラメーターサービスから取得します。

入口ごとにパースしておけば、中核のコードは検査済みの値を使えます。それでも、新しい境界にはその境界のためのチェックが必要です。「一度だけ」は信頼できる経路の中での話で、データを最初に書いたときに一度検査すれば以後ずっと安全、という意味ではありません。

04パースのコスト

パースを何度も繰り返すと、新しい根拠は増えないのに、コードと CPU のコストだけが増えることがあります。未知のフィールドについても、拒否する・取り除く・残すのどれにするか、互換性の方針を明示しておく必要があります。新しいクライアントから来たフィールドを拒否すると、それ以外の点では互換性のあるリクエストまで失敗させてしまいます。

スキーマライブラリはブラウザに読み込むコードを増やすので、保存データの小さな形には、慎重に書いた型ガードを使うこともあります。モデルの出力も、入ってくる境界でパースします。パースに失敗したら、回数を限ったリトライ、安全なフォールバック、目に見える失敗のいずれかで対処し、不正なデータを隠すキャストでごまかしません。

3行まとめ

  1. プロセスの外から来る値は、ブラウザのストレージに保存したものであっても、入ってくる時点では unknown です。
  2. 入ってくるデータは正確な型か拒否のどちらかにパースし、新しい信頼の境界を越えるときにはもう一度検査します。
  3. 設定は起動時に一つのモジュールで読み込み、不正な名前をすべて挙げたうえで起動を拒否します。
