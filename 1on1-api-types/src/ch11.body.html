なぜサーバーレンダリングでなく静的な SPA なのか

ログイン後の練習画面は、ネイティブアプリと API を共有しています。サーバーレンダリングにすれば動かし続ける層が一つ増え、静的ファイルにすれば最初の読み込みで待ち時間が残ります。

01四つのレンダリング方式

サーバーサイドレンダリング（SSR）は、リクエストごとに HTML を作ります。静的サイト生成（SSG）は、ビルド時にページを作ります。シングルページアプリケーション（SPA）は静的な外枠を送り、JavaScript と API のデータが届いてから描画します。ハイブリッドなフレームワークは、これらの仕組みを組み合わせます。

どの方式にも、運用面での影響があります。サーバーレンダリングには、実行環境、キャッシュの計画、安全なデータアクセスが必要です。静的なアプリでは、インタラクティブな描画とデータ取得がブラウザ側に移り、API は別の責務として残ります。

02Quickturn が静的ファイルを配信する理由

Quickturn のログイン後のアプリはネイティブのクライアントと API を共有しており、検索で見つけてもらうための公開コンテンツはほとんどありません。Web 用のレンダリングサーバーを置くと、セッションを扱う層がもう一つ増えます。公開用のランディングページは、練習用のアプリとは別に静的にできます。

ブラウザ用のアプリと API は同じオリジンを使い、API は /api の下に置いています。HttpOnly のセッション Cookie は、ページのスクリプトに値を見せずに、リクエストと一緒に送られます。同一オリジンにまとめると CORS や Cookie の設定は単純になりますが、状態を変えるリクエストには引き続き CSRF 対策が必要です。

その代わり、最初は JavaScript とデータを待つ時間があり、そのあいだアプリは読み込み中の状態を表示します。

ホーム画面だけをサーバーで描画するとしても、その層を動かし、守る必要はなくなりません。Quickturn はまず、バンドルとホーム用エンドポイントを最適化しています。最初の読み込みの問題が計測で確認され、それが続くようなら、レンダリング方式を見直す理由になります。

03手元のデータはサーバー状態のコピー

ブラウザにある連続記録やホーム画面のデータは、サーバーの状態をキャッシュしたコピーです。TanStack Query は、こうした読み取りの読み込み状態、エラー、無効化を管理します。Quickturn は、裏で動く処理が学習者を驚かせないよう、プロダクトの判断として、自動リトライとフォーカス時の再取得を明示的に無効にしています。

書き込みは、回答キューのリトライ方針に従います。読み取りのキャッシュと書き込みの再送の責務を分けておくと、繰り返しと復旧をどの層が担うのかがはっきりします。

const homeQuery = queryOptions({
  queryKey: ["home"],
  queryFn: () => api.getHome(),
});

const queryClient = new QueryClient({
  defaultOptions: {
    queries: { retry: false, refetchOnWindowFocus: false },
  },
});

04サーバーレンダリングが勝る場面

SSR や静的生成は、公開コンテンツ、検索での見つけやすさ、最初の表示の速さが求められる場面で役立ちます。機能の多いログイン後のアプリなら、静的な SPA を使うのも妥当です。これらは評価すべき条件であり、新しいフレームワークと古いフレームワークの順位付けではありません。

AI チャットでは、ストリーミングというやり取りが加わります。Server-Sent Events やストリーミングの fetch を使えば、テキストを少しずつ届けられます。UI には、キャンセル、途中までの応答の扱い、中断された回答を知らせる方法が必要です。完了した応答をキャッシュするクエリの仕組みだけでは、このやり取りには対応できません。データの流れは画面ごとに選びます。

3行まとめ

  1. サーバーレンダリングと静的生成は、公開ページ、検索、内容を先に見せたい画面で、そのコストに見合います。
  2. 同一オリジンの静的 SPA は、Quickturn の共有 API とログイン後の画面に合っています。ただし、最初の読み込みのコストは残ります。
  3. API のデータはサーバーの状態をキャッシュしたコピーとして扱い、チャットのようなストリームには、それに合ったデータの流れを選びます。
