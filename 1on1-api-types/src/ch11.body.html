Why a static SPA instead of server rendering?

After this page you can choose between server rendering, static generation and a single-page app. You can also explain why API data in the browser is a cached copy, not app state.

About 4 min readQuickturn case study

In this page

  • What are the ways to render a web app?

  • When does server rendering win?

01Four ways to render

Server-side rendering creates HTML per request. Static generation creates pages at build time. A single-page application sends a static shell, then renders after JavaScript and API data arrive. Hybrid frameworks combine these mechanisms.

Each option has operational consequences. Server rendering needs a runtime, a caching plan and secure data access. A static app moves interactive rendering and fetching into the browser while its API remains a separate responsibility.

02Why Quickturn serves static files

Quickturn's signed-in app shares an API with native clients and has little searchable public content. A web rendering server would add another session-aware tier. The public landing page can be static independently of the practice app.

The browser app and API use one origin, with the API under /api. An HttpOnly session cookie travels with requests without exposing its value to page scripts. Same-origin routing simplifies CORS and cookie policy, while state-changing requests still need CSRF protection.

The cost is an initial wait for JavaScript and data, during which the app shows a loading state.

Rendering only the home screen on a server would still require running and securing that tier. Quickturn first optimizes its bundle and home endpoint. A measured, persistent first-load problem could justify reconsidering rendering.

03Server state is a copy

The browser's streak and home data are cached copies of server state. TanStack Query tracks loading, errors and invalidation for those reads. Quickturn explicitly disables automatic retries and focus refetches as a product choice, rather than letting background activity surprise the learner.

Writes use the answer queue's retry policy. Keeping read caching and write replay responsibilities separate makes it clear which layer owns repetition and recovery.

const homeQuery = queryOptions({
  queryKey: ["home"],
  queryFn: () => api.getHome(),
});

const queryClient = new QueryClient({
  defaultOptions: {
    queries: { retry: false, refetchOnWindowFocus: false },
  },
});

04When server rendering wins

SSR or static generation can be useful for public content, search visibility and quick initial display. A rich signed-in app may reasonably use a static SPA. These are conditions to evaluate, not a ranking of modern and obsolete frameworks.

AI chat introduces a streaming interaction. Server-Sent Events or a streamed fetch can deliver text incrementally. The UI needs cancellation, partial-response handling and a way to report an interrupted answer. A completed-response query cache does not by itself provide that interaction model; choose the data flow for each screen.

Summary in three lines

  1. Server rendering and static generation earn their cost for public pages, search and content-first screens.
  2. Behind a sign-in, with rules in a shared API, a static SPA on the same origin is the simplest client.
  3. Treat API data as a cached copy of server state, and give streams like chat their own shape.
