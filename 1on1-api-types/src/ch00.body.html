エンジニアリング読本：API と TypeScript

型チェックを通ったコードにも、不正なデータを含むリクエストは届きます。設計に問題のない API でも、古いアプリや再送が加わると前提が崩れることがあります。この本では、そうした条件のもとで型・境界・契約がそれぞれ何を守れるのかを見ていきます。

題材にするアプリ

Quickturn は架空の語学学習アプリです。学習者はタイマーが切れる前にカードに答え、あとで進み具合や間違えた問題を振り返ります。Web・iOS・Android のクライアントが一つの API を共有しています。

各章ではこのアプリを例に、具体的な設計の選択とそのコスト、そして別の設計を選ぶべき条件を説明します。どの章も単独で読めるので、前の章から順に読む必要はありません。

各章のつながり

目次

  1. 実行時に消える型は、何のためにあるのか — 型が検査するのは自分たちのコードです。外部データは検査するまで unknown として扱います。
  2. コードの書き方を変えるコンパイラオプションはどれか — strict は最低ラインです。緩めたゲートは、もうゲートとして働きません。
  3. 真偽値フラグを足すだけでは、なぜ足りないのか — 判別可能なユニオン型は、検査済みコードの中で正しい選択肢だけを表します。
  4. 関数は例外を投げるべきか、失敗を返すべきか — 想定内の失敗はコード付きで返し、想定外の失敗は別に扱います。
  5. 境界では何も信用せず、一度だけパースする — 外部データは入口で一度だけパースし、正確な型にします。
  6. REST・GraphQL・RPC をどう選ぶか — API の方式は、クライアントとそのデータの読み方で決まります。
  7. API の契約は、実際にはどこにあるのか — 共有スキーマからドキュメントとクライアントの型を作り、生成結果と振る舞いをテストで確かめます。
  8. 古いアプリを壊さずに API を変えるには — 安定したコードを使い、変更は追加に限り、削除の前に非推奨の期間を設けます。
  9. 同じリクエストが二度届いたらどうなるか — クライアントが作る ID と条件付き書き込みで、繰り返しを無害にします。
  10. ルールをサーバーが持つアプリは、オフラインで動けるか — クライアントは事実を記録し、サーバーは届いた時点でルールを適用します。
  11. なぜサーバーレンダリングでなく静的な SPA なのか — 静的なクライアントは Quickturn のログイン後の画面と共有 API に合います。その代わり、最初の読み込みのコストがかかります。
