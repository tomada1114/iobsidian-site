REST, GraphQL or RPC: how do you choose?

After this page you can explain what REST really describes and how it differs from GraphQL and RPC. You can also pick a style from your clients instead of from taste.

About 4 min readQuickturn case study

In this page

  • What does REST actually mean?

  • Why did Quickturn pick REST with OpenAPI?
  • How does an AI agent call the same API?

01What REST really is

REST is an architectural style, not merely JSON with GET and POST. Its constraints include a uniform interface, stateless interactions and cache semantics. Quickturn uses resource URLs, standard HTTP methods and statuses, with a published OpenAPI contract.

It does not implement hypermedia-driven navigation, so its API follows a common resource-oriented subset rather than every constraint of Fielding's REST model. The useful design question is which interaction and compatibility needs that subset serves.

02Three families side by side

REST, GraphQL and RPC offer different ways to expose capabilities. GraphQL lets consumers choose fields; RPC names operations directly. TypeScript-oriented RPC tools can closely connect server and browser types.

REST with OpenAPI
Any client language. The contract is an OpenAPI document. The server fixes each read's shape. HTTP caching works as normal. The server team runs ordinary HTTP routes.
GraphQL
Any client language. The contract is a GraphQL schema. The client asks for exactly the fields it wants. HTTP caching is harder, since most queries are POSTs to one URL. The server team runs resolvers, one small function per field.
RPC
The tRPC library serves TypeScript clients only. It shares types straight from the server code. The gRPC framework serves many languages, with a contract in protocol buffers. Browsers need a proxy or a special protocol to call it.

Quickturn has TypeScript, Swift and Kotlin clients and a small number of predictable screen shapes. TypeScript types alone do not provide native clients with a language-neutral contract. GraphQL would support all three, but much of its flexible query surface would currently go unused.

03Why we chose REST

Quickturn chose HTTP resource endpoints and OpenAPI because independently deployed clients can generate types or clients from the same document. GraphQL would add resolvers and another caching model; browser gRPC would add protocol or proxy considerations.

REST can over-fetch or require several calls. Quickturn uses a fixed view endpoint for each screen, such as one home response containing the required data. The cost is more endpoint contracts to keep compatible.

A TypeScript-only internal tool controlled by one team could reasonably choose tRPC. The decision follows client languages, ownership and expected lifetime.

04An agent calls the same commands

The tutor agent exposes selected commands and queries through MCP tools. A gateway adapts those tool calls to the same application operations used by ordinary clients.

Every transport must supply validated command data and a trusted actor context. The model does not choose the learner by passing an arbitrary learner ID. Identity comes from the verified session, and the same authorization decision applies before the command runs.

Sharing the command implementation avoids separate agent rules. It does not eliminate the need to secure the gateway, delegated identity and tool permissions.

Summary in three lines

  1. REST names resources with URLs and uses standard methods; a published contract makes it work across languages.
  2. Choose from your clients: several languages and few fixed reads favor REST, varied reads favor GraphQL, TypeScript-only favors tRPC.
  3. Commands as plain data let apps and an agent's tools share one set of rules and one authorization check.
