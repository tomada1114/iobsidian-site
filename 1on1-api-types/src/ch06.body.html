REST・GraphQL・RPC をどう選ぶか

Quickturn は、TypeScript・Swift・Kotlin のクライアントに、画面ごとに決まった形のデータを返しています。これらのクライアントには、サーバーと同じ言語を使わなくても共有できる契約が必要です。

01REST とは何か

REST はアーキテクチャのスタイルであり、JSON を GET と POST でやり取りすることだけを指すわけではありません。その制約には、統一インターフェース、ステートレスなやり取り、キャッシュのセマンティクスが含まれます。Quickturn は、リソースの URL、標準の HTTP メソッドとステータスを使い、OpenAPI の契約を公開しています。

ハイパーメディアによる遷移は実装していないので、Quickturn の API は Fielding の REST モデルの制約をすべて満たすわけではありません。広く使われている、リソース指向の部分集合に従っています。設計で問うべきなのは、その部分集合がどんなやり取りと互換性の要件に応えるのかです。

02三つの方式を並べる

REST・GraphQL・RPC は、機能を公開する方法がそれぞれ異なります。GraphQL では利用側がフィールドを選び、RPC では操作を直接名前で呼びます。TypeScript 向けの RPC ツールを使うと、サーバーとブラウザの型を密接につなげられます。

OpenAPI を使う REST
クライアントの言語を選びません。契約は OpenAPI のドキュメントです。読み取りの形はサーバーが決め、HTTP キャッシュは通常どおり使えます。サーバー側のチームは、ふつうの HTTP ルートを運用します。
GraphQL
クライアントの言語を選びません。契約は GraphQL のスキーマです。クライアントは必要なフィールドだけを指定して取得します。ほとんどのクエリが一つの URL への POST になるため、HTTP キャッシュは使いにくくなります。サーバー側のチームは、フィールドごとの小さな関数であるリゾルバーを運用します。
RPC
tRPC ライブラリが対応するのは TypeScript のクライアントだけで、サーバーのコードから型をそのまま共有します。gRPC フレームワークは多くの言語に対応し、契約を Protocol Buffers で書きます。ブラウザから呼ぶには、プロキシか専用のプロトコルが必要です。

Quickturn には TypeScript・Swift・Kotlin のクライアントがあり、画面のデータの形は少数で予測しやすいものです。TypeScript の型だけでは、ネイティブのクライアントに言語に依存しない契約を渡せません。GraphQL なら三つすべてに対応できますが、柔軟なクエリ機能の多くは、今のところ使われないままになります。

03REST を選んだ理由

Quickturn が HTTP のリソースエンドポイントと OpenAPI を選んだのは、別々にデプロイされるクライアントが、同じドキュメントから型やクライアントを生成できるからです。GraphQL ならリゾルバーと別のキャッシュモデルが増え、ブラウザからの gRPC ならプロトコルやプロキシについての検討が増えます。

REST では、余分なデータまで取得したり、何度も呼び出しが必要になったりすることがあります。Quickturn は画面ごとに、決まった形のビュー用エンドポイントを用意しています。たとえばホーム画面には、必要なデータをまとめた一つのレスポンスを返します。その代わり、互換性を保たなければならないエンドポイントの契約が増えます。

一つのチームが管理する TypeScript だけの社内ツールなら、tRPC を選ぶのも妥当です。判断は、クライアントの言語、誰が管理するか、どれだけ長く使うかで決まります。

04エージェントも同じコマンドを呼ぶ

チューターエージェントは、選んだコマンドとクエリを MCP のツールとして公開しています。ゲートウェイがそのツール呼び出しを、通常のクライアントが使うのと同じアプリケーションの操作に変換します。

どの経路からでも、検証済みのコマンドのデータと、信頼できるアクターのコンテキストを渡す必要があります。モデルが任意の学習者 ID を渡して、対象の学習者を選ぶことはできません。ID は検証済みのセッションから取り出し、コマンドの実行前には同じ認可の判断が適用されます。

コマンドの実装を共有すれば、エージェント専用のルールを別に持たずに済みます。ただし、ゲートウェイ、委任された ID、ツールの権限を守る必要がなくなるわけではありません。

3行まとめ

  1. REST は URL でリソースに名前を付け、標準のメソッドを使います。契約を公開すれば、言語をまたいで使えます。
  2. 方式はクライアントを基準に選びます。言語が複数あり、読み取りの形が少数に決まっていれば REST、読み取りが多様なら GraphQL、TypeScript だけなら tRPC が向いています。
  3. コマンドを単純なデータとして扱えば、アプリとエージェントのツールが、一つのルールと一つの認可チェックを共有できます。
